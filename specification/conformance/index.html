Processor conformance suite

The processor conformance suite makes the normative text of the Processing Model, HEL, HDL and the conformance sections of conf and req executable. Each case is a description, an input and the output the specification requires: a parsed tree, an RDF graph, an error category, a compiled graph or a conformance run's report. The expected outputs are read off the specification text, never recorded from an implementation, so a processor that disagrees with a case disagrees with the text the case cites. Any implementation can run the suite; nothing in it is specific to the reference engine.

Requirement identifiers

Every sentence of those documents that states an RFC 2119 requirement (MUST, MUST NOT, SHALL, SHALL NOT, REQUIRED, SHOULD, SHOULD NOT, RECOMMENDED) carries a stable anchor, req-<document>-<section>-<n>: req-pm-… for the Processing Model, req-hel-…, req-hdl-…, and req-ce-conf-… and req-ce-req-… for the conformance sections of conf and req. A list or table introduced by such a sentence ending in a colon (for example “A conforming HEL 1.0 evaluator MUST:” or the Processing Model's error table) gives each item or row its own identifier, at the level of the sentence that introduces it. The identifier is a fragment of the page, so processing/index.html#req-pm-parsestruct-1 links to the sentence itself.

The requirement registry lists every identifier with its page, section, conformance class, level (MUST for MUST, SHALL and REQUIRED and their negations; SHOULD otherwise) and a hash of its text. Identifiers are never renumbered or reused: a new requirement takes the next free number of its section, a requirement whose text changes keeps its identifier and records the previous hash in its history, and one that disappears stays in the registry, marked withdrawn. Either change needs a CHANGELOG entry naming the identifier; tools/test_requirement_ids.py fails without one, and fails when a requirement sentence has no anchor, two anchors, or an anchor the registry does not list. python tools/_requirement_ids.py anchors new sentences and refreshes the registry.

Suite layout

A case is a directory specification/conformance/<class>/<case-id>/, where the class is one of the Processing Model's conformance classes: physical-parser, semantic-emitter, bundle-processor, hdl-compiler or conformance-evaluator. Case identifiers start with pp-, se-, bp-, hc- and ce- respectively; the pp-hel- cases are Physical Parser cases that evaluate HEL in a real parse context, and an hc-<name>-yaml case is the YAML mirror of the text case hc-<name>, with the same expected graph. Every case has a manifest.json and exactly one expected artifact, and cites at least one requirement identifier other than the blanket ones (req-pm-conformance-1, req-pm-introduction-1 and the list introductions of the HEL, HDL and conf conformance sections).

Canonical forms and comparison

Parsed trees. The canonical JSON form of a parsed value is: a struct, an object whose members are the struct's declared fields, in declaration order, a field that is unbound (an absent optional field, a derived field whose value is Null, a key no record carries) being null; a repeated field, a text table or a root read as a sequence, an array; an integer, a JSON number when its magnitude is at most 253 and otherwise its decimal digits as a string (so the largest uint64 is "18446744073709551615"); a float, a JSON number written with a fraction or an exponent, and NaN and the infinities as the strings "NaN", "Infinity" and "-Infinity"; a string, a JSON string; bytes, a string of lower-case hexadecimal digits; a Boolean, a JSON Boolean. A field with a data layout is its byte block. Keys that a processor adds to its tree beyond the declared fields (a root key bound by bddo:rootKeyFromField, bookkeeping) are not part of the canonical form. Trees compare structurally: objects member by member (member order is not compared), arrays element by element, an expected integer only with an integer and an expected float only with a float of the same value.

Graphs. Expected and actual graphs compare by isomorphism after these steps, applied to both:

  • A typed literal is put in its datatype's canonical lexical form, so literals compare by value ("0a0b"^^xsd:hexBinary equals "0A0B"^^xsd:hexBinary). The datatype itself must match exactly, for an HDL Compiler case too: "2"^^xsd:long is not "2"^^xsd:integer, because the HDL specification fixes the datatype of every integer it emits.
  • A literal of a HEL-bearing property (the properties of the HEL name-binding table) compares by expression equivalence: both strings are parsed and compared as expression trees, a bare name being instance. it, a hexadecimal literal its Integer and a float literal its binary64 value, so n*2 equals instance.n * 2. A string that does not parse compares as written.
  • The physical-extent annotations a processor MAY add to a minted resource (hexplain:byteOffset, hexplain:byteLength) are removed.
  • Bundle Processor: the bundle profile's own triples, which the asset graph carries, are removed — the profile's IRI and the blank nodes reachable from it — so the expected graph holds only what the processor derived.
  • HDL Compiler: the owl:Ontology header is removed unless the case's manifest sets compareOntologyHeader to true. The header is every triple whose subject is typed owl:Ontology and whose predicate is rdf:type, owl:imports, owl:versionIRI, owl:versionInfo, owl:priorVersion, owl:backwardCompatibleWith, owl:incompatibleWith or in the rdfs:, dcterms:, dc: or vann: namespace; a register binding on the ontology IRI is content, not header, and is always compared.
  • Semantic Emitter with no base: every IRI of the actual graph that is the base the processor reported, or a fragment of it, is rewritten to urn:hexplain:suite:reported-base.

Errors. expected-error.json is {"category": "…"}, one of the Processing Model's error categories: Sync, Bounds, Validation, Checksum, Expression (a Type / HEL error), Dispatch, Description, Unsupported or ResourceLimit. Dispatch is a category of its own, never a Description error. A processor passes when it reports that category, under whatever name it gives it, whether when the description is loaded or during the parse. For an HDL Compiler case it is {"severity": "ERROR"}, with "line": n only when the case fixes the line: the compiler must report at least one ERROR diagnostic, at line n of the source when, and only when, the case states a line, and must not produce output.

Conformance runs. expected-report.json states the verdict (conformant or nonconformant), whether the run was truncated, whether versionScopingApplied, the outcomes of the listed requirements by IRI (Evaluated, NotExercised, Errored, NotApplicable, NotReached) and the findings. Findings match one for one, each on the members it states: its kind (Violation, RuleError, Parse), severity, the requirements it cites and, where the specification fixes them, its message and error category. A member the expected summary leaves out is not compared.

expected-report.ttl states the conf:Run itself, in the run terms of the conf vocabulary (conf:verdict, conf:truncated, conf:versionScopingApplied, conf:fileVersion, conf:failOn, conf:profile, conf:input, conf:outcome and conf:finding). It compares by embedding: every blank node of the expected graph is a variable, bound to a distinct node of the actual report so that every expected triple is a triple of the actual report; the actual report may say more (messages, focus nodes, byte ranges, the copies of the requirements and constraints it cites). The actual run must have as many conf:finding values as the expected one, unless the expected run is truncated. A conf:errorCategory given as its deprecated string ("Bounds") is read as the category individual it names (conf:BoundsError). A requirement that is a blank node of the profile has no IRI a report can repeat; the expected report cites it by its description (a blank node with its req:requirementId and req:fromStandard), which the embedding binds to whatever node, a skolem IRI for example, the report gives the copy it carries.

Claims. expected-claims.json checks a processor's statement of what it claims: a JSON object with classes (the conformance class names) and optionalFeatures (feature tokens, as a list or as {token: {"claimed": true|false}}). Every member the case names as required is present, every class and feature is in the case's closed list, and the ones under mustInclude are claimed.

Running the suite

The cases are generated from Python sources in tools/conformance/ (one module per area, the binary inputs built there so every byte is reviewable), and the class directories are never edited by hand:

python tools/conformance/generate_inputs.py          # write specification/conformance/<class>/
python tools/_build_conformance_page.py               # regenerate the coverage section and coverage.json
python tools/run_gates.py --strict conformance requirement_ids

tools/test_conformance_suite.py checks that the tree on disk is exactly what the sources generate, that every manifest is complete and cites only requirement identifiers the registry lists (at least one of them specific) and sections the pages define, that each case has exactly one expected artifact, that every feature token is one of the Processing Model's, and that every description and expected graph parses.

The standalone comparator and runner. tools/conformance/compare.py is the reference reading of the comparison rules above, in Python with rdflib as its only dependency; it includes a HEL parser and the canonical serializer (tools/conformance/hel.py) for the expression-equivalence rule. It compares one output with one case:

python tools/conformance/compare.py specification/conformance/physical-parser/pp-bits-lsb-first actual.json
python tools/conformance/compare.py <case-dir> actual.ttl --reported-base urn:uuid:…    # a case with no base

The output it expects for each kind of case: the parsed tree as canonical JSON; a graph as Turtle or N-Triples; an error as {"category": "…"}; for the HDL Compiler, diagnostics as {"diagnostics": [{"severity": "ERROR", "line": 3}], "output": false}; a conformance run as the JSON summary or as RDF; a claims statement as JSON. tools/conformance/run_suite.py runs a whole implementation through the suite with one command template per class and reports PASS, FAIL or SKIP (with the reason) per case:

python tools/conformance/run_suite.py --claims my-claims.json \
    --pp-cmd "my-parser {description} {root} {input} --limits {limits} --out {out} --error {err}" \
    --hc-cmd "my-hdl {input} -o {out}" --json results.json

The template's placeholders ({case}, {manifest}, {description}, {input}, {root}, {base}, {rules}, {mode}, {version}, {instant}, {limits}, {withdraw}, {out}, {err}, {reported}) are listed in the runner's help; the command is run without a shell. An error is reported by writing {"category": "…"} to {err}; an HDL compiler's diagnostics may instead go to standard error as file:line:column: SEVERITY: message. A case applies when every feature it requires is in the claims statement given with --claims. tools/test_conformance_comparator.py, a gate, tests every comparison rule and checks that each case's own expected artifact passes it.

The reference engine (hexplain-tools) runs the suite in its own test suites from a specification checkout: ProcessorConformanceSuiteTest in its core module runs the Physical Parser, Semantic Emitter, Bundle Processor and Conformance Evaluator cases, and HdlConformanceSuiteTest in its hdl module the HDL Compiler cases:

HEXPLAIN_SPEC=/path/to/hexplain.io HEXPLAIN_REQUIRE_SPEC=1 ./gradlew :core:test :hdl:test
