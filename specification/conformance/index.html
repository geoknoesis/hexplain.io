Processor conformance suite

The processor conformance suite makes the normative text of the Processing Model, HEL, HDL and the conformance sections of conf and req executable. Each case is a description, an input and the output the specification requires: a parsed tree, an RDF graph, an error category, a compiled graph or a conformance run's report. The expected outputs are read off the specification text, never recorded from an implementation, so a processor that disagrees with a case disagrees with the text the case cites. Any implementation can run the suite; nothing in it is specific to the reference engine.

Requirement identifiers

Every sentence of those documents that states an RFC 2119 requirement (MUST, MUST NOT, SHALL, SHALL NOT, REQUIRED, SHOULD, SHOULD NOT, RECOMMENDED) carries a stable anchor, req-<document>-<section>-<n>: req-pm-… for the Processing Model, req-hel-…, req-hdl-…, and req-ce-conf-… and req-ce-req-… for the conformance sections of conf and req. A list or table introduced by such a sentence ending in a colon (for example “A conforming HEL 1.0 evaluator MUST:” or the Processing Model's error table) gives each item or row its own identifier, at the level of the sentence that introduces it. The identifier is a fragment of the page, so processing/index.html#req-pm-parsestruct-1 links to the sentence itself.

The requirement registry lists every identifier with its page, section, conformance class, level (MUST for MUST, SHALL and REQUIRED and their negations; SHOULD otherwise) and a hash of its text. Identifiers are never renumbered or reused: a new requirement takes the next free number of its section, a requirement whose text changes keeps its identifier and records the previous hash in its history, and one that disappears stays in the registry, marked withdrawn. Either change needs a CHANGELOG entry naming the identifier; tools/test_requirement_ids.py fails without one, and fails when a requirement sentence has no anchor, two anchors, or an anchor the registry does not list. python tools/_requirement_ids.py anchors new sentences and refreshes the registry.

Suite layout

A case is a directory specification/conformance/<class>/<case-id>/, where the class is one of the Processing Model's conformance classes: physical-parser, semantic-emitter, bundle-processor, hdl-compiler or conformance-evaluator. Case identifiers start with pp-, se-, bp-, hc- and ce- respectively; the pp-hel- cases are Physical Parser cases that evaluate HEL in a real parse context. Every case has a manifest.json and exactly one expected artifact.

Canonical forms and comparison

Parsed trees. The canonical JSON form of a parsed value is: a struct, an object whose members are the struct's declared fields, in declaration order, a field that is unbound (an absent optional field, a derived field whose value is Null, a key no record carries) being null; a repeated field, a text table or a root read as a sequence, an array; an integer, a JSON number when its magnitude is at most 253 and otherwise its decimal digits as a string (so the largest uint64 is "18446744073709551615"); a float, a JSON number written with a fraction or an exponent, and NaN and the infinities as the strings "NaN", "Infinity" and "-Infinity"; a string, a JSON string; bytes, a string of lower-case hexadecimal digits; a Boolean, a JSON Boolean. A field with a data layout is its byte block. Keys that a processor adds to its tree beyond the declared fields (a root key bound by bddo:rootKeyFromField, bookkeeping) are not part of the canonical form. Trees compare structurally: objects member by member, arrays element by element, an expected integer only with an integer and an expected float only with a float of the same value.

Graphs. Expected and actual graphs compare by isomorphism, with typed literals compared by value (each is put in its datatype's canonical lexical form first, so "0a0b"^^xsd:hexBinary equals "0A0B"^^xsd:hexBinary; the datatype itself must match). A processor may annotate a minted resource with its physical extent (hexplain:byteOffset, hexplain:byteLength); those triples are removed from both graphs first. A Bundle Processor's asset graph also carries the bundle profile's own triples; the profile's IRI and the blank nodes reachable from it are removed from both graphs, so the expected graph holds only what the processor derived. For an HDL Compiler case an integer of any XSD integer type compares by value with any other ("2"^^xsd:long equals "2"^^xsd:integer): the HDL specification fixes a count's or an offset's value, not the integer type it is written in.

Errors. expected-error.json is {"category": "…"}, one of the Processing Model's error categories: Sync, Bounds, Validation, Checksum, Expression (a Type / HEL error), Dispatch, Description, Unsupported or ResourceLimit. A processor passes when it reports that category, under whatever name it gives it, whether when the description is loaded or during the parse. For an HDL Compiler case it is {"severity": "ERROR", "line": n}: the compiler must report at least one ERROR diagnostic, at line n of the source when the case gives a line, and must not produce output.

Conformance runs. expected-report.json states the verdict (conformant or nonconformant), whether the run was truncated, whether versionScopingApplied, the outcomes of the listed requirements by IRI (Evaluated, NotExercised, Errored, NotApplicable, NotReached) and the findings. Findings match one for one, each on the members it states: its kind (Violation, RuleError, Parse), severity, the requirements it cites and, where the specification fixes them, its message and error category. A member the expected summary leaves out is not compared.

Running the suite

The cases are generated from Python sources in tools/conformance/ (one module per area, the binary inputs built there so every byte is reviewable), and the class directories are never edited by hand:

python tools/conformance/generate_inputs.py          # write specification/conformance/<class>/
python tools/_build_conformance_page.py               # regenerate the coverage section and coverage.json
python tools/run_gates.py --strict conformance requirement_ids

tools/test_conformance_suite.py checks that the tree on disk is exactly what the sources generate, that every manifest is complete and cites only requirement identifiers the registry lists and sections the pages define, that each case has exactly one expected artifact, and that every description and expected graph parses. The reference engine (hexplain-tools) runs the suite from a specification checkout: ProcessorConformanceSuiteTest in its core module runs the Physical Parser, Semantic Emitter, Bundle Processor and Conformance Evaluator cases, and HdlConformanceSuiteTest in its hdl module the HDL Compiler cases:

HEXPLAIN_SPEC=/path/to/hexplain.io HEXPLAIN_REQUIRE_SPEC=1 ./gradlew :core:test :hdl:test

Another implementation runs a case by loading description.ttl, processing input.bin with the manifest's root, limits and options, and comparing its output with the expected artifact under the rules above. An HDL Compiler case can also be checked by hand with the hdl command line (hdl input.hx).
