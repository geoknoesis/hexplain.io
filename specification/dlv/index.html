Complete reference: 43 terms and shapes · All vocabularies and reading guide

The Hexplain Data Layout Vocabulary (DLV) describes the organization of multi-dimensional data within a flat binary stream. It is a companion to the Binary Data Description Ontology (BDDO): while BDDO describes a field as a contiguous block of bytes, DLV explains how to interpret that block as a multi-dimensional grid by specifying the order, size, and semantic meaning of its dimensions. This is essential for scientific, geospatial, and complex media formats.

This document is an unofficial draft produced for the purpose of defining the Hexplain standard. It has no official standing and is not endorsed by any standards body.

Introduction

Many advanced formats (HDF5, NetCDF, GeoTIFF) store data as n-dimensional arrays or "data cubes." A field described merely as a sequence of bytes is insufficient to locate a specific data point. DLV answers: how many dimensions, what cell data type, what size and meaning per dimension, and in what order the data is stored.

A bddo:Field containing multi-dimensional data is linked to a dlv:DataLayout via hexplain:hasDataLayout (defined in Hexplain Core).

Conformance

The key words "MUST", "MUST NOT", "REQUIRED", "SHALL", "SHALL NOT", "SHOULD", "SHOULD NOT", "RECOMMENDED", "MAY", and "OPTIONAL" in this document are to be interpreted as described in [[RFC2119]].

Core Concepts

dlv:DataLayout
Describes the overall layout of a multi-dimensional array. Attached to a bddo:Field via hexplain:hasDataLayout.
dlv:Dimension
One dimension of the array (e.g. width, height, bands).
dlv:Axis
A semantic descriptor for a dimension. DLV provides five: dlv:axisX, dlv:axisY, dlv:axisZ, dlv:axisBand and dlv:axisTime. Domain vocabularies define specialised ones — the geospatial vocabulary adds latitude, longitude, elevation and point axes and relates them back to these with rdfs:seeAlso.

Properties

hexplain:hasDataLayout
Defined in Hexplain Core; links a bddo:Field to a dlv:DataLayout.
dlv:hasDimension
Links a dlv:DataLayout to an ordered rdf:List of its dlv:Dimension instances. The order is normative and defines the data-sequencing rule (interleaving): from the slowest-varying (outermost loop) to the fastest-varying (innermost loop) dimension.
  • Band Sequential (BSQ): (Band, Row, Column).
  • Pixel Interleaved (BIP): (Row, Column, Band).
  • Band Interleaved by Line (BIL): (Row, Band, Column).
dlv:cellDataType
The data type of each cell. Value MUST be a bddo:DataType.
dlv:dimensionSize / dlv:dimensionSizeFromField
The length of a dlv:Dimension: a fixed xsd:positiveInteger, or read from a bddo:Field. Exactly one MUST be present.
dlv:dimensionStride / dlv:dimensionStrideFromField / dlv:dimensionStrideFromExpression
Bytes to advance per step along a dimension (pitch): a fixed literal, a value read from a bddo:Field, or a computed HEL expression. Optional, but at most one mechanism may be used; when none is present, addressing is contiguous. The expression form is what padded rows actually need — BMP's row pitch is ((width * bitsPerPixel + 31) / 32) * 4, which no literal can express.
dlv:hasAxis
Links a dlv:Dimension to its semantic dlv:Axis.
dlv:chunkSize / dlv:chunkSizeFromField
Extent of one chunk (tile/block) along this dimension, in cells. Declaring either on any dimension makes the layout chunked; at most one of the two MAY be present on a given dimension. A dimension of a chunked layout that declares neither is chunked at its full extent — a layout chunked on X alone has chunks spanning all of Y. Inside a chunked layout, dlv:dimensionStride addresses cells within one chunk, not across the whole grid.
dlv:chunkOffsetsFromField / dlv:chunkLengthsFromField
The repeating fields holding each chunk's byte offset and length — TIFF's TileOffsets/TileByteCounts, NITF's block offsets.
dlv:chunkOrder / dlv:chunkOffsetBase
Traversal order of the chunk table and what its offsets are relative to. dlv:chunkOrder is one of dlv:rowMajor (the default), dlv:columnMajor, dlv:morton or dlv:hilbert — the last two being space-filling curves, used where chunk locality matters more than scan order. dlv:chunkOffsetBase defaults to bddo:streamStart.
dlv:cellBitWidth / dlv:cellBitWidthFromField / dlv:cellPackingOrder
Sub-byte cells. Every bddo:DataType is a whole number of bytes, so a grid whose cells are not — a 1-bit mask, a 4-bit palette index, GRIB2 packing, NITF 1-bit imagery — could not be addressed at all. dlv:cellBitWidth overrides the cell type's intrinsic width, so the type keeps saying how to interpret a cell (signed, unsigned, float) while the width says how much room it takes; cells are contiguous in the bit stream and MAY straddle byte boundaries. dlv:cellBitWidthFromField reads that width from a field, which GRIB2 needs because it carries the width in its data-representation section. dlv:cellPackingOrder says whether the first cell of a byte occupies the most or least significant bits, defaulting to bddo:MSBFirst; it is meaningful only alongside a packed width, and a width is either fixed or read, never both.

Distinct from asamp:bitDepth, which is significant bits carried inside a wider container — NITF's ABPP 12 within NBPP 16. That grid is padded and its cells stay two bytes apart; this one is packed. The two can hold different values for the same raster. Note also that dlv:dimensionStride stays in BYTES even for a packed layout, because rows are normally padded to a byte boundary while the cells within a row are not.

Conditional Layout

The cell type and the dimension order may each depend on something read earlier, because the same bytes are read differently depending on it. An ESRI .hdr-labelled grid's NBITS 32 means uint32 for a .bil and float32 for a .flt; an ENVI cube's three dimensions are ordered by its interleave keyword.

These are two independent conditionals over one set of dimensions, not one conditional layout. Making the whole layout conditional multiplies the cases — ENVI would need a layout per (interleave, width) pair, each restating every extent — whereas these are two small rule lists over the same dlv:Dimension nodes, so an extent is written once and the arms cannot disagree about it.

dlv:hasConditionalCellDataType → ordered list of dlv:CellDataTypeRule
Each rule carries a bddo:condition (a HEL expression) and a dlv:ruleCellDataType. Mutually exclusive with dlv:cellDataType.
dlv:hasConditionalDimensionOrder → ordered list of dlv:DimensionOrderRule
Each rule carries a bddo:condition and a dlv:ruleDimensionOrder, itself an ordered list of the same dlv:Dimension nodes in the order that arm selects. Mutually exclusive with dlv:hasDimension.

Both are first match wins, so a more specific arm MUST precede a more general one: a .flt arm has to come before a NBITS 32 arm, because a float grid is also 32 bits wide and the width arm would otherwise claim it.

dlv:chunkSize — chunk size

IRI: https://hexplain.io/ns/dlv#chunkSize

Label
chunk size
Definition
Extent of one chunk (tile/block) along this dimension, in cells. When any Dimension of a DataLayout declares a chunk extent, the layout is chunked: the grid is partitioned into chunks of this shape and each chunk is located through the layout's chunk offset table. A trailing partial chunk is padded to the full chunk extent. # ---------- Sub-byte cells ----------
# Every bddo:DataType is a whole number of bytes, so a grid whose cells are not could not be
# addressed at all: a 1-bit mask, a 4-bit palette index, GRIB2 simple packing at whatever
# width the header names, NITF's 1-bit imagery. dlv:cellBitWidth overrides the cell type's
# intrinsic width, so the type keeps saying how to INTERPRET a cell (signed, unsigned,
# float) while the width says how much room it takes.
#
# Distinct from asamp:bitDepth, which is a sampling concern: significant bits carried inside
# a wider container, NITF's ABPP 12 within NBPP 16. That grid is padded, not packed, and its

Example: Describing a BIL Image

A Band Interleaved by Line (BIL) image is a 3-D cube where all bands of the first row are written, then all bands of the second row, and so on.

@prefix bddo:     <https://hexplain.io/ns/bddo#> .
@prefix hexplain: <https://hexplain.io/ns/core#> .
@prefix dlv:      <https://hexplain.io/ns/dlv#> .
@prefix myformat: <https://hexplain.io/formats/myformat#> .

myformat:ImageFile a bddo:Struct ;
    bddo:hasField ( myformat:Width myformat:Height myformat:NumBands myformat:PixelData ) .

myformat:Width    a bddo:Field ; bddo:dataType bddo:uint32le .
myformat:Height   a bddo:Field ; bddo:dataType bddo:uint32le .
myformat:NumBands a bddo:Field ; bddo:dataType bddo:uint32le .

myformat:PixelData a bddo:Field ;
    bddo:dataType bddo:bytes ;
    bddo:sizeFromExpression "instance.parent.Width * instance.parent.Height * instance.parent.NumBands" ;
    hexplain:hasDataLayout myformat:BIL_Layout .

myformat:BIL_Layout a dlv:DataLayout ;
    dlv:cellDataType bddo:uint8 ;
    # Row (slowest) -> Band -> Column (fastest) == BIL.
    dlv:hasDimension ( myformat:HeightDimension myformat:BandDimension myformat:WidthDimension ) .

myformat:HeightDimension a dlv:Dimension ; dlv:hasAxis dlv:axisY ; dlv:dimensionSizeFromField myformat:Height .
myformat:WidthDimension  a dlv:Dimension ; dlv:hasAxis dlv:axisX ; dlv:dimensionSizeFromField myformat:Width .
myformat:BandDimension   a dlv:Dimension ; dlv:hasAxis dlv:axisBand ; dlv:dimensionSizeFromField myformat:NumBands .
