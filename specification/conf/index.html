Hexplain Conformance Vocabulary

Binds executable HEL assertions to the standards requirements they check, and describes the findings and coverage a conformance run reports. Format-agnostic. The processing rules (scope firing, version matching, truncation, verdict, parse attribution) are the Conformance Evaluator class of the Hexplain Processing Model.

Unofficial working specification. The namespace and version metadata below identify the vocabulary; documentation does not certify an implementation.

Conformance

The key words "MUST", "MUST NOT", "REQUIRED", "SHALL", "SHALL NOT", "SHOULD", "SHOULD NOT", "RECOMMENDED", "MAY", and "OPTIONAL" in this section are to be interpreted as described in BCP 14 (RFC 2119 and RFC 8174) when, and only when, they appear in all capitals, as shown here.

A conformance profile is valid when it satisfies the shapes of conf/shapes.ttl and req/shapes.ttl. A processor that evaluates profiles is a Conformance Evaluator, and MUST follow Processing Model §Conformance Evaluation. In summary:

  • A constraint whose conf:scope is a bddo:Struct MUST be evaluated once per parsed instance, with instance and self bound to it; one whose scope is a bddo:Field MUST be evaluated once per parsed value of the field, with instance bound to the containing struct and self to the value.
  • A false assertion MUST yield exactly one conf:Violation finding at the constraint's conf:severity, citing every requirement the constraint cites; any other result, or an evaluation failure, MUST yield one conf:RuleError finding. A finding MUST NOT cite a requirement its constraint does not cite.
  • A parse error MUST be reported as a conf:Parse finding with its conf:errorCategory (a conf:ErrorCategory; Dispatch is a category of its own), attributed to the requirement of the profile's conf:ParseAttribution for that category, or to no requirement when none names it. A resource limit is never a finding.
  • conf:message placeholders MUST be interpolated as that property defines: {field} is the focus node's path, and {value} the evaluated value when it is unambiguous, left as written otherwise.
  • Version scoping MUST use only a version the caller supplies, compared with req:appliesToVersion by exact string equality. Without one, every requirement MUST be evaluated and the report MUST say that version scoping was not applied.
  • A run stopped by a resource limit MUST either fail with a ResourceLimit error or be reported as truncated; requirements it did not reach MUST receive conf:NotReached. Every requirement of the profile MUST receive exactly one outcome, with the precedence conf:NotApplicable > conf:Errored > conf:Evaluated > conf:NotReached > conf:NotExercised; a requirement no constraint cites is conf:NotExercised.
  • A run is conformant if and only if it is not truncated, the parse completed, no finding reaches the run's conf:failOn severity (sh:Violation unless the caller chose sh:Warning or sh:Info), and no outcome is conf:Errored or conf:NotReached; a truncated run is never conformant. Findings below the fail-on severity do not affect the verdict.
  • A report written as RDF is one conf:Run shaped as the Processing Model’s Report rule states (req-pm-conformance-evaluation-7: its conf:verdict and conf:truncated flag once each, every finding linked with conf:finding), and validates on its own against conf/shapes.ttl and req/shapes.ttl, carrying copies of the requirements, constraints and parse attributions it references, a blank-node requirement under a skolem IRI (req-pm-conformance-evaluation-8).
