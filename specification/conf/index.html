Specification family

Hexplain Conformance Vocabulary

Binds executable HEL assertions to the standards requirements they check, and describes the findings and coverage a conformance run reports. Format-agnostic. The processing rules (scope firing, version matching, truncation, verdict, parse attribution) are the Conformance Evaluator class of the Hexplain Processing Model.

Unofficial working specification. The namespace and version metadata below identify the vocabulary; documentation does not certify an implementation.

Conformance

The key words "MUST", "MUST NOT", "REQUIRED", "SHALL", "SHALL NOT", "SHOULD", "SHOULD NOT", "RECOMMENDED", "MAY", and "OPTIONAL" in this section are to be interpreted as described in RFC 2119.

A conformance profile is valid when it satisfies the shapes of conf/shapes.ttl and req/shapes.ttl. A processor that evaluates profiles is a Conformance Evaluator, and MUST follow Processing Model §Conformance Evaluation. In summary:

  • A constraint whose conf:scope is a bddo:Struct MUST be evaluated once per parsed instance, with instance and self bound to it; one whose scope is a bddo:Field MUST be evaluated once per parsed value of the field, with instance bound to the containing struct and self to the value.
  • A false assertion MUST yield exactly one conf:Violation finding at the constraint's conf:severity, citing every requirement the constraint cites; any other result, or an evaluation failure, MUST yield one conf:RuleError finding. A finding MUST NOT cite a requirement its constraint does not cite.
  • A parse error MUST be reported as a conf:Parse finding with its conf:errorCategory, attributed to the requirement of the profile's conf:ParseAttribution for that category, or to no requirement when none names it.
  • conf:message placeholders MUST be interpolated as that property defines: {field} is the focus node's path, and {value} the evaluated value when it is unambiguous, left as written otherwise.
  • Version scoping MUST use only a version the caller supplies, compared with req:appliesToVersion by exact string equality. Without one, every requirement MUST be evaluated and the report MUST say that version scoping was not applied.
  • A run stopped by a resource limit MUST either fail with a ResourceLimit error or be reported as truncated; requirements it did not reach MUST receive conf:NotReached. Every requirement of the profile MUST receive exactly one outcome, with the precedence conf:NotApplicable > conf:Errored > conf:Evaluated > conf:NotReached > conf:NotExercised; a requirement no constraint cites is conf:NotExercised.
  • A run is conformant if and only if it is not truncated, the parse completed, and no finding has severity sh:Violation; a truncated run is never conformant. Findings at sh:Warning or sh:Info do not affect the verdict.

conf:EvaluationOutcome — Evaluation Outcome

IRI: https://hexplain.io/ns/conf#EvaluationOutcome

Label
Evaluation Outcome
Definition
The run-coverage outcome of one requirement in one conformance run. Closed set of five. Given the checks citing the requirement (its constraints and parse attributions), the outcome is the FIRST of these that holds: (1) conf:NotApplicable -- the run was given the input's format version, the requirement has req:appliesToVersion values, and none equals that version; (2) conf:Errored -- evaluating at least one citing constraint raised a rule error; (3) conf:Evaluated -- at least one citing constraint was evaluated, without error, on at least one scoped instance, or a citing parse attribution was checked (the parse ran to its end, or raised an error of the attributed category); (4) conf:NotReached -- the run was truncated, or the parse stopped, before every instance of the input had been visited; (5) conf:NotExercised -- otherwise, including a requirement cited by no constraint or parse attribution of the profile.
Usage scope
The class of the five controlled values of conf:outcomeValue; do not mint further outcomes.

conf:Finding — Finding

IRI: https://hexplain.io/ns/conf#Finding

Label
Finding
Definition
One reported discrepancy of a conformance run: a failed evaluation of a constraint (conf:Violation), a constraint whose evaluation could not complete (conf:RuleError), or an error raised while parsing the input (conf:Parse). A constraint finding is attributed to every requirement the constraint cites; a failed evaluation yields exactly one finding however many requirements the constraint cites. A Parse finding has no constraint, reports at sh:Violation and is attributed to the requirement a conf:ParseAttribution names for its error category, or to no requirement when none does. Otherwise a finding's severity is its constraint's conf:severity.
Usage scope
Assert on each finding of a run report, never in a profile. A finding locates its evidence with conf:focusNode and hexplain:byteOffset/hexplain:byteLength where those are known.

    rdfs:comment """Binds executable HEL assertions to the standards requirements they check, and

Conformance Evaluator class of the Hexplain Processing Model.

Severity: a constraint reports at its conf:severity (sh:Violation, sh:Warning or sh:Info),
sh:Violation when absent. req:discrepancyType classifies the defect (syntactic, semantic,
