The Hexplain Description Language (HDL) is a concise authoring language for Hexplain format descriptions. Instead of writing the canonical RDF/Turtle of the BDDO, Hexplain Core, DLV, and hx-bundle vocabularies by hand, an author writes a compact description that a compiler lowers to exactly that Turtle. HDL has two interchangeable concrete syntaxes — a purpose-built text surface (.hx) and an isomorphic YAML surface (.hx.yaml) — over a single abstract model, so either compiles to the same RDF graph.

This document is an unofficial draft produced for the purpose of defining the Hexplain standard. It has no official standing and is not endorsed by any standards body.

Introduction

A Hexplain format description is a set of RDF triples spanning several vocabularies: BDDO for the physical byte structure, Hexplain Core for the bytes→meaning mapping, HEL for dynamic expressions, DLV for multi-dimensional layout, and hx-bundle for multi-file formats. Authoring these by hand is verbose: every field is a separate subject, field order is carried by an rdf:List, and enumerations, checksums, layouts, and part-specs are blank-node structures. HDL removes that ceremony while remaining expressively complete — anything the underlying vocabularies can express, HDL can author.

HDL is an authoring front-end: compilation is one-directional (HDL→Turtle), and the emitted Turtle remains the canonical, SHACL-validated artifact that all downstream tooling (the Processing Model, semantic lifting, validation) consumes. HDL introduces no new run-time semantics of its own; it is a surface syntax whose meaning is defined entirely by the Turtle it produces.

Design Goals

  • Ergonomic. A field reads as name : type clause*; sibling fields are referenced by bare name; common patterns (sizing, enums, checksums, conditional dispatch) have dedicated sugar.
  • Complete. Every BDDO/Core/DLV/hx-bundle construct is reachable, and a raw escape hatch guarantees coverage even as the vocabularies evolve.
  • Two surfaces, one model. The text and YAML surfaces parse to the same abstract model and compile to isomorphic RDF, so a description may be authored or exchanged in either.
  • Grounded. Expressions are HEL; the compiler validates them and every closed-vocabulary value at compile time.

Conformance requirements, including the RFC 2119 key words, are stated in §Conformance.

Compilation Model

An HDL compiler transforms a source document into an RDF graph through the following stages. The stages are conceptual; an implementation MAY fuse them.

  1. Parse. The text or YAML surface is parsed into a single abstract model (a document: a format header, prefix declarations, structs, standalone fields, bundle profiles, and asset instances).
  2. Resolve. Prefixes are bound, IRIs are minted (§IRI Minting), and every bare identifier in an expression is checked against the fields in scope.
  3. Synthesize expressions. Each HDL expression is lowered to a canonical HEL string and validated.
  4. Emit. The resolved document is written as BDDO/Core/DLV/hx-bundle Turtle.

Errors at any stage are reported as diagnostics with a source location; a conforming compiler MUST NOT raise an uncaught exception to its caller on malformed input, and MUST report at least one ERROR diagnostic for input it cannot faithfully compile.

IRI Minting

Terms receive IRIs deterministically from the format's base namespace. The base namespace is the value of @namespace if present, otherwise https://hexplain.io/formats/<format-name>#.

This lets field IRIs be per-struct-unique (avoiding subject collisions between two structs that both have a length field) without changing the runtime data model.

A use declaration binds a prefix to a namespace IRI, written either as an angle-bracket IRI or as a quoted string (use menc: <https://hexplain.io/ns/register/media-encoding#>). The following prefixes are predeclared and need not be introduced with use:

No other prefix is predeclared. In particular, aspect and register prefixes (araster, acolor, ageom, menc, and the part-role register's own conventional prefix rpr, which is bound to the same namespace as role) are not predeclared: a description that uses one MUST bind it with use. A use of a predeclared prefix rebinds it for the document (a later use of the same prefix wins). An import alias is also a prefix, bound to the imported module's namespace; an alias that collides with a prefix already bound by a predeclaration or use is an error. The empty prefix is bound to the base namespace in the emitted Turtle (and inside raw-turtle), but it has no text-surface spelling outside a raw-turtle block: to name a term of the format's own namespace in a means or similar position, bind a prefix to the base namespace with use.

A CURIE whose prefix is none of the above — not predeclared, not bound by use, and not an import alias — is an error: a conforming compiler MUST report an ERROR diagnostic for it wherever it occurs (a means, @datatype, @encoded-with, @pipeline step, @object, @unit, @prop, enum symbol, register, part role, carries, or type position), and MUST NOT emit the unexpanded CURIE as an IRI.

Lexical Structure (text surface)

This section summarises the lexical rules; the normative token definitions are in §Grammar: Tokens.

  • Comments. // to end of line; /* … */ block (not nested). A block comment left open at end of input is a lexical ERROR.
  • Names. A name starts with a letter or _ and continues with letters, digits, _ and :; a single - or . is also folded into the name when a letter, digit or _ follows it. So naming-convention, roads.shp, root.Directory and araster:RasterGrid are each one token, while a..b, a--b and a trailing a- are not; a name containing : is a CURIE and a name ending in : is a prefix label (ageom:).
  • Field names. Although the lexer folds - and ., a field's name and its as alias, a struct parameter's name and a let binding's name MUST be HEL identifiers — an ASCII letter or _ followed by ASCII letters, digits and _, and not one of instance parent root self stream asset param and or not true false — because expressions reach a field by that name (asset is HEL's multi-part root, so a field so named could never be read). A compiler MUST report an ERROR for a hyphenated, dotted or reserved field name (the reference compiler suggests byte_order for byte-order). A quoted header/document key is a record key, not a name, and is exempt; its alias, if any, is not, and an expression reaches such a field only by its alias: a bare name that spells a quoted key, even one that is a HEL identifier, is an undeclared name. An unquoted name in a header is a field name like any other, and the record key the field is located by: the compiler emits no bddo:key for it, and the processor locates it by its simple key (Processing Model, key/value headers).
  • Literals. integers (42, -1, 0b1010; a binary literal is emitted in HEL as its decimal value; every integer fits in a signed 64-bit integer), floats (1.5, 2.5e-3, 1e6), strings ("…" or '…', with the escape set HEL uses — \\ \' \" \n \t \r \0 \xHH \uHHHH — any other escape being an ERROR; either quoting becomes a single-quoted HEL string with the same content), hex byte strings (0x89504E47), booleans (true/false). The lexer reads the whole alphanumeric run after 0x or 0b, so 0x12G4 and 0b102 are lexical errors, not a number followed by a name. Digits are ASCII only: a compiler MUST report a lexical ERROR for a non-ASCII digit (the Arabic-Indic ٣, the fullwidth １) outside a string, comment or raw-turtle block, never read it as a digit. A \uHHHH escape naming a surrogate that is not half of a high-low pair is an ERROR, as it is in HEL.
  • Unknown characters. A character that cannot begin any token (for example ;, # or $ outside a string, bracketed or backtick expression, IRI, raw-turtle block or comment) is a lexical ERROR; a string, block comment, backtick expression, bracketed expression or raw-turtle block left unterminated at end of input is also an ERROR.
  • Annotations. begin with @ (@endian, @at, @fixed, @bound-by, …).
  • Bracketed expressions. the text between a matching [ ] pair is captured whole (§Expressions).
  • Backtick expressions. a `…` literal denotes a raw HEL expression (§Raw HEL).
  • IRIs. <…> with no whitespace inside; a < that does not open one is the HEL operator <, <= or <<.

Keywords. HDL has no lexically reserved words: every keyword is contextual, recognised only in the position where the grammar expects it, so a field may be named type, size or value (subject to the field-name rule above). The keyword sets are listed in §Grammar: Keywords.

Physical Structure

A struct is an ordered sequence of fields. A field is written name : type clause*. The following example is the PNG chunk — a type-length-value record with a checksum and conditional dispatch on the chunk type:

format png
  @namespace "https://hexplain.io/formats/png#"
  @endian big

struct Chunk {
  length : u32
  type   : ascii[4]
  data   : bytes[length]                 // lone sibling → bddo:sizeFromField
             switch type {               // → bddo:hasConditionalDataType
               "IHDR" => IHDR_ChunkData
               "PLTE" => PLTE_ChunkData
             }
  crc    : u32 @checksum crc32(type .. data)   // coversFromField .. coversToField
}

struct IHDR_ChunkData {
  width : u32   height : u32   bitDepth : u8   colorType : u8
  compression : u8   filter : u8   interlace : u8
}

struct PLTE_ChunkData {
  entries : bytes[..]
}

A struct MAY declare parameters after its name (§Parameters and local bindings), and MAY carry @endian big|little, @bit-order msb|lsb, a means clause (§Semantic Mapping), a @root annotation (marking the format's entry point; the first struct is the default root), and an as alias. A field declared at document scope (outside any struct) mints a standalone bddo:Field.

One of each. A field MUST NOT carry two clauses of one kind, and a compiler MUST report an ERROR for a second size (two […]), count (two repeat), offset (two @at), fixed value (two @fixed), byte order (two @endian) or type selection (two of switch and dispatch), rather than emit both values of a property the Processing Model reads once. It MUST also report an ERROR for a derive field with a repeat clause (a derived field reads no bytes, so it has no elements), for @pipeline together with @encoded-with on one field, and for two declarations of one struct, header, table or document name in a document. A bytes or string field of a binary struct with neither a size nor a terminator has no extent (Processing Model, Size resolution) and is an ERROR; the fields of a header, table or document are exempt, since their container gives their extent. A size together with @terminator is not two clauses of one kind: the terminator is searched for inside the declared region, as the Processing Model defines.

Literal values. A compiler MUST report an ERROR for a literal outside the range of its position — a field size or struct @size below 1 (bytes[0], bytes[-3]), a repeat count or offset below 0 (repeat -2, @at -2), a stride below 1 (stride 0) — and for a FLOAT literal in any of these positions (bytes[2.0], repeat 1.5, @at 1e0): they take integers, and an integral float is not one. The literal positions differ in what they accept, and a compiler MUST hold each to its own set. @prop takes an IRIREF, a CURIE, or an INT, HEX, STRING, true or false literal, never a bare NAME (write the string "x" or the CURIE ex:x). A NAME or a CURIE as the key of a switch arm is the string it spells: IHDR => S tests discriminator == 'IHDR'; an IRIREF there is an ERROR. An enumeration value is neither an IRIREF nor a bare NAME. @fixed takes an INT (typed with the field's XSD type), a STRING (xsd:string) or a HEX (xsd:hexBinary) only; a NAME, a CURIE or a Boolean there is an ERROR, and so, as the Processing Model makes them description errors, are a STRING on a numeric field and an INT on a bytes or string field.

Fixed values. An integer @fixed on a numeric field is emitted typed with the field's XSD type (@fixed 9994 on an i32 becomes "9994"^^xsd:int) and is compared by value; a hex @fixed stays xsd:hexBinary and, on a numeric field, MUST have exactly the field's width in bytes (Processing Model, Fixed value). The widths are those of the types: three bytes for u24 and i24, two for f16, on which an integer @fixed is typed xsd:float and compared at binary16 width (@fixed 1 on an f16 matches 3C 00 big-endian).

offsetBase keywords: stream-start stream-end parent-start current. A switch arm may match a literal value against the discriminator ("IHDR" => S) or supply a full boolean guard (when expr => S).

Field-Form vs. Expression-Form (normative)

For any size, offset, or count clause: when the expression is exactly one sibling field name, a conforming compiler MUST emit the specific …FromField object property; otherwise it MUST emit the …FromExpression datatype property carrying the synthesized HEL string. An integer literal emits the plain form (bddo:size, bddo:repeatCount, bddo:atOffset). This rule is deterministic and identical across both surfaces. (DLV dimensionSize has no expression form: an integer → dimensionSize, a sibling name → dimensionSizeFromField.)

Literal datatypes. A compiler MUST emit every integer it writes as an xsd:integer literal (Turtle's bare integer), except where this document names another datatype: a size, repeat count, offset, alignment, radix, bit length, skip count, dimension size, stride, chunk extent, cell width, part count, enumeration raw value, dispatch key, pipeline parameter or @prop value is an xsd:integer, never an xsd:long or xsd:int, whatever range the targeted property declares; an integer @fixed on a numeric field takes the field's XSD type (Fixed values). A conformance suite compares literal datatypes exactly, so the choice is not left to the implementation.

In crc(…) a compiler MUST accept the six parameters width, poly, init, refin, refout and xorout in any order, each exactly once, and MUST report an ERROR for a missing, repeated or unknown parameter, a width outside 8..64, a poly, init or xorout that is negative or not below 2width, and a reflection flag that is not true or false. width, poly, init and xorout take an INT or a HEX, a HEX here denoting the unsigned integer its digits spell, of any length up to sixteen digits (0x8005 is 32773, 0xFFFFFFFFFFFFFFFF is 264−1); they are emitted as xsd:integer literals and the flags as xsd:boolean. A parameter's name and its colon may be written together (width:, which the lexer reads as one NAME ending in :) or apart (width :); both are the same parameter. The checksum field's own type decides how the stored value is read, so a little-endian CRC-16 is a u16le field, or a u16 in a little-endian struct. A CRC's width, named or custom, MUST equal the bit width of its checksum field's integer type; any other checksum field is an ERROR (the Processing Model makes it a description error).

Parameters and local bindings

A struct may take parameters: values its caller supplies, such as the element count of a row held by the table around it, or a width shared by every row. A parameter list follows the struct's name; each parameter is a name, optionally followed by a colon and the kind of value it accepts (int, float, string, bytes, bool → bddo:parameterType bddo:IntegerParameter, bddo:FloatParameter, bddo:StringParameter, bddo:BytesParameter, bddo:BooleanParameter). A field whose type is a parameterised struct supplies the arguments in parentheses after the struct name, in the same order, and so does a switch or dispatch arm that selects one. A local binding, let <name> = <expr> as a member of a struct, names a value computed where it stands, for the members after it.

struct Header { count : u8  width : u8 }

struct Table {
  hdr  : Header
  rows : Row(hdr.count, 4)
}

struct Row(n: int, w) {
  cells : bytes[w] repeat n
}

struct Image {
  width  : u16
  height : u16
  let area = width * height
  pixels : bytes[area]
}

compiles to

ex:Table.rows a bddo:Field ; bddo:dataType ex:Row ; bddo:hasArgument ( "instance.hdr.count" "4" ) .
ex:Row a bddo:Struct ; bddo:hasParameter ( ex:Row.n ex:Row.w ) ; bddo:hasField ( ex:Row.cells ) .
ex:Row.n a bddo:Parameter ; bddo:parameterType bddo:IntegerParameter .
ex:Row.w a bddo:Parameter .
ex:Row.cells a bddo:Field ; bddo:dataType bddo:bytes ; bddo:sizeFromExpression "param.w" ;
    bddo:repeatCountFromExpression "param.n" .
ex:Image a bddo:Struct ; bddo:hasField ( ex:Image.width ex:Image.height ex:Image.area ex:Image.pixels ) .
ex:Image.area a bddo:LocalBinding ; bddo:localExpression "instance.width * instance.height" .
ex:Image.pixels a bddo:Field ; bddo:dataType bddo:bytes ; bddo:sizeFromExpression "instance.area" .
  • Names. Inside a parameterised struct, a bare name that names one of its parameters compiles to param.name, and a bare name that names a let binding compiles to instance.name, as a sibling field's does. A parameter, a binding and a field are all members of one namespace per struct, so a bare name has one reading. A reference to a binding never takes the …FromField form of the field-form rule, because a binding is not a field: bytes[area] is bddo:sizeFromExpression "instance.area".
  • Arguments. Each argument is an expression, ended by a , or the closing ) at parenthesis depth 0, and is resolved in the caller's struct: bare names are its fields, bindings and parameters, so Cell(w) inside Row passes param.w on. It is emitted as the canonical HEL string, an integer literal included ("4").
  • Order. A let binding is a member of the struct's bddo:hasField list at its position, and a reference to it from an earlier member is a forward reference under the rules of §Expressions, exactly as a reference to a later field is.
  • Recursion. A struct may name itself, with arguments, in its own fields: struct Node(depth) { v : u8 child : Node(depth - 1) if depth > 0 }. The Processing Model's nesting-depth limit bounds a recursion the data does not end.
  • Colons. The colon of a typed parameter, like that of a crc(…) parameter, may be written with or without spaces: in a parameter list the lexer's n: (a NAME ending in :) and n:int (a NAME that would elsewhere be a CURIE) are read as the name, colon and type they spell.

A compiler MUST report an ERROR for: a type position that supplies a number of arguments other than its struct's number of parameters (including arguments for a struct without parameters, and none for one with parameters); a parameterised struct in a position that cannot state arguments — a dispatch default, a layout cell type, a described-by part struct, and the root struct (@root, or the first struct) — since none of them has a caller that could supply them; two parameters, two bindings, or a parameter, binding and field of one struct, that share a name; a parameter type other than the five words above; param used as a name, and param.x in a struct with no parameter x; a forward or self reference in an argument, which is evaluated at the position of the field that passes it, or in a let expression, which is evaluated at the binding's position; a clause on a let (it has a name and an expression, nothing else); a let binding named where a field is required — a layout extent or stride, a checksum range bound, @root-key, @lang-from — since it has neither bytes nor a place in the tree; and a let in a header, table or document, whose members have no evaluation order. A literal argument whose kind differs from a typed parameter's (Row("a", 4) for n: int) is also an ERROR; an argument that is an expression is checked by the processor when it is evaluated.

Delimited Text Containers

Not every format addresses its bytes by offset. A great many raster formats pair a raw binary grid with a text label — key = value lines, or whitespace-aligned columns — and the label carries exactly the parameters the grid needs: its extents, its sample type, its byte order. Two container forms cover them, declared like a struct but located by delimiter rather than by position. 

header EnviHeader @record-separator 0x0A @separator 0x3D @trim @ci {
  "samples"    : anum
  "lines"      : anum
  "byte order" : anum
}

table Points @record-separator 0x0A @whitespace @comment "#" @skip 1 {
  x : adec
  y : adec
  z : adec
}

A header compiles to bddo:KeyValueHeader: its records are key/value pairs, each field is located by the quoted key, and record ORDER is not significant. A table compiles to bddo:DelimitedTable: its records are rows with a fixed column sequence, so its fields are named rather than quoted and are located by POSITION. The distinction is not cosmetic — it is why a header tolerates a missing or reordered line and a table does not.

Tree documents

A document container compiles to bddo:TreeDocument: its bytes go to a parser for the declared syntax, and each field names the node supplying its value. Paths are an abbreviated XPath for @xml and RFC 6901 pointers for @json. 

document Label @xml
  @ns "pds"  "http://pds.nasa.gov/pds4/pds/v1"
  @ns "disp" "http://pds.nasa.gov/pds4/disp/v1"
{
  "/pds:Product_Observational/pds:File_Area_Observational/pds:Array_2D_Image/pds:Axis_Array[1]/pds:elements" : anum
  "/pds:Product_Observational/pds:Observation_Area/@unit" : str
}

document ArrayMeta @json {
  "/shape/0"       : anum
  "/dtype"         : str
  "/compressor/id" : str
}

@ns "<prefix>" "<iri>" binds a prefix used in the paths, and an XML document generally needs it: an unprefixed path against a namespaced document matches nothing rather than failing. @ns "" "<iri>" binds the default namespace, which an abbreviated XPath cannot otherwise reach.

As with a nested header, the field syntax does not change — a quoted name becomes a bddo:nodePath because the container is a document. A field located by path has no byte extent, so a byte-level clause on it (a size, terminator, @at, bit length, @align, @fixed, checksum, @encoding, layout or repeat until) is an ERROR. A binary numeric type such as u32 is accepted with a WARNING: the value is read as a number written as text, so anum/adec say what happens. One quoting convention across all three container forms, with the container deciding what the quoted string means.

Nested labels

A flat container stops at the label formats that are otherwise the same shape. PVL/ODL nests with OBJECT = … END_OBJECT, the ERMapper header with Name Begin … Name End, and INI-style labels with bracketed sections. @group declares which, and the two tokens that delimit a group: 

header Label @record-separator 0x0A @separator 0x3D @trim
  @group keyed "OBJECT" "END_OBJECT"
{
  "RECORD_BYTES"    : anum
  "IMAGE/LINES"     : anum
  "IMAGE/BAND/NAME" : str
}

Styles are keyed (the record's KEY is the token, its VALUE names the group), valued (the mirror image — ERMapper) and section (a bracketed header opens a group and implicitly closes the previous one). Both tokens are required: a grouping that says where a group starts but not where it ends cannot be read, because every record after the first group would be inside it.

The field syntax does not change. A quoted name becomes a bddo:keyPath instead of a bddo:key when — and only when — the container declares a grouping. An author writes the same thing either way and the two decisions cannot disagree, which is why HDL has no way to pair a path with a flat container. @path-separator "." overrides the default /, needed by any format whose group names may themselves contain a slash.

Expressions

Expression clauses (sizes, offsets, counts, presence, conditions, computed values) are written in HEL and follow the HEL name-binding rules. For an expression attached to a field, instance is the struct that contains the field, parent is that struct's parent, root is the root struct, and self is the value being tested (in repeat until and @valid). The one exception is repeat until over struct elements: there instance and self are the element just read, so a bare name is a field of that element, and parent is the struct containing the repeated field; over scalar elements the general rule holds and self is the value just read (HEL name binding). A struct-level expression (@size, means-when, @endian switch) and every dispatch condition (switch, dispatch … on, cell switch, order switch) evaluate against the containing struct as instance in the same way.

  • A bare name x is shorthand for instance.x: a field of the same struct (a sibling of the field being described). The compiler emits it in the canonical form instance.<name>, after applying any as alias of that sibling.
  • A field of the enclosing struct's parent is written parent.x; a field of the root struct is root.x. What parent.x reads depends on the property: for a field-level expression it is a field of the struct that contains the containing struct (never a sibling); for repeat until over struct elements it is a field of the struct that contains the repeated field; for a struct-level expression it is a field of the struct's parent. The deprecated alias that made parent mean instance in a dispatch condition is never emitted.
  • In the predicate of all/any over struct elements, a bare name resolves to a field of the element (instance.v) or, failing that, of the enclosing struct (parent.n); a name that both declare is an ERROR, since either reading would be a guess.
  • A bare name that names a parameter of the containing struct becomes param.name; one that names a let binding becomes instance.name (§Parameters and local bindings).
  • The reserved roots instance parent root self stream asset param and the HEL function names (sizeof len count eof trim substringBefore substringAfter substring concat toNumber partExtension, when followed by () pass through unchanged.
  • Dotted paths and subscripts pass through: root.Directory[i].Entries[0].Tag.
  • Contents of string literals are never rewritten (so type == 'IHDR' keeps 'IHDR' intact).

Undefined and forward references. A bare name that is not a field of the containing struct is an error, as is a reference to a field that is not yet bound at the point where the expression is evaluated (a forward reference): a field-level size, count, offset or presence expression may name only fields declared before the field it describes, and not the field itself (except in @valid, which runs after the field is read). An optional field that is legitimately absent (its if condition was false) is bound and reads as Null; that is not an error.

A forward reference is a compile-time ERROR wherever the compiler can determine it, by these rules:

  • Within the struct. In a size, count, offset, presence, derived value, switch or dispatch selection or layout expression, a bare name (or instance. path) naming the field being described or a later field of its struct is forward. In @valid and a checksum's covers expressions the field itself has been read, so a reference is forward from the next field on. In repeat until a reference is forward from the repeated field itself when the elements are scalars (self is the element), and from the next field when they are structs. A struct's @size has no order rule within its struct: it is evaluated once every field it names is bound (Processing Model, Struct-level size).
  • Through root. root.x is forward when x is declared after the root field that holds the struct the expression belongs to, or is that very field with no further step.
  • Through parent. parent.x follows the same rule against the struct's container, when exactly one field of exactly one struct holds the struct. A struct with several possible containers is not checked (it may be forward in one and not in another), and the Processing Model's forward-reference error covers it at run time.
  • Evaluated after the parse. A value expression, a map guard and a means-when guard are evaluated when the tree is complete and may name later fields; an @endian switch guard that names a field not yet bound counts as not holding (Processing Model, conditional byte order).

Keys on values. A compiler MUST report an ERROR for a key step applied to a field that holds a scalar (n.foo), or to a repeated field without a subscript (es.size; the number of elements is len(es)): neither has fields. A subscripted element of a repeated struct field has its struct's fields (es[0].v).

Root keys. A root.k path whose k is not a field of the root struct is an undeclared name, except when some struct of the document declares @root-key: k may then be a key only the data names (Processing Model, Root key), and a compiler MUST then accept root.k for any identifier k.

Names in repeat until. A compiler MUST resolve the names of a repeat until condition as follows. Over struct elements a bare name in a repeat until condition is looked up first among the element's fields, emitted as instance.x, and, failing that, among the fields of the struct that contains the repeated field, emitted as parent.x (HEL binds parent to that struct there). A name both declare is an ERROR, since either reading would be a guess; a container field declared after the repeated field is a forward reference. Over scalar elements a bare name is a field of the containing struct, as in every other field-level expression.

A conforming compiler MUST validate every synthesized expression against the HEL grammar and MUST report an ERROR diagnostic, at compile time, for: a bare identifier that does not resolve to a declared field; a forward reference, including a field's reference to itself outside @valid; self outside repeat until, @valid and a quantifier predicate; a stream. key other than length, position and remaining; evaluationInstant() in an expression evaluated while parsing (it exists only for conformance assertions); and a root., parent. or asset. path that does not resolve to a declared field. The canonical HEL string is produced by parsing and re-serializing the resolved expression, so equivalent inputs converge on one normal form.

Ternaries. ? is the HEL conditional operator (c ? a : b) and may be written in any expression position, bracketed or not: count : derive v == 0 ? a : b. In an unbracketed expression a : belongs to the expression while a ? is open, and otherwise ends it (§Grammar: Embedded expressions).

Layout references. The names in a layout — a dimension's size and chunk, cell-bits from, chunks offsets/lengths, a stride expression, and the guards of cell switch and order switch — are sibling references like any other: each MUST name a field of the containing struct, and an unknown one is an ERROR.

Raw HEL

A backtick-delimited expression is a literal HEL string that bypasses sibling resolution — the escape hatch for the rare expression the sugar cannot express, or that references a context the resolver cannot see:

data : bytes[`instance.ChunkLength - (sizeof(instance.Keyword) + 1)`]

Semantic Mapping (Hexplain Core)

The keyword means carries the OWL 2 punning that Hexplain Core uses: on a struct it emits hexplain:mapsToClass; on a field, hexplain:mapsToProperty.

use araster: <https://hexplain.io/ns/aspect/raster#>
use menc:    <https://hexplain.io/ns/register/media-encoding#>
use png:     <https://hexplain.io/formats/png#>      // the base namespace, for format-local terms

struct IHDR_ChunkData means araster:RasterGrid {
  width  : u32 means araster:width
  height : u32 means araster:height
  gamma  : u32 means png:gamma value gamma / 100000.0 @datatype xsd:double
  data   : bytes[..] @encoded-with menc:Zlib
}

The use lines are required: araster and menc are not predeclared (§Prefixes), and an undeclared prefix is an error.

HDLTurtle
means <Class> (struct)hexplain:mapsToClass <Class>
means <Property> (field)hexplain:mapsToProperty <Property>
value <expr> @datatype <dt>hexplain:valueExpression "…HEL…" [+ hexplain:valueDatatype <dt>]
@encoded-with <concept>hexplain:isEncodedWith <concept>
@pipeline { <codec>(<name> <value>, …), … }hexplain:hasEncodingStep → an ordered list of hexplain:EncodingStep

One codec is the exception rather than the rule, so @encoded-with has a pipeline form. A TIFF strip is horizontally differenced and then deflated; a Zarr array chains delta into a Blosc parameterised by an inner codec, a shuffle mode and a level. With only the single-codec shorthand a description could name the last step and lost both the earlier ones and every setting — enough to identify the compression, never enough to undo it. Parameters are juxtaposed rather than written name = value, as everywhere else in the DSL. 

use menc: <https://hexplain.io/ns/register/media-encoding#>

struct Segment {
  strip : bytes[..] @pipeline { menc:Delta(elementSize 1, predictor 2), menc:Zlib(level 6) }   // TIFF predictor 2, then deflate
}
struct Tile {
  tile  : bytes[..] @pipeline { menc:Zlib(level 9) }                             // one parameterised step
}

A step's parameters are integer literals (the Processing Model rejects any other parameter value), and the codec is a concept of the media-encoding register. Every processor decodes the minimum codec set: menc:Store, menc:Deflate, menc:Zlib, menc:Gzip and menc:Delta, whose parameters are named there (elementSize, required; littleEndian, samplesPerPixel, rowBytes, predictor). The first line above would read menc:Delta(elementSize 1, predictor 2) for 8-bit samples. Other register concepts — menc:Blosc, menc:Zstd, … — compile and describe the encoding faithfully, but are optional: a processor that has no codec for a step refuses the description with Unsupported feature rather than returning undecoded bytes. The Processing Model defines three of them (Codecs beyond the minimum set): menc:LZ4 (the LZ4 frame format) and menc:Zstd take no parameters, and menc:LZ4Block, a bare LZ4 block, requires its decoded size: @pipeline { menc:LZ4Block(decodedSize 4096) }.

Order is ENCODE order — the steps as the writer applied them, so a reader inverts them in reverse. Stating this matters, because a pipeline read the wrong way round is still a plausible-looking pipeline. The two forms are mutually exclusive (a field that writes both is an ERROR, One of each): @encoded-with remains the shorthand for a single unparameterised codec.

A field's value expression may reference the field by its own name. Conditional mapping (hexplain:hasConditionalMapping) is written with map, mirroring switch:

struct TextChunk {
  keyword : latin1 @terminator 0x00
  text    : latin1[..] map {
    when keyword == "Title"  => dcterms:title
    when keyword == "Author" => dcterms:creator value trim(text)
  }
}

Each arm becomes a hexplain:MappingRule with hexplain:condition + hexplain:semanticProperty, and an optional per-arm valueExpression/valueDatatype.

Multi-dimensional Layout (DLV)

A layout clause on a field emits hexplain:hasDataLayout → a dlv:DataLayout. Dimensions are listed slowest to fastest (the dlv:hasDimension list order); size <int> → dimensionSize, size <sibling> → dimensionSizeFromField.

struct Image {
  width    : u32
  height   : u32
  rowBytes : u32                                   // row pitch, including padding
  pixels   : bytes[..] layout cell u8 {
    dim axis Y    size height  stride rowBytes     // lone sibling → dlv:dimensionStrideFromField (bytes per row)
    dim axis X    size width
    dim axis Band size 3
  }
}

Axes: X Y Z Band Time → dlv:axisX/axisY/axisZ/axisBand/axisTime. A stride is measured in bytes (even for a bit-packed cell) and follows the same field-form/expression-form rule as sizing: an integer literal → dlv:dimensionStride (a positive xsd:integer, Literal datatypes), a lone sibling → dimensionStrideFromField, anything else → dimensionStrideFromExpression, evaluated with the containing struct as instance. A dimension with no stride is contiguous. A size takes only an integer literal or a sibling name (no expression form), and chunk <int|sibling> after a dimension's size and stride gives its chunk (tile) extent in cells (dlv:chunkSize / dlv:chunkSizeFromField); chunks offsets <field> [lengths <field>] [base <offset-base>] [order row-major|column-major|morton|hilbert] in the layout body says where the chunks are stored.

Conditional layouts

The cell type and the dimension order may each depend on something read earlier, because the same bytes are read differently: an ESRI grid's NBITS 32 is uint32 for a .bil and float32 for a .flt, and an ENVI cube's dimensions are ordered by its interleave keyword. These are two independent conditionals over one set of dimensions rather than one conditional layout, which would multiply into a case per (interleave, width) pair. 

use araster: <https://hexplain.io/ns/aspect/raster#>

bundle EsriGrid @bound-by naming-convention {
  part ".bil" ".bip" ".bsq" ".flt" role Payload required primary described-by Grid
  part ".hdr" role Metadata required carries araster: described-by Header
}

header Header means araster:RasterGrid @record-separator 0x0A @separator 0x20 @trim @ci {
  nrows  : anum means araster:height
  ncols  : anum means araster:width
  nbands : anum
  nbits  : anum
  "layout" as interleave : str
}

struct Grid {
  // Zero-byte derived siblings bring the header part's values into this struct's scope,
  // because a dimension size must be a literal or a sibling name.
  nrows      : derive asset.Header.nrows
  ncols      : derive asset.Header.ncols
  nbands     : derive asset.Header.nbands
  nbits      : derive asset.Header.nbits
  interleave : derive asset.Header.interleave
  pixels : bytes[..] layout {
    cell switch {                                  // dlv:hasConditionalCellDataType
      when partExtension(asset.Grid) == ".flt" => f32
      when nbits == 8                          => u8
    }
    dim axis Y    size nrows
    dim axis Band size nbands
    dim axis X    size ncols
    order switch {                                 // dlv:hasConditionalDimensionOrder
      when interleave == "BIL" => Y Band X
      when interleave == "BSQ" => Band Y X
    }
  }
}

This example reads values from another part of a multi-file asset (asset.Header.…) and the grid part's own extension (partExtension(asset.Grid); a part is named by the struct its part spec is described-by), so it can only be processed by a processor in the Bundle Processor conformance class (Processing Model §Conformance classes); a Physical Parser handed the raster part alone MUST fail the asset references with an error rather than read them as Null. The when guards refer to the derived siblings by bare name, which is instance.<name>. A single-file variant replaces each derive asset.Header.x with a field read from the same file. The payload part lists its four extensions as alternatives: the grid is whichever one of them is present, and partExtension reports which. A Bundle Processor parses the header part first, whatever order the files arrive in, because the grid reads it.

Rules are first match wins, so a more specific arm must precede a more general one — the .flt arm above comes first because a float grid is also 32 bits wide. The header form layout cell <type> { … } is unchanged and mutually exclusive with cell switch. An order arm lists axes, not new dimensions: the dimensions are declared once and each arm permutes those same nodes, so an extent is written once and the arms cannot disagree about it. An arm must list every declared axis exactly once; omitting one silently drops a dimension.

Sub-byte cells

Every bddo:DataType is a whole number of bytes, so a grid whose cells are not — a 1-bit mask, a 4-bit palette index, GRIB2 packing, NITF 1-bit imagery — needs its packed width stated separately. cell-bits overrides the cell type's intrinsic width, so the type keeps saying how to interpret a cell while the width says how much room it takes. 

struct Mask {
  h    : u16
  w    : u16
  mask : bytes[..] layout cell u8 { cell-bits 4  packing msb  dim axis Y size h  dim axis X size w }
}
struct PackedValues {
  nbits : u8
  n     : u32
  grib  : bytes[..] layout cell u8 { cell-bits from nbits      dim axis X size n }
}

packing msb|lsb → dlv:cellPackingOrder, defaulting to MSB-first, which is what GRIB2, NITF and the 1-bit and 4-bit image formats all use. It is only meaningful alongside a packed width, and a width is either fixed or read from a field, never both. Distinct from asamp:bitDepth, which is significant bits carried inside a wider container: that grid is padded, this one is packed, and the two can hold different values for the same raster.

Some formats are not a single file. hx-bundle models a logical Asset realized by several physical Parts. A bundle profile is a reusable template; an asset is an instance.

A profile that expects several files declares several parts.

Escape Hatch

Two constructs guarantee completeness against the evolving vocabularies:

  • raw-turtle { … } at struct scope injects arbitrary Turtle triples into the output graph; its body is preserved verbatim. There is no field-scoped form, but a struct-scope block can still inject a triple about any of the struct's fields (e.g. :S asref:wktString :Field .).

  • Scalars follow YAML's quoting. A scalar's content is what YAML's own quoting and escaping give: a double-quoted "\x41" is A, a single-quoted '\n' is a backslash and an n, and HDL's escape set is not applied to it a second time, except inside an expression, whose string literals keep HEL's escapes. A quoted scalar in a literal position is a string (a quoted "0x…" excepted, below); a CURIE or an IRI value is written as the mapping { curie: ex:Primary } or { iri: "https://…" } (in prop:, for example), since a bare scalar there is a string.
  • Mappings and sequences. A conforming YAML loader MUST report an ERROR for a mapping that repeats a key (YAML leaves the outcome to the loader, and last-wins would drop a field or a clause silently) and for a null entry in a sequence (a stray - in a field list), rather than skip it.
  • Literals follow the text rules. An unquoted scalar is read as the text surface reads the same characters, whatever a YAML resolver would make of it: an unquoted 0x10 is a hex byte string (as @fixed 0x10), 010 is the decimal integer 10 (not octal), and 0b101 is the binary integer 5. fixed: has exactly the semantics of @fixed. Quoting a hex literal (fixed: "0x89504E47") is still accepted.
  • Bit fields use type: bits with a sibling bit-length scalar.
  • HEL string literals inside a YAML expression scalar use single quotes, HEL's own delimiter (until: "self.ChunkType == 'IEND'", where self is the element just read).
  • Booleans. A conforming YAML loader MUST restrict implicit boolean resolution to true/false; the YAML 1.1 words on/off/yes/no are strings (so a struct field or switch key named on is not silently coerced).

Grammar (text surface)

This section is normative. It defines the complete text surface of HDL: a conforming compiler MUST accept every document the grammar generates (subject to the static rules below and elsewhere in this document) and MUST report an ERROR diagnostic for any document it does not generate.

Notation. The grammar uses the EBNF notation of [[XML]] (§6 Notation): ::= defines a symbol; | separates alternatives; ?, * and + mean optional, zero-or-more and one-or-more; "…" is a literal; […] and [^…] are character classes; #xN is a code point; /* … */ is a comment. Upper-case symbols are tokens (§Tokens); a quoted word such as "struct" in a syntactic production matches a NAME token with exactly that text (keywords are contextual, §Keywords) and a quoted "@…" word matches an ANNOT token. Tokens may be separated by whitespace and comments, which are otherwise ignored; there are no statement separators, and a "," shown as optional in a list is purely cosmetic.

Tokens

WS            ::= ( #x20 | #x9 | #xD | #xA )+
Comment       ::= "//" [^#xA]* | "/*" ( [^*] | "*"+ [^*/] )* "*"+ "/"   /* block comments do not nest */

NameChar      ::= Letter | Digit | "_" | ":"

                | "'" ( [^'\] | Escape )* "'"

                       | "x" HexDigit HexDigit | "u" HexDigit HexDigit HexDigit HexDigit )

                | "."                       /* only as described below */

  • A NAME is one token even when it contains -, . or :: stream-start, root.Directory, roads.shp, asset.Header.nbits and araster:RasterGrid are single tokens, but a..b, a--b and n- are not (a - or . is joined only singly and only before a name character). A NAME used as a field name or alias MUST additionally be a HEL identifier (§Lexical Structure). A : that does not follow a name character is the field separator ":"; consequently an empty-prefix CURIE (:x) has no text-surface spelling outside raw-turtle.
  • A - immediately followed by a digit begins a number (-1); otherwise, outside a NAME, it is an OP.
  • After 0x, 0X, 0b or 0B the lexer reads the whole run of letters and digits: a character that is not a hex (respectively binary) digit in it is a lexical ERROR.
  • A . that is not part of a NAME, a FLOAT or .. is the OP . (a key step, as in Items[0].Tag) only when a NameStart follows it, after optional spaces or tabs; any other lone . is a lexical ERROR.
  • A < begins an IRIREF only when the next character is not whitespace, < or = and a > occurs before the next whitespace; otherwise it is the OP <, <= or <<.
  • A BRACKET_EXPR whose trimmed content is itself a single backtick expression ([`…`]) is a BACKTICK_EXPR.
  • A STRING, whichever quote delimits it, denotes its content; where it appears in an expression it becomes a single-quoted HEL string with that content.
  • ;, #, $ and any other character not covered above cannot begin a token. Outside a STRING, BRACKET_EXPR, BACKTICK_EXPR, IRIREF, RAW_BLOCK or comment such a character is a lexical ERROR, as is a STRING, block comment, BACKTICK_EXPR, BRACKET_EXPR or RAW_BLOCK that is still open at end of input.

Embedded expressions

Every Expr, Guard and CoverExpr denotes a HEL expression: after the rewriting of §Expressions, its text MUST match the Expression production of the HEL grammar. HDL itself only decides where an embedded expression ends:

Expr           ::= BRACKET_EXPR | BACKTICK_EXPR | TokenRun
TokenRun       ::= RunToken+       /* maximal, subject to the stop rule below */
RunToken       ::= NAME | INT | HEX | FLOAT | STRING | OP | BRACKET_EXPR | BACKTICK_EXPR
                 | "(" | ")" | "," | ":" | ".."
Guard          ::= GuardToken+     /* every token up to, not including, the next "=>" */
GuardToken     ::= /* any token except "=>", "{" and "}" */
CoverExpr      ::= CoverToken+     /* every token up to a "," or ")" at parenthesis depth 0 */
CoverToken     ::= /* any token except "{" and "}"; "(" and ")" must balance */
  • Bracketed ([ … ]): the text between the brackets is the expression, delimited only by the matching bracket; it may contain any HEL syntax. It undergoes the same rewriting as an unbracketed expression: bare names become sibling references, a double-quoted string becomes a single-quoted HEL string, and a 0b literal is written in decimal.
  • Backtick (` … `): the text is raw HEL, emitted verbatim with no rewriting at all, so it MUST already be valid HEL (single-quoted strings, no 0b literals, explicit instance. accessors where wanted).
  • Unbracketed (TokenRun): the run stops, without consuming it, before:
    • {, }, =>, any ANNOT, or the end of input;
    • a , or an unmatched ) outside parentheses (a separator of the enclosing clause);
    • a ":" when no ? is open — while a ternary's ? is open, the next ":" is part of the expression;
    • the start of the next field declaration, NAME ":" or NAME "as" NAME ":", or in a header or document STRING ":" or STRING "as" NAME ":", outside parentheses and ternaries;
    • an expression stopper in keyword position, that is, directly after a complete operand. After an operator, (, ,, ?, : or and/or/not, the same word is an operand, so repeat n + value reads the sibling value.
    The HEL text is the run's tokens joined by single spaces (no space inside parentheses or before a comma), rewritten as for a bracketed expression (so type == "IHDR" becomes instance.type == 'IHDR').
  • Subscripts and groups in a run. A BRACKET_EXPR directly after a NAME (other than and, or, not), a ) or another subscript, with no whitespace between, is a subscript (Items[i].Tag). Any other BRACKET_EXPR in a run is a parenthesised group and is emitted as ( … ).
  • Backticks are all or nothing: a BACKTICK_EXPR MUST be the whole Expr or Guard; one inside a longer run is an ERROR.
  • Guards (when … =>) run to the arrow; they may contain a ternary directly. A guard that is a single BRACKET_EXPR or BACKTICK_EXPR token is that expression; otherwise a bracket token is a subscript or group as in a run.

Language version

A document MAY begin with a version declaration, hdl 1.0, before any other declaration. A document without one is HDL 1.0, the language this document defines. On the YAML surface the declaration is the top-level key hdl: 1.0; a mapping has no order, so it has no position rule there, and every other value of the key is an unsupported language version.

A compiler that does not recognise the declaration, or that recognises it but does not implement the version named, MUST report an ERROR diagnostic (unsupported language version) and MUST NOT compile the document under the rules of a different version. A version declaration anywhere but first is an ERROR. The reference compiler accepts hdl 1.0 and reports every other version as unsupported.

Modules, imports and keyed dispatch

A module is a format description that is not a file format: it declares a namespace and structs for other descriptions to import. An import "<path>" as <alias> binds the alias as a prefix to the module's namespace; the imported module is compiled, not copied, and the importing document's ontology carries owl:imports for it. alias:Name then names an imported struct in any type position and an imported dispatch table in extend dispatch. Nothing of the imported module is re-emitted, so a fix to the base is a fix for every importer.

File iso-bmff/iso-bmff.hx — a module, complete on its own:

module isobmff @namespace "https://hexplain.io/ns/profile/iso-bmff#" @endian big

struct Box @size `instance.size == 1 ? instance.largesize : (instance.size == 0 ? stream.remaining + 8 : instance.size)` {
  size      : u32
  type      : ascii[4]
  largesize : u64 if size == 1              // present only for a 64-bit box size
  payload   : bytes[..] dispatch BoxPayload on type { "ftyp" => FileTypeBox  "meta" => MetaBox }
}
struct FullBoxHeader { version : u8  flags : bytes[3] }
struct FileTypeBox   { majorBrand : ascii[4]  minorVersion : u32  compatibleBrands : bytes[..] }
struct MetaBox       { hdr : FullBoxHeader  children : bytes[..] }

File heif/heif.hx — a second module that imports the first. It compiles only as a file next to iso-bmff/, with an import root that contains both directories (see Import resolution):

module heif @namespace "https://hexplain.io/ns/profile/heif#"
import "../iso-bmff/iso-bmff.hx" as iso
extend dispatch iso:BoxPayload { "ispe" => ImageSpatialExtents }
struct ImageSpatialExtents { hdr : iso:FullBoxHeader  width : u32  height : u32 }

Struct size. @size <expr> on a struct gives the struct's total extent in bytes, counted from its first byte (bddo:size / sizeFromField / sizeFromExpression by the field-form rule). Its expression evaluates with the struct itself as instance, and it is evaluated once every field it references is bound — not before the first field is read — so it may name fields of the struct it sizes; naming a field that is not yet bound when the size is needed (for example one declared after a field whose extent depends on the struct's remaining size) is a forward reference and an error. Above, largesize is read (or skipped, and then Null) before payload, whose [..] extends to the end of the box, so the size is known when payload needs it; with size == 0 the box runs to the end of the stream, 8 header bytes having been read.

The @size clause above is written as backtick raw HEL, which is emitted verbatim; the same size can be written with bare sibling names, bracketed or not, since ? is HEL's ternary operator in every expression position: @size [ size == 1 ? largesize : (size == 0 ? stream.remaining + 8 : size) ]. A ternary's : belongs to the expression while its ? is open, so it is not mistaken for a field separator (§Grammar: Embedded expressions). (derive <expr> is the zero-byte computed-field type — name : derive <expr>, lowering to bddo:valueFromExpression — not a modifier applied to @size.)

Keyed dispatch. dispatch <Name> on <expr> [default <Struct>] { <key> => <Struct> … } lowers to a named bddo:DispatchTable whose arms are independent bddo:DispatchArm resources (bddo:armTable, bddo:armKey, bddo:armDataType). A lone sibling in on becomes bddo:dispatchOnField; any other expression becomes bddo:dispatchOnExpression, resolved like a switch condition. Keys are string or integer literals and typed: the string "7" and the integer 7 are distinct arms. Keys are unique per table across the declaring document and every extend dispatch on it — including an extension targeting an imported table — but the HDL compiler does not check uniqueness across separate modules; the loader and the bddo:DispatchKeyUniquenessShape SHACL shape enforce it against the merged graph. switch remains the form for ordered, possibly overlapping guards; a field uses one or the other. extend dispatch at top level contributes arms to a table declared in this document or in an imported module — the mechanism for open type registries.

Seek scope. @seek stream on an offset-addressed field (bddo:seekScope bddo:streamScope) lets that one read leave the innermost bounded region; the default @seek region keeps the Processing Model's containment rule. @seek on a field with no @at clause is a compile-time error, since seek scope only bounds an offset-addressed read that must already exist. An item-location table inside a meta box that points into mdat is the motivating case.

Import resolution. An import path is resolved relative to the directory of the file that contains it, and MUST resolve within an import root. By default the import root is the directory of the root document being compiled, so a document can read only files in its own tree; a caller compiling a profile library whose modules import their siblings (../iso-bmff/iso-bmff.hx above) names the library directory as the root instead. A path that resolves outside the root — an absolute path, a .. escape, or a symbolic link pointing out of the tree, since links are resolved to their real path before the check — MUST be rejected with an ERROR diagnostic on the import line; the root is inherited by every nested import, so an imported module cannot widen it. An import that names no file, cannot be read, or closes a cycle is likewise an ERROR. A document compiled from a string with no file context has no directory to resolve against, so every import in it is an unresolvable-import ERROR.

Processor behaviour of the reference compiler: the library API takes ImportPolicy.WithinDocumentDirectory (the default), ImportPolicy.Within(root) or ImportPolicy.Unrestricted, the last intended only for a trusted caller compiling its own files. The command-line tool (hdl <input.hx|input.hx.yaml> [-o out.ttl] [--import-root <dir> | --unrestricted-imports] [--vocab <terms.ttl>]… [--no-validate]) confines imports to the input document's directory by default; --import-root widens the root to the directory named, and --unrestricted-imports removes the confinement for a trusted operator's own files (the two are mutually exclusive). A service compiling documents it did not write should never pass the latter. By default the tool also validates the emitted description, merged with its imports, against the SHACL shapes of the whole profile family and exits with status 1, writing no Turtle, on a violation; --vocab adds a Turtle file declaring the description's own non-family terms to the validated graph (not to the output), and --no-validate skips the validation. Diagnostics go to standard error as file:line:column: SEVERITY: message; the exit status is 1 when any diagnostic is an ERROR and 2 on a usage error.

Loading a modular description. The published Turtle of a module, or of a format that imports one, is loaded as the union of the document's own graph and every ontology it transitively owl:imports. A processor handed only the importing graph cannot resolve the imported structs (an alias:Name type position points at an IRI that graph does not describe) or the arms an extend dispatch contributed to an imported table, because those arms are subjects in the importing graph whose bddo:armTable names a table declared elsewhere. The reference engine does not fetch imports itself: ProfileLoader and RdfToIrCompiler read exactly the graph they are given. Assembling the union is the caller's responsibility — or the HDL compiler's, whose mergedModel() assembles it from the .hx sources it just compiled.

The YAML surface has no imports: key; a document that imports must use the text surface, and a YAML document that writes one is rejected with a diagnostic (see §Conformance).

Conformance

The key words "MUST", "MUST NOT", "REQUIRED", "SHALL", "SHALL NOT", "SHOULD", "SHOULD NOT", "RECOMMENDED", "MAY", and "OPTIONAL" in this document are to be interpreted as described in [[RFC2119]]. Sections not marked informative are normative, including the grammar.

Two normative artifacts define HDL: this document, and the RDF vocabularies it targets. Where a mapping in this document and a targeted vocabulary disagree, the vocabulary's shapes govern the validity of the output; this document governs the meaning of the input.

This document defines the HDL Compiler conformance class of the Processing Model. What a compiled description may then require of a processor (for example, cross-part asset.… references, which need a Bundle Processor) is defined there, not here.

A conforming HDL compiler MUST:

  1. Accept both the text and YAML surfaces and parse each into the same abstract model, such that a text document and its YAML mirror compile to isomorphic RDF graphs — except for the text-only constructs module, import, dispatch/extend dispatch and @seek, which the YAML surface rejects with a diagnostic.
  2. Accept every text-surface document generated by the grammar (subject to the static rules stated alongside it) and report an ERROR diagnostic for any text-surface input it does not generate.
  3. Mint IRIs per §IRI Minting and bind prefixes per §Prefixes; a CURIE whose prefix is not bound MUST yield an ERROR diagnostic, never a warning and never a silently emitted IRI.
  4. Apply the field-form-vs-expression-form rule and resolve expression identifiers per §Expressions and the HEL name-binding rules, emitting canonical HEL validated against [[?hel]]; a bare reference to an undeclared name MUST yield an ERROR diagnostic, and so MUST every other static error §Expressions lists, a forward reference included, wherever it is statically determinable (§Expressions): the compiler knows the declaration order of every struct it compiles, so every bare-name forward reference, and every root. or parent. one whose path it can follow, is determinable within one document.
  5. Emit BDDO/Core/DLV/hx-bundle triples whose meaning matches the mappings in this document, such that the output satisfies the SHACL shapes of the targeted vocabularies for any well-formed input.
  6. Report malformed input as source-located diagnostics and never raise an uncaught exception to its caller; input that cannot be faithfully compiled MUST yield at least one ERROR diagnostic.
  7. Preserve raw-turtle bodies verbatim in the output graph.
  8. Report an ERROR for a field name or alias that is not an ASCII HEL identifier or is reserved (asset included; §Lexical Structure), and for every layout name that does not name a sibling (§Expressions).
  9. By default, confine import resolution to an import root (the root document's directory unless the caller names another) and reject, with an ERROR, any import whose real path lies outside it (Import resolution). A compiler MAY offer an explicit unrestricted mode for trusted callers.
  10. Report an ERROR diagnostic for a language version declaration naming a version it does not implement.

Compilation is one-directional; a conforming compiler is NOT required to reconstruct HDL from Turtle.

Examples

PNG chunk → Turtle

The PNG chunk compiles to the canonical BDDO form:

@prefix bddo: <https://hexplain.io/ns/bddo#> .
@prefix png:  <https://hexplain.io/formats/png#> .

png:Chunk a bddo:Struct ;
    bddo:endianness bddo:BigEndian ;
    bddo:hasField ( png:Chunk.length png:Chunk.type png:Chunk.data png:Chunk.crc ) .

png:Chunk.length a bddo:Field ; bddo:dataType bddo:uint32 .
png:Chunk.type   a bddo:Field ; bddo:dataType bddo:string ; bddo:size 4 ; bddo:encoding bddo:ascii .
png:Chunk.data a bddo:Field ;
    bddo:dataType bddo:bytes ;
    bddo:sizeFromField png:Chunk.length ;
    bddo:hasConditionalDataType (
        [ a bddo:DataTypeRule ; bddo:condition "instance.type == 'IHDR'" ; bddo:ruleDataType png:IHDR_ChunkData ]
        [ a bddo:DataTypeRule ; bddo:condition "instance.type == 'PLTE'" ; bddo:ruleDataType png:PLTE_ChunkData ]
    ) .
png:Chunk.crc a bddo:Field ;
    bddo:dataType bddo:uint32 ;
    bddo:checksum [ a bddo:Checksum ; bddo:checksumAlgorithm bddo:crc32 ;
        bddo:coversFromField png:Chunk.type ; bddo:coversToField png:Chunk.data ] .
