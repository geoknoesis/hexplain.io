Executive summary

The layered architecture (physical → layout → semantic, joined by a thin "glue" module) is a sound design, and the choice of RDF/OWL/SHACL/JSON-LD is right. But the family is not yet publishable or implementable as it stands. Four of seven domain-vocabulary links are broken, two advertised vocabularies do not exist, two normative artifacts contain logic bugs, several terms used throughout the examples are never defined, and — most importantly for the stated goal of "parse any data structure" — the physical model cannot express offsets/pointers, bitfields, count-based arrays, or a processing model. The good news: every issue below is fixable without disturbing the architecture's spine.

Blockers — broken or logically incorrect

1. Scrambled vocabulary files & dead navigation Blocker

axv/index.html contains the Audio vocabulary; vdv/index.html contains the Document & Font vocabulary. The index links adv/index.html and dfv/index.html (which don't exist) and labels vdv/axv as Video/Archive (which don't exist either).

Rename axv/→adv/ and vdv/→dfv/; correct the module list in the index; link HEL; and either author the Video/Archive specs or remove them from the advertised family until they exist.

2. bddo:dataType is declared twice with conflicting domain/range Blocker

In bddo/index.html:212–223:

:dataType a owl:ObjectProperty ; rdfs:domain :Field ;        rdfs:range [ owl:unionOf ( :DataType :Struct ) ] .
:dataType a owl:ObjectProperty ; rdfs:domain :DataTypeRule ; rdfs:range :Struct .

rdfs:domain/rdfs:range are conjunctive, not alternative. This entails that anything carrying bddo:dataType is simultaneously a Field and a DataTypeRule, and its object is both a Struct and a member of the union — a genuine logical defect.

Give the rule its own predicate (e.g. bddo:ruleDataType), or model the rule's target without redeclaring dataType.

3. bddo:sizeFromExpression is used everywhere but never defined Blocker

HEL's intro (hel:49), the DLV example (dlv:225), and the Core example (hexplain:230) all rely on bddo:sizeFromExpression, but BDDO's normative ontology only defines bddo:size and bddo:sizeFromField. The most important dynamic-sizing primitive is missing from the ontology it belongs to.

Add bddo:sizeFromExpression as a datatype property (range xsd:string, HEL-valued) to BDDO, and add SHACL so a field has at most one sizing mechanism.

4. hexplain:hasDataLayout is claimed to be Core but isn't in Core Blocker

The index:72 and dlv:77 both say hexplain:hasDataLayout comes "from the Hexplain Core ontology," but the Core OWL (hexplain:118–145) never defines it.

Define it in Core: hexplain:hasDataLayout a owl:ObjectProperty ; rdfs:domain bddo:Field ; rdfs:range dlv:DataLayout .

5. The DLV sh:xone Dimension shape can never pass Blocker

In dlv:162–165:

sh:xone (
    [ sh:path dlv:dimensionSize ]
    [ sh:path dlv:dimensionSizeFromField ]
) .

Each branch is a property shape with a path but no constraint, so every node conforms to both. sh:xone requires conformance to exactly one → every dlv:Dimension is reported invalid.

Put a real cardinality test in each branch:

sh:xone (
  [ sh:property [ sh:path dlv:dimensionSize ;          sh:minCount 1 ] ]
  [ sh:property [ sh:path dlv:dimensionSizeFromField ; sh:minCount 1 ] ]
) .

Implementability — you cannot yet "parse any data structure"

The current model handles sequential, byte-aligned, fixed/chunked formats (WAV, PNG chunks, simple headers) well. It cannot express several constructs that are ubiquitous in real formats — and some of those formats (GeoTIFF, PDF, ZIP) are explicitly advertised.

6. No offset / pointer / seek — excludes TIFF, GeoTIFF, ZIP, ELF, PDF xref Major

bddo:hasField is a strictly ordered, contiguous list; there is no absolute/relative offset or pointer-follow. Yet GeoTIFF is advertised (index:109) and forensic carving of PDF/ZIP is a headline use case. TIFF IFDs are offset tables; ZIP is parsed backward from its End-Of-Central-Directory record. None of this is describable today. This is the single biggest gap for "any data structure."

Add an addressing model: an offset base concept plus properties such as bddo:atAbsoluteOffset / bddo:atRelativeOffset (constant, from-field, or HEL-valued), and a "parse-at" instruction that decouples a struct's position from sequence order.

7. No bitfields / sub-byte fields Major

bddo:bitWidth exists only on DataType with values 8/16/32/64. There is no way to carve a 4-bit nibble or a single flag bit — so the IPv4 version/IHL nibbles, TCP data-offset + flags, and PNG bit-depth packing are inexpressible, despite NPV's own tcpFlags/IPv4 example.

Add bit-granular field extraction (bit offset + bit length) with a defined bit-order, and endianness-aware bit packing.

8. No count-based repetition Major

The only array construct is bddo:repeatUntil. The most common binary-format pattern — "read count N, then N records" — has no repeatCount / repeatCountFromField, and HEL has no index/counter to emulate it. The LAS example reads NumberOfPointRecords (gv:275) but nothing expresses "now parse that many point records."

Add bddo:repeatCount and bddo:repeatCountFromField to bddo:Field.

9. No EOF / "rest of stream" concept Major

Many formats end with "read until end of file" (trailing chunks, concatenated IDAT, container payloads). There is no sizeToEndOfStream and no stream-length variable in HEL.

Add a rest-of-stream sizing option and expose stream length / current offset to HEL.

10. bddo:encoding for strings is described but not defined Major

Core types say string "may have an encoding property" (bddo:130), but no such property exists in the ontology and no allowed-encodings vocabulary is provided.

Define bddo:encoding and an enumeration of encodings (UTF-8, ASCII, UTF-16LE/BE, Latin-1, …).

11. Checksums / CRC are promised but not modeled Major

The abstract and the digital-forensics use case (index:147) claim integrity validation via checksums, but the only validation primitive is bddo:hasFixedValue (magic numbers). There is no way to declare "this field is a CRC-32 over byte range X." The PNG ChunkCRC in the example is an inert field.

Add a checksum construct (algorithm identifier + covered byte range + stored-value field), or remove the advertised capability.

12. Conditional dispatch is Struct-only Major

bddo:DataTypeRuleShape forces the dispatched dataType to be a bddo:Struct (bddo:300–305), so you cannot switch a field between two primitives (e.g. uint16 vs uint32 by version byte).

Loosen the rule range to DataType ∪ Struct.

13. No enumerations / value maps Major

There is no way to say colorType 0=Grayscale, 2=RGB, 3=Indexed. Conditions compare raw integers, and the generated RDF loses the symbolic meaning. (Kaitai Struct's enums is the reference feature.)

Add an enumeration construct mapping raw values to named/IRI symbols, usable in conditions and emitted into the output graph.

14. HEL is under-specified for a conformant implementation Major

  • Grammar vs. examples conflict. Accessor = "instance" *(…) requires every accessor to start with instance, but hexplain:230 uses parent.ChunkLength (no instance) and instance.Keyword.size (a .size meta-accessor the data model never defines).
  • "instance = root" vs instance.parent. The data-model text (hel:65) calls instance the root; but instance.parent.X only makes sense if instance is the current node. This ambiguity blocks implementation.
  • No value-coercion rules. How does a 4-byte field (ChunkType) compare to the ASCII literal 'IHDR'? Undefined — yet this underlies every dispatch condition.
  • No current-element reference for repeatUntil (what value is tested each iteration?).
  • No bitwise operators, modulo, or functions (length, substring). "IP header length = (byte & 0x0F) * 4" is inexpressible.
  • Dangling reference: the Type System section (hel:168) defers to "the previous version of this specification," which isn't included.

Reconcile grammar with examples; define instance/parent/current-element precisely; specify a type-coercion table (bytes↔string↔int↔bool); add bitwise/modulo operators and a small function library; inline the comparison rules.

15. No Processing Model spec — the central missing document Major

Hexplain's whole value proposition is "(binary + description) → RDF instance graph," yet no document defines how that graph is produced: parse order, how the parsing context is built, how instance IRIs are minted (essential for the advertised SPARQL queries), what xsd datatype a parsed uint32be becomes as an RDF literal, array/instance identity, and error handling. Without this, two implementations produce different graphs and none of the cross-format SPARQL examples are reproducible.

Author a normative "Hexplain Processing Model" spec covering evaluation order, context construction, IRI minting policy, primitive→xsd literal mapping, and error semantics.

Ontology-engineering best practices

16. The formal ontologies are far weaker than their own prose Major

In IDV/ADV/NPV/DFV/GV, nearly every property is a bare owl:DatatypeProperty ; rdfs:label "…" with no rdfs:range, no rdfs:domain, no rdfs:comment — e.g. idv:150 :pixelWidth a owl:DatatypeProperty ; rdfs:label "Pixel Width" . The ranges (xsd:positiveInteger, …) live only in the HTML tables, so no reasoner or SHACL engine can enforce them.

Push range/domain/definition into the OWL, and add rdfs:isDefinedBy to every term. Better still, generate the tables from the ontology (single source of truth).

17. rdfs:Class vs owl:Class inconsistency Minor

BDDO and DLV declare classes as rdfs:Class; Core/IDV/GV/DFV/ADV/NPV use owl:Class.

Standardize on owl:Class for OWL-DL consistency across the family.

18. Core mapping properties are annotation properties with (inert) domain/range Major

hexplain:119–130 declare mapsToClass/mapsToProperty/isEncodedWith as owl:AnnotationProperty and give them rdfs:domain/rdfs:range — which OWL-DL ignores on annotation properties. Meanwhile the parallel conditional mapping (hasConditionalMapping, semanticProperty) is an owl:ObjectProperty. Same concept, two metamodeling treatments.

If the intent is to avoid punning (a Struct individual referencing an owl:Class), document that rationale and adopt OWL 2 punning consistently, rather than mixing annotation and object properties for one concept.

19. Prose says SHOULD, SHACL says MUST Minor

mapsToClass's subject "SHOULD be a bddo:Struct" (hexplain:59) but MapsToClassShape enforces sh:class bddo:Struct (a hard MUST).

Align the normative language — pick SHOULD (relax the shape to a warning) or MUST (update the prose).

20. Base-type modeling is inconsistent and double-typed Minor

Prose says baseType MUST be one of integer/float/string (bddo:175), but the ontology also defines a fourth, :bytes, and :string/:bytes are each declared both as an owl:NamedIndividual base type and as a :DataType instance (bddo:236–259).

Separate the base-type enum values (e.g. :baseTypeString) from the datatype instances (:string), and reconcile the prose with the four actual base types.

21. Redundant / duplicated axes Minor

DLV defines dlv:axisX/Y/Band; IDV re-defines img:axisX/axisY/axisBand (idv:159–161) instead of reusing or subclassing the DLV ones.

Decide the relationship explicitly (reuse, rdfs:subClassOf, or skos:exactMatch) rather than silently duplicating.

22. Endianness modeled two ways with two names Minor

bddo:Struct uses bddo:endianness; bddo:DataType uses bddo:hasEndianness. Because every integer primitive is endianness-bound (uint32be/uint32le) with no neutral uint32, the struct-level property has nothing to govern — in the LAS example it is set but unused (gv:282).

Either add endianness-neutral primitives that inherit the struct's byte order, or drop struct-level endianness. Unify the property name.

23. Reuse established vocabularies (the big interoperability win) Major

The domain vocabs reinvent well-standardized terms, which undercuts the stated interoperability goal:

  • DFV author/title/creationDate/modificationDate → Dublin Core Terms (dcterms:creator/title/created/modified).
  • GV SensorModel/Platform/AcquisitionInfo/acquisitionTime → W3C/OGC SOSA/SSN + PROV-O; epsgCode/wktString/CRS → GeoSPARQL.
  • ADV/VDV/IDV technical metadata (sampleRate, frameRate, codec, bitDepth) → W3C Ontology for Media Resources (ma:) / EBUCore.
  • Units (Hz, seconds, pixels) → QUDT or OM.

At minimum, publish alignment axioms (owl:equivalentProperty/skos:exactMatch) so a Hexplain graph joins the wider linked-data cloud.

24. Missing ontology metadata / FAIR hygiene, on every module Minor

No owl:versionIRI, dcterms:license, dcterms:created, vann:preferredNamespacePrefix/preferredNamespaceUri; only Core carries an rdfs:comment on the ontology node. owl:imports is never declared even though modules use each other's terms.

Add the standard ontology-header annotations to all modules and declare owl:imports (Core→BDDO, DLV→BDDO, domain vocabs→DLV).

25. No dereferenceable artifacts Major

The OWL/SHACL/JSON-LD live only inside HTML <pre> blocks. The namespace IRIs (https://hexplain.io/ns/bddo#Struct) do not resolve to a machine-readable document — the opposite of linked-data best practice for a project whose thesis is linked data.

Publish real .ttl / .shacl.ttl / .jsonld files with content negotiation, and generate the HTML from them so prose and formal definitions cannot drift.

Additional minor / polish items

  • Copy-pasted ReSpec github. Every spec sets github: "https://github.com/w3c/respec" — ReSpec's own repo, not Hexplain's. Point it at the real repo or remove it.
  • Prefix/acronym drift. IDV is called both "Image Description Vocabulary" and "Image Vocabulary," uses prefix img: and namespace /ns/image# — the acronym "IDV" matches none of them. Establish one prefix registry (name ↔ prefix ↔ namespace) and apply it uniformly.
  • UDPDDatagram typo in NPV (npv:149) — double "D".
  • SHACL doesn't validate list membership. StructShape only checks hasField points to one node; it never checks the members are bddo:Fields (needs an rdf:rest*/rdf:first path). Same for the conditional lists and hasDimension.
  • FieldShape sh:nodeKind sh:IRI forbids inline (blank-node) structs as a field's type, which you may want for anonymous nested structures.
  • Architecture diagram is a placeholder (placehold.co image, index:49).

What's genuinely good — worth preserving Keep

  • The three-layer separation (physical / layout / semantic) with a thin "glue" Core module is a sound architecture.
  • Choosing RDF + OWL + SHACL + JSON-LD, and using rdf:List for field ordering.
  • Expressing interleaving (BSQ/BIP/BIL) purely as list ordering (dlv:81) rather than a fixed enum — elegant and extensible.
  • The conditional-dispatch mechanism for TLV/chunked formats.
  • The map-everything-to-a-shared-domain-vocabulary interoperability strategy.

The problems above are fixable without disturbing this spine.

Suggested priority order

  1. Fix the file scramble + navigation (#1) and the two logic bugs (#2 dataType, #5 sh:xone) — these are objectively broken.
  2. Define the missing terms the examples already use (#3 sizeFromExpression, #4 hasDataLayout, #10 encoding).
  3. Write the Processing Model spec and fix HEL (#14, #15) — nothing is truly implementable without these.
  4. Add the addressing / bitfield / repeat-count / enum primitives (#6–#9, #12, #13) to actually reach "any data structure."
  5. Harden the ontologies — ranges/domains, metadata, external alignments, dereferenceable files (#16–#25).
