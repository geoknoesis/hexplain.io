The Binary Data Description Ontology (BDDO) provides a formal vocabulary to declaratively describe the structure, syntax, and layout of binary data. It is the foundational physical layer of the Hexplain Ontology Family. BDDO allows authors to model binary formats as nested structures and typed fields, with support for dynamic layouts through conditional logic, variable sizing, offset-based addressing, bit-level fields, arrays, stream synchronization, enumerations, and integrity checksums. This specification provides the normative OWL vocabulary for BDDO and a set of SHACL shapes for validating BDDO descriptions.

This document is an unofficial draft produced for the purpose of defining the Hexplain standard. It has no official standing and is not endorsed by any standards body.

Change log. Version 1.4 (this version) adds offset-based addressing (bddo:atOffset and companions), bit-level fields (bddo:bitLength), count-based repetition (bddo:repeatCount and companions), rest-of-stream sizing (bddo:sizeToEndOfStream), string/byte bddo:encoding, integrity checksums (bddo:Checksum), value enumerations (bddo:Enumeration), and endianness-neutral primitive types. It defines bddo:sizeFromExpression (previously used but undefined), fixes the double declaration of bddo:dataType by introducing bddo:ruleDataType, separates base-type individuals from primitive datatype instances, unifies byte-order onto bddo:endianness, and adds a normative primitive→xsd datatype mapping via bddo:xsdType. Property value types are declared with rdfs:range; domain and cardinality constraints are expressed in SHACL (no rdfs:domain). Version 1.3 introduced conditional data type dispatching. Version 1.2 moved repetition properties to bddo:Field. Version 1.1 introduced bddo:terminator and bddo:syncOnMarker.

Introduction

The primary goal of the Hexplain project is to make opaque binary data machine-understandable. The first step is to provide a standardized, unambiguous way to describe the physical structure of the data. The Binary Data Description Ontology (BDDO) serves this purpose.

BDDO provides a set of RDF classes and properties that can be used to create a graph-based model of a binary format. This model can then be used by a conforming Hexplain processor (see the Processing Model specification) to parse a binary stream into a structured, logical representation, and ultimately into an RDF instance graph.

Modeling Approach: Vocabulary vs. Constraints

BDDO follows a deliberate separation of concerns that is a recommended ontology-engineering practice:

  • The OWL vocabulary declares terms (classes, properties, individuals) with human-readable metadata (rdfs:label, rdfs:comment, rdfs:isDefinedBy), lightweight semantics (rdfs:subClassOf, alignment axioms), and each property's rdfs:range (its value type). It deliberately does not assert rdfs:domain, because a domain axiom would silently type any subject of a property — a term is often reused across several classes.
  • The SHACL shapes carry the remaining constraints — the classes a property may apply to (its "domain"), value cardinalities, and any refinement of the declared ranges (controlled-vocabulary membership, numeric bounds). Validation therefore never mutates the graph, and errors are reported rather than repaired by inference.

Conformance

The key words "MUST", "MUST NOT", "REQUIRED", "SHALL", "SHALL NOT", "SHOULD", "SHOULD NOT", "RECOMMENDED", "MAY", and "OPTIONAL" in this document are to be interpreted as described in [[RFC2119]].

Core Concepts

The BDDO model is built upon the following classes.

bddo:Struct
A composite structure or container for other elements. A Struct is an ordered sequence of Fields. Examples: a file header, a network packet, a PNG chunk.
bddo:Field
A single element within a Struct. A Field may represent one value, a bit-level slice, or an array of values, and is associated with a data type.
bddo:DataType
The type of data a Field contains. BDDO defines core primitive data types (e.g. bddo:uint32be). This class can be extended in profiles to create user-defined type aliases (e.g. media:fourCC).
bddo:DataTypeRule
A single rule for conditionally selecting a data type for a field, consisting of a condition and the data type to use when the condition holds.
bddo:Enumeration / bddo:EnumValue
A mapping of raw parsed values to named symbols, so that (for example) a colour-type byte of 2 can be surfaced as RGB in the output graph and referenced by name in conditions.
bddo:Checksum
A declarative description of an integrity check: the algorithm and the byte range it covers. A field that stores a checksum value links to it so that a processor can verify data integrity.

Sequencing, Addressing & Alignment

By default, the Fields listed in bddo:hasField are parsed sequentially and contiguously: each field begins where the previous one ended. Many real formats (TIFF/GeoTIFF IFDs, ZIP central directories, ELF section tables, PDF cross-reference tables) instead locate structures by offset. BDDO supports both models.

bddo:atOffset, bddo:atOffsetFromField, bddo:atOffsetFromExpression
Relocate a Field or Struct to a fixed offset, an offset read from another field, or an offset computed by a HEL expression, respectively. A field with an offset does not advance the sequential cursor for its siblings unless the processor is told otherwise.
bddo:offsetBase
The reference point the offset is measured from: bddo:streamStart (default), bddo:streamEnd (for formats parsed from the tail, such as ZIP), bddo:parentStart, or bddo:currentPosition.
bddo:alignment
An xsd:positiveInteger. Before parsing the field, the processor MUST advance the cursor to the next multiple of this value (padding bytes are skipped).

Bit-Level Fields

Formats such as IPv4, TCP, and many compression headers pack several logical values into a single byte. A Field MAY declare bddo:bitLength (an xsd:positiveInteger number of bits). Consecutive bit-length fields are packed into the underlying bytes; the packing order is governed by bddo:bitOrder (bddo:MSBFirst, the default, or bddo:LSBFirst) declared on the enclosing Struct. A run of bit fields SHOULD align to a byte boundary; a processor MUST pad to the next byte before parsing a subsequent non-bit field.

Core Data Types

BDDO provides a normative set of built-in primitive data types. All conforming processors MUST support these types. Each is an instance of bddo:DataType and carries a normative bddo:xsdType that fixes the RDF literal datatype produced when a value of that type is emitted into the output graph.

Integer and floating types come in three forms: an endianness-neutral form (e.g. bddo:uint32) that inherits its byte order from the enclosing Struct or Field via bddo:endianness, and explicit big-endian / little-endian forms (e.g. bddo:uint32be, bddo:uint32le). Single-byte types have no byte order.

Properties

Structural Properties

bddo:hasField
Links a bddo:Struct to its ordered components. The object MUST be an rdf:List of bddo:Field to preserve order.
bddo:endianness
The byte order for a bddo:Struct, bddo:Field, or bddo:DataType. Value MUST be bddo:BigEndian or bddo:LittleEndian. The nearest declaration wins (DataType > Field > Struct > inherited from the parent).
bddo:bitOrder
The bit-packing order for bit-level fields in a Struct. Value MUST be bddo:MSBFirst or bddo:LSBFirst.
bddo:syncOnMarker
A byte sequence a processor MUST scan for before parsing this bddo:Struct. Value MUST be an xsd:hexBinary literal.

Field Properties

bddo:dataType
The Field's default data type. Value MUST be a bddo:DataType or a bddo:Struct. A Field MUST have either a bddo:dataType or a bddo:hasConditionalDataType (or both).
bddo:hasConditionalDataType
An rdf:List of bddo:DataTypeRule allowing the processor to select a more specific data type at runtime.
bddo:size / bddo:sizeFromField / bddo:sizeFromExpression / bddo:sizeToEndOfStream
The size of the field in bytes: fixed, read from another field, computed by a HEL expression, or "consume the remainder of the stream" (xsd:boolean). A Field MUST use at most one sizing mechanism, and variable-length types (bddo:bytes, bddo:string) MUST use exactly one sizing or termination mechanism.
bddo:terminator
A byte sequence terminating a variable-length field. Value MUST be an xsd:hexBinary literal.
bddo:encoding
The character encoding of a bddo:string field. Value MUST be one of the encoding individuals (bddo:utf8, bddo:ascii, bddo:utf16le, bddo:utf16be, bddo:latin1). Defaults to bddo:utf8.
bddo:bitLength
The width, in bits, of a sub-byte field (see Bit-Level Fields).
bddo:repeatCount / bddo:repeatCountFromField / bddo:repeatCountFromExpression / bddo:repeatUntil
Turn the field into an array parsed a fixed number of times, a number read from another field, a number computed by a HEL expression, or repeatedly until a HEL boolean expression evaluates to true. A Field MUST use at most one repetition mechanism.
bddo:atOffset / bddo:atOffsetFromField / bddo:atOffsetFromExpression / bddo:offsetBase / bddo:alignment
Addressing and alignment (see Sequencing, Addressing & Alignment).
bddo:hasFixedValue
A constant expected value, used to validate markers and magic numbers. The literal is compared against the parsed value after decoding according to the field's data type.
bddo:isPresentIf
A HEL boolean expression; the field is present only if it evaluates to true.
bddo:enumeration
Links a Field to a bddo:Enumeration that maps its raw value to a named symbol.
bddo:checksum
Links a Field (the one storing the checksum value) to a bddo:Checksum describing the algorithm and covered range.

Data Type, Rule, Enumeration & Checksum Properties

bddo:baseType
The fundamental kind of data. Value MUST be one of bddo:baseInteger, bddo:baseFloat, bddo:baseString, or bddo:baseBytes.
bddo:bitWidth, bddo:isSigned, bddo:xsdType
Describe a bddo:DataType: its width in bits, its signedness, and the RDF literal datatype produced on output.
bddo:condition, bddo:ruleDataType
A bddo:DataTypeRule's HEL condition and the data type (a bddo:DataType or bddo:Struct) to apply when it holds.
bddo:hasEnumValue, bddo:enumRawValue, bddo:enumSymbol
An bddo:Enumeration's members; each bddo:EnumValue pairs a raw literal (bddo:enumRawValue) with an optional symbolic IRI (bddo:enumSymbol) and/or rdfs:label.
bddo:checksumAlgorithm, bddo:coversFromField, bddo:coversToField, bddo:coversExpression
A bddo:Checksum's algorithm (e.g. bddo:crc32) and the byte range it protects, given either as a start/end field pair or a HEL expression.

bddo:StructShape a sh:NodeShape ;
    sh:targetClass bddo:Struct ;
    sh:property [ sh:path bddo:hasField ; sh:maxCount 1 ; sh:nodeKind sh:BlankNodeOrIRI ;
        sh:message "bddo:hasField must point to a single rdf:List." ] ;
    sh:property [ sh:path ( bddo:hasField [ sh:zeroOrMorePath rdf:rest ] rdf:first ) ;
        sh:class bddo:Field ;
        sh:message "Every member of a Struct's hasField list must be a bddo:Field." ] ;
    sh:property [ sh:path bddo:endianness ; sh:maxCount 1 ; sh:in ( bddo:BigEndian bddo:LittleEndian ) ] ;
    sh:property [ sh:path bddo:bitOrder ; sh:maxCount 1 ; sh:in ( bddo:MSBFirst bddo:LSBFirst ) ] ;
    sh:property [ sh:path bddo:syncOnMarker ; sh:maxCount 1 ; sh:datatype xsd:hexBinary ] .

bddo:FieldShape a sh:NodeShape ;
    sh:targetClass bddo:Field ;

    sh:property [ sh:path ( bddo:hasConditionalDataType [ sh:zeroOrMorePath rdf:rest ] rdf:first ) ;

# At most one sizing mechanism per field.
bddo:FieldSizingShape a sh:NodeShape ;
    sh:targetClass bddo:Field ;
    sh:sparql [ sh:message "A bddo:Field must use at most one sizing/termination mechanism." ;
        sh:prefixes bddo:_prefixes ;
        sh:select """SELECT $this WHERE {
            $this ?p ?v .
            FILTER(?p IN (bddo:size, bddo:sizeFromField, bddo:sizeFromExpression,
                          bddo:sizeToEndOfStream, bddo:terminator))
        } GROUP BY $this HAVING (COUNT(DISTINCT ?p) > 1)""" ] .

# A variable-length field (bytes/string) MUST declare exactly one sizing/termination.
bddo:VariableLengthFieldShape a sh:NodeShape ;
    sh:targetClass bddo:Field ;
    sh:sparql [ sh:message "A bddo:bytes or bddo:string field must declare a sizing or termination mechanism." ;
        sh:prefixes bddo:_prefixes ;
        sh:select """SELECT $this WHERE {
            $this bddo:dataType ?dt . FILTER(?dt IN (bddo:bytes, bddo:string))
            FILTER NOT EXISTS {
                $this ?p ?v .
                FILTER(?p IN (bddo:size, bddo:sizeFromField, bddo:sizeFromExpression,
                              bddo:sizeToEndOfStream, bddo:terminator))
            }
        }""" ] .

# At most one repetition mechanism per field.
bddo:FieldRepetitionShape a sh:NodeShape ;
    sh:targetClass bddo:Field ;

# At most one offset mechanism per field.

Examples

Conditional Data Type Dispatch (PNG chunk)

A generic chunk is parsed first; the ChunkData field is then re-interpreted using a more specific structure based on ChunkType. This is the type-length-value (TLV) pattern.

@prefix bddo: <https://hexplain.io/ns/bddo#> .
@prefix png:  <https://hexplain.io/formats/png#> .

png:Chunk a bddo:Struct ;
    bddo:endianness bddo:BigEndian ;
    bddo:hasField ( png:ChunkLength png:ChunkType png:ChunkData png:ChunkCRC ) .

png:ChunkLength a bddo:Field ; bddo:dataType bddo:uint32 .
png:ChunkType   a bddo:Field ; bddo:dataType bddo:string ; bddo:size 4 ; bddo:encoding bddo:ascii .

png:ChunkData a bddo:Field ;
    bddo:dataType bddo:bytes ;
    bddo:sizeFromField png:ChunkLength ;
    bddo:hasConditionalDataType (
        [ a bddo:DataTypeRule ; bddo:condition "instance.parent.ChunkType == 'IHDR'" ; bddo:ruleDataType png:IHDR_ChunkData ]
        [ a bddo:DataTypeRule ; bddo:condition "instance.parent.ChunkType == 'PLTE'" ; bddo:ruleDataType png:PLTE_ChunkData ]
    ) .

# CRC-32 over the ChunkType and ChunkData bytes.
png:ChunkCRC a bddo:Field ;
    bddo:dataType bddo:uint32 ;
    bddo:checksum [ a bddo:Checksum ;
        bddo:checksumAlgorithm bddo:crc32 ;
        bddo:coversFromField png:ChunkType ;
        bddo:coversToField   png:ChunkData ] .

Count-based array, enumeration, and offset (sketch)

@prefix bddo: <https://hexplain.io/ns/bddo#> .
@prefix tiff: <https://hexplain.io/formats/tiff#> .

# An IFD entry count followed by that many entries.
tiff:IFD a bddo:Struct ;
    bddo:hasField ( tiff:NumEntries tiff:Entries tiff:NextIFDOffset ) .
tiff:NumEntries a bddo:Field ; bddo:dataType bddo:uint16 .
tiff:Entries a bddo:Field ;
    bddo:dataType tiff:IFDEntry ;
    bddo:repeatCountFromField tiff:NumEntries .

# A colour-type byte surfaced as a symbol.
tiff:ColorType a bddo:Field ;
    bddo:dataType bddo:uint8 ;
    bddo:enumeration [ a bddo:Enumeration ; bddo:hasEnumValue
        [ a bddo:EnumValue ; bddo:enumRawValue 0 ; rdfs:label "Grayscale" ] ,
        [ a bddo:EnumValue ; bddo:enumRawValue 2 ; rdfs:label "RGB" ] ,
        [ a bddo:EnumValue ; bddo:enumRawValue 3 ; rdfs:label "Indexed" ] ] .

# A structure located by an absolute offset read from a header field.
tiff:FirstIFD a bddo:Field ;
    bddo:dataType tiff:IFD ;
    bddo:atOffsetFromField tiff:IFDOffset ;
    bddo:offsetBase bddo:streamStart .
