The Binary Data Description Ontology (BDDO) provides a formal vocabulary to declaratively describe the structure, syntax, and layout of binary data. It is the foundational physical layer of the Hexplain Ontology Family. BDDO allows authors to model binary formats as nested structures and typed fields, with support for dynamic layouts through conditional logic, variable sizing, offset-based addressing, bit-level fields, arrays, stream synchronization, enumerations, and integrity checksums. This specification provides the normative OWL vocabulary for BDDO and a set of SHACL shapes for validating BDDO descriptions.

This document is an unofficial draft produced for the purpose of defining the Hexplain standard. It has no official standing and is not endorsed by any standards body.

Introduction

The primary goal of the Hexplain project is to make opaque binary data machine-understandable. The first step is to provide a standardized, unambiguous way to describe the physical structure of the data. The Binary Data Description Ontology (BDDO) serves this purpose.

BDDO provides a set of RDF classes and properties that can be used to create a graph-based model of a binary format. This model can then be used by a conforming Hexplain processor (see the Processing Model specification) to parse a binary stream into a structured, logical representation, and ultimately into an RDF instance graph.

Modeling Approach: Vocabulary vs. Constraints

BDDO follows a deliberate separation of concerns that is a recommended ontology-engineering practice:

  • The OWL vocabulary declares terms (classes, properties, individuals) with human-readable metadata (rdfs:label, rdfs:comment, rdfs:isDefinedBy), lightweight semantics (rdfs:subClassOf, alignment axioms), and each property's rdfs:range (its value type). It deliberately does not assert rdfs:domain, because a domain axiom would silently type any subject of a property — a term is often reused across several classes.
  • The SHACL shapes carry the remaining constraints — the classes a property may apply to (its "domain"), value cardinalities, and any refinement of the declared ranges (controlled-vocabulary membership, numeric bounds). Validation therefore never mutates the graph, and errors are reported rather than repaired by inference.

Conformance

The key words "MUST", "MUST NOT", "REQUIRED", "SHALL", "SHALL NOT", "SHOULD", "SHOULD NOT", "RECOMMENDED", "MAY", and "OPTIONAL" in this document are to be interpreted as described in [[RFC2119]].

A validator checking a BDDO description graph against § Normative SHACL Shapes MUST either include the BDDO rdfs:subClassOf axioms of § Normative OWL Vocabulary in the graph it validates, or apply RDFS subclass closure to that graph before validating. SHACL selects the targets of sh:targetClass through rdf:type/rdfs:subClassOf*, so a validator that omits those axioms silently under-validates every subclass: a bddo:KeyValueHeader, for example, would not be reached by bddo:StructShape and its bddo:endianness would go unchecked.

Core Concepts

The BDDO model is built upon the following classes.

bddo:Struct
A composite structure or container for other elements. A Struct is an ordered sequence of Fields. Examples: a file header, a network packet, a PNG chunk.
bddo:Field
A single element within a Struct. A Field may represent one value, a bit-level slice, or an array of values, and is associated with a data type.
bddo:DataType
The type of data a Field contains. BDDO defines core primitive data types (e.g. bddo:uint32be). This class can be extended in profiles to create user-defined type aliases (e.g. media:fourCC).
bddo:DataTypeRule
A single rule for conditionally selecting a data type for a field, consisting of a condition and the data type to use when the condition holds.
bddo:EndiannessRule
A single rule for conditionally selecting a byte order for a Struct or Field, consisting of a condition and the endianness to use when the condition holds. Used by formats that declare their own byte order in a magic or version field.
bddo:Enumeration / bddo:EnumValue
A mapping of raw parsed values to named symbols, so that (for example) a colour-type byte of 2 can be surfaced as RGB in the output graph and referenced by name in conditions.
bddo:Checksum
A declarative description of an integrity check: the algorithm and the byte range it covers. A field that stores a checksum value links to it so that a processor can verify data integrity.

Sequencing, Addressing & Alignment

By default, the Fields listed in bddo:hasField are parsed sequentially and contiguously: each field begins where the previous one ended. Many real formats (TIFF/GeoTIFF IFDs, ZIP central directories, ELF section tables, PDF cross-reference tables) instead locate structures by offset. BDDO supports both models.

bddo:atOffset, bddo:atOffsetFromField, bddo:atOffsetFromExpression
Relocate a Field or Struct to a fixed offset, an offset read from another field, or an offset computed by a HEL expression, respectively. A field with an offset does not advance the sequential cursor for its siblings unless the processor is told otherwise.
bddo:offsetBase
The reference point the offset is measured from: bddo:streamStart (default), bddo:streamEnd (for formats parsed from the tail, such as ZIP), bddo:parentStart, or bddo:currentPosition.
bddo:alignment
An xsd:positiveInteger. Before parsing the field, the processor MUST advance the cursor to the next multiple of this value (padding bytes are skipped).

Bit-Level Fields

Formats such as IPv4, TCP, and many compression headers pack several logical values into a single byte. A Field MAY declare bddo:bitLength (an xsd:positiveInteger number of bits). Consecutive bit-length fields are packed into the underlying bytes; the packing order is governed by bddo:bitOrder (bddo:MSBFirst, the default, or bddo:LSBFirst) declared on the enclosing Struct. A run of bit fields SHOULD align to a byte boundary; a processor MUST pad to the next byte before parsing a subsequent non-bit field.

Delimited Text Records

Record- and line-oriented text — key = value headers, CSV, whitespace-separated grids — cannot be addressed by byte offset. bddo:DelimitedRecords is a bddo:Struct whose children are located by delimiter position instead: bddo:recordDelimiter splits the byte run into records, and bddo:fieldDelimiter splits each record into values. Its two specialisations cover the common cases — bddo:KeyValueHeader, where each field is matched by bddo:key rather than position, and bddo:DelimitedTable, where bddo:hasField gives an ordered column list that repeats per row.

A field of a bddo:DelimitedRecords takes its extent from its container's delimiters, so it declares no bddo:size and no bddo:terminator of its own; restating a delimiter as a field's terminator is redundant and breaks when a column is inserted. Such fields are therefore exempt from the sizing requirements that apply to variable-length and ASCII-coded numeric fields elsewhere.

Column-aligned text needs a different separation rule. In an ASCII grid a key and its value, or two adjacent numbers, are parted by a run of spaces whose width exists only to line the columns up — ncols 100. A fixed bddo:fieldDelimiter would read each of those spaces as another separator and yield a row of empty values, so bddo:whitespaceSeparated says instead that a run of one or more whitespace bytes, of any length, separates exactly two values. Leading and trailing whitespace on a record is ignored. The two rules are mutually exclusive.

Omitting bddo:recordDelimiter as well makes the content one flat stream of values rather than rows. That is how an ASCII grid whose rows wrap freely across lines is read: line breaks carry no meaning, and the grid's shape comes from the field's dlv:DataLayout or repeat count.

This primitive is deliberately non-recursive. It describes flat delimited text only; nested grammars such as XML and JSON are outside BDDO's scope by design.

Core Data Types

BDDO provides a normative set of built-in primitive data types. All conforming processors MUST support these types. Each is an instance of bddo:DataType and carries a normative bddo:xsdType that fixes the RDF literal datatype produced when a value of that type is emitted into the output graph.

Integer and floating types come in three forms: an endianness-neutral form (e.g. bddo:uint32) that inherits its byte order from the enclosing Struct or Field via bddo:endianness, and explicit big-endian / little-endian forms (e.g. bddo:uint32be, bddo:uint32le). Single-byte types have no byte order.

Tree Documents

A great many formats wrap a payload that BDDO can already describe in a label it could not read at all: PDS4, DIMAP, SAFE, Sentinel-2, RadarSat-2, TerraSAR-X and CPHD are all an XML manifest over a clean binary array, and Zarr's chunk store was fully covered by chunked layout and encoding pipelines while .zarray — being JSON — kept it out of reach. A bddo:TreeDocument is a Struct whose fields are located by a path into a parsed node tree.

BDDO does not describe the syntax of these documents. It addresses nodes in the tree a conforming parser produces. That distinction is what keeps this from turning into an XML specification: the tree is someone else's output, and BDDO's only job is to say which node supplies which field.

bddo:treeSyntaxbddo:nodePath is…Example
bddo:xmlAn abbreviated XPath: child steps, attribute steps, positional predicates (1-based). No axes, no functions, no comparison predicates./pds:Product/pds:Array_2D_Image/pds:Axis_Array[1]/pds:elements
bddo:jsonA JSON Pointer [[RFC6901]]: member names and array indices (0-based)./shape/0, /compressor/id

Both are adopted rather than invented. JSON Pointer already specifies how to escape / and ~ inside a member name, and is already implemented everywhere; the XPath subset is deliberately small because a description states where a value is, and a path that can compute is a query engine's problem rather than a description's. The two index conventions differ — XPath predicates are 1-based, JSON Pointer indices 0-based — and are kept as their standards define them, because normalising to one would surprise everyone who knows either.

XML paths need their prefixes bound with bddo:hasNamespaceBinding, and this is not optional in practice: PDS4, DIMAP and SAFE are all namespaced, and an unprefixed path against a namespaced document matches nothing rather than failing. The prefix is matched to the document's own namespace declarations rather than to whatever prefix the document happens to spell them with. An empty prefix binds the default namespace, which an abbreviated XPath cannot otherwise reach — an unprefixed step means "no namespace", not "the default one". A binding on a JSON document is rejected, since JSON Pointer has no prefixes and such a binding signals a misunderstanding of what the paths below will match.

A path selecting no node leaves the field absent; one selecting several is an error unless the field repeats, in which case its value is the selected nodes in document order. Every field of a tree document is located by exactly one bddo:nodePath and by nothing else — a byte offset or a record key here is a leftover from another container form and would address nothing.

Nested Records

A bddo:DelimitedRecords is flat unless it declares bddo:hasGrouping. That was enough for ESRI .hdr, ENVI and their kin, but stopped at the label formats that are otherwise the same shape — PVL/ODL, the ERMapper header, INI-style labels — for want of a closing token. Those labels always sat over a payload that was already a clean array; only the label could not be decomposed.

A bddo:RecordGrouping names one of three styles and the two tokens that delimit a group. Three styles rather than one general grammar, because each is fully described by two tokens plus where the group's NAME comes from — and a general nested-grammar surface would be a parser generator, which this is not.

bddo:groupingStyleOpens / closesGroup nameExample
bddo:keyedGroupA record whose key is the tokenThe opening record's valueOBJECT = IMAGE … END_OBJECT (PVL/ODL)
bddo:valuedGroupA record whose value is the tokenThe opening record's keyCoordinateSpace Begin … CoordinateSpace End (ERMapper)
bddo:sectionHeadedA record bracketed by the two tokens; the next one implicitly closes itThe text between the tokens[OVERVIEW] (INI)

Both tokens are always required. A grouping that says where a group starts but not where it ends cannot be read at all — every record after the first group would be inside it. bddo:sectionHeaded nests one deep: a section is ended by the next one, so sections cannot contain sections. That is what the style permits, not a limitation of this model.

Inside a grouped container a field is located by bddo:keyPath — the group names and finally the key, joined by bddo:pathSeparator (default /, declared on the container because a format whose group names contain a slash must choose something else). bddo:keyPath and bddo:key are mutually exclusive: a field cannot be found two ways, and a description asserting both would leave a reader to guess which wins. A path in a container that does not nest is rejected by bddo:KeyPathShape, because it would otherwise silently match nothing rather than fail.

Variable-Length Integers

An integer whose WIDTH is discovered from its own bytes rather than declared. Framing such a field was always possible byte by byte; reconstructing the VALUE was not, which is what kept protobuf-framed and SQLite-backed formats out of reach.

IRIEncodingxsdType
bddo:varuintUnsigned base-128 (LEB128): seven value bits per byte, little-endian, high bit set on every byte but the last. Protobuf's plain varint.xsd:nonNegativeInteger
bddo:varintLEB128 carrying a zigzag-encoded value, so small negatives stay short. Protobuf's sint32/sint64. Distinct from reading a varuint and reinterpreting the bits, which sign-extends instead.xsd:integer
bddo:sqliteVarintOne to nine BIG-endian bytes, high bit as continuation for the first eight, the ninth contributing all eight bits. A different scheme from LEB128, not a dialect of it; used by GeoPackage, MBTiles and Rasterlite.xsd:integer

A field of one of these types MUST NOT declare a width or terminator — bddo:size, bddo:sizeFromField, bddo:sizeFromExpression, bddo:sizeToEndOfStream, bddo:terminator or bddo:bitLength — because its length comes from the data and a declared one could contradict it. bddo:VarintWidthShape enforces this.

ASCII-Coded Numeric Types

Many record-oriented formats write numbers as text in fixed-width fields — NITF BCS-N, FITS card values, USGS DEM Fortran fields. bddo:asciiInteger and bddo:asciiDecimal read such a field as a number rather than a string, so its value may drive bddo:sizeFromExpression, bddo:atOffsetFromExpression and bddo:repeatCountFromExpression. The field's width comes from bddo:size (or a terminator), except for a field of a bddo:DelimitedRecords, whose extent comes from its container's delimiters; bddo:numericBase selects the radix.

Properties

Structural Properties

bddo:hasField
Links a bddo:Struct to its ordered components. The object MUST be an rdf:List of bddo:Field to preserve order.
bddo:endianness
The byte order for a bddo:Struct, bddo:Field, or bddo:DataType. Value MUST be bddo:BigEndian or bddo:LittleEndian. The nearest declaration wins (DataType > Field > Struct > inherited from the parent).
bddo:hasConditionalEndianness
Ordered list of bddo:EndiannessRule; the first rule whose bddo:condition holds sets the byte order for this term and its descendants. For formats that declare their own byte order. Mutually exclusive with bddo:endianness.
bddo:bitOrder
The bit-packing order for bit-level fields in a Struct. Value MUST be bddo:MSBFirst or bddo:LSBFirst.
bddo:syncOnMarker
A byte sequence a processor MUST scan for before parsing this bddo:Struct. Value MUST be an xsd:hexBinary literal.
bddo:size / bddo:sizeFromField / bddo:sizeFromExpression (on a Struct)
Bounds the Struct's total byte extent, establishing a bounded region for its children: descendant reads MUST NOT cross it, bddo:sizeToEndOfStream resolves to the region end, and trailing/padding bytes are skipped. Essential for length-delimited containers (MP4/ISOBMFF boxes, EBML, chunk payloads). At most one mechanism.

Field Properties

bddo:dataType
The Field's default data type. Value MUST be a bddo:DataType or a bddo:Struct. A Field MUST have either a bddo:dataType or a bddo:hasConditionalDataType (or both).
bddo:hasConditionalDataType
An rdf:List of bddo:DataTypeRule allowing the processor to select a more specific data type at runtime.
bddo:size / bddo:sizeFromField / bddo:sizeFromExpression / bddo:sizeToEndOfStream
The size of the field in bytes: fixed, read from another field, computed by a HEL expression, or "consume the remainder of the stream" (xsd:boolean). A Field MUST use at most one sizing mechanism, and variable-length types (bddo:bytes, bddo:string) MUST use exactly one sizing or termination mechanism — except for a field of a bddo:DelimitedRecords, which is exempt because its extent is set by its container's delimiters.
bddo:terminator
A byte sequence terminating a variable-length field. Value MUST be an xsd:hexBinary literal.
bddo:trimNull
For a fixed-size (padded) bddo:string, the emitted value ends at the first 0x00 within the field's width (NUL-padded names, e.g. TAR/ZIP).
bddo:encoding
The character encoding of a bddo:string field. Value MUST be one of the encoding individuals (bddo:utf8, bddo:ascii, bddo:utf16le, bddo:utf16be, bddo:latin1). Defaults to bddo:utf8.
bddo:numericBase
Radix (8, 10 or 16) for reading a bddo:asciiInteger field. Default 10.
bddo:bitLength
The width, in bits, of a sub-byte field (see Bit-Level Fields).
bddo:repeatCount / bddo:repeatCountFromField / bddo:repeatCountFromExpression / bddo:repeatUntil
Turn the field into an array parsed a fixed number of times, a number read from another field, a number computed by a HEL expression, or repeatedly until a HEL boolean expression evaluates to true. A Field MUST use at most one repetition mechanism.
bddo:atOffset / bddo:atOffsetFromField / bddo:atOffsetFromExpression / bddo:offsetBase / bddo:alignment
Addressing and alignment (see Sequencing, Addressing & Alignment).
bddo:hasFixedValue
A constant expected value, used to validate markers and magic numbers. The literal is compared against the parsed value after decoding according to the field's data type.
bddo:isPresentIf
A HEL boolean expression; the field is present only if it evaluates to true.
bddo:valueFromExpression
Declares a derived, zero-byte field: its value is computed by a HEL expression rather than read from the stream. The field consumes no bytes; its computed value is placed in the parse context under the field's name so later sizing, offset, presence, mapping and validation expressions may reference it. Such a field declares no bddo:dataType and no sizing, offset or bit-length; the result's type is that of the HEL expression.
bddo:validIf
A HEL boolean expression that MUST hold once this field is parsed; if it evaluates to false the parse fails with a validation error. Use for post-parse constraints such as a bound on a count. Richer, graph-level constraints belong in SHACL at the semantic layer.
bddo:enumeration
Links a Field to a bddo:Enumeration that maps its raw value to a named symbol. If the Enumeration sets bddo:enumIsFlags true, the raw value is a bitmask and every matching flag symbol is emitted.
bddo:checksum
Links a Field (the one storing the checksum value) to a bddo:Checksum describing the algorithm and covered range.
bddo:recordDelimiter / bddo:fieldDelimiter / bddo:keyValueSeparator
On a bddo:DelimitedRecords (see Delimited Text Records): the byte sequence splitting the byte run into records, splitting a record into values, and (in a bddo:KeyValueHeader) splitting a key from its value. Each value MUST be an xsd:hexBinary literal.
bddo:quoteChar / bddo:escapeChar
On a bddo:DelimitedRecords: the byte that quotes a value so it may contain a delimiter, and the byte that escapes the following byte. Values MUST be xsd:hexBinary literals.
bddo:commentPrefix / bddo:skipRecords / bddo:trimWhitespace
On a bddo:DelimitedRecords: a leading string marking a record as a comment to ignore, a count of leading records to discard before parsing, and whether to strip leading/trailing whitespace from every key and value.
bddo:key / bddo:keyIsCaseInsensitive
On a Field of a bddo:KeyValueHeader: the key naming the field, which replaces positional location, and whether key matching ignores ASCII case.

Data Type, Rule, Enumeration & Checksum Properties

bddo:baseType
The fundamental kind of data. Value MUST be one of bddo:baseInteger, bddo:baseFloat, bddo:baseString, or bddo:baseBytes.
bddo:bitWidth, bddo:isSigned, bddo:xsdType
Describe a bddo:DataType: its width in bits, its signedness, and the RDF literal datatype produced on output.
bddo:condition, bddo:ruleDataType
A bddo:DataTypeRule's HEL condition and the data type (a bddo:DataType or bddo:Struct) to apply when it holds.
bddo:condition, bddo:ruleEndianness
A bddo:EndiannessRule's HEL condition and the byte order (bddo:BigEndian or bddo:LittleEndian) to apply when it holds.
bddo:hasEnumValue, bddo:enumRawValue, bddo:enumSymbol
An bddo:Enumeration's members; each bddo:EnumValue pairs a raw literal (bddo:enumRawValue) with an optional symbolic IRI (bddo:enumSymbol) and/or rdfs:label.
bddo:checksumAlgorithm, bddo:coversFromField, bddo:coversToField, bddo:coversFromExpression, bddo:coversToExpression
A bddo:Checksum's algorithm and the byte range it protects. The algorithm is one of bddo:crc16, bddo:crc32, bddo:adler32, bddo:md5, bddo:sha1 or bddo:sha256 — a closed set, since a checksum names an algorithm a reader must already implement to verify anything. Each end of the range is stated independently, as a field reference or a HEL expression, so a range may start at a named field and end at a computed offset. The field form is inclusive of coversToField's last byte; the expression form is the half-open [start,end). (bddo:coversExpression, a single expression for the whole range, is deprecated in favour of the pair.)

# A varint's width is neither intrinsic (as with uint32) nor declared (as with
# asciiInteger's bddo:size): it is DISCOVERED while reading, from the values of the bytes
# themselves. These are therefore the first data types with no width at all, and a field
# using one must not declare a size -- there is nothing for a size to mean, and stating one
# would contradict the bytes. sizeof() on such a field still yields the length actually
# consumed, once it is known.
#
# They are what modern container formats are built from: protobuf key/length prefixes (MVT,
# OSM PBF), the PMTiles directory, Parquet's Thrift-compact footer, FlatGeobuf and
# OpenFileGDB geometry. Framing those was already possible byte by byte; reconstructing the
# VALUE was not, which is what kept them out of reach.
:varuint a :DataType ; rdfs:label "varuint" ; :baseType :baseInteger ; :isSigned false ; :xsdType xsd:nonNegativeInteger ;
    rdfs:comment "Unsigned base-128 varint (LEB128): 7 value bits per byte, little-endian, the high bit set on every byte but the last. Protobuf's plain varint." .
:varint a :DataType ; rdfs:label "varint" ; :baseType :baseInteger ; :isSigned true ; :xsdType xsd:integer ;
    rdfs:comment "Signed base-128 varint: LEB128 carrying a zigzag-encoded value, so small negatives stay short -- n maps to (n << 1) XOR (n >> 63). Protobuf's sint32/sint64. Distinct from reading an unsigned varint and reinterpreting the bits, which is protobuf's int32 and sign-extends instead." .
:sqliteVarint a :DataType ; rdfs:label "sqliteVarint" ; :baseType :baseInteger ; :isSigned true ; :xsdType xsd:integer ;
    rdfs:comment "SQLite's variable-length integer: one to nine BIG-endian bytes, high bit as continuation for the first eight, the ninth contributing all eight bits. A different scheme from LEB128, not a dialect of it; used by SQLite-backed formats (GeoPackage, MBTiles, Rasterlite)." .

    # Both tokens, always. A grouping that says where a group starts and not where it ends
    # cannot be read: every record after the first group would be inside it.
    sh:property [ sh:path bddo:groupOpenToken ; sh:datatype xsd:string ; sh:minCount 1 ; sh:maxCount 1 ] ;
    sh:property [ sh:path bddo:groupCloseToken ; sh:datatype xsd:string ; sh:minCount 1 ; sh:maxCount 1 ] .

bddo:GroupedRecordsShape a sh:NodeShape ;
    sh:targetClass bddo:DelimitedRecords ;
    sh:property [ sh:path bddo:hasGrouping ; sh:class bddo:RecordGrouping ; sh:maxCount 1 ] ;
    sh:property [ sh:path bddo:pathSeparator ; sh:datatype xsd:string ; sh:maxCount 1 ] .

# A path has nothing to traverse unless its container nests.
bddo:KeyPathShape a sh:NodeShape ;
    sh:targetClass bddo:Field ;
    sh:property [ sh:path bddo:keyPath ; sh:datatype xsd:string ; sh:maxCount 1 ] ;
    sh:sparql [ sh:message "bddo:keyPath locates a field inside nested groups, so its container must declare bddo:hasGrouping; without one the container is flat and the path addresses nothing." ;
        sh:prefixes bddo:_prefixes ;
        sh:select """SELECT $this WHERE {
            $this bddo:keyPath ?path .
            FILTER NOT EXISTS {
                ?container bddo:hasField/rdf:rest*/rdf:first $this .
                ?container bddo:hasGrouping ?g .
            }
        }""" ] .

# bddo:key is meaningful only inside a KeyValueHeader; a table's columns are positional.
bddo:DelimitedTableShape a sh:NodeShape ;
    sh:targetClass bddo:DelimitedTable ;
    sh:or ( [ sh:property [ sh:path bddo:fieldDelimiter ; sh:minCount 1 ] ]
            [ sh:property [ sh:path bddo:whitespaceSeparated ; sh:hasValue true ] ] ) ;
    sh:property [ sh:path bddo:keyValueSeparator ; sh:maxCount 0 ;
        sh:message "bddo:keyValueSeparator applies to a KeyValueHeader, not a DelimitedTable." ] ;
    sh:property [ sh:path ( bddo:hasField [ sh:zeroOrMorePath rdf:rest ] rdf:first ) ;
        sh:node [ sh:property [ sh:path bddo:key ; sh:maxCount 0 ;
            sh:message "bddo:key applies to a field of a KeyValueHeader; a DelimitedTable's columns are located by position." ] ] ] .

Conditional Data Type Dispatch (PNG chunk)

A generic chunk is parsed first; the ChunkData field is then re-interpreted using a more specific structure based on ChunkType. This is the type-length-value (TLV) pattern.

@prefix bddo: <https://hexplain.io/ns/bddo#> .
@prefix png:  <https://hexplain.io/formats/png#> .

png:Chunk a bddo:Struct ;
    bddo:endianness bddo:BigEndian ;
    bddo:hasField ( png:ChunkLength png:ChunkType png:ChunkData png:ChunkCRC ) .

png:ChunkLength a bddo:Field ; bddo:dataType bddo:uint32 .
png:ChunkType   a bddo:Field ; bddo:dataType bddo:string ; bddo:size 4 ; bddo:encoding bddo:ascii .

png:ChunkData a bddo:Field ;
    bddo:dataType bddo:bytes ;
    bddo:sizeFromField png:ChunkLength ;
    bddo:hasConditionalDataType (
        [ a bddo:DataTypeRule ; bddo:condition "instance.parent.ChunkType == 'IHDR'" ; bddo:ruleDataType png:IHDR_ChunkData ]
        [ a bddo:DataTypeRule ; bddo:condition "instance.parent.ChunkType == 'PLTE'" ; bddo:ruleDataType png:PLTE_ChunkData ]
    ) .

# CRC-32 over the ChunkType and ChunkData bytes.
png:ChunkCRC a bddo:Field ;
    bddo:dataType bddo:uint32 ;
    bddo:checksum [ a bddo:Checksum ;
        bddo:checksumAlgorithm bddo:crc32 ;
        bddo:coversFromField png:ChunkType ;
        bddo:coversToField   png:ChunkData ] .
