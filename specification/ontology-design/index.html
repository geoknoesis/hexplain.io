Hexplain specification

Ontology modeling policy

Modeling policy · aspects last modified 2026-09-27

Hexplain separates physical byte description (BDDO), array addressing (DLV), semantic lifting (Core), reusable aspects, controlled concept registers and format profiles. This separation is a compatibility boundary.

Rules for ontology changes

  1. Model entities and concepts separately. OWL classes and properties describe the domain; SKOS concepts provide controlled values. SKOS matching predicates are reserved for concepts. Related external ontology terms use rdfs:seeAlso until a reviewed logical alignment establishes the required entailment. Similar names do not justify owl:equivalentClass or owl:equivalentProperty.
  2. Separate inference from validation. RDFS ranges and OWL axioms describe meaning under an open-world model. SHACL supplies explicit validation constraints. Domain declarations can infer unexpected types on every use of a property, so reusable facets use scoped shapes instead. Shape targets include linked objects where omitting rdf:type would otherwise bypass validation.
  3. State completeness boundaries. A partial graph may omit bands; an explicitly declared array dimension list is complete. Required values are scoped to an asserted model rather than imposed on every asset. No closed-world completeness is inferred from RDF absence.
  4. Specify mathematics and units. State index bases, coordinate conventions, numeric domains, rounding, missing-value behavior and failure conditions. Keep byte offsets, calibration offsets, georeferencing origins and coordinate epochs distinct. Ordered values use validated finite lists; order must not be guessed from triple order.
  5. Keep extensions reusable. Core and aspects do not name individual binary formats. Open concept schemes and profiles carry format-specific choices. Reuse units and CRS identifiers rather than inventing a parallel authority registry.
  6. Version validation changes. Every changed module declares a new owl:versionIRI and owl:versionInfo, an owl:priorVersion naming a version that a pinned snapshot has frozen, and dcterms:modified; the raster, spatial-reference and geometry aspects are working drafts (raster 1.3 working draft, spatialref 1.4 working draft, geometry 1.4 working draft). Stable namespace IRIs remain unchanged. A stricter shape is a validation compatibility change and must be described in migration notes. No claim is made that draft version IRIs are already deployed.
  7. Require evidence. Every capability claim identifies its level: vocabulary expression, RDF validation, compilation, binary parsing, payload decoding, semantic output or independent conformance. Positive fixtures alone are insufficient; test malformed lists, numeric boundaries, missing declarations and nonfinite values.

Controlled values: one idiom per category

A value drawn from a fixed or managed set is modeled in exactly one of three ways, chosen by who may extend the set. tools/test_controlled_values.py checks every value against them; values older than this rule that fit none are listed there, with the reason, and the list may only shrink.

  1. Closed enumeration (the vocabulary owns every value): an owl:Class, individuals typed with it, and a shape that lists every individual in sh:in. Examples: bddo:Endianness, conf:FindingKind, conf:EvaluationOutcome, hexplain:RegisterStatus. Adding a value is a vocabulary change.
  2. Open individual set (other modules and profiles add values): an owl:Class, constrained with sh:class, whose individuals anyone may add. Examples: bddo:DataType primitives, dlv:Axis, the hxf function catalogue.
  3. Swappable values (a jurisdiction or community owns the list): skos:Concept in a register module, reached through a property whose range is skos:Concept and bound per profile with hexplain:RegisterBinding. Examples: codecs, part roles, security markings. A register concept is never deleted: it is deprecated with a hexplain:status, a history note and dcterms:isReplacedBy. Links from a concept to an ontology individual use hexplain:correspondsTo, never a SKOS mapping property.

A format's wire codes (PNG's colour type, a NITF digraph) are none of these: they belong in that format's profile, which maps them to one of the three.

Documentation annotations

  1. One definition, stated once. A term's rdfs:comment is its author's definition. A skos:definition is added only where it says what no comment says: an editorial definition for a term whose source gives none (tools/_term_editorial.py), or a generated one for a shape or primitive datatype. The two never repeat each other; the term reference shows the skos:definition when there is one and the comment otherwise.
  2. Scope notes are about the term. A skos:scopeNote says how to use that particular term. The module's note sits on its ontology; a shape's activation and a property's shape usage are rows of the term reference, not notes.
  3. Generated prose never templates SPARQL. A generated definition never copies a message that names result variables ({?x}); a shape with nothing else to say gets an editorial rdfs:comment.
  4. English, tagged. Every rdfs:label, rdfs:comment and SKOS documentation literal of a family term is tagged @en.
  5. Readable generated Turtle. tools/_build_term_reference.py --enrich appends its annotations after the marker # BEGIN GENERATED TERM DOCUMENTATION as prefixed Turtle, one statement per term; it adds annotations only. tools/test_documentation_annotations.py and tools/test_language_tags.py check these rules.

HEL expressions and versions

A HEL expression is RDF text: bddo:sizeFromExpression, bddo:condition, bddo:validIf, hexplain:condition, hexplain:valueExpression, dlv:dimensionStrideFromExpression, conf:assertion, the members of bddo:hasArgument and the other expression-valued properties. Their shapes accept a literal typed xsd:string, as every existing description writes it, or bddo:HelExpression, a datatype whose lexical space is HEL expression text and whose values are strings, so both forms satisfy the xsd:string range. Authoring tools SHOULD emit bddo:HelExpression, which lets a reader tell an expression from ordinary text. A description MAY state the HEL version its expressions are written against with bddo:helVersion on its ontology ("1.0"); absent, it is the version of the specification edition the description conforms to. Both terms are in bddo, not core, because bddo is the lowest layer that holds expressions and must load without core.

Deprecation, units and external alignments

  1. Deprecation. A deprecated term names its replacement with dcterms:isReplacedBy or, where no single term replaces it, says why in a skos:historyNote (tools/test_deprecations.py).
  2. Units. A property whose values have a fixed unit says so in its definition and links the QUDT unit and quantity kind with rdfs:seeAlso. qudt:hasUnit and qudt:hasQuantityKind describe quantities, not properties, and are not asserted on a property.
  3. Alignment. rdfs:subPropertyOf or rdfs:subClassOf to an external term is asserted only when every use of the family term entails the external statement, domain and range included (afs:modificationTime is a dcterms:modified; abnd:hasPart a dcterms:hasPart). Otherwise the link is rdfs:seeAlso; SKOS mapping properties relate concepts only (rule 1 above).
  4. Licence. Every module declares dcterms:license CC BY 4.0 and its dcterms:creator (tools/test_ontology_licenses.py; see LICENSING.md).

Naming

Classes and datatypes are UpperCamelCase, properties lowerCamelCase. Individuals were named in both styles before this rule (bddo:BigEndian, conf:Violation, bddo:baseInteger, dlv:axisX, hexplain:statusValid), and they keep their names: an individual's IRI is written into every description that uses it, so renaming one is a breaking change. A NEW individual is UpperCamelCase, like the values of a closed enumeration (abnd:Containment, conf:NotReached), with two exceptions: a value added to an existing set follows the case of that set's other values (a new axis is named like dlv:axisX, a new lifecycle status like hexplain:statusValid), and a value with an established spelling of its own keeps it (a primitive datatype bddo:uint16le, a character encoding bddo:utf8, a function as SPARQL calls it, hxf:bytes). Every individual of a family class is declared owl:NamedIndividual (tools/test_named_individuals.py); register concepts are skos:Concept instead.

Namespace prefixes

Prefixes and namespace IRIs were chosen at different times and do not always match: adv names the audio namespace, the image vocabulary sits in directory idv but declares img, gv is the geo namespace, hexplain the core and hxf the function library, axv the archive, dfv the document and font and npv the network vocabulary, and menc and usnato are register prefixes beside the r… ones. None of them is renamed; a published prefix and namespace IRI are part of every description that uses them. This table is the authority, kept as the namespaces list of specification/family.json; tools/test_namespace_prefixes.py checks that every module declares exactly its row (vann:preferredNamespacePrefix, vann:preferredNamespaceUri). A shapes document (conf/shapes.ttl, req/shapes.ttl) declares no prefix of its own: its terms are in its vocabulary's namespace.

Where shapes live

A module's SHACL shapes are in the module's own Turtle, beside the terms they validate, so loading a vocabulary loads its validation rules. Two modules are split: conf and req publish their shapes as separate ontologies, conf/shapes.ttl and req/shapes.ttl. The conformance vocabulary is read by report consumers that never validate, and its shapes need core (byte offsets of findings) and, through it, bddo (the admissible conf:scope values), which the vocabulary itself does not import; embedding them would make every report reader load the physical layer. req follows the same layout so that the requirement/conformance pair is packaged alike. A new module embeds its shapes unless its shapes need imports its vocabulary does not.

Validation messages and severity

Every property shape whose results a validator reports carries an sh:message saying what the constraint wants, in terms of the property (tools/test_shape_messages.py). A property shape nested in sh:not, sh:or, sh:and, sh:xone or sh:node is exempt: SHACL reports the enclosing constraint, with the enclosing message. A shape enforcing a MUST reports at the default sh:Violation; one enforcing a SHOULD reports at sh:Warning (the use of a deprecated register value, a sensitivity level recorded without its verbatim text); advice at MAY level is sh:Info or no shape at all. Any result, whatever its severity, makes sh:conforms false, so adding a Warning or Info shape is itself a validation compatibility change.

Acceptance bar for 10/10

A maximum score requires reviewed competency questions across representative format families, independent semantic/interoperability review, a versioned compatibility policy, actual binary corpora with expected results, and at least one independent implementation or differential oracle. A count of ontology terms or driver names cannot substitute for these. This revision improves the model but does not meet that entire bar.

What changed

Misleading SKOS mappings on ontology entities were replaced with non-entailing references. The incorrect CRS-WKT/geometry-WKT association was removed. Raster grids, bands, masks, calibration and arbitrary-rank arrays gained explicit models. Spatial-reference validation now requires finite affines (skews optional and zero when absent), distinguishes GCP CRS, and describes rational-polynomial metadata with an explicit basis contract. Geometry flags preserve Z/M meaning.

Standards basis

  • W3C SKOS mapping vocabulary
  • W3C SHACL validation model
  • W3C OWL 2 semantics
  • W3C linked-data publication practices
