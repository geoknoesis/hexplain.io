The Hexplain Expression Language (HEL) is a small, declarative language for the conditions and calculations inside Hexplain format descriptions. It powers dynamic sizing, conditional presence, repetition counts, offsets, derived values, conformance assertions, and conditional data-type and semantic dispatch. HEL operates on a hierarchical logical data model built from the binary data being parsed; a name in an expression is the local name of a field of the struct the expression is evaluated in.

This document is a prerelease working draft of HEL 1.0, produced for the purpose of defining the Hexplain standard. It has no official standing and is not endorsed by any standards body. The language, its function groups and its conformance vectors may still change incompatibly before HEL 1.0 is released. The executable statement of this draft is the vector set validation/test/hel-vectors.tsv; where a vector and the prose disagree, that is a defect in this document to be reported.

Introduction

A key requirement of the Hexplain framework is handling dynamic structures where the presence, size, count, offset, or type of a field depends on previously parsed data. HEL provides a concise, unambiguous syntax for these expressions. Design goals: simplicity, clarity, determinism (the same expression over the same data gives the same result or the same error in every conforming implementation), and grounding in stable standards (XPath-style operator semantics, IEEE 754 binary64 floating point).

A HEL expression is the lexical form of an xsd:string literal. The complete list of properties whose values are HEL expressions, and what each expression's names are bound to, is the name-binding table.

Language Version and Extension Groups

This document defines HEL 1.0. A later 1.x version MAY add functions and extension groups, but MUST NOT change the value or the error an expression that is valid under HEL 1.0 produces.

Version marker. An expression carries no version marker; a description does. The declared HEL version of a description is the greatest value of hexplain:helVersion stated on an owl:Ontology of its graph, imports included: a string major.minor, two decimal numbers without leading zeros ("1.0", "1.2"). A description that states none declares HEL 1.0, which is what every description written before the marker existed was written against. Every evaluator implements some latest HEL version (this document defines 1.0) and states it with its claims. A processor MUST read the declared HEL version when the description is loaded, and MUST raise a Description error for a hexplain:helVersion that is not of that form. A declared major version other than 1 MUST be refused with an Unsupported feature error when the description is loaded: HEL 1 rules cannot be assumed to read it. A call to a function name that is neither a core function nor in an extension group of the version the evaluator implements MUST be rejected when the description is loaded, as an Unsupported feature error when the declared version is a later 1.x version than the evaluator implements (the name may be one that version defines), and as a Type / HEL error otherwise (the name is simply not HEL).

The function library is divided into a core set, which every conforming evaluator MUST implement, and named extension groups, which an evaluator MAY implement. An extension group is implemented all or nothing: an evaluator either implements every function of the group as specified here, or none of them. An extension group is identified by its group name (text, temporal, geometry, register, quantifiers) and, wherever an IRI is needed (a processor's statement of the groups it supports, a report of an unsupported feature), by the IRI of its section in this document, https://hexplain.io/specification/hel/#ext-name (for example https://hexplain.io/specification/hel/#ext-text). Every function name belongs to exactly one group, so the groups a description needs are determined statically by the function names its expressions call.

Conformance

The key words "MUST", "MUST NOT", "REQUIRED", "SHALL", "SHALL NOT", "SHOULD", "SHOULD NOT", "RECOMMENDED", "MAY", and "OPTIONAL" in this document are to be interpreted as described in BCP 14 [[RFC2119]] [[RFC8174]] when, and only when, they appear in all capitals, as shown here.

The Logical Data Model

A HEL expression is evaluated against a temporary, in-memory parsing context — a hierarchical tree that the processor builds as it parses (see the Processing Model). Each parsed Struct instance is a struct node whose named children are its fields; each scalar field yields a value node; a repeated field yields an ordered array node.

Reserved Roots

An expression is evaluated in a current struct node, determined by the property that carries the expression (see Name Binding). The reserved roots are resolved relative to it:

RootDenotes
instanceThe current struct node. For an expression attached to a Field (or to a rule governing a Field), the struct instance that contains that field; for an expression attached to a Struct, that struct instance itself. instance.x reads field x of it, and a bare name x is shorthand for instance.x.
parentThe parent struct node of instance: the struct instance that holds instance as a field value or as an element of an array field. parent and instance.parent are the same node. assetThe enclosing abnd:Asset. A processor MUST raise a Description error, when the description is loaded, for param.n in an expression whose instance struct declares no parameter n, and for param without a key: whether a struct has a parameter is known from the description alone, so this is never deferred to the data. Inside the predicate of all/any over struct elements instance is the element, so a processor MUST make that check against the element’s struct, not the struct holding the expression, wherever the description determines the element’s struct (the collection is a path of fields whose declared types are structs, none chosen at parse time); where it does not, a param.n the element’s struct lacks is an undefined name when it is evaluated.

Any other key after stream is an undefined-name error.

Dispatch conditions. A bddo:dispatchOnExpression and the bddo:condition of a bddo:DataTypeRule choose the type of a field that has not been read yet, so they are evaluated against the containing struct. In these two contexts, and only in them, parent (and so instance.parent) is an alias for instance: ChunkType, instance.ChunkType and parent.ChunkType all read the containing struct's ChunkType. The alias is deprecated in HEL 1.0: it is kept only so that descriptions written against the earlier field-relative reading of instance stay valid. New descriptions MUST NOT use it; a processor SHOULD warn when it loads a description that does; an HDL compiler never emits it. A dispatch condition cannot reach the containing struct's parent other than through root.

Repeat-until over structs. The two bddo:repeatUntil rows differ on purpose. Over struct elements the condition is about the element just read (until type == 'IEND' tests that chunk's type), so instance is that element and parent is the struct holding the sequence; over scalar elements there is no element struct, so instance stays the containing struct and self is the value. parent.x is therefore a field of the containing struct in the first case and of its parent in the second.

A processor that evaluates HEL outside parsing — for example the SPARQL function hxf:hel — binds instance to the node's struct, parent to its container and root to the root of the file, as the table does for a field-level expression.

Names and Key Resolution

An identifier in an accessor — a bare name, or a key after a dot — is the local name of a field of the struct node it is applied to. In an RDF description a field is a bddo:Field resource, and its HEL name is the local name of that resource's IRI (the part after the final # or /), which is also the name the HDL gives it. Identifiers are not IRIs and are never expanded through @prefix declarations or a JSON-LD context: ChunkType means "the field named ChunkType in this struct", whatever namespace its IRI is in. Within one struct, field local names MUST be unique. A processor MUST reject a description in which two fields of one struct share a local name, with a Description error when the description is loaded: an expression could not tell which of them a name reads.

A bare name x is exactly instance.x. A key MUST name a field declared by the bddo:Struct of the node it is applied to, or be the keyword parent; a bare name, or a key applied directly to instance, MAY also name a bddo:LocalBinding of that struct, and a key after param names a parameter. This is checked at every step of a path, not only the first, and inside the predicate of all/any a bare name is checked against the element's struct. There is no .size or other pseudo-accessor: after a dot, size is an ordinary key, so Entries.size is an error unless the struct declares a field size; the number of elements is len(Entries) or count(Entries). Root keys. A field declared with bddo:rootKeyFromField binds, in the root context, keys that only the data names; root.k for such a key reads Null, not an undefined-name error, when no record bound k — the one case where a key the root struct does not declare is not an error. A name that is also a reserved word (instance parent root self stream asset param and or not true false) cannot be written as a bare name or a key, so a field, parameter or local binding that expressions need to reference MUST NOT have such a local name.

Local bindings. A bddo:LocalBinding of a struct is visible only through instance of that struct's own instances: by bare name or instance.name, in expressions evaluated after its position in the member list. It is not a node of the tree, so parent.name, root.name, self.name (even where self is the same node as instance), a key after a subscript and a key applied to any other struct node do not reach it: for those it is an undefined name. Read before its position it is a forward reference, like a later field.

An array node (a repeated field) MAY be subscripted with [ Expression ]. The index expression MUST evaluate to a non-negative Integer strictly less than the array's length (elements are 0-based); otherwise a range error is raised. Subscripts and key steps compose freely (e.g. root.Directory[i].Entries[0].Tag). Applying a key to a value that is not a struct node (an Integer, Float, String, Bytes or Boolean, or an array node), or a subscript to a value that is not an array node, is an error. A key applied to Null (an absent optional field) yields Null.

Undefined Names and Forward References

Three cases are distinguished, and a conforming evaluator MUST keep them apart:

  • Undefined name. A key that names no field declared by the addressed struct (a typo, or a field of some other struct), or self where the property defines no value under test, MUST raise an undefined-name error. It MUST NOT evaluate to Null: a misspelt name that read as Null would silently turn a presence condition false or a comparison false.
  • Forward reference. A key that names a declared field which has not yet been reached at the moment of evaluation (it comes later in field order, or belongs to a struct instance still being parsed further on) MUST raise a forward-reference error.
  • Absent optional field. A declared field that has been reached but is not present in this instance (its bddo:isPresentIf was false) reads as Null. This is the only way a field reference yields Null.

Both errors are type/HEL errors in the sense of the Processing Model.

Syntax and Grammar

Formal Grammar (ABNF)

The following grammar [[RFC5234]] defines HEL. Operators are listed lowest-precedence first. WS MAY appear between any two tokens, and is required only where two adjacent tokens would otherwise read as one (for example between not and a name); the productions show it where it is commonly written.

Expression   = Conditional
Conditional  = OrExpr [ WS "?" WS Expression WS ":" WS Conditional ]
OrExpr       = AndExpr *( WS "or" WS AndExpr )
AndExpr      = NotExpr *( WS "and" WS NotExpr )
NotExpr      = "not" WS NotExpr / Comparison
Comparison   = BitOrExpr [ WS CompOp WS BitOrExpr ]
BitOrExpr    = BitXorExpr *( WS "|" WS BitXorExpr )
BitXorExpr   = BitAndExpr *( WS "^" WS BitAndExpr )
BitAndExpr   = ShiftExpr  *( WS "&" WS ShiftExpr )
ShiftExpr    = AddExpr    *( WS ( "<<" / ">>" ) WS AddExpr )
AddExpr      = MulExpr    *( WS ( "+" / "-" ) WS MulExpr )
MulExpr      = Unary      *( WS ( "*" / "/" / "%" ) WS Unary )
Unary        = ( "-" / "~" ) WS Unary / Primary
Primary      = FunctionCall / Accessor / Literal / ( "(" WS Expression WS ")" )

FunctionCall = FunctionName WS "(" WS [ Expression *( WS "," WS Expression ) ] WS ")"
FunctionName = IDENTIFIER                            ; a core function or a function of an extension group

Accessor     = ( Root / Name ) *( Step )             ; a bare Name is shorthand for "instance." Name
Step         = "." ( "parent" / Name ) / "[" WS Expression WS "]"
Root         = "instance" / "parent" / "root" / "self" / "stream" / "asset" / "param"
Name         = IDENTIFIER                            ; not a ReservedWord
ReservedWord = Root / "and" / "or" / "not" / "true" / "false"

CompOp       = "==" / "!=" / "<=" / ">=" / "<" / ">"
Literal      = StringLiteral / HexLiteral / FloatLiteral / IntegerLiteral / BooleanLiteral
StringLiteral= %x27 *( SChar / Escape ) %x27        ; single-quoted
Escape       = "\" ( "\" / %x27 / %x22 / "n" / "t" / "r" / "0"
                    / "x" 2HEXDIG / "u" 4HEXDIG )
SChar        = %x00-26 / %x28-5B / %x5D-D7FF / %xE000-10FFFF
                                                     ; any character except ' and \, controls included
HexLiteral   = "0" ( "x" / "X" ) 1*HEXDIG
FloatLiteral = 1*DIGIT "." 1*DIGIT [ Exponent ] / 1*DIGIT Exponent
Exponent     = ( "e" / "E" ) [ "+" / "-" ] 1*DIGIT
IntegerLiteral = 1*DIGIT
BooleanLiteral = "true" / "false"
IDENTIFIER   = ( ALPHA / "_" ) *( ALPHA / DIGIT / "_" )
WS           = *( %x20 / %x09 / %x0D / %x0A )

Notes on the grammar:

  • Alternation order. FloatLiteral precedes IntegerLiteral in Literal so that a lexeme such as 0.05 is read as one Float rather than the Integer 0 followed by a stray .05; a literal is a Float exactly when it carries a fractional part or an exponent. A . after digits begins a fraction only when a digit follows it, so Items[0].Tag is a subscript followed by a key step. An IDENTIFIER immediately followed (after optional WS) by ( is a FunctionCall; otherwise it is an Accessor.
  • Ternary. The Conditional is right-associative and lower in precedence than every binary operator, so a ? b : c ? d : e parses as a ? b : (c ? d : e); its condition is an OrExpr, so a nested ternary in the condition position must be parenthesised.
  • Comparisons do not chain. Comparison takes at most one operator: a < b < c and a == b == c are syntax errors.
  • No signed literals. Numeric literals are unsigned; -5 is unary minus applied to 5.
  • String escapes. HEL and HDL string literals share one escape set: \\ (backslash), \' (apostrophe), \" (quotation mark), \n (U+000A), \t (U+0009), \r (U+000D), \0 (U+0000), \xHH (the code point U+0000–U+00FF given by exactly two hex digits) and \uHHHH (the UTF-16 code unit given by exactly four hex digits; a high surrogate MUST be followed by a \uHHHH low surrogate, the pair denoting one code point, and a lone surrogate is an error). Any other backslash sequence, or too few hex digits, is a syntax error. Any other character, including a tab, a line break, any other control character (U+0000–U+001F, U+007F) or a non-ASCII character, MAY also be written literally; the canonical form writes the control characters other than tab, line feed and carriage return as \xHH.
  • ASCII lexing. ALPHA, DIGIT and HEXDIG are the ASCII ranges of [[RFC5234]]: identifiers and numbers are ASCII. A non-ASCII letter or digit outside a string literal (café, the fullwidth １) is a syntax error, never a name or a number.
  • Integer literal range. An IntegerLiteral or HexLiteral denotes a non-negative Integer and MUST NOT exceed 263−1 (9223372036854775807, 0x7FFFFFFFFFFFFFFF); a larger literal is a syntax error, not a wrap-around. A hex literal therefore cannot spell a bit pattern with the top bit set: 0xFFFFFFFFFFFFFFFF is an error, and the pattern 0x8000000000000000 is written ~0x7FFFFFFFFFFFFFFF. The minimum Integer is written -9223372036854775807 - 1.
  • Float literal value. A FloatLiteral denotes the IEEE 754 binary64 value nearest to its decimal value (round half to even). A literal whose value is too large to be finite in binary64 (1e999) is a syntax error, not Infinity; one too small to be distinguished from zero denotes zero.

Core Functions

A conforming evaluator MUST implement every core function. Each takes exactly the number of arguments shown (concat takes any number); a call with a different number of arguments is an error that names the function. An argument of the wrong type is an error. Where a String is required, a Bytes value is accepted and decoded as for a Bytes-vs-String comparison; one that is not well-formed in its encoding is an error. Character positions and lengths count Unicode code points.

FunctionResult

For a String value whose byte span was not recorded (a value computed by an expression), the length of its UTF-8 encoding; for such a Bytes value, its length. sizeof of a derived field, which has no byte extent, or of a node not yet parsed, is an error.

substring(string, start, length)String: length characters of string beginning at start, which is 0-based, as array subscripts are. A range error if start is negative, length is negative, or start + length exceeds the string's length — a fixed-width subfield that runs off the end means the field was misread, and silently returning a short string would carry that error onward as plausible data. (Contrast the clamping substr.)
concat(string, …)String: the arguments joined in order (concat() is the empty string). Every argument MUST already be a String (or Bytes): there is no implicit conversion, so a number must be rendered deliberately rather than picking up whatever spelling the engine happens to use for it.

The accessor MUST be exactly asset.<Part>, naming a part (e.g. partExtension(asset.Raster)); it is a runtime error otherwise, when the part is missing or more than one file was matched to it, and — like asset itself — when the description is not being parsed as part of an asset. The accessor is not evaluated: partExtension reads the part's identity, so the part need not have been parsed.

toNumber

The String argument MUST match this grammar in its entirety:

NumericText  = [ "+" / "-" ] 1*DIGIT [ "." 1*DIGIT ] [ ( "e" / "E" ) [ "+" / "-" ] 1*DIGIT ]

The result is an Integer when the text has neither a . nor an exponent (so '10' is an Integer and '10.0' a Float), and a Float otherwise, rounded to the nearest binary64 value. Everything else is a runtime error, specifically: leading or trailing whitespace (it is not trimmed — write toNumber(trim(x))); an empty string; NaN, Infinity and other named values; a bare .5 or 5.; hexadecimal forms; type suffixes such as f, d or L; grouping separators; an Integer outside the signed 64-bit range (it is an error, not a fallback to Float); and a Float whose magnitude overflows binary64. toNumber is needed only for numbers carried in a bddo:string field; a field typed bddo:asciiInteger or bddo:asciiDecimal already yields a number.

substring and concat are what make a hexplain:valueExpression able to reshape a field rather than only rescale it. Fixed-width records pack several quantities into one field with no separator between them, so substringBefore/substringAfter have nothing to cut on: NITF's IGEOLO is 60 characters holding four corner coordinates, each a latitude and a longitude at known offsets. Reading them needs slicing by position, and reporting them as one geometry needs joining the slices back together.

partExtension exists because an abnd:PartSpec may list several abnd:extension values as ALTERNATIVES, and which one matched can change how the part is read. An ESRI .hdr-labelled raster is the case: NBITS 32 means uint32 when the grid is .bil/.bip/.bsq and float32 when it is .flt. The width is in the header, but the choice between integer and float is carried only by the filename, so without this the two are indistinguishable and every sample of a float grid is decoded as a meaningless integer.

A part's IDENTITY — its name, and so its extension — is fixed when the asset is assembled, before any part is parsed. So unlike a part's CONTENT, which asset.X.field can only read once part X has been parsed, partExtension is available to every part's conditions from the start, including a part asking about ITSELF. That self-reference is the common case: the rule selecting a grid's cell type lives on that same grid's layout.

Extension Groups

An evaluator MAY implement any of the following groups, each all or nothing (see Language Version and Extension Groups). A processor that does not implement a group MUST reject a description whose expressions call a function of that group when the description is loaded, with an unsupported-feature error naming the function and the group's IRI; it MUST NOT defer the failure to the first evaluation, where it would depend on the data. A call to a function that is in neither the core set nor any group is likewise rejected when the description is loaded: as a Type / HEL error when the description declares a HEL version this evaluator implements, since a later 1.x version cannot give the name a meaning retroactively, and as an Unsupported feature error when it declares a later 1.x version, which may define the name (version marker). The argument rules of the core set (fixed arity, Bytes accepted as String) apply here too.

An error if the run supplies none.

Group geometry

Both functions take two arrays of numbers of equal length, the x and y coordinates of a ring's vertices in order; the ring is implicitly closed from the last vertex back to the first. Coordinates are planar. Arrays of different length, or containing a non-number, are an error.

FunctionResult

isSelfIntersecting(xs, ys)Boolean: true when two non-adjacent edges of the ring properly cross (each edge's endpoints lie strictly on opposite sides of the other). Collinear overlaps and touching at a vertex are not crossings; a ring of fewer than 4 vertices is never self-intersecting.

Group quantifiers

FunctionResult
all(array, predicate)Boolean: true when predicate holds for every element of array; true for an empty array.
any(array, predicate)Boolean: true when predicate holds for at least one element; false for an empty array.

The first argument MUST be an array node. The second is not evaluated before the call: it is evaluated once per element, in order, with self bound to the element and, when the element is a struct node, instance bound to it (so bare names read the element's fields) and parent bound to the enclosing instance; when the element is not a struct node, instance and parent are unchanged. When the element is a struct node, param.n and a name that reaches a local binding MUST resolve against the element’s struct: param.n is the argument the element was parsed with, a bare name or instance.name may name a local binding of the element’s struct, and the parameters and bindings of the struct holding the expression are not reachable in the predicate. Each evaluation MUST yield a Boolean, else it is an error. Evaluation stops at the first element that decides the result (a false for all, a true for any), so later elements are not evaluated. An evaluator MUST bound the total number of predicate evaluations during one evaluation of an expression, nested quantifiers included, by its configured quantifier limit (the Processing Model’s quantifier evaluations, at least 1,000,000 by default), and MUST report exceeding it as a ResourceLimit error.

Numeric Semantics

HEL arithmetic uses signed 64-bit two's-complement Integers and IEEE 754 binary64 Floats. The following are normative:

  • Integer overflow is an error. Integer-only +, -, *, / and unary - are exact within [−263, 263−1]; a result outside that range MUST raise an error, never wrap. This includes (-9223372036854775807 - 1) / -1 and -(-9223372036854775807 - 1).
  • Integer division. Integer / truncates toward zero (thus 5 / 2 = 2, -3 / 2 = -1), and % is the remainder with the dividend's sign. This is deliberately different from XPath numeric division. Mixing Integer and Float promotes the operation to Float (thus 5 / 2.0 = 2.5).
  • Division and modulo by zero MUST raise an error, for Float operands as well as Integer ones: 1.0 / 0.0 is an error, not Infinity.
  • Float arithmetic otherwise follows IEEE 754 binary64 with round-to-nearest: a result too large in magnitude is ±Infinity, and an invalid operation such as Infinity - Infinity is NaN.
  • Bitwise operators require Integer operands and act on their 64-bit two's-complement representation; ~x is -x - 1.
  • Shifts. The shift count MUST be an Integer in [0, 63]; a count outside that range MUST raise an error (it is not reduced modulo 64). >> is an arithmetic (sign-propagating) right shift. x << n MUST raise an error when x × 2n is outside the signed 64-bit range, so 1 << 63 is an error.
  • Unsigned 64-bit values. A parsed unsigned integer above 263−1 (from a uint64 field) keeps its exact value for comparisons and for Float arithmetic, but its use in Integer arithmetic, bitwise operations, shifts or indexes MUST raise an out-of-range error. No literal can denote such a value (see literal range).
  • Indexes MUST be non-negative Integers within the addressed collection; a Float, negative or out-of-range index MUST raise an error.

Evaluation Semantics

Operator Precedence

From highest to lowest: grouping () and function calls; unary -/~; * / %; + -; shifts << >>; bitwise &; bitwise ^; bitwise |; comparisons; not; and; or; and lowest of all, the ternary ? :. Within one level, evaluation is left to right, except the ternary, which is right-associative. Note that, unlike C, the bitwise operators bind tighter than comparisons, so Flags & 0x01 == 0x01 tests the masked bit. The logical and and or operators MUST evaluate BOTH operands: they do not short-circuit, so an expression whose right operand raises — a division by zero, an out-of-range subscript — raises even when the left operand already decides the result. A guard MUST therefore be written with the ternary rather than with and: count(Items) > 0 ? Items[0] == 1 : false, not count(Items) > 0 and Items[0] == 1. The ternary evaluates its condition (which must yield a Boolean) and then only the selected branch; both branches SHOULD have compatible types, and the result takes the type of the selected branch. The operands of and, or and not MUST be Booleans, and both operands of and and or are type-checked: false and 1 is an error even though false decides the result.

Value Types

Every HEL value is one of: Integer, Float, Boolean, String, Bytes, or Null (an absent optional field), or a struct node or array node reached by an accessor. A field's parsed value takes the HEL type implied by its bddo:DataType's bddo:baseType: bddo:baseInteger → Integer, bddo:baseFloat → Float, bddo:baseString → String, bddo:baseBytes → Bytes. This is determined by baseType alone, so the ASCII-coded numeric types bddo:asciiInteger and bddo:asciiDecimal yield Integer and Float respectively and may be used wherever a number is required.

Type Coercion & Comparison Rules

These rules are normative and resolve the comparisons used throughout Hexplain (e.g. comparing a 4-byte ChunkType to 'IHDR'):

  • Arithmetic / bitwise operands MUST be numeric. Mixing Integer and Float promotes to Float. Bitwise operators require Integer operands. A non-numeric operand, including Null, is an error.
  • Integer vs. Float compares by numeric value. Integer comparisons MUST be exact; mixed comparisons compare the exact represented numeric values without first rounding the Integer to Float.
  • NaN. == with a NaN operand is false (so NaN == NaN is false), != with a NaN operand is true, and every ordered comparison (< <= > >=) involving NaN is false. Infinities order as usual.
  • String vs. String compares by Unicode code point; < > <= >= use code-point order.
  • Bytes vs. String. For == and !=, when one operand is Bytes and the other a String, the Bytes value is decoded to a String using the field's bddo:encoding (default bddo:utf8) by the Processing Model's text-decoding rule, and equality holds iff the decoded strings are code-point-identical. A Bytes value that is not well-formed in its encoding decodes to no String: it is never replaced by U+FFFD, it equals no String (== is false and != is true), and where a String is required it is an error. Ordering a Bytes value against a String is an error.
  • Bytes vs. Bytes is equal iff the byte sequences are identical; ordering two Bytes values is an error.
  • Boolean vs. Boolean may be compared with == and !=; ordering Booleans is an error.
  • Null. An access to an absent optional field yields Null. Null == Null is true and Null == x is false for any other x. Every other comparison with a Null operand is false — including !=: Null != 1 and Null != Null are both false, so for an optional field x != 1 is not the same as not (x == 1). Arithmetic, bitwise and logical operators, the ternary condition, and function arguments do not accept Null: each is an error.
  • Comparing values of otherwise incompatible types (e.g. Boolean vs. Integer, String vs. Integer, or a struct or array node) is an error.

Conformance

A conforming HEL 1.0 evaluator MUST:

  1. Parse all valid expressions per the ABNF grammar, and reject as a syntax error every string it does not generate, including out-of-range literals and unknown escapes.
  2. Implement the parsing context, the reserved roots (instance, parent, root, self, stream, asset, param) and the name-binding table. A processor that does not parse multi-part assets MAY leave asset and partExtension unimplemented, but MUST then raise a runtime error on an expression that uses them rather than resolving them to Null.
  3. Implement all operators and every core function with the specified precedence, the numeric semantics, and the value-type and coercion rules; and implement each extension group it claims in full.
  4. Reject, at load time, a description that calls a function of an extension group it does not implement, with an unsupported-feature error.
  5. Yield a Boolean in a boolean context, an Integer in a numeric context and a String in a string context, as the name-binding table gives for each property (e.g. a hexplain:valueExpression whose hexplain:valueDatatype is xsd:string yields a String); any other result is an error, and a Float is never an Integer, even one whose value is integral: a size expression that yields 2.0 is an error, not a size of 2.
  6. Report a runtime error (rather than silently continue) on type errors, integer overflow, shift counts out of range, out-of-range unsigned values, division/modulo by zero, out-of-range subscripts, undefined names and forward references.
  7. Accept, by default, expressions whose expression tree is at least 512 levels deep and at least 64 KiB long, when they are parsed and when they are evaluated, and quantifier and match-cost budgets of at least the Processing Model’s minimums; let the user configure all four limits; and report an expression beyond its configured nesting or length limit, a quantifier that exceeds its evaluation budget, a regular-expression match that exceeds its cost limit, and a deadline or cancellation as the Processing Model's ResourceLimit error, not as a syntax or runtime error: it is fatal in every mode, including a lenient one that records other errors and continues (Security and Privacy Considerations).
  8. Produce, for every row of hel-vectors.tsv whose functions it implements, the value the row gives, or an error of the condition the row names; a row's message column is informative.

Error conditions

Every error an expression raises is one of the conditions below. All of them are Type / HEL errors in the sense of the Processing Model (category Expression); an unsupported extension group or HEL version is an Unsupported feature error, and a limit reached is a ResourceLimit error, neither of them a condition here. The conditions are what the vectors assert, so conformance never depends on the words of a diagnostic. A conforming evaluator MUST be able to state, for every error it raises, which of these conditions it is; it MAY report them under names of its own and with any message.

Expression depth. The nesting depth of an expression, which the limit of item 7 bounds, is the depth of its expression tree, with one exception: a left-associative chain of one binary operator (a + b + c + d, x and y and z, f | g | h) is one n-ary node whose depth is one more than that of its deepest operand, however long the chain. A chain that mixes operators of one precedence level (a + b - c) is not one node. An evaluator MUST count depth this way, so that a long flat sum or conjunction, which descriptions generate, is accepted whatever its length allows.

Canonical Form

Two HEL strings are equivalent when they parse to the same expression tree once a bare name x is read as instance.x, a hexadecimal literal as the Integer it denotes and a Float literal as the binary64 value it denotes; whitespace, redundant parentheses and the spelling of a literal do not matter. The conformance suite compares HEL-bearing literals by this equivalence. The canonical form is one spelling of each class, the one the reference implementation's serializer writes and the HDL compiler emits:

  • An accessor starts with its root, so a bare name is written instance.x; key steps are .name and subscripts [e], with no spaces.
  • An Integer literal is written in decimal (a hexadecimal literal becomes decimal); a Float literal as the shortest decimal that denotes the same binary64 value, with a . and at least one fraction digit when its magnitude is at least 10−3 and below 107, and otherwise as a mantissa with a fraction, E and a signed-if-negative exponent (1.0E7, 1.0E-4); Booleans are true and false.
  • A string literal is single-quoted; \ and ' are written \\ and \', the control characters U+0000–U+0008, U+000B, U+000C, U+000E–U+001F and U+007F as \xHH with upper-case hex digits, and every other character, tab, line feed and carriage return included, as itself.
  • A binary operation is written l op r with single spaces, and an operand that is itself a binary operation or a ternary is parenthesised, whatever the precedences: a + b + c becomes (instance.a + instance.b) + instance.c.
  • A unary operation is -e, ~e or not e, its operand parenthesised when it is a binary operation or a ternary.
  • A call is name(a, b); a ternary is c ? t : e, its condition parenthesised when it is itself a ternary.

So Flags&0x01==1 and not(done) has the canonical form ((instance.Flags & 1) == 1) and not instance.done.
