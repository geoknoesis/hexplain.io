The Hexplain Expression Language (HEL) is a small, declarative language for the conditions and calculations inside Hexplain format descriptions. It powers dynamic sizing, conditional presence, repetition counts, offsets, derived values, conformance assertions, and conditional data-type and semantic dispatch. HEL operates on a hierarchical logical data model built from the binary data being parsed; a name in an expression is the local name of a field of the struct the expression is evaluated in.

This document is a prerelease working draft of HEL 1.0, produced for the purpose of defining the Hexplain standard. It has no official standing and is not endorsed by any standards body. The language, its function groups and its conformance vectors may still change incompatibly before HEL 1.0 is released. The executable statement of this draft is the vector set validation/test/hel-vectors.tsv; where a vector and the prose disagree, that is a defect in this document to be reported.

Introduction

A key requirement of the Hexplain framework is handling dynamic structures where the presence, size, count, offset, or type of a field depends on previously parsed data. HEL provides a concise, unambiguous syntax for these expressions. Design goals: simplicity, clarity, determinism (the same expression over the same data gives the same result or the same error in every conforming implementation), and grounding in stable standards (XPath-style operator semantics, IEEE 754 binary64 floating point).

Expression Literals

A HEL expression is the lexical form of a literal typed xsd:string or bddo:HelExpression, the datatype BDDO derives from xsd:string for expression text: a bddo:HelExpression literal's value is its text as a string, so it is a value of every property whose range is xsd:string, and it lets a reader tell an expression from a name or a label without knowing which property holds it. Authoring tools SHOULD type the expressions they write bddo:HelExpression; an expression typed xsd:string remains valid. A processor MUST accept an expression in a literal of either datatype and MUST evaluate the two alike: the datatype never changes what an expression means. The complete list of properties whose values are HEL expressions, and what each expression's names are bound to, is the name-binding table.

Language Version and Extension Groups

This document defines HEL 1.0. A later 1.x version MAY add functions and extension groups, but MUST NOT change the value or the error an expression that is valid under HEL 1.0 produces.

Version marker. An expression carries no version marker; a description does. The declared HEL version of a description is the greatest value of bddo:helVersion stated on an owl:Ontology of its graph, imports included: a string major.minor, two decimal numbers without leading zeros ("1.0", "1.2"). A description that states none declares HEL 1.0, which is what every description written before the marker existed was written against. Every evaluator implements some latest HEL version (this document defines 1.0) and states it with its claims. A processor MUST read the declared HEL version when the description is loaded, and MUST raise a Description error for a bddo:helVersion that is not of that form. A declared major version other than 1 MUST be refused with an Unsupported feature error when the description is loaded: HEL 1 rules cannot be assumed to read it. A call to a function name that is neither a core function nor in an extension group of the version the evaluator implements MUST be rejected when the description is loaded, as an Unsupported feature error when the declared version is a later 1.x version than the evaluator implements (the name may be one that version defines), and as a Type / HEL error otherwise (the name is simply not HEL).

The function library is divided into a core set, which every conforming evaluator MUST implement, and named extension groups, which an evaluator MAY implement. An extension group is implemented all or nothing: an evaluator either implements every function of the group as specified here, or none of them. An extension group is identified by its group name (text, temporal, geometry, register, quantifiers) and, wherever an IRI is needed (a processor's statement of the groups it supports, a report of an unsupported feature), by the IRI of its section in this document, https://hexplain.io/specification/hel/#ext-name (for example https://hexplain.io/specification/hel/#ext-text). Every function name belongs to exactly one group, so the groups a description needs are determined statically by the function names its expressions call.

Conformance

The key words "MUST", "MUST NOT", "REQUIRED", "SHALL", "SHALL NOT", "SHOULD", "SHOULD NOT", "RECOMMENDED", "MAY", and "OPTIONAL" in this document are to be interpreted as described in BCP 14 [[RFC2119]] [[RFC8174]] when, and only when, they appear in all capitals, as shown here.

The Logical Data Model

A HEL expression is evaluated against a temporary, in-memory parsing context — a hierarchical tree that the processor builds as it parses (see the Processing Model). Each parsed Struct instance is a struct node whose named children are its fields; each scalar field yields a value node; a repeated field yields an ordered array node.

Reserved Roots

An expression is evaluated in a current struct node, determined by the property that carries the expression (see Name Binding). The reserved roots are resolved relative to it:

paramThe parameters of the struct instance instance denotes: param.n is the argument its caller supplied for the parameter named n of a parameterised struct (BDDO, Parameterised Structs). param is always followed by a key, which names a parameter. A parameter's value is a scalar or Null, or, for a parameter typed bddo:NodeParameter, a struct node, and for one typed bddo:ArrayParameter, an array value. After a scalar parameter a further key step or a subscript is an error, as on any scalar (a .parent step apart, which reads Null: above). After a node parameter, key steps read the fields of the caller's node, which the parameter denotes by identity (it is that node, not a copy), and after an array parameter a subscript reads an element: param.n.x, param.a[0] and param.a[0].x are paths like any other. A .parent step follows the path rule: param.n.parent and param.a[0].parent read Null, the parameter scope holding no field, and param.n.x.parent is the node param.n denotes — x’s actual holder in the tree, since the node's identity is preserved. A processor MUST raise a Description error, when the description is loaded, for param.n in an expression whose instance struct declares no parameter n, and for param without a key: whether a struct has a parameter is known from the description alone, so this is never deferred to the data. Inside an element-scoped argument whose elements are struct nodes instance is the element, so a processor MUST make that check against the element’s struct, not the struct holding the expression, wherever the description determines the element’s struct (the collection is a path of fields whose declared types are structs, none chosen at parse time); where it does not, a param.n the element’s struct lacks is an undefined name when it is evaluated.
repeatThe repetition of the field whose bddo:hasArgument list or bddo:repeatUntil condition is being evaluated. repeat.index is the zero-based position of the element being read or written, an Integer, and it is the only key repeat takes; arithmetic and subscripts over it are ordinary (repeat.index + 1, columns[repeat.index]). A processor MUST raise a Description error, when the description is loaded, for repeat in any expression other than an argument of a repeated field or its bddo:repeatUntil condition, and for repeat without the key index: whether an expression sits in a repetition is known from the description alone. An evaluator MUST bind repeat.index to the innermost repetition whose element arguments or bddo:repeatUntil condition lexically contain the expression: an argument of a repeated field inside a repeated struct sees the index of that inner field’s element, never the outer one, which the outer field passes to the struct as an argument if the struct needs it.
streamStream metadata, all byte counts (Integers), as defined by the Processing Model: stream.length is the length of the whole stream; stream.position is the cursor's offset; stream.remaining is the number of bytes from the cursor to the end of the innermost bounded region or decoded sub-stream being read (so it is not, in general, stream.length - stream.position). eof() is relative to the same innermost region: it is true exactly when stream.remaining == 0. Any other key after stream is an undefined-name error, parent apart, which reads Null.

Dispatch conditions. A bddo:dispatchOnExpression and the bddo:condition of a bddo:DataTypeRule choose the type of a field that has not been read yet, so they are evaluated against the containing struct. In these two contexts, and only in them, parent (and so instance.parent) is an alias for instance: ChunkType, instance.ChunkType and parent.ChunkType all read the containing struct's ChunkType. The alias is deprecated in HEL 1.0: it is kept only so that descriptions written against the earlier field-relative reading of instance stay valid. New descriptions MUST NOT use it; a processor SHOULD warn when it loads a description that does; an HDL compiler never emits it. A dispatch condition cannot reach the containing struct's parent other than through root.

Evaluated over the complete tree. Three rows are evaluated after the part is parsed rather than while it is: hexplain:valueExpression, and hexplain:condition on a hexplain:MappingRule (a map guard) and on a hexplain:ClassMappingRule (a means-when guard). For these three, and only these, the whole tree of the part is bound: a field declared later than the one carrying the expression MUST read as its parsed value, not raise a forward-reference error, and an absent optional field reads as Null (Processing Model, evaluation time). Every other row is evaluated during the parse, at the moment the Processing Model states, with only the fields parsed so far bound.

Repeat-until over structs. The two bddo:repeatUntil rows differ on purpose. Over struct elements the condition is about the element just read (until type == 'IEND' tests that chunk's type), so instance is that element and parent is the struct holding the sequence; over scalar elements there is no element struct, so instance stays the containing struct and self is the value. parent.x is therefore a field of the containing struct in the first case and of its parent in the second.

A processor that evaluates HEL outside parsing — for example the SPARQL function hxf:hel — binds instance to the node's struct, parent to its container and root to the root of the file, as the table does for a field-level expression.

Names and Key Resolution

An identifier in an accessor — a bare name, or a key after a dot — is the local name of a field of the struct node it is applied to. In an RDF description a field is a bddo:Field resource, and its HEL name is the local name of that resource's IRI (the part after the final # or /), which is also the name the HDL gives it. Identifiers are not IRIs and are never expanded through @prefix declarations or a JSON-LD context: ChunkType means "the field named ChunkType in this struct", whatever namespace its IRI is in. Within one struct, field local names MUST be unique. A processor MUST reject a description in which two fields of one struct share a local name, with a Description error when the description is loaded: an expression could not tell which of them a name reads.

A bare name x is exactly instance.x. A key MUST name a field declared by the bddo:Struct of the node it is applied to, or be the keyword parent; a bare name, or a key applied directly to instance, MAY also name a bddo:LocalBinding of that struct, and a key after param names a parameter. This is checked at every step of a path, not only the first, and inside an element-scoped argument whose element is a struct node a bare name is checked against the element's struct. There is no .size or other pseudo-accessor: after a dot, size is an ordinary key, so Entries.size is an error unless the struct declares a field size; the number of elements is len(Entries) or count(Entries). Root keys. A field declared with bddo:rootKeyFromField binds, in the root context, keys that only the data names; root.k for such a key reads Null, not an undefined-name error, when no record bound k — the one case where a key the root struct does not declare is not an error. A name that is also a reserved word (instance parent root self stream asset param repeat and or not true false) cannot be written as a bare name or a key, so a field, parameter or local binding that expressions need to reference MUST NOT have such a local name.

Local bindings. A bddo:LocalBinding of a struct is visible only through instance of that struct's own instances: by bare name or instance.name, in expressions evaluated after its position in the member list. It is not a node of the tree, so parent.name, root.name, self.name (even where self is the same node as instance), a key after a subscript and a key applied to any other struct node do not reach it: for those it is an undefined name. Read before its position it is a forward reference, like a later field.

An array node (a repeated field), and any other array value reached through a name, MAY be subscripted with [ Expression ]. The index expression MUST evaluate to a non-negative Integer strictly less than the array's length (elements are 0-based); otherwise a range error is raised. Subscripts and key steps compose freely (e.g. root.Directory[i].Entries[0].Tag). Applying a key other than the keyword parent to a value that is not a struct node (an Integer, Float, String, Bytes or Boolean, or an array value), or a subscript to a value that is not an array value, is an error; a .parent step is resolved from the path, not from the value (Reserved Roots). A key applied to Null (an absent optional field) yields Null.

Undefined Names and Forward References

Three cases are distinguished, and a conforming evaluator MUST keep them apart:

  • Undefined name. A key that names no field declared by the addressed struct (a typo, or a field of some other struct), or self where the property defines no value under test, MUST raise an undefined-name error. It MUST NOT evaluate to Null: a misspelt name that read as Null would silently turn a presence condition false or a comparison false.
  • Forward reference. A key that names a declared field which has not yet been reached at the moment of evaluation (it comes later in field order, or belongs to a struct instance still being parsed further on) MUST raise a forward-reference error. The exception is an expression evaluated over the complete tree (a value expression, a map guard, a means-when guard), where every field of the part has been reached.
  • Absent optional field. A declared field that has been reached but is not present in this instance (its bddo:isPresentIf was false) reads as Null. This is the only way a field reference yields Null.

Both errors are type/HEL errors in the sense of the Processing Model.

Syntax and Grammar

Formal Grammar (ABNF)

The following grammar [[RFC5234]] defines HEL. Operators are listed lowest-precedence first. WS MAY appear between any two tokens, and is required only where two adjacent tokens would otherwise read as one (for example between not and a name); the productions show it where it is commonly written.

Expression   = Conditional
Conditional  = OrExpr [ WS "?" WS Expression WS ":" WS Conditional ]
OrExpr       = AndExpr *( WS "or" WS AndExpr )
AndExpr      = NotExpr *( WS "and" WS NotExpr )
NotExpr      = "not" WS NotExpr / Comparison
Comparison   = BitOrExpr [ WS CompOp WS BitOrExpr ]
BitOrExpr    = BitXorExpr *( WS "|" WS BitXorExpr )
BitXorExpr   = BitAndExpr *( WS "^" WS BitAndExpr )
BitAndExpr   = ShiftExpr  *( WS "&" WS ShiftExpr )
ShiftExpr    = AddExpr    *( WS ( "<<" / ">>" ) WS AddExpr )
AddExpr      = MulExpr    *( WS ( "+" / "-" ) WS MulExpr )
MulExpr      = Unary      *( WS ( "*" / "/" / "%" ) WS Unary )
Unary        = ( "-" / "~" ) WS Unary / Primary
Primary      = FunctionCall / Accessor / Literal / ( "(" WS Expression WS ")" )

FunctionCall = FunctionName WS "(" WS [ Expression *( WS "," WS Expression ) ] WS ")"
FunctionName = IDENTIFIER                            ; a core function or a function of an extension group

Accessor     = ( Root / Name ) *( Step )             ; a bare Name is shorthand for "instance." Name
Step         = "." ( "parent" / Name ) / "[" WS Expression WS "]"
Root         = "instance" / "parent" / "root" / "self" / "stream" / "asset" / "param" / "repeat"
Name         = IDENTIFIER                            ; not a ReservedWord
ReservedWord = Root / "and" / "or" / "not" / "true" / "false"

CompOp       = "==" / "!=" / "<=" / ">=" / "<" / ">"
Literal      = StringLiteral / HexLiteral / FloatLiteral / IntegerLiteral / BooleanLiteral
StringLiteral= %x27 *( SChar / Escape ) %x27        ; single-quoted
Escape       = "\" ( "\" / %x27 / %x22 / "n" / "t" / "r" / "0"
                    / "x" 2HEXDIG / "u" 4HEXDIG )
SChar        = %x00-26 / %x28-5B / %x5D-D7FF / %xE000-10FFFF
                                                     ; any character except ' and \, controls included
HexLiteral   = "0" ( "x" / "X" ) 1*HEXDIG
FloatLiteral = 1*DIGIT "." 1*DIGIT [ Exponent ] / 1*DIGIT Exponent
Exponent     = ( "e" / "E" ) [ "+" / "-" ] 1*DIGIT
IntegerLiteral = 1*DIGIT
BooleanLiteral = "true" / "false"
IDENTIFIER   = ( ALPHA / "_" ) *( ALPHA / DIGIT / "_" )
WS           = *( %x20 / %x09 / %x0D / %x0A )

Notes on the grammar:

  • Alternation order. FloatLiteral precedes IntegerLiteral in Literal so that a lexeme such as 0.05 is read as one Float rather than the Integer 0 followed by a stray .05; a literal is a Float exactly when it carries a fractional part or an exponent. A . after digits begins a fraction only when a digit follows it, so Items[0].Tag is a subscript followed by a key step. An IDENTIFIER immediately followed (after optional WS) by ( is a FunctionCall; otherwise it is an Accessor.
  • Reserved words are never function names. A FunctionName MUST NOT be a ReservedWord: an evaluator MUST read not(x), not (x) and not x alike, as the not operator applied to x (so not(a) and b is (not a) and b, by precedence), and instance(1), and(), true() are syntax errors, not calls. Consequently no function of any version is ever named not, and, or, true, false or a root.
  • Every root is reserved, in every position. asset, param and repeat are roots like instance and stream, although one exists only inside an asset, another only inside a parameterised struct and the third only in the element arguments and until condition of a repeated field. An evaluator MUST report a syntax error for a root written as a function name (asset(1), param(), repeat()) and for a root written as a key after a dot (x.param, x.asset, x.repeat, x.stream, x.self, x.root, x.instance): a Step is parent or a Name, and a Name is never a reserved word. It is a syntax error whether or not an asset or a parameter is in scope, so it is reported when the description is loaded and never depends on the data; a field that expressions need is not given a root's name (Key resolution).
  • Ternary. The Conditional is right-associative and lower in precedence than every binary operator, so a ? b : c ? d : e parses as a ? b : (c ? d : e); its condition is an OrExpr, so a nested ternary in the condition position must be parenthesised.
  • Comparisons do not chain. Comparison takes at most one operator: a < b < c and a == b == c are syntax errors.
  • No signed literals. Numeric literals are unsigned; -5 is unary minus applied to 5.
  • String escapes. HEL and HDL string literals share one escape set: \\ (backslash), \' (apostrophe), \" (quotation mark), \n (U+000A), \t (U+0009), \r (U+000D), \0 (U+0000), \xHH (the code point U+0000–U+00FF given by exactly two hex digits) and \uHHHH (the UTF-16 code unit given by exactly four hex digits; a high surrogate MUST be followed by a \uHHHH low surrogate, the pair denoting one code point, and a lone surrogate is an error). Any other backslash sequence, or too few hex digits, is a syntax error. Any other character, including a tab, a line break, any other control character (U+0000–U+001F, U+007F) or a non-ASCII character, MAY also be written literally; the canonical form writes the control characters other than tab, line feed and carriage return as \xHH.
  • ASCII lexing. ALPHA, DIGIT and HEXDIG are the ASCII ranges of [[RFC5234]]: identifiers and numbers are ASCII. A non-ASCII letter or digit outside a string literal (café, the fullwidth １) is a syntax error, never a name or a number.
  • Integer literal range. An IntegerLiteral or HexLiteral denotes a non-negative Integer and MUST NOT exceed 263−1 (9223372036854775807, 0x7FFFFFFFFFFFFFFF); a larger literal is a syntax error, not a wrap-around. A hex literal therefore cannot spell a bit pattern with the top bit set: 0xFFFFFFFFFFFFFFFF is an error, and the pattern 0x8000000000000000 is written ~0x7FFFFFFFFFFFFFFF. The minimum Integer is written -9223372036854775807 - 1.
  • Float literal value. A FloatLiteral denotes the IEEE 754 binary64 value nearest to its decimal value (round half to even). A literal whose value is too large to be finite in binary64 (1e999) is a syntax error, not Infinity; one too small to be distinguished from zero denotes zero.

Core Functions

A conforming evaluator MUST implement every core function. Each takes exactly the number of arguments shown (concat takes any number, min and max at least one); a call with a different number of arguments is an error that names the function. An argument of the wrong type is an error. Where a String is required, a Bytes value is accepted and decoded as for a Bytes-vs-String comparison; one that is not well-formed in its encoding is an error. Character positions and lengths count Unicode code points.

toNumber

The String argument MUST match this grammar in its entirety:

NumericText  = [ "+" / "-" ] 1*DIGIT [ "." 1*DIGIT ] [ ( "e" / "E" ) [ "+" / "-" ] 1*DIGIT ]

The result is an Integer when the text has neither a . nor an exponent (so '10' is an Integer and '10.0' a Float), and a Float otherwise, rounded to the nearest binary64 value. Everything else is a runtime error, specifically: leading or trailing whitespace (it is not trimmed — write toNumber(trim(x))); an empty string; NaN, Infinity and other named values; a bare .5 or 5.; hexadecimal forms; type suffixes such as f, d or L; grouping separators; an Integer outside the signed 64-bit range (it is an error, not a fallback to Float); and a Float whose magnitude overflows binary64. toNumber is needed only for numbers carried in a bddo:string field; a field typed bddo:asciiInteger or bddo:asciiDecimal already yields a number.

The math group of the core set

These functions are core: every evaluator implements them. They take Integers and Floats only; a Null, Boolean, String, Bytes or node argument is a type error, and an argument count outside what is shown is a syntax error. They are functions of a number's value, not Integer arithmetic: an evaluator MUST accept an unsigned 64-bit Integer above 263−1 (Unsigned 64-bit values) as an argument of floor, ceil, trunc, round, abs, min, max and toString, and MUST NOT raise the out-of-range error that arithmetic on such a value raises. The rounding functions and abs return it unchanged, with its exact value; min and max compare it by value like any other argument and return the selected argument unchanged; toString renders its decimal digits (toString of 264−1 is '18446744073709551615'). They exist so that a size or count can be computed from a Float without guessing how an engine rounds, and so that a number can be rendered into a string deliberately (concat converts nothing).

Float rendering. The rendering of a Float is the one spelling of its binary64 value that the canonical form writes, defined here so that two evaluators render alike: NaN is NaN, the infinities Infinity and -Infinity, and zero 0.0 or -0.0. Any other value is written from the shortest round-trip digits: the decimal digit string with the fewest significant digits that, read back as a decimal and rounded to the nearest binary64 value (ties to even), gives the value again, and, among such strings of that length, the one whose decimal value is nearest to the exact binary64 value When a single digit would do, two are written: the two-digit decimal strings that read back to the value are taken, and the one nearest the exact value (the even one of a tie). For every value but a few of the smallest subnormals that is the single digit followed by 0 (2.0, 1.0E23); the smallest subnormal, which 5E-324 reads back to, is written 4.9E-324, the two-digit string nearest its exact value 4.94…×10−324. (This is the definition; the algorithm of Steele and White, Ryū and Grisu-exact are ways of computing the digits.) With d those digits and e the decimal exponent such that the value is 0.d × 10e, an evaluator MUST write a value whose magnitude is at least 10−3 and below 107 in positional notation — the digits with the point after the e-th, zeros supplied on either side as needed, and at least one digit on each side of the point (123.0, 0.001, 1234567.0) — and every other value in scientific notation: the first digit, a point, the remaining digits or a single 0, then E and the exponent e−1 in decimal with a - when negative and no + (1.0E7, 1.5E-5, 1.7976931348623157E308, 4.9E-324), with a leading - for a negative value. The rendering is defined by the two rules above and by nothing else: no platform's number formatting is its definition, and an evaluator whose platform function differs on any value (several wrote more digits than the shortest before they were corrected) MUST NOT use it. toNumber reads every rendering back to the same value. Informative: Java's Double.toString has produced this spelling since Java 19.

substring and concat are what make a hexplain:valueExpression able to reshape a field rather than only rescale it. Fixed-width records pack several quantities into one field with no separator between them, so substringBefore/substringAfter have nothing to cut on: NITF's IGEOLO is 60 characters holding four corner coordinates, each a latitude and a longitude at known offsets. Reading them needs slicing by position, and reporting them as one geometry needs joining the slices back together.

partExtension exists because an abnd:PartSpec may list several abnd:extension values as ALTERNATIVES, and which one matched can change how the part is read. An ESRI .hdr-labelled raster is the case: NBITS 32 means uint32 when the grid is .bil/.bip/.bsq and float32 when it is .flt. The width is in the header, but the choice between integer and float is carried only by the filename, so without this the two are indistinguishable and every sample of a float grid is decoded as a meaningless integer.

A part's IDENTITY — its name, and so its extension — is fixed when the asset is assembled, before any part is parsed. So unlike a part's CONTENT, which asset.X.field can only read once part X has been parsed, partExtension is available to every part's conditions from the start, including a part asking about ITSELF. That self-reference is the common case: the rule selecting a grid's cell type lives on that same grid's layout.

Group quantifiers

The group holds the functions that walk, build and convert array values, and the byte and text conversions those arrays need. It began with all and any; the functions from countWhere on were added to it before the HEL 1.0 snapshot, so they are part of the group as HEL 1.0 defines it, and an evaluator that implements the group implements every one of them (all or nothing). The Processing Model names the group by the feature token hel-ext-quantifier.

Element-scoped arguments. The second argument of all, any, countWhere, sumOf and project is an element-scoped argument: an expression that is not evaluated before the call, but once per element of the array given as the first argument, in the element's scope. In all, any and countWhere it is a predicate; in sumOf and project, an element expression. No other argument of any function is element-scoped.

The first argument of a function that takes an element-scoped argument MUST be an array value (an array node or a computed array), else it is a type error; the element-scoped argument is evaluated once per element, in order, with self bound to the element and, when the element is a struct node, instance bound to it (so bare names read the element's fields) and parent bound to the enclosing instance; when the element is not a struct node, instance remains the enclosing instance and parent also names that enclosing instance. When the element is a struct node, param.n and a name that reaches a local binding MUST resolve against the element’s struct: param.n is the argument the element was parsed with, a bare name or instance.name may name a local binding of the element’s struct, and the parameters and bindings of the struct holding the expression are not reachable in the element-scoped argument. Every other argument, of every HEL function, MUST be evaluated exactly once, before the call, in the scope of the expression that contains the call. In all, any and countWhere each evaluation of the predicate MUST yield a Boolean, else it is a type error. all and any MUST stop at the first element that decides the result (a false for all, a true for any) and MUST NOT evaluate the predicate for a later element; countWhere, sumOf and project MUST evaluate their element-scoped argument for every element. In sumOf each evaluation of the element expression MUST yield an Integer or a Float, else it is a type error, and the sum MUST be formed left to right with HEL's +, starting from the Integer 0: an Integer sum outside the signed 64-bit range is an overflow error, and a Float element makes the running sum a Float from that element on. In project each evaluation of the element expression yields the element at the same position of the result, and MUST NOT yield Null, which is a type error (an element is never Null).

An unsigned 64-bit value above 263−1 (Unsigned 64-bit values) MUST be accepted by floatCast, which, like the math group, reads a number's value, and MUST be raised as a range error where any other function of this group requires an Integer. No bit pattern is lost by that: a 64-bit pattern with its top bit set is the negative Integer with that two's-complement pattern, which integerBytes and fromIEEE accept.

Numeric Semantics

HEL arithmetic uses signed 64-bit two's-complement Integers and IEEE 754 binary64 Floats. The following are normative:

  • Integer overflow is an error. Integer-only +, -, *, / and unary - are exact within [−263, 263−1]; a result outside that range MUST raise an error, never wrap. This includes (-9223372036854775807 - 1) / -1 and -(-9223372036854775807 - 1).
  • Integer division. Integer / truncates toward zero (thus 5 / 2 = 2, -3 / 2 = -1), and % is the remainder with the dividend's sign. This is deliberately different from XPath numeric division. Mixing Integer and Float promotes the operation to Float (thus 5 / 2.0 = 2.5).
  • Float remainder. Float % MUST be the truncated remainder of IEEE 754 binary64 arithmetic (C's fmod, Java's and Kotlin's % on doubles), never the floored or the IEEE remainder operation: for finite operands the result is x - y * trunc(x / y) computed exactly, so it has the dividend's sign and a magnitude below |y| (5.5 % 2.0 = 1.5, -5.5 % 2.0 = -1.5, 5.5 % -2.0 = 1.5, -5.5 % -2.0 = -1.5, 6.0 % 2.0 = 0.0, -6.0 % 2.0 = -0.0); a finite dividend with an infinite divisor is returned unchanged (3.0 % (1e308 * 10.0) = 3.0), an infinite dividend or a NaN operand yields NaN, and a zero divisor is a division-by-zero error (above). A mixed Integer and Float % is a Float remainder.
  • Division and modulo by zero MUST raise an error, for Float operands as well as Integer ones: 1.0 / 0.0 is an error, not Infinity.
  • Float arithmetic otherwise follows IEEE 754 binary64 with round-to-nearest: a result too large in magnitude is ±Infinity, and an invalid operation such as Infinity - Infinity is NaN.
  • Bitwise operators require Integer operands and act on their 64-bit two's-complement representation; ~x is -x - 1.
  • Shifts. The shift count MUST be an Integer in [0, 63]; a count outside that range MUST raise an error (it is not reduced modulo 64). >> is an arithmetic (sign-propagating) right shift. x << n MUST raise an error when x × 2n is outside the signed 64-bit range, so 1 << 63 is an error.
  • Unsigned 64-bit values. A parsed unsigned integer above 263−1 (from a uint64 field) keeps its exact value for comparisons and for Float arithmetic, but its use in Integer arithmetic, bitwise operations, shifts or indexes MUST raise an out-of-range error. No literal can denote such a value (see literal range). The functions of the math group are not Integer arithmetic and accept it.
  • Indexes MUST be non-negative Integers within the addressed collection; a Float, negative or out-of-range index MUST raise an error.

Evaluation Semantics

Operator Precedence

From highest to lowest: grouping () and function calls; unary -/~; * / %; + -; shifts << >>; bitwise &; bitwise ^; bitwise |; comparisons; not; and; or; and lowest of all, the ternary ? :. Within one level, evaluation is left to right, except the ternary, which is right-associative. Note that, unlike C, the bitwise operators bind tighter than comparisons, so Flags & 0x01 == 0x01 tests the masked bit. The logical and and or operators MUST evaluate BOTH operands: they do not short-circuit, so an expression whose right operand raises — a division by zero, an out-of-range subscript — raises even when the left operand already decides the result. A guard MUST therefore be written with the ternary rather than with and: count(Items) > 0 ? Items[0] == 1 : false, not count(Items) > 0 and Items[0] == 1. The ternary evaluates its condition (which must yield a Boolean) and then only the selected branch; both branches SHOULD have compatible types, and the result takes the type of the selected branch. The operands of and, or and not MUST be Booleans, and both operands of and and or are type-checked: false and 1 is an error even though false decides the result.

Value Types

Every HEL value is one of: Integer, Float, Boolean, String, Bytes, or Null (an absent optional field), a struct node reached by an accessor, or an array value — an array node reached by an accessor, or an array a function computed. A field's parsed value takes the HEL type implied by its bddo:DataType's bddo:baseType: bddo:baseInteger → Integer, bddo:baseFloat → Float, bddo:baseString → String, bddo:baseBytes → Bytes. This is determined by baseType alone, so the ASCII-coded numeric types bddo:asciiInteger and bddo:asciiDecimal yield Integer and Float respectively and may be used wherever a number is required.

Array Values

An array value is an ordered, finite sequence of HEL values, its elements, indexed from 0. It is one of two kinds. An array node reached by an accessor (a repeated field) is an array value whose elements are its element nodes: the struct nodes of a repeated struct field, or the values of a repeated scalar field. A computed array is an array value a function returns: project, repeatValue, concatArrays, slice of an array, integralScan and patchValues (the quantifiers group). An element of an array value is an Integer, Float, Boolean, String, Bytes, struct node or array value, never Null; the elements of one array need not share a type (project and concatArrays may mix them, and may nest arrays), and nothing checks them when the array is made: each use checks the elements it reads, and an element of the wrong type for that use is a type error. A struct node that is an element of a computed array is that node, not a copy: keys read its fields and sizeof its byte length. Making a computed array copies no bytes and changes no node.

An evaluator MUST support exactly these operations on an array value of either kind: a subscript a[i], under the index rule of key resolution (a non-negative Integer below the length, a range error otherwise); len(a) and count(a), its number of elements; use as the array argument of a function of the quantifiers group; use as an element of a computed array; and use as the argument of a parameter typed bddo:ArrayParameter, which then denotes the same array value, nothing copied (Processing Model, argument types). Array values do not compare: an evaluator MUST raise a type error for ==, != or an ordering with an array value as an operand, of either kind, and for an array value as an operand of an arithmetic, bitwise or logical operator or as a ternary condition; two arrays are compared element by element through the functions (countWhere, all) instead. A Step follows only a root or a name, so a computed array is subscripted where a name reaches it — a local binding, a parameter, or self inside an element-scoped argument whose elements are arrays (all(project(rows, repeatValue(v, 2)), self[0] == self[1])) — and project(rows, v)[0] is a syntax error.

A computed array is not a node of the parsed tree: it has no byte extent and no holder, so an evaluator MUST raise a type error for sizeof of a computed array, and MUST read a .parent step taken on it, or on a subscript of it, as Null, as it reads every .parent after a local binding, self or param (Reserved Roots), never as the struct of some array node the computed array was made from. A scalar element of a computed array is a computed value, for which sizeof follows its rule for a value whose byte span was not recorded; a struct-node element keeps its own place in the tree, so a key step from it, and a .parent after that key, are resolved as for that node. A computed array MUST NOT be the result of a bddo:valueFromExpression, and no array value, of either kind, the result of a hexplain:valueExpression that gives no hexplain:valueDatatype: an evaluator MUST raise a type error for one. A computed array is not a node of the parsed tree, so a derived field cannot hold it; an array node or a struct node reached by an accessor can, and the derived field then names that node, as one of two version-specific repeated fields is unified under one name (toItemIds: derive version == 0 ? toItemIds16 : toItemIds32). A bddo:localExpression may yield an array value of either kind; the binding then names that array value.

Type Coercion & Comparison Rules

These rules are normative and resolve the comparisons used throughout Hexplain (e.g. comparing a 4-byte ChunkType to 'IHDR'):

  • Arithmetic / bitwise operands MUST be numeric. Mixing Integer and Float promotes to Float. Bitwise operators require Integer operands. A non-numeric operand, including Null, is an error.
  • Integer vs. Float compares by numeric value. Integer comparisons MUST be exact; mixed comparisons compare the exact represented numeric values without first rounding the Integer to Float.
  • NaN. == with a NaN operand is false (so NaN == NaN is false), != with a NaN operand is true, and every ordered comparison (< <= > >=) involving NaN is false. Infinities order as usual.
  • String vs. String compares by Unicode code point; < > <= >= use code-point order.
  • Bytes vs. String. For == and !=, when one operand is Bytes and the other a String, the Bytes value is decoded to a String using the field's bddo:encoding (default bddo:utf8) by the Processing Model's text-decoding rule, and equality holds iff the decoded strings are code-point-identical. A Bytes value that is not well-formed in its encoding decodes to no String: it is never replaced by U+FFFD, it equals no String (== is false and != is true), and where a String is required it is an error. Ordering a Bytes value against a String is an error.
  • Bytes vs. Bytes is equal iff the byte sequences are identical; ordering two Bytes values is an error.
  • Boolean vs. Boolean may be compared with == and !=; ordering Booleans is an error.
  • Null. An access to an absent optional field yields Null. Null == Null is true and Null == x is false for any other x. Every other comparison with a Null operand is false — including !=: Null != 1 and Null != Null are both false, so for an optional field x != 1 is not the same as not (x == 1). Arithmetic, bitwise and logical operators, the ternary condition, and function arguments do not accept Null: each is an error.
  • Comparing values of otherwise incompatible types (e.g. Boolean vs. Integer, String vs. Integer, or a struct node or an array value) is an error.

Conformance

A conforming HEL 1.0 evaluator MUST:

  1. Parse all valid expressions per the ABNF grammar, and reject as a syntax error every string it does not generate, including out-of-range literals and unknown escapes.
  2. Implement the parsing context, the reserved roots (instance, parent, root, self, stream, asset, param, repeat) and the name-binding table. A processor that does not parse multi-part assets MAY leave asset and partExtension unimplemented, but MUST then raise a runtime error on an expression that uses them rather than resolving them to Null.
  3. Implement all operators and every core function with the specified precedence, the numeric semantics, and the value-type and coercion rules; and implement each extension group it claims in full.
  4. Reject, at load time, a description that calls a function of an extension group it does not implement, with an unsupported-feature error.
  5. Yield a Boolean in a boolean context, an Integer in a numeric context and a String in a string context, as the name-binding table gives for each property (e.g. a hexplain:valueExpression whose hexplain:valueDatatype is xsd:string yields a String); any other result is an error, and a Float is never an Integer, even one whose value is integral: a size expression that yields 2.0 is an error, not a size of 2.
  6. Report a runtime error (rather than silently continue) on type errors, integer overflow, shift counts out of range, out-of-range unsigned values, division/modulo by zero, out-of-range subscripts, undefined names and forward references.
  7. Accept, by default, expressions whose expression tree is at least 512 levels deep and at least 64 KiB long, when they are parsed and when they are evaluated, and element (quantifier) and match-cost budgets of at least the Processing Model’s minimums; let the user configure all four limits; and report an expression beyond its configured nesting or length limit, a charge beyond its element budget, a regular-expression match that exceeds its cost limit, and a deadline or cancellation as the Processing Model's ResourceLimit error, not as a syntax or runtime error: it is fatal in every mode, including a lenient one that records other errors and continues (Security and Privacy Considerations).
  8. Produce, for every row of hel-vectors.tsv whose functions it implements, the value the row gives — of the type the row states, where its expectation is typed (int:3, float:2) — or an error of the condition the row names; a row's message column is informative.

Canonical Form

Two HEL strings are equivalent when they parse to the same expression tree once a bare name x is read as instance.x, a hexadecimal literal as the Integer it denotes and a Float literal as the binary64 value it denotes; whitespace, redundant parentheses and the spelling of a literal do not matter. The conformance suite compares HEL-bearing literals by this equivalence. The canonical form is one spelling of each class, the one the reference implementation's serializer writes and the HDL compiler emits:

  • An accessor starts with its root, so a bare name is written instance.x; key steps are .name and subscripts [e], with no spaces.
  • An Integer literal is written in decimal (a hexadecimal literal becomes decimal); a Float literal as the shortest decimal that denotes the same binary64 value, with a . and at least one fraction digit when its magnitude is at least 10−3 and below 107, and otherwise as a mantissa with a fraction, E and a signed-if-negative exponent (1.0E7, 1.0E-4); Booleans are true and false.
  • A string literal is single-quoted; \ and ' are written \\ and \', the control characters U+0000–U+0008, U+000B, U+000C, U+000E–U+001F and U+007F as \xHH with upper-case hex digits, and every other character, tab, line feed and carriage return included, as itself.
  • A binary operation is written l op r with single spaces, and an operand that is itself a binary operation or a ternary is parenthesised, whatever the precedences: a + b + c becomes (instance.a + instance.b) + instance.c.
  • A unary operation is -e, ~e or not e, its operand parenthesised when it is a binary operation or a ternary.
  • A call is name(a, b); a ternary is c ? t : e, its condition parenthesised when it is itself a ternary.

So Flags&0x01==1 and not(done) has the canonical form ((instance.Flags & 1) == 1) and not instance.done.
