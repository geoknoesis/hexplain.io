This document defines how the Hexplain vocabulary family is decomposed into modules. It replaces file-type-centric grouping with an aspect-oriented decomposition: cross-cutting concerns (codec, colour, time, spatial reference, provenance…) are defined once as orthogonal aspect ontologies, and each format/domain vocabulary is a thin composition that imports the aspects it exhibits and adds only its genuinely-unique terms. The goal is maximum reusability and orthogonality — every term has exactly one home, and adding a new data paradigm never forces a reorganization of existing modules.

Unofficial draft for defining the Hexplain standard; no official standing. This is a normative architecture and a refactoring roadmap; individual aspect and domain ontologies are published as their own artifacts under aspect/ and the domain paths.

1. Motivation

The original domain vocabularies were carved by file type (image / video / audio / geo), but the concepts they carry are properties of intrinsic aspects of data that cut across file types. colorSpace belongs to any raster or vector-styled content (image, video, geo-raster); codec belongs to any encoded stream (audio, video, compressed image); duration belongs to any timeline (audio, video). When modules are partitioned by file type, every cross-cutting concept has an ambiguous home and is either duplicated or forced into a "shared" grab-bag.

Two symptoms made this concrete: colorSpace was defined in both the image and video vocabularies; and an interim "Media Vocabulary" whose membership rule was "terms shared by audio ∩ video" ended up bundling two unrelated concerns (visual colour and stream/time). A set-intersection of domains is not a concern. Meanwhile the Geospatial Vocabulary fuses five concerns in one module (spatial reference, raster georeferencing, point-cloud geometry, sensor/acquisition provenance, and even a security marking, then called classificationLevel) — the same disease at a larger scale. Tellingly, the layout layer already models data as a composition of independent axes (dlv:axisX, axisTime, axisBand, …); the semantic layer should adopt the same facet discipline.

2. Principles

Invariant. Every term has exactly one home = its aspect. Aspects never import siblings; imports point only downward to base aspects. A domain/format is a composition — import(aspects) + only-its-unique terms.

  1. One concept, one home. A property is defined in exactly one module. Two domains needing it ⇒ it belongs to a more general module both import — never copied.
  2. Modules are aspects (facets), not file types. Each semantic module models one coherent, format-independent concern.
  3. Aspects are mutually independent. Aspect modules import nothing from each other. Orthogonality = zero sideways coupling. The only permitted imports are downward, to a small set of base aspects.
  4. Domains are thin compositions. "Video" = import(raster) + import(time) + import(encoding) + a few video-only terms. A format is a boolean AND of aspects; hybrids (a GeoPDF = raster ∧ vector) need no special module.
  5. Registers are decoupled data. A register is governed and versioned on its own, and an aspect does not reference it: hx-security defines what a security marking HAS, while a register supplies one set of values it may take. The binding is declared per profile with hexplain:usesRegister, which is what lets a profile using a different classification system bind a different register without touching the aspect. That absence of a reference is the whole mechanism, so it is checked in both directions by tools/test_vocab_neutrality.py.
  6. Normative vocabularies name no format. BDDO, DLV, core and every aspect describe any format; a profile describes one. The moment a term like bddo:nitfSecurityBlock exists, BDDO has stopped being a byte vocabulary and become NITF's. Naming a format in a comment is the opposite — that is the evidence a term is needed, and is encouraged. An ALGORITHM named for its specifying document (crc32, sqliteVarint) is not a violation: it is a general encoding that happens to be specified somewhere. The same gate enforces this, with every exemption carrying its reason so the judgment can be argued with rather than merely trusted.
  7. Map to external standards at the leaf. Descriptive metadata, provenance, and rights reuse dcterms:, PROV, SOSA/SSN, ODRL directly (with skos:closeMatch/owl:equivalentProperty) rather than minting parallel terms.

hx-security is the worked example of the register mechanism, and of getting it wrong first. Version 1.1 already drew its VALUES from a per-profile register, which looked agnostic — but its property SET was US IC ISM's: declassificationExemption, classificationReason, classificationAuthorityType are categories of one national policy. A system that marks documents differently had to leave them empty and had nowhere to put what it did have. Swappable values on a fixed skeleton is not agnostic. 2.0 keeps only what every system has and routes the rest through one open asec:marking whose value's skos:inScheme identifies the kind, so supporting a system means publishing registers rather than editing the aspect. The lesson generalises: when an aspect enumerates the KINDS of something, check whose taxonomy those kinds came from.

6. The Decision Rule

Home = the most general aspect for which the term is always meaningful.

  1. Meaningful without naming a file format? If no → it is a profile/domain term. If yes → it is an aspect term.
  2. Needed by more than one format? → it must live in the shared aspect, never duplicated.
  3. Value drawn from a governed list? → a SKOS register, defined separately from the property.
  4. Computable/measurable scalar? → a literal + SHACL (e.g. aspectRatio).

If a term seems to belong to two aspect modules, the modules are not orthogonal — split the concern. Extract a shared aspect the moment a second consumer appears (lazy factoring); one-concept-one-home makes the extraction cheap and mechanical.

7. Conventions

7.1 Naming

Aspect ontologies live under https://hexplain.io/ns/aspect/<name># and are labelled hx-<name>. Prefixes carry a leading a to mark the aspect layer and avoid collisions with common prefixes (e.g. time: for OWL-Time): atime, aenc, acolor, araster, ageom, asref, asamp, asig, aprov, asec, …

7.2 Registers

Controlled vocabularies are open skos:ConceptSchemes living under https://hexplain.io/ns/register/<name>#, in specification/register/<name>/. They were originally hosted inside the aspect that referenced them; that split has since happened, moving 111 concepts out of six aspects into standalone registers (us-nato-security, media-encoding, color, checksum, part-role, geometry-type).

Three rules follow, all machine-checked:

  • An aspect declares no skos:Concept of its own — concepts live in a register.
  • An aspect never references a register term. A profile declares the binding with hexplain:usesRegister.
  • A register never references an aspect term. The dependency runs one way, so a register can be reused by a second property and versioned alone.

A register concept carries no skos:notation: a notation is one format's spelling of a concept (NITF's digraphs, a codec's short name), and belongs in the profile's mapping rather than in a format-neutral register.

7.3 Versioning & compatibility

The family is pre-release. Every module is version 1.0 with no prior-version history: terms are defined (or placed during this refactor) directly, with no deprecation, no backward-compatibility layer, and no owl:priorVersion. A compatibility policy will be defined when the first version is released.
