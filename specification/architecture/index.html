This document defines how the Hexplain vocabulary family is decomposed into modules. It replaces file-type-centric grouping with an aspect-oriented decomposition: cross-cutting concerns (codec, colour, time, spatial reference, provenance…) are defined once as orthogonal aspect ontologies, and each format/domain vocabulary is a thin composition that imports the aspects it exhibits and adds only its genuinely-unique terms. The goal is maximum reusability and orthogonality — every term has exactly one home, and adding a new data paradigm never forces a reorganization of existing modules.

Unofficial draft for defining the Hexplain standard; no official standing. This is a normative architecture and a refactoring roadmap; individual aspect and domain ontologies are published as their own artifacts under aspect/ and the domain paths.

1. Motivation

The original domain vocabularies were carved by file type (image / video / audio / geo), but the concepts they carry are properties of intrinsic aspects of data that cut across file types. colorSpace belongs to any raster or vector-styled content (image, video, geo-raster); codec belongs to any encoded stream (audio, video, compressed image); duration belongs to any timeline (audio, video). When modules are partitioned by file type, every cross-cutting concept has an ambiguous home and is either duplicated or forced into a "shared" grab-bag.

Two symptoms made this concrete: colorSpace was defined in both the image and video vocabularies; and an interim "Media Vocabulary" whose membership rule was "terms shared by audio ∩ video" ended up bundling two unrelated concerns (visual colour and stream/time). A set-intersection of domains is not a concern. Meanwhile the Geospatial Vocabulary fuses five concerns in one module (spatial reference, raster georeferencing, point-cloud geometry, sensor/acquisition provenance, and even a security marking, then called classificationLevel) — the same disease at a larger scale. Tellingly, the layout layer already models data as a composition of independent axes (dlv:axisX, axisTime, axisBand, …); the semantic layer should adopt the same facet discipline.

2. Principles

Invariant. Every term has exactly one home = its aspect. Aspects never import siblings; imports point only downward to base aspects. A domain/format is a composition — import(aspects) + only-its-unique terms.

  1. One concept, one home. A property is defined in exactly one module. Two domains needing it ⇒ it belongs to a more general module both import — never copied.
  2. Modules are aspects (facets), not file types. Each semantic module models one coherent, format-independent concern.
  3. Aspects are mutually independent. Aspect modules import nothing from each other. Orthogonality = zero sideways coupling. The only permitted imports are downward, to a small set of base aspects.
  4. Domains are thin compositions. "Video" = import(raster) + import(time) + import(encoding) + a few video-only terms. A format is a boolean AND of aspects; hybrids (a GeoPDF = raster ∧ vector) need no special module.
  5. Registers are decoupled data. A register is governed and versioned on its own, and an aspect does not reference it: hx-security defines what a security marking HAS, while a register supplies one set of values it may take. The binding is declared per profile with hexplain:usesRegister, which is what lets a profile using a different classification system bind a different register without touching the aspect. That absence of a reference is the whole mechanism, so it is checked in both directions by tools/test_vocab_neutrality.py.
  6. Normative vocabularies name no format. BDDO, DLV, core and every aspect describe any format; a profile describes one. The moment a term like bddo:nitfSecurityBlock exists, BDDO has stopped being a byte vocabulary and become NITF's. Naming a format in a comment is the opposite — that is the evidence a term is needed, and is encouraged. An ALGORITHM named for its specifying document (crc32, sqliteVarint) is not a violation: it is a general encoding that happens to be specified somewhere. The same gate enforces this, with every exemption carrying its reason so the judgment can be argued with rather than merely trusted.
  7. Map to external standards at the leaf. Descriptive metadata, provenance, and rights reuse dcterms:, PROV, SOSA/SSN, ODRL directly rather than minting parallel terms. A minted term that is related to an external one links it with rdfs:seeAlso, or with rdfs:subPropertyOf/rdfs:subClassOf when every use entails the external statement; SKOS mapping properties relate concepts only, and no owl:equivalentClass or owl:equivalentProperty is asserted (modeling policy, alignments).

hx-security is the worked example of the register mechanism, and of getting it wrong first. Version 1.1 already drew its VALUES from a per-profile register, which looked agnostic — but its property SET was US IC ISM's: declassificationExemption, classificationReason, classificationAuthorityType are categories of one national policy. A system that marks documents differently had to leave them empty and had nowhere to put what it did have. Swappable values on a fixed skeleton is not agnostic. 2.0 keeps only what every system has and routes the rest through one open asec:marking whose value's skos:inScheme identifies the kind, so supporting a system means publishing registers rather than editing the aspect. The lesson generalises: when an aspect enumerates the KINDS of something, check whose taxonomy those kinds came from.

6. The Decision Rule

Home = the most general aspect for which the term is always meaningful.

  1. Meaningful without naming a file format? If no → it is a profile/domain term. If yes → it is an aspect term.
  2. Needed by more than one format? → it must live in the shared aspect, never duplicated.
  3. Value drawn from a governed list? → a SKOS register, defined separately from the property.
  4. Computable/measurable scalar? → a literal + SHACL (e.g. aspectRatio).

If a term seems to belong to two aspect modules, the modules are not orthogonal — split the concern. Extract a shared aspect the moment a second consumer appears (lazy factoring); one-concept-one-home makes the extraction cheap and mechanical.

7. Conventions

7.1 Naming

Aspect ontologies live under https://hexplain.io/ns/aspect/<name># and are labelled hx-<name>. Prefixes carry a leading a to mark the aspect layer and avoid collisions with common prefixes (e.g. time: for OWL-Time): atime, aenc, acolor, araster, ageom, asref, asamp, asig, aprov, asec, … The one exception is st, the structure aspect's prefix, which has no leading a; a published prefix is not renamed.

7.2 Registers

Controlled vocabularies are open skos:ConceptSchemes living under https://hexplain.io/ns/register/<name>#, in specification/register/<name>/. They were originally hosted inside the aspect that referenced them; that split has since happened, moving 111 concepts out of six aspects into standalone registers (us-nato-security, media-encoding, color, checksum, part-role, geometry-type). A seventh, protection (ciphers, signature and message authentication algorithms, error-correcting codes), was published as a register from the start, beside the hx-protection aspect it serves. A register defines its own concepts: each states its skos:definition in the register file, so the register can be read without the generated annotation graph beside it.

Three rules follow, all machine-checked:

  • An aspect declares no skos:Concept of its own — concepts live in a register.
  • An aspect never references a register term. A profile declares the binding with hexplain:usesRegister.
  • A register never references an aspect term. The dependency runs one way, so a register can be reused by a second property and versioned alone.

A register concept carries no skos:notation: a notation is one format's spelling of a concept (NITF's digraphs, a codec's short name), and belongs in the profile's mapping rather than in a format-neutral register.

7.3 Conformance & portability

Every shape is SHACL Core where SHACL Core can say it, and the family's shapes carry an sh:message at both the property and the node level, so that a result from any conforming validator names what was wanted. Two constructs go beyond SHACL Core, and a consumer choosing a validator should know which: RDF lists as values (bddo:hasField, dlv:hasDimension, every rdf:List-ranged property) are validated through sequence paths over rdf:rest*/rdf:first, which every SHACL Core validator supports but which a plain triple-pattern checker does not; and the family's 84 SHACL-SPARQL constraints (sh:sparql: mutual exclusion of sizing mechanisms, CRC parameter bounds, key uniqueness, path syntax, register membership, the widths a float format exists at) require a validator that implements SHACL-SPARQL, which pySHACL, TopBraid and Jena do and some lightweight validators do not. A processor that validates descriptions with a Core-only validator therefore enforces every cardinality, datatype, class and value-set rule but not the cross-property rules; the Processing Model restates those as load-time checks so that no conforming processor depends on SHACL-SPARQL to refuse a contradictory description. The requirements the shapes stand for are catalogued, one req:Requirement per node shape of every module, in req/requirements.ttl, so a conformance run can cite them; the catalogue is generated from the shapes (tools/_build_shape_requirements.py) and a gate keeps the two in bijection. A result's severity matters: a description is valid when validation yields no result of severity sh:Violation, and the shapes report at sh:Warning what is permitted but worth an author's attention (Validation contracts).

7.4 Versioning & compatibility

The family is pre-release, but it is versioned: local release snapshots are recorded under releases/, and a module whose canonical Turtle changes after a snapshot gets a new owl:versionIRI (https://hexplain.io/ns/<module>/<major>.<minor>, matching owl:versionInfo), an owl:priorVersion naming the snapshot's version and a dcterms:modified date. Namespace IRIs do not change. Removed or renamed terms are not silently dropped: a term that existing descriptions or processors still use is kept with owl:deprecated true and, where one exists, dcterms:isReplacedBy its successor (for example the pre-release bddo:hasEndianness and the media-specific DLV axes). Module versions, page subtitles and Turtle header comments are checked against each other by tools/test_html_sync.py; the change history is in CHANGELOG.md. Stricter shapes are validation-compatibility changes and are listed there too.

9. Not yet modelled

Concerns the review of the family identified and that no module yet covers, listed so that a profile author knows what cannot be described and a future revision knows where to start. Each would be an aspect or a BDDO extension in its own right; none is implied by a term that exists today.

  • Decryption, signature verification and error correction as processing. hx-protection describes that a field or struct is encrypted (aprot:EncryptedRegion), that a field carries a signature or authentication tag over a byte range (aprot:Signature) and that a range is protected by an error-correcting code (aprot:ErrorCorrection), with the algorithm as a register concept. It defines no processing: no pipeline step decrypts, no key is supplied or located, no signature is verified and no error is corrected, and a processor reads protected bytes as the bytes their fields declare. Those semantics (where a key comes from, what a failed verification is, how corrected data re-enters the parse) are an optional feature a later version may define.
  • A HEL offsetof. A field can now be placed relative to an earlier sibling (bddo:offsetBase bddo:fieldStart with bddo:offsetBaseField), but HEL still has no primitive returning the byte offset at which a named field was read, so an expression cannot compute with that offset. That is a HEL change, outside this vocabulary revision.
  • Rights and descriptive metadata aspects (hx-rights, hx-descriptive, hx-style in the catalogue above) remain planned reuses of ODRL and Dublin Core rather than modules.

Modelled in this revision, and therefore no longer gaps: protection metadata (the hx-protection aspect and its register), offsets relative to a sibling field (bddo:fieldStart), struct-level alignment and padding (bddo:alignment, bddo:padTo, bddo:padByte) with a selectable origin (bddo:alignmentOrigin), non-IEEE floating-point formats (bddo:floatFormat, with the three VAX formats named separately), fixed-point scaling (bddo:fixedPointScale) and binary-coded decimal (bddo:bcd), an open character-encoding set (bddo:CustomEncoding), the expression form of every DLV sizing triad, and a field-level bddo:bitOrder.
