The Hexplain Processing Model defines, normatively, how a conforming processor turns a binary stream plus a Hexplain description (BDDO + Core + domain vocabularies) into two outputs: a transient parsing context and a persistent RDF instance graph. It specifies the parse algorithm, the construction of the HEL context, the minting of instance IRIs, the mapping of primitive values to RDF literals, the emission of semantic triples, and error handling. This document makes Hexplain descriptions executable and reproducible across implementations.

This document is an unofficial draft produced for the purpose of defining the Hexplain standard. It has no official standing and is not endorsed by any standards body. It is a prerelease working draft: the processing rules below are normative for the current Hexplain toolchain, but they may still change incompatibly before a stable release.

Introduction

The other Hexplain specifications define vocabulary; this one defines behaviour. Without a shared processing model, two implementations could parse the same file against the same description and emit different graphs, defeating the interoperability and SPARQL-query goals of the framework. Everything here is REQUIRED behaviour for a conforming processor unless marked otherwise.

Conformance

The key words "MUST", "MUST NOT", "REQUIRED", "SHALL", "SHALL NOT", "SHOULD", "SHOULD NOT", "RECOMMENDED", "MAY", and "OPTIONAL" in this document are to be interpreted as described in [[RFC2119]].

A conforming processor implements one or more of the conformance classes below, and states which. It MUST implement every rule of this document that the classes it claims require, and it MUST NOT silently mis-parse a description that uses a construct outside them (see ).

The processor conformance suite makes this document executable: every requirement sentence carries a stable identifier (for example req-pm-parsestruct-1), and each case cites the identifiers and sections its expected output is read from.

Conformance Classes

Hexplain is used by tools with different jobs: a validator needs only the physical parse, a catalogue needs the RDF, an archive tool needs whole multi-part assets, an authoring tool needs the HDL compiler. Requiring every tool to implement everything would make most of them non-conforming, so conformance is divided into five classes. A processor claims one or more of them; the classes are cumulative only where stated.

ClassJobConstructs it MUST support

Every physical construct of BDDO: structs, fields, bounded regions, addressing, repetition, dispatch tables and conditional data types, bit fields, byte order (), size resolution and terminators (), text numbers, delimited records and tables (including a flat whitespace-separated value sequence with no record delimiter) and flat key/value headers (), fixed values, enumerations, checksums, bddo:validIf, bddo:valueFromExpression, bddo:rootKeyFromField; the DLV layout constructs (dimensions, literal and field-supplied sizes and strides, conditional cell types and dimension orders, packed cells) as described in ; HEL evaluation (HEL) except the asset root and partExtension(); hexplain:isEncodedWith for at least the minimum codec set; and the resource limits.
Semantic Emitter Lifts a logical tree to an RDF instance graph. Requires Physical Parser. The Hexplain Core mapping properties (): hexplain:mapsToClass, hexplain:hasConditionalClassMapping, hexplain:mapsToProperty, hexplain:mapsToObjectProperty, hexplain:hasConditionalMapping, hexplain:valueExpression / hexplain:valueDatatype, units and language tags; the literal mapping (); and IRI minting ().

The bundle aspect (abnd:BundleProfile, abnd:PartSpec, abnd:extension, abnd:pathPattern, abnd:required, abnd:minParts, abnd:maxParts, abnd:primary, abnd:describedBy, abnd:partRole, abnd:carriesAspect, and the lifting rule); assembly, the HEL asset root and partExtension(), and part ordering (). abnd:nestedProfile is optional in this version: a Bundle Processor that does not assemble nested profiles MUST reject a bundle profile that uses one with Unsupported feature.

A processor MAY refuse a description, by raising an Unsupported feature error, only when the description uses either (a) a construct outside the conformance classes it claims, or (b) one of the optional features in the closed list below that it does not claim. Refusing, or failing to execute, any other construct of a class it claims is non-conformance, not an Unsupported feature. A refusal SHOULD be raised when the description is loaded rather than when the construct is first met in a stream, and MUST be raised no later than the first time the construct would affect the result. A processor MUST NOT ignore a construct and parse on as though it were absent: a partly understood description yields a plausible but wrong tree, which is worse than no tree.

The optional features (a closed list; no other construct of a claimed class is optional). Each has a feature token, the name by which a processor's claims, a conformance suite manifest and a report of an unsupported feature refer to it:

  • tree-documents — Tree documents: bddo:TreeDocument with bddo:treeSyntax, bddo:nodePath and bddo:hasNamespaceBinding ().
  • grouped-headers — Grouped key/value headers: bddo:hasGrouping with bddo:groupingStyle and bddo:keyPath ().
  • nested-profiles — Nested bundle profiles: abnd:nestedProfile ().
  • chunked-cell-access — Chunked-layout cell access: addressing a cell through dlv:chunkSize, dlv:chunkSizeFromField, dlv:chunkOffsetsFromField, dlv:chunkLengthsFromField and dlv:chunkOffsetBase (see below).
  • chunk-order-other — Chunk orders other than row- and column-major: a dlv:chunkOrder other than dlv:rowMajor or dlv:columnMajor.
  • hel-ext-text — the HEL extension group text.
  • hel-ext-temporal — the HEL extension group temporal.
  • hel-ext-quantifier — the HEL extension group quantifiers.
  • hel-ext-geometry — the HEL extension group geometry.
  • hel-ext-register — the HEL extension group register.
  • codecs-beyond-minimum — Codecs beyond the minimum set: a hexplain:isEncodedWith or encoding-step codec that is not in the minimum codec set.

Each HEL extension group is its own optional feature, implemented all or nothing (HEL, extension groups). The tokens are case-sensitive and are never translated: a processor that states its claims in a file or a report names each feature by its token.

A processor MUST state which classes and which optional features it claims. Tree documents and grouped key/value headers are no class's requirement: a processor that claims them MUST implement them exactly as specifies, and one that does not MUST reject a description that uses them, when the description is loaded, and MUST NOT read such a container's fields by byte offset or as a flat header. A processor that claims tree documents MAY still reject, with Unsupported feature, a construct this document does not define for a field located by path: a byte-level clause (a size, terminator, offset, bit length, alignment, fixed value, checksum, encoding, data layout or repeat-until condition), a conditional or dispatched data type, or a data type that is a struct but not a bddo:TreeDocument of the same syntax.

Informative: the reference implementation (hexplain-tools) claims the Physical Parser, Semantic Emitter, Bundle Processor, HDL Compiler and Conformance Evaluator classes and the optional features tree-documents, grouped-headers, hel-ext-text, hel-ext-temporal, hel-ext-quantifier, hel-ext-geometry, hel-ext-register; it does not implement nested-profiles, chunked-cell-access, chunk-order-other, codecs-beyond-minimum, and refuses them with Unsupported feature. Its full capability statement — classes, optional features, the codecs it decodes and its default resource limits — is the machine-readable reference-engine-claims.json, which this note restates and which the engine's README mirrors.

Chunked layouts. A Physical Parser MUST accept a description that declares a chunked layout and parse the field's bytes. A processor that does not claim chunked-layout cell access MUST raise Unsupported feature when a cell is addressed through the chunk table and MUST NOT address the bytes as contiguous cells; one that does not claim other chunk orders MUST reject a dlv:chunkOrder other than dlv:rowMajor or dlv:columnMajor when the description is loaded.

Codecs

hexplain:isEncodedWith names a concept from a codec or compression register. A processor MUST decode every registered codec it claims to support, MUST state which ones those are, and MUST raise Unsupported feature for any other. Every Physical Parser MUST support at least these concepts of the media-encoding register:

ConceptDecoding
menc:StoreIdentity: the decoded bytes are the stored bytes.
menc:DeflateRaw DEFLATE [[RFC1951]], no framing.
menc:Zlibzlib framing [[RFC1950]] around DEFLATE, including its header and Adler-32 check; an Adler-32 mismatch is a Checksum error.
menc:Gzipgzip framing [[RFC1952]]. A block MAY hold several gzip members; they are decoded in order and their outputs concatenated. A member's CRC-32 or length (ISIZE) mismatch, or a header CRC-16 mismatch, is a Checksum error. Bytes after the last member that do not begin another member are a Validation error.
menc:DeltaDelta / horizontal predictor, with the parameters below: each sample is restored by adding the restored sample that precedes it in the same channel.

Delta parameters. A codec's parameters are the hexplain:codecParameter nodes of its hexplain:EncodingStep (hexplain:parameterName, and an integer hexplain:parameterValue). menc:Delta takes exactly these; any other parameter name, a missing required parameter, or a value outside its range is a Description error.

ParameterValuesMeaning
elementSizeREQUIRED: 1, 2, 4 or 8Bytes per sample. Arithmetic is modulo 28×elementSize.
littleEndian0 (default) or 1Byte order of a sample wider than one byte: 0 big-endian, 1 little-endian.
samplesPerPixel≥ 1, default 1Interleaved samples per pixel. A sample is predicted from the sample samplesPerPixel positions earlier — the same channel of the previous pixel — as TIFF Predictor 2 does for chunky data.
rowBytes0 (default) or a positive multiple of elementSize × samplesPerPixelBytes per row. The predictor restarts at each row: the first pixel of every row is stored as is. 0 means the whole block is one row.
predictor2 (default) or 12: horizontal differencing, as above. 1: no prediction; the stage is the identity. Other values (for example TIFF's floating-point predictor 3) are not defined by this version: a processor MUST refuse them with Unsupported feature.

Decoding: within each row, for each sample position i from elementSize × samplesPerPixel bytes after the row start, in increasing order, out[i] = (out[i − elementSize × samplesPerPixel] + in[i]) mod 28×elementSize, each sample read and written in the stated byte order. A block whose length is not a whole number of samples is a Validation error; a last row shorter than rowBytes is decoded as far as it goes.

A processor MUST report compressed data that cannot be decoded (truncated, malformed, needing a preset dictionary, or followed by trailing bytes inside a zlib or raw DEFLATE block) as a Validation error. When a field lists several encodings they were applied in list order when the data was written, so they are decoded in reverse list order. Every intermediate and final decoded output counts toward the decoded-byte limit ().

Inputs and Outputs

Inputs
(1) a byte stream S with known length |S|; (2) a Hexplain description graph D; (3) a designated root Struct R in D; (4) an optional base IRI B for minting instance IRIs.
Outputs
(1) the parsing context C (transient, used by HEL); (2) the instance graph G (RDF, persistent). A processor MAY expose either or both.

Parse Algorithm

Parsing maintains a cursor (byte position, initially 0) and a bit cursor for bit-level fields. To parse the root, invoke ParseStruct(R, cursor=0, parent=nil).

ParseStruct(struct, cursor, parent)

A Physical Parser MUST parse a struct by these steps, in this order:

  1. If struct has bddo:syncOnMarker, advance the cursor past the next occurrence of the marker bytes: the marker is consumed, and the struct (its start offset and its first field) begins after it. If no occurrence exists, raise a sync error.
  2. Create a new context node n with a back-link to parent; record its start offset.
  3. Bounded region. If struct declares a size (bddo:size / bddo:sizeFromField / bddo:sizeFromExpression), it establishes a bounded region [start, start+size). A read by this struct or any descendant that would cross the region end raises a bounds error, and a descendant's bddo:sizeToEndOfStream resolves to the region end (not |S|). This is what lets length-delimited containers (ISOBMFF/MP4 boxes, EBML, chunk payloads) bound their children. A literal bddo:size establishes the region before the first field is read; a bddo:sizeFromField or bddo:sizeFromExpression establishes it as soon as every field it references is bound (). A region whose end would lie beyond the enclosing region, or a negative size, raises a bounds error.
  4. Resolve the effective byte order and bit order (). The byte order declared by an ancestor struct is inherited, which is what "nearest declaration wins" means: DataType > Field > this Struct (fixed or conditional) > inherited from the enclosing struct > big-endian.
  5. If struct is a bddo:DelimitedRecords (or subclass) or a bddo:TreeDocument, parse it by the container rules of instead of the next step, then continue at the last step.
  6. For each field in the bddo:hasField list, in order, call ParseField(field, n). Members MUST be processed in list order. When struct declares the deprecated bddo:usesStruct T, the fields of T are processed first, then the struct's own fields, as one list.
  7. If struct declared a size, advance the cursor to start+size (skipping any trailing padding/unknown bytes); otherwise the end offset is the current cursor. Record the node's end offset (sizeof = end − start) and return n.

ParseField(field, node)

A Physical Parser MUST parse a field by these steps, in this order; a step whose property the field does not declare does nothing:

  1. Presence. If bddo:isPresentIf is present and its HEL expression evaluates to false, skip the field (bind it to Null in the context) and return.
  2. Derived value. If bddo:valueFromExpression E is present, evaluate E in the field's context (), bind the result under the field's key, and return. The field consumes no bytes and has no byte extent; none of the steps below apply to it. A Null result leaves the field unbound, exactly as an absent optional field.
  3. Alignment. If bddo:alignment = a, advance the cursor to the next multiple of a, measured from the start of the current stream: the input stream, or, inside a field decoded by hexplain:isEncodedWith and re-parsed as a struct, the decoded sub-stream, whose offsets start at 0 (Stream metadata). Bounded regions do not move the origin: a field aligned to 4 inside a region starting at offset 6 starts at offset 8, not 10. The same origin applies to an offset-addressed field's aligned target.
  4. Addressing. If an offset property is present, compute the target offset from bddo:atOffset / atOffsetFromField / atOffsetFromExpression, relative to bddo:offsetBase: streamStart (the default) counts from the start of the current stream, streamEnd counts backward from |S|, the length of the current stream, and currentPosition from the cursor. The current stream is the input stream or, inside a field decoded by hexplain:isEncodedWith and re-parsed as a struct, the decoded sub-stream (Stream metadata); a bounded region is not a stream, so streamEnd inside one still counts from the end of the stream that holds it. Save the current cursor — the byte position and any partially consumed byte of the bit cursor — seek to the target, parse, then restore the saved cursor, bit position included (an offset field does not advance sibling parsing and does not disturb a run of bit fields) unless offsetBase is currentPosition. A target outside the innermost bounded region raises a bounds error, unless the field declares bddo:seekScope bddo:streamScope: then the target is resolved against the whole stream [0, |S|) and the region bound is suspended for the duration of this one read (and restored before the cursor is).
  5. Repetition. If a repetition property is present, determine the iteration policy: a fixed bddo:repeatCount, a count via repeatCountFromField/repeatCountFromExpression, or repeat-until (bddo:repeatUntil, evaluated after each element with the bindings of ). A bddo:repeatUntil on a field whose data type is a text container () is a description error: the container consumes its whole region, so no element could follow the first. Produce an ordered array node; each element is parsed by the single-value procedure below, and the fixed-value, enumeration and bddo:validIf steps apply to each element, self being the element.
  6. Type selection. If bddo:hasDispatchTable is present, a processor MUST evaluate the table's key — the parsed value of bddo:dispatchOnField, or bddo:dispatchOnExpression evaluated exactly as a bddo:DataTypeRule condition is — and select the bddo:DispatchArm of that table whose bddo:armKey equals it (strings by code points, integers numerically); if none matches, it uses bddo:dispatchDefault, else bddo:dataType. A processor MUST collect arms from the whole description graph, including imported ontologies; two arms with one key are a description error. Otherwise, if bddo:hasConditionalDataType is present, a processor MUST evaluate each bddo:DataTypeRule in list order and take the effective type from the first whose bddo:condition is true, via its bddo:ruleDataType. Otherwise it uses bddo:dataType. When none of these yields a type the processor raises a dispatch error; a field that declares both selection mechanisms is a description error ().
  7. Value. If the effective type is a bddo:Struct, recurse via ParseStruct. If it is a bddo:DataType:
    • Determine the field's extent by the single rule of .
    • If bddo:bitLength is present, read that many bits per the bit-cursor rules () instead of whole bytes.
    • Decode the raw bytes to a typed value per , honouring the byte order of and (for strings) bddo:encoding. For a fixed-size bddo:string with bddo:trimNull true, the value is the characters before the first NUL code unit of the field's bddo:encoding within the field's width: the first 0x00 byte for a single-byte encoding or UTF-8, the first 00 00 pair at an even offset for bddo:utf16le and bddo:utf16be (a zero byte inside a UTF-16 code unit does not end the string). This is how NUL-padded names (TAR, ZIP) are read.
  8. Fixed value. If bddo:hasFixedValue is present and the field's value differs from it, raise a validation error. The fixed value's literal decides what is compared. Only an xsd:hexBinary literal denotes bytes: on a bytes or string field a processor MUST compare it with the field's raw bytes, byte for byte, and on a numeric field it is the field's encoding in the field's byte order and MUST be exactly the field's width. Every other string literal (an xsd:string, a plain or a language-tagged literal) denotes characters, never hexadecimal digits: on a bytes field a processor MUST compare the field's bytes with the literal's UTF-8 encoding, so "CAFE" matches the four bytes 43 41 46 45 and not CA FE, and on a string field it MUST compare the decoded value with the literal by code points, whatever the field's bddo:encoding (a bddo:utf16le field holding 41 00 42 00 matches "AB"). A numeric literal on a numeric field MUST be compared by value at the field's width: an integer field matches an integer literal of equal value however the literal is typed and the field stored ("9994"^^xsd:int matches the integer 9994), and a float field matches the literal's value rounded to the field's format, so "0.1"^^xsd:double on a bddo:float32 field matches the float32 nearest to 0.1. A processor MUST raise a description error, when the description is loaded, for an xsd:hexBinary of another width on a numeric field, a string or Boolean literal on a numeric field, a numeric or Boolean literal on a string or bytes field, a fraction on an integer field, an integer outside the field's range, and a finite value that overflows a float field's format.
  9. Enumeration. If bddo:enumeration is present, look up the raw value among the enumeration's bddo:EnumValue resources; the matching symbol/label is attached to the value node (and emitted per ). If the enumeration has bddo:enumIsFlags true, the raw value is a bitmask: every bddo:EnumValue whose raw value's bits are all set in the parsed value matches, and all matching symbols are attached/emitted.
  10. Checksum. If bddo:checksum is present, compute the algorithm over the covered byte range — from the first byte of coversFromField, or the offset coversFromExpression yields, to the last byte of coversToField (inclusive), or up to and excluding the offset coversToExpression yields (the two bounds may mix a field and an expression); or the [start, end) range yielded by the deprecated coversExpression — and compare with the stored value; a mismatch raises a checksum error. A coverage bound outside the current (sub-)stream raises a bounds error; a range whose end precedes its start covers nothing and is not checked. The bddo:checksumAlgorithm values are bddo:crc32 (CRC-32 as in zlib), bddo:adler32, bddo:crc16 (CRC-16/CCITT-FALSE: polynomial 0x1021, initial value 0xFFFF), bddo:md5, bddo:sha1 and bddo:sha256; an integer checksum is compared numerically, a digest byte for byte.
  11. Constraint. If bddo:validIf E is present, evaluate E once the field is bound (after the fixed-value and checksum checks), with self bound to the field's value (). false raises a validation error; an evaluation failure raises a Type / HEL error, not a validation error, because it reports a defect of the description rather than of the data.
  12. Root key. If bddo:rootKeyFromField is present, let k be the parsed value of the named sibling field; if k is a string and the root context has no binding for k, bind this field's value in the root context under k (first occurrence wins). This is what lets a later field say root.k.… about a record inside a repeated sequence.
  13. Bind the field's value into node under the field's simple key, and return.

Conflicting forms. Where a description gives one construct two forms, this document orders them only for the extent of a field (): of the four region forms the first in the order stated there decides, and declaring several is not an error. Every other pair has no order, and a processor that picked one would parse the other description's meaning as silently as a wrong guess. A processor MUST raise a description error, when the description is loaded, for each of these:

  • A repeat count and a repeat-until condition on one field: any of bddo:repeatCount, bddo:repeatCountFromField and bddo:repeatCountFromExpression together with bddo:repeatUntil, or two of the three count forms.
  • Two offset forms on one field: two of bddo:atOffset, bddo:atOffsetFromField and bddo:atOffsetFromExpression.
  • A dispatch table and conditional type rules on one field: bddo:hasDispatchTable together with bddo:hasConditionalDataType.
  • More than one value of a functional property on one resource: a property the family's vocabularies or shapes allow at most once (for example two bddo:dataType, two bddo:size, two bddo:endianness or two bddo:hasFixedValue values on one field).

Bit-level fields (the bit cursor)

Bit-level fields (bddo:bitLength) are read through a bit cursor that tracks the current byte offset and a bit offset within it (0–7). A Physical Parser MUST move the bit cursor by these rules:

  1. Consecutive bddo:bitLength fields pack contiguously: each consumes the next bitLength bits from the current bit offset, advancing the cursor (rolling into the next byte when it reaches 8).
  2. Bits are consumed within each byte per the effective bddo:bitOrder: bddo:MSBFirst takes bits from the most-significant end first; bddo:LSBFirst from the least-significant end.
  3. Every bit keeps its significance: under bddo:MSBFirst the first bit taken is the most significant bit of the field's value, under bddo:LSBFirst the least significant (as DEFLATE and GIF read their codes), so a 3-bit field read LSBFirst from 0xB4 is 4, the low three bits' value. A field spanning a byte boundary continues into the next byte in the same bit order, its later bits more significant under LSBFirst and less significant under MSBFirst.
  4. The bit cursor realigns to the next whole byte boundary before any byte-oriented read (a field without bitLength), before bddo:alignment, and at the end of a Struct; partial bits before the boundary are skipped.
  5. A bit read that would cross the end of the innermost bounded region (or |S|) raises a bounds error.

This makes sub-byte structures (IPv4 version/IHL, TCP data-offset + flags, PNG bit-packed samples) parse identically across implementations.

Size resolution

A field's extent is decided by exactly one rule. A Physical Parser MUST take the first of these cases that matches, and MUST NOT consult the later ones:

  1. Bits. A field with bddo:bitLength occupies that many bits (, bit cursor).
  2. Separated. A field with bddo:separatedBy is read as a separated token (). The bddo:FieldShape forbids combining it with any size or terminator.
  3. Fixed width. A field whose effective data type has a bddo:bitWidth occupies bitWidth / 8 bytes. Size properties on such a field do not change its width and are ignored.
  4. Self-delimiting. A variable-length integer (bddo:varuint, bddo:varint, bddo:sqliteVarint) occupies as many bytes as its encoding says ().
  5. Declared region and terminator. Otherwise (bytes, string, numbers written as text, and fields whose type is a Struct), the field's declared region is given by the first of these that the field declares: bddo:sizeToEndOfStream (up to the end of the innermost bounded region, or of the current stream if there is none), bddo:size, bddo:sizeFromField, bddo:sizeFromExpression. The region starts at the cursor.
    • With no bddo:terminator, the value is the declared region's bytes.
    • With a bddo:terminator, the value is found by the terminator rule below; the search is bounded by the declared region if there is one, else by the innermost enclosing bounded region (or the end of the current stream).
    • With neither a declared region nor a terminator, a field whose type is a Struct is sized by its own fields (and its own struct-level size, if any); any other field is a description error.

The bddo:FieldShape does not forbid declaring more than one of the four region forms, so the order above is normative. A description SHOULD declare at most one.

A declared region acts as a bounded region for everything read inside it: a nested struct cannot read past it, and after the field is read the cursor moves to the region's end whatever was consumed inside. A region that is negative or extends past the enclosing region raises a bounds error. bddo:sizeFromField names a field that is already bound: it is looked up in the containing struct first, then in its parent. Its value, or the value of bddo:sizeFromExpression, MUST be an integer; a number written as text is accepted by its numeric value.

Repetition. A processor MUST read a repeated field's extent as follows. With bddo:repeatCount (or repeatCountFromField / repeatCountFromExpression) the rule above gives the extent of each element. With bddo:repeatUntil a declared region bounds the whole sequence: elements are read until repeatUntil holds or the region is exhausted, and the cursor then moves to the region end. For a repeatUntil sequence only, a negative declared size means an empty sequence rather than an error, which is how formats write an absent area as a length of zero minus a header. A repeat count MUST be a non-negative integer; a negative count is a bounds error, as a negative size is. A sequence element that consumes no bytes and does not satisfy repeatUntil raises a bounds error rather than looping.

Terminators

A Physical Parser MUST read a field that declares bddo:terminator by these rules:

  1. The terminator is the byte sequence given by bddo:terminator; an empty terminator is a description error.
  2. The search starts at the cursor and finds the first occurrence of the sequence that lies entirely within the search bound. For a bddo:string whose bddo:encoding has a multi-byte code unit (bddo:utf16le, bddo:utf16be), only occurrences that start at an offset from the search start that is a multiple of the code-unit size (2) count, so a terminator can never match across two code units. For every other encoding and for bytes the search is byte-aligned.
  3. The value is the bytes from the search start up to, and excluding, the terminator. The terminator is consumed: it is part of the field's byte extent but not of its value.
  4. With a declared region, the cursor then moves to the end of the region (the bytes after the terminator are padding); without one, the cursor moves to just after the terminator.
  5. If no occurrence lies within the search bound, raise a bounds error.

Struct-level size

A processor MUST apply a struct-level size as this section states. A struct-level bddo:size, bddo:sizeFromField or bddo:sizeFromExpression gives the size of the struct's bounded region, which starts at the struct's start offset (after any bddo:syncOnMarker seek). A literal size is applied before the first field is read. A field-supplied or computed size is evaluated once every field of this struct that it references is bound — that is, immediately after the last such field in declaration order is parsed — and the region is applied from that moment on. Fields of ancestor structs are already bound and may be referenced freely.

  • The size MUST NOT reference a field of this struct that has not been bound when the struct's field list is exhausted (a field declared later than every field that could supply it, or one skipped by bddo:isPresentIf): that is a forward reference and raises a Type / HEL error. The struct MUST NOT be left unbounded instead.
  • If, when the region is applied, the cursor already lies beyond its end, raise a bounds error.
  • The expression is evaluated with the struct as instance, and sizeof() of a field already parsed is available to it.
  • sizeof(x) is the byte length of the node x names, wherever it is in the tree — a field, a struct, an array element or a node reached through parent, root or asset — once that node has been parsed: its end offset minus its start offset. A derived field (bddo:valueFromExpression) has no byte extent, and sizeof of it is a Type / HEL error.

Byte order and bit order

A Physical Parser MUST read a multi-byte integer or float in the byte order given by the first of the following that applies:

  1. The data type's own byte order: an explicit big- or little-endian type such as bddo:uint32be or bddo:float64le always reads in its own order.
  2. The field's own declaration: bddo:endianness on the field, or the first rule of the field's bddo:hasConditionalEndianness whose condition holds, evaluated just before the field is read.
  3. The containing struct's own declaration: its bddo:endianness, or its resolved bddo:hasConditionalEndianness (below). The two are mutually exclusive.
  4. The byte order inherited from the enclosing struct: the order that was in force (by this same list) for the field through which this struct is being parsed. This applies equally to a struct re-parsed from a decoded sub-stream.
  5. Big-endian.

Conditional byte order on a struct. A processor MUST resolve a struct's conditional byte order as follows. The bddo:EndiannessRules are evaluated in list order, against the struct as instance, after each field of the struct is bound, until one rule's bddo:condition is true. That rule's bddo:ruleEndianness then applies to every later field of the struct and, by inheritance, to their descendants; it is resolved at most once per struct instance. Until a rule matches, the fields are read in the provisional order — the order cases 4 and 5 give — which is why the discriminating field (TIFF's II/MM) is normally byte-order-agnostic. A condition that cannot yet be evaluated because it names a field not yet bound counts as not holding. If no rule has matched when the field list is exhausted, the provisional order was the struct's order throughout.

Bit order is the struct's own bddo:bitOrder, or bddo:MSBFirst when it declares none; it is not inherited. An offset-addressed read starts with a fresh bit cursor at its target.

Numbers written as text, separated tokens and varints

A Physical Parser MUST read these self-describing values as follows:

  • Text numbers. A field of bddo:asciiInteger or bddo:asciiDecimal (or any type with an integer or float base type and no bit width) is read from its extent () and decoded per its bddo:encoding. Surrounding whitespace and NUL bytes and a leading + are removed. An integer is then read in radix bddo:numericBase (8, 10 or 16; default 10); a decimal accepts a sign, a decimal point, and an exponent introduced by E, e, D or d, and the spelling nan in any case with an optional sign. Anything else, including an infinite value, is a validation error: the value is never kept as a string.
  • Separated tokens (bddo:separatedBy "whitespace"). The separator class is the bytes space, tab, CR and LF. An element consumes the run of separator bytes before it, then the token (the maximal run of non-separator bytes), then the run after it; the token is read as a text number. An empty token (the region holds only separators) is a bounds error. The scan is byte-wise, so the field's encoding MUST be UTF-8, US-ASCII or ISO-8859-1; any other is a validation error.
  • Varints. bddo:varuint is LEB128: seven value bits per byte, least-significant group first, the high bit set on every byte but the last. bddo:varint is a LEB128 value carrying a zigzag-encoded signed integer. bddo:sqliteVarint is one to nine big-endian bytes, the high bit of each of the first eight a continuation flag and the ninth contributing all eight bits. A varint that runs past its bound, or that exceeds the 64-bit range, is a bounds error.

Delimited, key/value and tree containers

A struct typed bddo:DelimitedRecords, bddo:KeyValueHeader, bddo:DelimitedTable or bddo:TreeDocument locates its fields by delimiter position, by key, or by path, not by byte offset. Such a container consumes all remaining bytes of the innermost bounded region — including a region established by the size of the field through which it is parsed — or, when it is the root or nothing bounds it, the rest of the current stream. Its field list is then processed as follows instead of by ParseField; bddo:isPresentIf, bddo:validIf, enumerations and mappings on its fields still apply to the values found.

Records

A Physical Parser MUST split a delimited container into records and values by these rules:

  1. The bytes are decoded in the bddo:encoding declared on the field through which the container is parsed, or as UTF-8 when none is declared. A malformed sequence is a validation error (recorded as a finding and skipped in a lenient mode); it is never replaced silently. A leading UTF-8 byte order mark is ignored.
  2. The text is split into records at each occurrence of bddo:recordDelimiter (default 0A, LF) that is not inside a quoted value (below). When the delimiter is 0A, a CR immediately before it is removed, so CRLF text reads the same as LF text. A record delimiter at the very end yields no final empty record.
  3. The first bddo:skipRecords records (default 0) are discarded; then every record that, after leading whitespace, begins with bddo:commentPrefix is discarded.
  4. Values within a record. With bddo:fieldDelimiter, a record is split into values at each occurrence of the delimiter sequence outside a quoted value. With bddo:whitespaceSeparated true, values are separated by runs of space, tab, CR or LF: a run of any length separates exactly two values, and leading and trailing whitespace on the record is ignored; if bddo:recordDelimiter is also absent, the whole content is one flat sequence of values, whose shape comes from the field's layout or repeat count. With neither, a record is a single value.
  5. Quoting. With bddo:quoteChar q, a value that begins with q is quoted: it extends to the next q not immediately followed by another q, may contain the field delimiter, the record delimiter and line breaks, and has its quotes removed; a doubled qq inside it denotes one literal q. With bddo:escapeChar e, e followed by any character yields that character with no delimiter or quote meaning. A quoted value still open at the end of the container is a validation error.
  6. With bddo:trimWhitespace true, leading and trailing whitespace is removed from every key and value.

Key/value headers

A processor MUST locate the fields of a key/value header as this paragraph states. In a bddo:KeyValueHeader, each record is split at the first occurrence of bddo:keyValueSeparator into a key and a value; a record without the separator carries no pair and is ignored. Each field takes the value of the record whose key equals its bddo:key, or, for a field that declares no bddo:key, its simple key () (compared ignoring ASCII case when bddo:keyIsCaseInsensitive is true, else exactly); a key that no record carries leaves the field unbound (Null); when several records carry the key, the last wins. Record order is not significant, and records whose key no field names are ignored. The container yields one node.

Nested groups. A container with bddo:hasGrouping nests records into named groups by its bddo:groupingStyle: bddo:keyedGroup (a record whose key is bddo:groupOpenToken opens a group named by its value; one whose key is bddo:groupCloseToken closes the innermost open group), bddo:valuedGroup (the mirror: the value is the token and the key names the group), or bddo:sectionHeaded (a record groupOpenToken name groupCloseToken opens a group and closes the previous one; the last group runs to the end; sections do not nest). A field is then located by bddo:keyPath: the enclosing group names and finally the key, joined by bddo:pathSeparator (default /), matched by the same rules as bddo:key; a field of a grouped container located by bddo:key names a record outside every group. Group tokens are compared, and group names matched, by the same rule (ignoring ASCII case under bddo:keyIsCaseInsensitive), after removing surrounding whitespace. A record that carries no bddo:keyValueSeparator still counts as a group record when, after removing surrounding whitespace, it is the close token alone (keyed style: ODL's bare END_OBJECT) or a name, a run of whitespace and the open or close token (valued style: ERMapper's DatasetHeader Begin). A close token with no open group, or a group of the keyed or valued style still open at the end of the container, is a validation error.

Tables and record lists

A processor MUST bind the records of a table as this paragraph states. In a bddo:DelimitedTable or plain bddo:DelimitedRecords, each record yields one row node, in record order, and the container's value is the ordered array of rows. The values of a record are matched to the fields by position, in bddo:hasField order. A record whose number of values differs from the number of fields is a validation error; a lenient mode MAY record it as a finding and continue with the next record, binding the values it has and discarding the extra ones. (An empty value is a value: a record a,,c has three.)

Flat value sequences. A bddo:whitespaceSeparated container with no bddo:recordDelimiter is one sequence of values; every Physical Parser MUST support it. The values are bound to the container's field that repeats (by its repeat count, or by the element count of its data layout); a number of values different from that count is a validation error.

Typed values

A value found in any text container is a String unless its field's data type is a number written as text, in which case it is read by the text-number rule of . A value that does not parse as the declared number is a validation error; it MUST NOT be kept as a string, because an expression reading a declared number cannot tell such a string from a real one. An empty value of a numeric field is likewise a validation error; a value that is absent (no cell, no key) leaves the field unbound instead.

Tree documents

A bddo:TreeDocument hands its bytes to a parser for its bddo:treeSyntax: bddo:xml (XML 1.0 with namespaces) or bddo:json (JSON, [[RFC8259]]). A document that is not well-formed is a validation error. JSON is read as UTF-8, strictly as [[RFC8259]] defines it: a leading byte order mark is ignored, and malformed UTF-8, a trailing value, single quotes or NaN make the document not well-formed. An XML parser MUST NOT fetch external entities or DTDs, and entity expansion counts toward the resource limits; a processor MAY decline to process a document type declaration at all, and a reference to an entity that only a declaration would define is then a validation error (the reference implementation processes no DTD, so the billion-laughs and external-entity attacks both end there). A reference to an external entity MUST be reported as a validation error whether or not the processor reads the declaration, since the entity's text is never fetched.

  • Each field is located by its bddo:nodePath. For bddo:xml the path is abbreviated XPath restricted to child steps, one final attribute step (@name) and 1-based positional predicates ([n], the n-th child matching the step's name); its prefixes are those bound by bddo:hasNamespaceBinding (bddo:namespacePrefix to bddo:namespaceIRI; the empty prefix binds the default namespace), and a prefix not bound is a description error. Names are matched by namespace IRI and local name, never by the prefix the document happens to use; an unprefixed element step is in the namespace bound to the empty prefix (in no namespace if none is), an unprefixed attribute step is in no namespace, as in XML Namespaces, and the prefix xml is predeclared. A path beginning with / starts at the document root; one without starts at the context node, which for the container itself is the document. For bddo:json the path is a JSON Pointer [[RFC6901]]. A path that does not follow its syntax is a description error.
  • A path selecting no node leaves the field unbound. A path selecting several nodes (for JSON, a duplicated member name) is a validation error unless the field repeats (declares a repeat count), in which case its value is the selected nodes in document order, and a number of nodes other than the count is a validation error. Because a JSON Pointer selects one node, a repeating field whose pointer selects one JSON array repeats over the array's elements.
  • The value of a selected XML element is its string value (the concatenation of its descendant text), of an attribute its value; the value of a JSON string, number or boolean is its text, and JSON null leaves the field unbound. The value is then typed as in . Selecting a JSON object or array for a field that is not a struct is a Type / HEL error.
  • A field whose data type is a bddo:TreeDocument of the same syntax binds, for each node it selects, a struct whose fields are located with that node as the context: a JSON Pointer is evaluated against the selected value, and an XML path without a leading / from the selected element. Selecting an attribute or a JSON scalar for such a field is a Type / HEL error.

Data layouts

A field with hexplain:hasDataLayout is read as a byte block by the rules above; the DLV layout then says how cells are addressed within it. Before any cell is addressed, a processor MUST resolve the layout against the field's containing struct: each dlv:dimensionSizeFromField, dlv:dimensionStrideFromField and dlv:cellBitWidthFromField reads the named field (looked up as for bddo:sizeFromField), each dlv:dimensionStrideFromExpression is evaluated, and the first holding arm of dlv:hasConditionalCellDataType and of dlv:hasConditionalDimensionOrder is selected (DLV conditional layout). A size or stride that does not resolve to an integer, or a conditional list with no holding arm, is a Type / HEL error; an arm whose condition fails to evaluate is also an error, never an arm that is merely false. A packed cell (dlv:cellBitWidth not a multiple of 8) is an integer read in dlv:cellPackingOrder. A packed width on a cell type that is not an integer is a description error: raised when the description is loaded when the width is a literal, and when the layout is resolved when the width comes from a field (dlv:cellBitWidthFromField). Chunked layouts are covered in .

The HEL Parsing Context

The parsing context is the tree of nodes produced above. It is the sole input, besides stream metadata and (for a Bundle Processor) the asset, to HEL evaluation. Fields already parsed within the current and ancestor nodes are visible; forward references (to fields not yet parsed) MUST raise an error, except where this document defers an evaluation until its references are bound (, ).

The names instance, parent, root, self, stream and asset are bound exactly as the HEL name-binding table states; this document does not restate them. In particular, the key or condition of a bddo:DispatchTable and the condition of a bddo:DataTypeRule are evaluated against the containing struct, since the field whose type they choose does not exist yet; self is the field's value for bddo:validIf; every other expression on a field (presence, size, offset, repeat count, derived value) and every struct-level expression is evaluated with the containing struct as instance.

bddo:repeatUntil. The condition is evaluated after each element. When the elements are structs, instance and self are the element just parsed, so a bare name reads a field of that element, and parent is the struct that contains the repeated field. When the elements are scalars, instance is the containing struct, parent its parent, and self the value just read. (parent.x therefore reads the containing struct's x for struct elements, and the grandparent's for scalar elements.)

The deprecated parent alias. In a dispatch key or a bddo:DataTypeRule condition, parent is an alias for instance. The alias is deprecated in HEL 1.0: a processor SHOULD warn when it loads a description that uses it, new descriptions MUST NOT use it, and an HDL compiler never emits it.

Stream metadata and eof()

The current stream is the input byte stream, or, inside a field decoded by hexplain:isEncodedWith and re-parsed as a struct, the decoded bytes (a fresh sub-stream whose offsets start at 0). The current bound is the end of the innermost bounded region in force (, ), or the end of the current stream if none is. A region's bound is suspended only for the duration of a bddo:streamScope read. At the moment an expression is evaluated:

NameValue
stream.lengthThe length in bytes of the whole current stream. It is not narrowed by bounded regions.
stream.positionThe cursor, as a byte offset from the start of the current stream (not from the start of the region). During a run of bit fields it is the offset of the first byte not yet touched, so a partly consumed byte counts as consumed.
stream.remainingThe current bound minus stream.position: region-relative.
eof()stream.remaining == 0: true at the end of the innermost bounded region, not only at the end of the stream. This is what makes bddo:repeatUntil "eof()" stop at the end of a length-delimited container.

The cursor seen by an expression is the one in force when it is evaluated: before alignment for presence and derived value; after alignment but before the field is read for size, offset, type selection and repeat count; after the element for repeatUntil; after the field for validIf and checksum coverage.

Instance IRI Minting

To make the instance graph queryable, every emitted subject MUST have a stable, deterministic IRI. The default policy mints every IRI as a fragment of the base: B'#path, where B' is the base IRI B with any fragment (and its #) removed. If B is absent, a processor MUST choose a base itself (for example a fresh urn:uuid: IRI) and report it with the graph.

Every node of the logical tree has a node path:

path     = "root" *( "/" segment )
segment  = key / index
key      = the field's simple key, escaped as below
index    = "0" / ( %x31-39 *DIGIT )      ; array position, 0-based, decimal, no leading zeros
  • The root node's path is root. When the root struct is itself parsed as a bddo:repeatUntil sequence, its i-th element's path is root/i.
  • A struct bound under field key k of a node with path p has path p/k; the i-th struct element of an array field k has path p/k/i. Segments are appended for every struct on the way down, whether or not it is mapped to a class.
  • A field's simple key is the local name of the field's IRI after its last ., so the struct-qualified IRI ex:Chunk.length that an HDL compiler mints and the flat IRI ex:length both give length. The exception is a field of a text container whose IRI is the container's IRI, a ., and the field's own bddo:key, bddo:keyPath or bddo:nodePath (what an HDL compiler mints for a quoted key with no alias): its simple key is that key or path, which may contain spaces, . and /.
  • A character of a key that is not permitted in an IRI fragment ([[RFC3987]] ifragment) is percent-encoded as its UTF-8 octets, upper-case hex; in particular U+0020 SPACE becomes %20. A / in a key is percent-encoded as %2F, so it is never read as a segment separator.

So the root struct, when it is mapped by hexplain:mapsToClass (or a conditional class mapping), is B'#root; the fourth element of a Chunks array under the root is B'#root/Chunks/3, and a struct in its Data field is B'#root/Chunks/3/Data. Only a struct node that resolves to a class is minted. The literal properties of an unmapped struct are emitted on the nearest mapped ancestor's subject; an unmapped struct with no mapped ancestor emits nothing, and neither do its descendants. Two further nodes use the same path form: a unit-bearing value (hexplain:unit) is a quantity node B'#p/k, and a field with a data layout that has hexplain:mapsToObjectProperty is an array node B'#p/k, where p is the containing struct's path and k the field's key.

A processor MAY offer alternative minting policies (e.g. hash-based or field-derived keys) but MUST document them and MUST be deterministic: parsing the same bytes with the same description and base IRI MUST yield an isomorphic graph.

Primitive Value → RDF Literal Mapping

When a mapped field's value is emitted, its RDF literal datatype is the bddo:xsdType of the field's effective bddo:DataType. This fixes, for example, that a bddo:uint32be becomes an xsd:unsignedInt literal and a bddo:float64le becomes an xsd:double. Integers are decoded with the resolved endianness and signedness; floats per IEEE 754; bddo:string per its bddo:encoding; bddo:bytes as xsd:hexBinary.

Semantic Triple Emission

The instance graph G is produced from the mapping properties of Hexplain Core, and holds nothing else except that a processor MAY annotate each minted resource with its physical extent: hexplain:byteOffset and hexplain:byteLength, typed xsd:nonNegativeInteger, the core vocabulary's range for both.

A Semantic Emitter MUST emit these triples:

  • For a Struct instance s whose description has hexplain:mapsToClass C, emit <IRI(s)> rdf:type C.
  • For a Field with hexplain:mapsToProperty P, emit <IRI(parent)> P "value"^^xsdType. If the field also carries hexplain:valueExpression E, emit instead the value obtained by evaluating E in the field's context (e.g. fixed-point or unit scaling), typed with hexplain:valueDatatype if given, else the natural datatype of the HEL result.
  • For a Field with hexplain:mapsToObjectProperty P, emit <IRI(parent)> P o, where o is the IRI minted for the struct instance the field holds when its data type is a bddo:Struct, or the bddo:enumSymbol IRI of the matched bddo:EnumValue when the field carries an enumeration; a value that has neither emits nothing.
  • For a Field with hexplain:hasConditionalMapping, evaluate rules in order and emit the property of the first rule whose condition holds.
  • A repeated field emits one such triple per element, in element order; a Null element, like an unbound field, emits nothing.
  • For a Field with hexplain:hasDataLayout, the layout (DLV) governs how the multi-dimensional cells are addressed; a processor MAY additionally emit per-cell triples but is not required to materialize them.
  • For a Field with hexplain:isEncodedWith A, a processor MUST decode the block with algorithm A (a concept from whichever codec or compression register the profile binds; see for the codecs every processor supports and the Unsupported feature error for the rest); when the field's effective data type is a bddo:Struct, it MUST then re-parse the decoded bytes as a fresh bounded sub-stream against that Struct.
  • If an enumeration matched, a processor SHOULD also emit the symbolic value (the bddo:enumSymbol IRI, if any) alongside the raw literal.

Multi-part Assets

A Bundle Processor processes an abnd:Asset: several files (parts) described together by an abnd:BundleProfile in the bundle aspect. Its input is the bundle profile, the descriptions its part specs are abnd:describedBy, the asset IRI, and the asset's files, each with its path relative to the asset root (/-separated; a flat sibling set is just the file names) and its IRI.

  1. Assembly. Each file is matched to an abnd:PartSpec of the profile. An abnd:extension value is the shorthand for the pattern *<ext> (so it matches a file at the asset root, not in a subdirectory), compared ignoring ASCII case, since a filename's case is not significant to the formats that name members by extension; an abnd:pathPattern is a glob matched exactly against the relative path (* within one segment, ** across segments, ? one character). Several values of either property are alternatives. A file that matches no part spec, or the part specs of more than one, is a validation error: the caller chooses which files form the asset, and a file that could be either of two parts would be read by a guess. The part count of each spec is the number of files matched to it; it MUST lie within abnd:minParts (default 1 when abnd:required is true, else 0) and abnd:maxParts (default 1 for a spec located by abnd:extension, which names one member; unbounded for a pattern). A count outside that range, including a required part with no file, is a validation error. A part's identity, and so the value of partExtension() for it, is fixed here, before any part is parsed: the abnd:extension alternative it matched, or, for a part located by a pattern, the part of its file name from the last .; in both cases lower-cased with its leading ., and empty when there is none.
  2. Order. Each part whose spec is abnd:describedBy a struct is parsed with that struct, and is named in HEL by the struct's local name; two part specs of one profile described by structs with the same local name are a description error. A part whose description (the struct and every struct reachable from it) reads asset.X.… MUST be parsed after part X; a processor MUST order the parts so that every such reference is to a part already parsed. partExtension(asset.X) reads a part's identity, not its content, and imposes no order. References that form a cycle, including a part reading its own content through asset, are a description error, raised before any part is parsed. Reading asset.X before X is parsed, naming a part the asset does not have, naming a part more than one file was matched to, or reading a key the part's root struct does not declare is a Type / HEL error, never Null. A part whose spec has no abnd:describedBy is carried but not parsed. Cross-part references are written with the asset root: a …FromField property resolves its field within the part being parsed, as it does in a single file.
  3. Parsing and minting. Each part is parsed as an independent stream by this document's rules, and its instance IRIs are minted against the part's own IRI as base, so the part's root is <part>#root. A part that is carried but not parsed (its spec has no abnd:describedBy) MUST still be minted the same way: its root is <part>#root, which the lifting below links and types, and which carries no triple of its own content.
  4. Lifting. The asset IRI is typed abnd:Asset, linked to the bundle profile by dcterms:conformsTo and to each part root by abnd:hasPart, and to the root of the part whose spec is abnd:primary by abnd:primaryPart when exactly one file was matched to that spec; each part root is typed abnd:Part and carries its spec's abnd:partRole. The bundle profile's triples are in the graph, since the lifting rule joins through them; the descriptions of the parts' bytes are not. The bundle aspect's lifting rule then copies each part's facet properties whose aspect the part's role abnd:carriesAspects onto the asset. No inverse (abnd:partOf) or other inferred edge is added.

A processor that is not a Bundle Processor MUST treat the asset root and partExtension() as HEL errors when a single part is parsed on its own, so that a description depending on a sibling part fails rather than reading Null. A Bundle Processor parsing a part on its own, outside an asset, does the same.

Conformance Evaluation

A Conformance Evaluator takes a parsed input (the parsing context of ), a conformance profile — the conf:Constraint, conf:ParseAttribution and req:Requirement resources of a description graph — and optionally the input's format version, and produces a run report: a conf:Run with one outcome per requirement, and the conf:Findings of the run. The vocabulary is defined in conf and req; this section defines the behaviour.

  1. Scope firing. A constraint whose conf:scope is a bddo:Struct MUST be evaluated once for every parsed instance of that struct, after the instance is complete, with instance and self bound to the instance, parent to the struct that holds it and root to the root of the input. A constraint whose scope is a bddo:Field MUST be evaluated once for every parsed value of that field — each element of a repeated field is one value, and an absent optional field fires nothing — with instance bound to the containing struct and self to the value. Instances are visited in document order.
  2. Assertion results. An assertion that evaluates to true passes. false yields one finding of kind conf:Violation, at the constraint's conf:severity (default sh:Violation), attributed to every requirement the constraint cites. Any other result, or an evaluation error, yields one finding of kind conf:RuleError at sh:Violation, attributed the same way. A ResourceLimit reached while evaluating an assertion is not a rule error: it truncates the run (item 5).
  3. Messages. A finding's conf:findingMessage is the constraint's conf:message with {field} replaced by the node path () of the focus node, and {value} replaced by the evaluated value when it is unambiguous — the field's value under a Field scope, and under a Struct scope the value of the instance's only bound scalar field when there is exactly one — and otherwise left as written. Values are rendered as conf:message defines. For a rule error the message describes the evaluation failure.
  4. Version. The input's format version is supplied by the caller; an evaluator MUST NOT guess it from the data. When it is supplied, a requirement with req:appliesToVersion values none of which equals it (exact string equality) is not applicable: its constraints are not evaluated on its behalf, and its outcome is conf:NotApplicable. When no version is supplied, every requirement is evaluated and the report MUST state that version scoping was not applied.
  5. Truncation. An evaluator MUST enforce resource limits on a run (at least the parse limits, and a limit on the number of findings). When one is reached it MUST either fail with a ResourceLimit error or stop and return a report marked truncated, stating the limit; it MUST NOT return an unmarked partial report. A parse that stops at an error likewise leaves the rest of the input unvisited.
  6. Parse attribution. An error raised while parsing the input () is reported as one finding of kind conf:Parse, with no constraint, at sh:Violation, stating its conf:errorCategory: Sync, Bounds, Validation, Checksum, Expression (a Type / HEL error), Description (a Description or Dispatch error), Unsupported or ResourceLimit. It is attributed to the requirement of the profile's conf:ParseAttribution for that category (each attribution cites exactly one requirement, and a profile attributes a category at most once), and to no requirement when none names the category. In a lenient mode that recovers from parse errors, each recorded error is such a finding.
  7. Recovered trees. When a lenient parse recovered from errors and an assertion reads a declared field that is absent from the recovered tree, the evaluation of that instance yields no finding — neither a violation nor a rule error — and does not count as exercising the constraint: the defect is carried by the Parse finding.
  8. Outcomes. Every requirement of the profile receives exactly one outcome, the first of these that holds: conf:NotApplicable (item 4); conf:Errored, when a citing constraint raised a rule error; conf:Evaluated, when a citing constraint was evaluated without error on at least one instance, or a citing parse attribution was checked (the parse ran to its end, or raised the attributed category); conf:NotReached, when the run was truncated or the parse stopped before the whole input was visited; conf:NotExercised otherwise — including a requirement no constraint or parse attribution cites.
  9. Verdict. A run is conformant if and only if it was not truncated, the parse completed, no finding has severity sh:Violation (so no Parse finding and no rule error), and no requirement's outcome is conf:Errored or conf:NotReached. Findings at sh:Warning or sh:Info are reported and do not affect the verdict.

Informative: the reference implementation reports the categories under its own error kinds (Sync, Bounds, Validation, Checksum and Expression as the kinds of the same name, Description as DISPATCH and load-time description errors, Unsupported as UNSUPPORTED, ResourceLimit as the ResourceLimit marker), writes the report as JSON or as conf: RDF, and its command-line validator's --fail-on=violation|warning|info option chooses the lowest severity that makes the command fail.

Resource Limits

Descriptions and inputs are untrusted: a small file can declare a huge repeat count, a deep recursion, or a compression bomb. A processor MUST enforce limits on the work of one invocation, and MUST let its user configure each limit below. Its default configuration MUST allow at least the values below; it MAY allow more, and MUST allow a user to configure lower limits.

Exceeding a configured limit raises a ResourceLimit error. That error is fatal in every mode, including a lenient mode that otherwise records errors and continues: returning a partial tree or graph would hide the exhaustion.

A wall-clock limit (the reference implementation's default is 30 s per parse and per emission), and cancellation by the caller, are implementation safeguards rather than part of the processing model: they are not required and their values are not normative. When one fires, the result MUST be a ResourceLimit error, never a different or partial parse. A processor MUST NOT fall back to a cheaper interpretation of the description to finish in time.

Recovery in a Lenient Mode

A lenient mode () records an error and continues. Continuing needs a cursor, and a processor that chose its own would record different errors, and return a different partial tree, from another given the same bytes. The rules below fix it. A check on a value that has been read in full — a fixed value, a checksum, a bddo:validIf or a text value that is not the declared number — leaves the cursor sound: the error is recorded, the field keeps its value and parsing continues with the next field. When reading a field fails, a processor in a lenient mode MUST record the error once and recover by the first of these rules that applies:

  1. Pointer. A field read at an offset (bddo:atOffset, bddo:atOffsetFromField, bddo:atOffsetFromExpression) that fails leaves the field unbound and does not move the cursor: the saved cursor is restored, as after any offset-addressed read, and parsing continues with the next field.
  2. Counted sequence of fixed-width elements. A repeated field whose count is known (its repeat count resolved) and whose elements have a fixed width (a data type with a bddo:bitWidth and no bddo:bitLength) is left unbound, and the cursor moves to the field's start plus count × width, or to the end of the innermost bounded region if that comes first; parsing continues with the next field.
  3. Otherwise, abandon the rest of the struct. The field that failed and every later field of its struct are left unbound, the fields read before it keep their values, and the cursor moves to the struct's declared end (the end of its bounded region, ) or, when it has none, to the end of the innermost enclosing bounded region, or of the current stream. The struct's node, with the fields it has, is bound in its parent, which continues with its next field. Abandoning the root struct ends the parse.

Each rule records exactly one error for the failure it recovers from; a later field that then fails is a new failure, recovered by the same rules. A processor MUST NOT recover from a ResourceLimit, Description or Unsupported feature error (), and MUST NOT use a recovery rule to skip a read it could have made.
