The Hexplain Processing Model defines, normatively, how a conforming processor turns a binary stream plus a Hexplain description (BDDO + Core + domain vocabularies) into two outputs: a transient parsing context and a persistent RDF instance graph. It specifies the parse algorithm, the construction of the HEL context, the minting of instance IRIs, the mapping of primitive values to RDF literals, the emission of semantic triples, and error handling. This document makes Hexplain descriptions executable and reproducible across implementations.

This document is an unofficial draft produced for the purpose of defining the Hexplain standard. It has no official standing and is not endorsed by any standards body. It is a prerelease working draft: the processing rules below are normative for the current Hexplain toolchain, but they may still change incompatibly before a stable release.

Introduction

The other Hexplain specifications define vocabulary; this one defines behaviour. Without a shared processing model, two implementations could parse the same file against the same description and emit different graphs, defeating the interoperability and SPARQL-query goals of the framework. Everything here is REQUIRED behaviour for a conforming processor unless marked otherwise.

Conformance

The key words "MUST", "MUST NOT", "REQUIRED", "SHALL", "SHALL NOT", "SHOULD", "SHOULD NOT", "RECOMMENDED", "MAY", and "OPTIONAL" in this document are to be interpreted as described in BCP 14 [[RFC2119]] [[RFC8174]] when, and only when, they appear in all capitals, as shown here.

A conforming processor implements one or more of the conformance classes below, and states which. It MUST implement every rule of this document that the classes it claims require, and it MUST NOT silently mis-parse a description that uses a construct outside them (see ).

The processor conformance suite makes this document executable: every requirement sentence carries a stable identifier (for example req-pm-parsestruct-1), and each case cites the identifiers and sections its expected output is read from.

Scope and non-goals

This version describes a byte stream that is complete before parsing starts, read once and deterministically, and it writes the same descriptions back. What follows is outside it. Each entry says what a description can still state, what a processor does when it meets the construct, and where the rule is; none is implied by a term that exists today, and a later version that takes one up will say so in the section named.

  • Streaming. There is no streaming model. Every bound — stream.length, streamEnd addressing, bddo:sizeToEndOfStream, each terminator and marker search — is measured against the length of the whole input, which is known before the root struct is parsed, and an input longer than the processor's limit is refused before any of it is read (, ). A processor may read its input incrementally as an implementation choice; no rule lets a description say that more bytes will arrive.
  • Implicit decryption, signature verification and error correction. No step of a parse decrypts, verifies a signature or corrects errors of its own accord. The one exception is a codec a description names explicitly in a field’s pipeline: the scoped-key ciphers of the media-encoding register (menc:AESGCM, menc:AESCTR, menc:AESGCMSignature) and menc:VerifyCRC32, which run only with keys and bindings the caller supplies for the operation and raise the errors their contracts declare. Error correction is never performed. A description can locate an encrypted payload, a signature block or a parity area as bytes, and the aspect vocabularies may carry description-only terms that name a cipher, a signer or a code; such a term states a fact about the format for a reader of the graph and directs no processor behaviour. Otherwise the integrity a processor does check is the bddo:checksum of the checksum register (Checksum error), which detects damage and repairs none.
  • Speculative or backtracking choice. A parse never tries an alternative and retreats. Which struct a field holds is decided before it is read, by a dispatch key, a conditional data type or a presence condition evaluated over what is already bound (ParseField, type selection); a struct that then fails to parse is an error (in a lenient mode, a recorded one), never a signal to try the next arm. A format whose variants can only be told apart by attempting each is described by a discriminating expression over the bytes at hand, or is outside this version.
  • Byte-wise obfuscation transforms. There is no built-in XOR mask, bit rotation (ROL/ROR), byte substitution or similar transform, keyed or not, and HEL computes over parsed values rather than rewriting the bytes a later field is read from. The extension point is a codec contract: a transform is registered as a concept with a contract (its kind, its parameters, the categories it raises and its vectors), named by an encoding step, and claimed by the processors that implement it (). A processor that meets a codec it does not implement reports Unsupported feature.
  • Writer limits. The optional Writer covers the byte-level constructs only. It refuses, with Unsupported feature, text and tree containers, layouts with a chunk table, and codecs whose contract has no encode direction; it takes every offset from the tree and derives no offset table; it starts each encode afresh, keeping no codec session; and it reproduces the tree, not the bytes: fill bytes, codec output, a non-minimal varint and the spelling of a text number may differ from the stream a tree was parsed from (Symmetry).
  • Protection processing. The protection aspect (aprot:EncryptedRegion, aprot:Signature, aprot:ErrorCorrection, aprot:ByteRange) and its register describe what a format declares about the encryption, signatures, message authentication codes and error-correcting codes applied to its bytes. They are description only: this version defines no decryption, verification or correction, and no conformance class obliges a processor to perform any. A Physical Parser reads protected bytes as the physical constructs of the description say (an encrypted region is the opaque bytes it is), and a Semantic Emitter emits these terms as it emits any aspect term a description maps to.
  • Zstandard dictionaries. A menc:Zstd frame that names a dictionary (a non-zero Dictionary_ID) is refused with Unsupported feature, and Deflate or Zlib data needing a preset dictionary is refused as undecodable: no parameter, part or register supplies a dictionary in this version (, ).

The vocabulary-level gaps — concerns no module models yet — are listed in the architecture document (§9, Not yet modelled).

A processor MUST decode every registered codec it claims to support, MUST state which ones those are, and MUST raise Unsupported feature for any other. Codecs beyond the minimum set

Every other register codec is optional, and is claimed one codec at a time. A processor MUST list, in the codecs member of its claims statement, the IRI of every codec it decodes, MUST decode each codec it lists exactly as its contract () and this section define it, except for a parameter value or coding feature it refuses under case (d) of , and MUST raise Unsupported feature for every codec it does not list. This section defines three; the register's contracts and vectors define the others:

ConceptDecoding
menc:LZ4The LZ4 Frame format (LZ4 Frame Format Description, version 1.6): the magic number 04 22 4D 18, a frame descriptor closed by its header checksum, data blocks each stored or LZ4-compressed, an end mark, and an optional content checksum. An encoded byte run MAY hold several frames; they are decoded in order and their outputs concatenated, and skippable frames (magic 50 2A 4D 18 to 5F 2A 4D 18) are skipped. A processor MUST verify every checksum the frame declares — the header checksum, each block checksum and the content checksum, all the xxHash-32 the format specifies — and the content size when the descriptor states one; a mismatch is a Checksum error. A frame that names a dictionary (the descriptor's dictionary ID) is refused with Unsupported feature. The legacy frame format is not menc:LZ4.
menc:LZ4BlockOne LZ4 block (LZ4 Block Format Description): a sequence of token, literals, offset and match copies, the last sequence ending after its literals. The format records neither its own length nor its output's, so the step takes the parameter decodedSize below: the block is the whole encoded byte run, and decoding it MUST yield exactly decodedSize bytes.
menc:ZstdThe Zstandard frame format [[RFC8878]]. An encoded byte run MAY hold several frames; they are decoded in order and their outputs concatenated, and skippable frames are skipped. A processor MUST verify the content checksum (the low 32 bits of the frame's XXH64) when the frame declares one, and the frame content size when the header states one; a mismatch is a Checksum error. A frame that names a dictionary (a non-zero Dictionary_ID) is refused with Unsupported feature: this version defines no way to supply one.

Parameters. menc:LZ4 and menc:Zstd take no parameters. menc:LZ4Block takes exactly one, given as a hexplain:codecParameter of its hexplain:EncodingStep like Delta's; any other parameter name, a missing required parameter, or a literal value outside its range is a Description error, raised when the description is loaded (an expression's value outside it is a Validation error, ). hexplain:isEncodedWith menc:LZ4Block, which cannot carry the parameter, is therefore always a Description error.

Errors. A processor that decodes these codecs MUST report their failures in these categories: a checksum or content-size mismatch that the format declares is a Checksum error; data that is not a well-formed frame or block — a wrong magic number, reserved bits set, a truncated frame or block, a match offset of 0 or reaching before the start of the output, a block that decodes to more or fewer bytes than decodedSize or than its frame's maximum block size allows, or bytes after the last frame that do not begin another frame — is a Validation error, as requires for every codec; a dictionary is Unsupported feature; and a missing decodedSize, or a literal one that is invalid, is a Description error (a decodedSize expression whose value is invalid is raised as requires). The decoded output counts toward the decoded-byte limit as it is produced, and a processor MUST raise ResourceLimit before decoding when a decodedSize or a declared content size already exceeds what remains of that limit.

Codec contracts

Every codec a processor runs is a concept of the media-encoding register that carries a hexplain:codecContract, and the specification publishes normative vectors for it under codecs/<Name>/vectors/. The contract states the codec's kind in the decode direction — hexplain:BytesToBytes (compression, byte transforms, and predictors and filters on serialized samples, which take the sample geometry as parameters), hexplain:SamplesToSamples (colour conversions) or hexplain:BytesToSamples (image codecs, whose output reports its geometry: width, height, bands, sample type, byte order, and whether bands are pixel-interleaved or band-sequential) —, its parameters (hexplain:declaresParameter: a key, a type among integer, boolean, string, bytes, IRI and float, or a list of one of these, a required flag, a default and the allowed values or range), whether it keeps a session across blocks (hexplain:keepsSession), the error categories it raises (hexplain:raisesCategory), whether it also encodes (hexplain:encodes), and the version of the contract and of its vector suite. A contract names a category by its conformance-suite notation: Validation is a Validation error, Checksum a Checksum error, Unsupported an Unsupported feature error, ResourceLimit a ResourceLimit error and Description a Description error (). Description is the category of a parameter value that the contract's declaration admits, so that the load-time check below cannot refuse it, but that the codec cannot act on once it runs: a predictor whose sample geometry does not divide the block it is given, a parameter combination the contract's text excludes. A codec raises it only where its contract declares it, and a processor MUST report it as a Description error, which no lenient mode continues past, never as a Validation error: the bytes are not at fault, the description is. Adding an optional parameter raises the contract version; removing a parameter or changing its meaning requires a new IRI.

A concept of the register is contracted when it carries a hexplain:codecContract: it has a contract and a vector suite, and a processor can list and decode it. A concept without one is catalogue-only: the register names it so that a description can record an encoding (menc:BZip2, menc:Snappy, menc:BitShuffle), but this version defines no contract for it, so that no conforming processor can decode it and every processor refuses it with Unsupported feature. The distinction is the presence of the contract and nothing else. Every concept also carries a hexplain:status, which is its register lifecycle status (hexplain:statusValid, hexplain:statusDeprecated or hexplain:statusSuperseded) and says nothing about whether it can be decoded: every concept of this version, contracted or catalogue-only, is hexplain:statusValid. Every contract states its direction, as it states its session: hexplain:encodes true when it also covers the encode direction, and its vector suite then holds encode steps and a round trip, hexplain:encodes false when it is decode-only (hexplain:CodecContractShape requires the statement; codec vectors, completeness). An HDL compiler SHOULD warn when a description names a catalogue-only concept in @encoded-with, a pipeline step or a candidate, since the description it compiles can be read but never decoded; it MUST still compile it, because recording the encoding of data no processor yet decodes is what the catalogue is for.

A processor MUST decode every codec it lists exactly as its contract and its normative vectors define it, except for a parameter value or coding feature it refuses with Unsupported feature under case (d) of ; a vector's expected output or expected error category is normative.

When the description is loaded, a processor MUST check every encoding step against the contract of its codec: a parameter name the contract does not declare, a missing required parameter, and a literal value of the wrong type or outside the declared values are a Description error, and a value the contract defines but the processor does not implement is Unsupported feature (, case (d)).

A pipeline's steps are listed in encode order and decoded in reverse list order; the first step decoded reads the field's bytes and each next step reads what the previous one produced. A processor MUST raise a Description error, when the description is loaded, for a pipeline in which a step reads bytes where the step decoded before it produces samples, or samples where it produces bytes, or in which the first step decoded reads samples. A pipeline whose last decoded step produces samples yields the samples' bytes as the field's value: every sample at the full width of its sample type (a sample of fewer significant bits is not packed), in the byte order and the interleave (pixel-interleaved or band-sequential) of the geometry that step reports, pixels in row order from the first row, with no padding.

Every codec MUST honour the decoded-byte limit () and cancellation, and MUST NOT allocate output beyond what remains of the limit before it has validated the sizes its input declares.

Parameter expressions

A codec parameter is given either by a literal (hexplain:parameterValue) or by a HEL expression (hexplain:parameterExpression). A processor MUST raise a Description error, when the description is loaded, for a codec parameter that carries both, or neither. The expression is evaluated each time its step runs, with the field's containing struct as instance, exactly as a bddo:sizeFromExpression of the field is evaluated; for a repeated field it is evaluated anew for every element.

A processor MUST raise a Description error, when the description is loaded, for a parameter expression whose parameter name the contract does not declare. A value of the wrong HEL type for the parameter is a Type / HEL error and a value of the right type outside the parameter's declared values is a Validation error; a processor MUST raise either before the codec runs.

Run-time codec selection

A step may choose its codec when it runs: instead of hexplain:codec it carries a HEL expression hexplain:codecFromExpression, whose String value is the IRI of the codec to run or that IRI's local name, and a hexplain:codecCandidates list naming, as encoding steps with their own parameters, every codec the expression may select; parameters belong to the candidates. A processor MUST raise a Description error, when the description is loaded, for a selecting step that carries a hexplain:codecParameter of its own, a step that carries both hexplain:codec and hexplain:codecFromExpression, and a selecting step without hexplain:codecCandidates or whose candidate list is empty.

The candidates of a step MUST name distinct codecs, and a processor MUST check each of them when the description is loaded as it checks a step that names its codec, raising Unsupported feature for a candidate whose codec it does not decode even when no input ever selects it. Kinds are checked per candidate: each candidate's kind must connect with the step decoded before it and the step decoded after it, as requires of a step that names its codec, and candidates may differ in kind from one another.

The expression is evaluated when the step runs, with the field's containing struct as instance. A local name that more than one candidate shares names none of them. A String value that names none of the candidates, a shared local name included, MUST be raised as a Validation error; a value that is not a String is a Type / HEL error.

Codec sessions

A codec whose contract keeps a session carries state from one decode to the next: JPEG tables, a fax coding's reference line. hexplain:codecSessionScope on the field says how far a session reaches: with bddo:PerInstance, one session per step serves every decode of the field within one instance of its struct; with bddo:PerLayout, one session per step serves the field for the whole parse; without it, every decode starts a new session. On a field none of whose codecs (or candidates) keeps a session, hexplain:codecSessionScope has no effect and is ignored.

A processor MUST NOT let a session outlive the parse that created it, and under bddo:PerInstance MUST NOT share one between two instances of the struct.

Inputs and Outputs

Inputs
(1) a byte stream S with known length |S|; (2) a Hexplain description graph D; (3) a designated root Struct R in D; (4) an optional base IRI B for minting instance IRIs.
Valid description
The description D is valid when validating it against the family's shapes yields no result of severity sh:Violation (Validation, description validity). A result of severity sh:Warning or sh:Info — the portability warning bddo:CustomEncodingCharsetShape reports for a custom encoding that re-spells a registered one, for one — says something about the description and does not make it invalid. A processor MUST NOT refuse a description, or report it invalid, for results of severity sh:Warning or sh:Info alone; it MAY report them beside its output. A tool that refuses a description for a warning applies a stricter policy of its own, outside this specification. The same reading governs a conformance run's verdict (), whose fail-on severity is sh:Violation unless the caller lowers it.
Known length
This version defines no streaming model: stream.length, streamEnd addressing, bddo:sizeToEndOfStream and the bound of every terminator and marker search are defined in terms of |S|. A processor MUST know |S| before it reads the first field, and a processor given an input whose length is not known in advance (a pipe, a socket) MUST read it to its end — bounded by the input-byte limit of — before parsing, rather than parse incrementally and guess, and MUST NOT report a parse of a prefix of the input as a parse of the input. A decoded sub-stream () is likewise complete before it is re-parsed.
Outputs
(1) the parsing context C (transient, used by HEL); (2) the instance graph G (RDF, persistent). A processor MAY expose either or both.

Parse Algorithm

Parsing maintains a cursor (byte position, initially 0) and a bit cursor for bit-level fields. To parse the root, invoke ParseStruct(R, cursor=0, parent=nil).

ParseStruct(struct, cursor, parent)

A Physical Parser MUST parse a struct by these steps, in this order:

  1. If struct has bddo:syncOnMarker, advance the cursor past the first occurrence of the marker bytes that starts at or after the cursor — one that starts exactly at the cursor counts — and lies entirely before the current bound: the end of the innermost bounded region in force, or of the current stream when none is (Stream metadata). The struct’s own size is applied after the seek, so it does not bound the search. The marker is consumed, and the struct begins after it: its start offset, from which its own size region is measured, and its first field. If no occurrence lies entirely before the bound — including one that starts before the bound and ends after it — raise a sync error; the search never continues past the bound.
  2. Create a new context node n with a back-link to parent; record its start offset.
  3. Parameters. If struct declares bddo:hasParameter, a processor MUST bind each parameter, by name, to the argument its caller supplied in the same position (ParseField, Value), in a parameter scope of n that HEL reads as param.name and that is not a child of n. A struct with a non-empty parameter list has no caller when it is the root R or the struct of a bundle part: that is a description error.
  4. Bounded region. If struct declares a size (bddo:size / bddo:sizeFromField / bddo:sizeFromExpression), it establishes a bounded region [start, start+size). A read by this struct or any descendant that would cross the region end raises a bounds error, and a descendant's bddo:sizeToEndOfStream resolves to the region end (not |S|). This is what lets length-delimited containers (ISOBMFF/MP4 boxes, EBML, chunk payloads) bound their children. A literal bddo:size establishes the region before the first field is read; a bddo:sizeFromField or bddo:sizeFromExpression establishes it as soon as every field it references is bound (). A region whose end would lie beyond the enclosing region, or a negative size, raises a bounds error.
  5. Resolve the effective byte order and bit order (). The byte order declared by an ancestor struct is inherited, which is what "nearest declaration wins" means: DataType > Field > this Struct (fixed or conditional) > inherited from the enclosing struct > big-endian.
  6. If struct is a bddo:DelimitedRecords (or subclass) or a bddo:TreeDocument, parse it by the container rules of instead of the next step, then continue at the last step.
  7. For each field in the bddo:hasField list, in order, call ParseField(field, n). Members MUST be processed in list order. When struct declares the deprecated bddo:usesStruct T, the fields of T are processed first, then the struct's own fields, as one list. A member that is a bddo:LocalBinding is not a field: when its position is reached a processor MUST evaluate its bddo:localExpression with n as instance and bind the result under the binding's name in a local scope of n, which HEL reads by bare name or instance.name from the next member on; the binding consumes no bytes, is not a child of n, and a Null result binds Null.
  8. If struct declared a size, advance the cursor to start+size (skipping any trailing padding/unknown bytes); otherwise the end offset is the current cursor. Record the node's end offset (sizeof = end − start) and return n.

Struct alignment. A struct MAY declare bddo:alignment itself, which aligns every instance of it, wherever it is used. A processor MUST apply it before step 1: the cursor advances to the next multiple of the alignment (), and only then is a bddo:syncOnMarker searched for and the node's start offset recorded, so the skipped bytes lie before the struct and are not part of its extent. When the field that names the struct declares bddo:alignment too, the field's is applied first (ParseField, Alignment) and the struct's after it.

Struct padding. A struct MAY declare bddo:padTo. A processor MUST apply it after the last member is processed and before the last step: the cursor advances to the next multiple of the padding boundary (), the skipped bytes are part of the struct's extent, and a struct that also declares a size still ends at start+size.

ParseField(field, node)

A Physical Parser MUST parse a field by these steps, in this order; a step whose property the field does not declare does nothing:

  1. Presence. If bddo:isPresentIf is present and its HEL expression evaluates to false, skip the field (bind it to Null in the context) and return.
  2. Derived value. If bddo:valueFromExpression E is present, evaluate E in the field's context (), bind the result under the field's key, and return. The field consumes no bytes and has no byte extent; none of the steps below apply to it. A Null result leaves the field unbound, exactly as an absent optional field.
  3. Alignment. If bddo:alignment = a, advance the cursor to the next multiple of a, measured from the start of the current stream: the input stream, or, inside a field decoded by hexplain:isEncodedWith and re-parsed as a struct, the decoded sub-stream, whose offsets start at 0 (Stream metadata). Bounded regions do not move the origin: a field aligned to 4 inside a region starting at offset 6 starts at offset 8, not 10. The same origin applies to an offset-addressed field's aligned target.
  4. Addressing. If an offset property is present, compute the target offset from bddo:atOffset / atOffsetFromField / atOffsetFromExpression, relative to bddo:offsetBase: streamStart (the default) counts from the start of the current stream, streamEnd counts backward from |S|, the length of the current stream, currentPosition from the cursor, fieldStart from the start of the sibling field bddo:offsetBaseField names (Offsets from a sibling), and parentStart from the start offset of the containing struct node — the node node this field is bound into, whose start ParseStruct recorded in step 2, after any bddo:syncOnMarker seek (). The current stream is the input stream or, inside a field decoded by hexplain:isEncodedWith and re-parsed as a struct, the decoded sub-stream (Stream metadata); a bounded region is not a stream, so streamEnd inside one still counts from the end of the stream that holds it. Save the current cursor — the byte position and any partially consumed byte of the bit cursor — seek to the target, parse — the steps below, the field's bddo:padTo included, are all carried out at the target (Padding) —, then restore the saved cursor, bit position included (an offset field does not advance sibling parsing and does not disturb a run of bit fields) unless offsetBase is currentPosition. A target outside the innermost bounded region raises a bounds error, unless the field declares bddo:seekScope bddo:streamScope: then the target is resolved against the whole stream [0, |S|) and the region bound is suspended for the duration of this one read (and restored before the cursor is).
  5. Repetition. If a repetition property is present, determine the iteration policy: a fixed bddo:repeatCount, a count via repeatCountFromField/repeatCountFromExpression, or repeat-until (bddo:repeatUntil, evaluated after each element with the bindings of ). A bddo:repeatUntil on a field whose data type is a text container () is a description error: the container consumes its whole region, so no element could follow the first. Produce an ordered array node; each element is parsed by the single-value procedure below, and the fixed-value, enumeration and bddo:validIf steps apply to each element, self being the element.
  6. Type selection. If bddo:hasDispatchTable is present, a processor MUST evaluate the table's key — the parsed value of bddo:dispatchOnField, or bddo:dispatchOnExpression evaluated exactly as a bddo:DataTypeRule condition is — and select the bddo:DispatchArm of that table whose bddo:armKey equals it (strings by code points, integers numerically); if none matches, it uses bddo:dispatchDefault, else bddo:dataType. A processor MUST collect arms from the whole description graph, including imported ontologies; two arms with one key are a description error. Otherwise, if bddo:hasConditionalDataType is present, a processor MUST evaluate each bddo:DataTypeRule in list order and take the effective type from the first whose bddo:condition is true, via its bddo:ruleDataType. Otherwise it uses bddo:dataType. When none of these yields a type the processor raises a dispatch error; a field that declares both selection mechanisms is a description error ().
  7. Value. If the effective type is a bddo:Struct, recurse via ParseStruct. When that struct declares parameters, the arguments are evaluated first — the bddo:hasArgument list of what named the struct: the bddo:DataTypeRule or bddo:DispatchArm that selected it, or the field when it is the field's bddo:dataType — in list order, each with the containing struct as instance exactly as a bddo:sizeFromExpression of the field is evaluated, and passed to ParseStruct; for a repeated field they are evaluated anew before each element. An argument whose value is not of its parameter's bddo:parameterType (an Integer is accepted for bddo:FloatParameter and converted to Float), or that is a struct node or an array value for a parameter without a bddo:parameterType or with a scalar one, is an error; a bddo:NodeParameter accepts exactly a struct node and a bddo:ArrayParameter exactly an array value (an array node or a computed array), each passed by identity — nothing is copied, no byte is read, and the node keeps its place in the tree — and neither accepts Null. A wrong argument is a description error when it is a literal, known when the description is loaded, and otherwise a Type / HEL error raised when the argument is evaluated (). If the effective type is a bddo:DataType:
    • Determine the field's extent by the single rule of .
    • If bddo:bitLength is present, read that many bits per the bit-cursor rules () instead of whole bytes.
    • Decode the raw bytes to a typed value per , honouring the byte order of and (for strings) bddo:encoding. For a fixed-size bddo:string with bddo:trimNull true, the first NUL code unit of the field's bddo:encoding within the field's width is found in the raw bytes, before anything is decoded: the first 0x00 byte for a single-byte encoding or UTF-8, the first 00 00 pair at an even offset for bddo:utf16le and bddo:utf16be (a zero byte inside a UTF-16 code unit does not end the string). The value is the bytes before it, decoded by ; the NUL and every byte after it are padding, which is neither decoded nor validated. Without a NUL the value is the whole width, decoded. This is how NUL-padded names (TAR, ZIP) are read, whose padding real files often leave uninitialised.
  8. Fixed value. If bddo:hasFixedValue is present and the field's value differs from it, raise a validation error. The fixed value's literal decides what is compared. Only an xsd:hexBinary literal denotes bytes: on a bytes or string field a processor MUST compare it with the field's raw bytes, byte for byte, and on a numeric field it is the field's encoding in the field's byte order and MUST be exactly the field's width. Every other string literal (an xsd:string, a plain or a language-tagged literal) denotes characters, never hexadecimal digits: on a bytes field a processor MUST compare the field's bytes with the literal's UTF-8 encoding, so "CAFE" matches the four bytes 43 41 46 45 and not CA FE, and on a string field it MUST compare the decoded value — after bddo:trimNull, when the field declares it — with the literal by code points, whatever the field's bddo:encoding (a bddo:utf16le field holding 41 00 42 00 matches "AB", and a six-byte NUL-padded field holding 41 42 00 00 00 00 matches it too). A numeric literal on a numeric field MUST be compared by value at the field's width: an integer field matches an integer literal of equal value however the literal is typed and the field stored ("9994"^^xsd:int matches the integer 9994), and a float field matches the literal's value rounded to the field's format, so "0.1"^^xsd:double on a bddo:float32 field matches the float32 nearest to 0.1. On a bddo:float16 field a processor MUST round the literal to binary16 (round half to even) and compare at that width: "0.1"^^xsd:double matches the stored 2E 66 (0.0999755859375), "65504"^^xsd:float matches 7B FF, and a finite literal that rounds beyond 65504 overflows the format. A processor MUST raise a description error, when the description is loaded, for an xsd:hexBinary of another width on a numeric field, a string or Boolean literal on a numeric field, a numeric or Boolean literal on a string or bytes field, a fraction on an integer field, an integer outside the field's range, and a finite value that overflows a float field's format.
  9. Enumeration. If bddo:enumeration is present, look up the raw value among the enumeration's bddo:EnumValue resources; the matching symbol/label is attached to the value node (and emitted per ). If the enumeration has bddo:enumIsFlags true, the raw value is a bitmask: every bddo:EnumValue whose raw value's bits are all set in the parsed value matches, and all matching symbols are attached/emitted.
  10. Checksum. If bddo:checksum is present, compute the algorithm over the covered byte range — from the first byte of coversFromField, or the offset coversFromExpression yields, to the last byte of coversToField (inclusive), or up to and excluding the offset coversToExpression yields (the two bounds may mix a field and an expression); or the [start, end) range yielded by the deprecated coversExpression — and compare with the stored value; a mismatch raises a checksum error. A coverage bound outside the current (sub-)stream raises a bounds error; a range whose end precedes its start covers nothing and is not checked. The bddo:checksumAlgorithm values are the named algorithms of BDDO, Checksum Algorithms — bddo:crc32 (CRC-32 as in zlib), bddo:crc16 (CRC-16/CCITT-FALSE: polynomial 0x1021, initial value 0xFFFF), the further CRC-8, CRC-16, CRC-32 and CRC-64 variants, bddo:adler32, bddo:md5, bddo:sha1 and bddo:sha256 — and bddo:CustomCrc; an integer checksum is compared numerically, a digest byte for byte. Every CRC, named or custom, is computed by the Rocksoft model with the algorithm's six parameters as BDDO defines it, and compared with the checksum field's value read in the field's own data type, width and byte order. A CRC whose checksum field is not an integer field exactly as wide as the CRC (a bddo:uint16 for a CRC-16, a bddo:uint24 for a 24-bit custom CRC) is a description error. A digest (bddo:md5, bddo:sha1, bddo:sha256) is compared byte for byte with the checksum field's raw bytes, so its checksum field is a bddo:bytes field whose extent is exactly the digest's length — 16, 20 and 32 bytes — given as a literal bddo:size; a digest whose checksum field is not such a field (an integer or string field, a bddo:bytes field of another or of a non-literal size) is a description error, raised when the description is loaded. bddo:adler32 is a 32-bit integer check: its checksum field is an integer field exactly 32 bits wide, as for a CRC-32. An Adler-32 whose checksum field is not such a field is a description error, exactly as a CRC of another width and a digest whose field is not its bytes are (Checksum fields).
  11. Constraint. If bddo:validIf E is present, evaluate E once the field is bound (after the fixed-value and checksum checks), with self bound to the field's value (). false raises a validation error; an evaluation failure raises a Type / HEL error, not a validation error, because it reports a defect of the description rather than of the data.
  12. Root key. If bddo:rootKeyFromField is present, let k be the parsed value of the named sibling field; if k is a string and the root context has no binding for k, bind this field's value in the root context under k (first occurrence wins). This is what lets a later field say root.k.… about a record inside a repeated sequence.
  13. Bind the field's value into node under the field's simple key, and return.

Checksum fields. An algorithm fixes the kind and the width of the field that stores its result, and a field of another kind could only be compared by a conversion this document does not define. A processor MUST raise a description error, when the description is loaded, for a bddo:checksum on a field that is not of its algorithm's kind and width: for a CRC, named or custom, an integer field exactly as wide as the CRC; for bddo:adler32, an integer field exactly 32 bits wide, so that a bddo:uint16, a bddo:uint64, a bddo:bytes and a string field are each refused; for a digest (bddo:md5, bddo:sha1, bddo:sha256), a bddo:bytes field whose literal bddo:size is the digest's length, 16, 20 or 32 bytes.

Padding. A field MAY declare bddo:padTo. A processor MUST apply it once the field's value has been read and its checks made (after the Root key step): the cursor advances to the next multiple of the padding boundary (). For a repeated field the padding follows the whole sequence, not each element; an element that is padded is a struct that declares its own bddo:padTo. For an offset-addressed field a processor MUST apply the padding at the field's target, not at the saved cursor: after the value has been read there and the field's checks made, and before the saved cursor is restored, so that the padding is measured where the value ends and never moves the cursor from which the field's siblings are parsed. With bddo:offsetBase bddo:currentPosition, which restores nothing, the cursor is left after the padding.

Offsets from the containing struct. A format whose offsets are relative to the record that holds them (a TIFF IFD entry, a RIFF chunk, an ISOBMFF box) addresses its fields with bddo:offsetBase bddo:parentStart. A processor MUST resolve such an offset against the start offset of the containing struct node — the offset ParseStruct recorded for node in step 2, in the current stream, after any bddo:syncOnMarker seek, which is also the offset the struct's own size region is measured from — so the target is that start plus the offset's value. The containing struct is the struct the field is a member of, never an ancestor further up: a processor MUST NOT resolve parentStart against the root or any other struct, and for the root struct, or a struct parsed from a decoded sub-stream, the start offset is 0 in its own stream. A parentStart offset whose target lies outside the innermost bounded region (unless the field declares bddo:seekScope bddo:streamScope, which resolves it against the whole stream as above) MUST raise a bounds error; its value is never negative (below), so a target before the struct's start is reachable only through streamStart.

Negative offsets. An offset's value is what bddo:atOffset states, bddo:atOffsetFromField reads or bddo:atOffsetFromExpression yields; its target is the position that value gives from the field's bddo:offsetBase. Four bases count a distance from a fixed origin: streamStart forward from the start of the current stream, streamEnd backward from its end, parentStart forward from the start of the containing struct, and fieldStart forward from the start of a sibling field. A processor MUST raise a bounds error for a negative value with any of these four bases, whether the value is a literal, read from a field or computed: a negative distance names no position, and it is never reinterpreted as counting the other way. bddo:currentPosition is the one relative base: its value MAY be negative, which moves backward from the cursor, and for it a processor MUST NOT refuse the value for its sign but MUST raise a bounds error when the target lies outside the innermost bounded region (or, with bddo:seekScope bddo:streamScope, outside the stream), exactly as for a positive value. (bddo:FieldShape refuses a negative literal bddo:atOffset whatever the base, so a negative value of a validated description comes from a field or an expression.)

Offsets from a sibling. With bddo:offsetBase bddo:fieldStart an offset counts forward from the start of the sibling field bddo:offsetBaseField names: an earlier member of the same struct, so that "the table that begins 12 bytes after the directory" is an offset and a base rather than arithmetic over the sibling's own offset expression. The start of the base field is the position at which its value was read: after its alignment, at its target when it is offset-addressed, and, when it repeats, the first byte of its first element. A processor MUST resolve such an offset from the start of the base field in the current stream and MUST raise a bounds error when the target lies outside the innermost bounded region (or, with bddo:seekScope bddo:streamScope, outside the stream). A processor MUST raise a description error when the base field is not read before the offset-addressed field: when bddo:offsetBaseField names no earlier member of the same struct, or appears without bddo:fieldStart (both refused by bddo:OffsetBaseFieldShape, and raised when the description is loaded), and when the base field is absent, its bddo:isPresentIf having evaluated to false (raised when the offset is resolved).

Conflicting forms. Where a description gives one construct two forms, this document orders them only for the extent of a field (): of the four region forms the first in the order stated there decides, and declaring several is not an error. Every other pair has no order, and a processor that picked one would parse the other description's meaning as silently as a wrong guess. A processor MUST raise a description error, when the description is loaded, for each of these:

  • A repeat count and a repeat-until condition on one field: any of bddo:repeatCount, bddo:repeatCountFromField and bddo:repeatCountFromExpression together with bddo:repeatUntil, or two of the three count forms.
  • Two offset forms on one field: two of bddo:atOffset, bddo:atOffsetFromField and bddo:atOffsetFromExpression.
  • A dispatch table and conditional type rules on one field: bddo:hasDispatchTable together with bddo:hasConditionalDataType.
  • More than one value of a functional property on one resource: a property the family's vocabularies or shapes allow at most once, stated with two different values (for example two bddo:dataType, two bddo:size, two bddo:endianness or two bddo:hasFixedValue values on one field). The data type individuals the family's vocabularies define themselves (bddo:uint32 and the like) are exempt.

Bit-level fields (the bit cursor)

Bit-level fields (bddo:bitLength) are read through a bit cursor that tracks the current byte offset and a bit offset within it (0–7). A Physical Parser MUST move the bit cursor by these rules:

  1. Consecutive bddo:bitLength fields pack contiguously: each consumes the next bitLength bits from the current bit offset, advancing the cursor (rolling into the next byte when it reaches 8).
  2. Bits are consumed within each byte per the effective bddo:bitOrder (the field's own, else its containing struct's, else bddo:MSBFirst: ): bddo:MSBFirst takes bits from the most-significant end first; bddo:LSBFirst from the least-significant end.
  3. Every bit keeps its significance: under bddo:MSBFirst the first bit taken is the most significant bit of the field's value, under bddo:LSBFirst the least significant (as DEFLATE and GIF read their codes), so a 3-bit field read LSBFirst from 0xB4 is 4, the low three bits' value. A field spanning a byte boundary continues into the next byte in the same bit order, its later bits more significant under LSBFirst and less significant under MSBFirst.
  4. The bit cursor realigns to the next whole byte boundary before any byte-oriented read (a field without bitLength), before bddo:alignment, and at the end of a Struct; partial bits before the boundary are skipped.
  5. A bit read that would cross the end of the innermost bounded region (or |S|) raises a bounds error.

This makes sub-byte structures (IPv4 version/IHL, TCP data-offset + flags, PNG bit-packed samples) parse identically across implementations.

Size resolution

A field's extent is decided by exactly one rule. A Physical Parser MUST take the first of these cases that matches, and MUST NOT consult the later ones:

  1. Bits. A field with bddo:bitLength occupies that many bits (, bit cursor).
  2. Separated. A field with bddo:separatedBy is read as a separated token (). The bddo:FieldShape forbids combining it with any size or terminator.
  3. Fixed width. A field whose effective data type has a bddo:bitWidth occupies bitWidth / 8 bytes. Size properties on such a field do not change its width and are ignored.
  4. Self-delimiting. A variable-length integer (bddo:varuint, bddo:varint, bddo:sqliteVarint) occupies as many bytes as its encoding says ().
  5. Declared region and terminator. Otherwise (bytes, string, numbers written as text, and fields whose type is a Struct), the field's declared region is given by the first of these that the field declares: bddo:sizeToEndOfStream (up to the end of the innermost bounded region, or of the current stream if there is none), bddo:size, bddo:sizeFromField, bddo:sizeFromExpression. The region starts at the cursor.
    • With no bddo:terminator, the value is the declared region's bytes.
    • With a bddo:terminator, the value is found by the terminator rule below; the search is bounded by the declared region if there is one, else by the innermost enclosing bounded region (or the end of the current stream).
    • With neither a declared region nor a terminator, a field whose type is a Struct is sized by its own fields (and its own struct-level size, if any); any other field is a description error.

The bddo:FieldShape does not forbid declaring more than one of the four region forms, so the order above is normative. A description SHOULD declare at most one.

A declared region acts as a bounded region for everything read inside it: a nested struct cannot read past it, and after the field is read the cursor moves to the region's end whatever was consumed inside. A region that is negative or extends past the enclosing region raises a bounds error. bddo:sizeFromField names a field that is already bound: it is looked up in the containing struct first, then in its parent. Its value, or the value of bddo:sizeFromExpression, MUST be an integer; a number written as text is accepted by its numeric value.

Repetition. A processor MUST read a repeated field's extent as follows. With bddo:repeatCount (or repeatCountFromField / repeatCountFromExpression) the rule above gives the extent of each element. With bddo:repeatUntil a declared region bounds the whole sequence: elements are read until repeatUntil holds or the region is exhausted, and the cursor then moves to the region end. For a repeatUntil sequence only, a negative declared size means an empty sequence rather than an error, which is how formats write an absent area as a length of zero minus a header. A repeat count MUST be a non-negative integer; a negative count is a bounds error, as a negative size is. A sequence element that consumes no bytes and does not satisfy repeatUntil raises a bounds error rather than looping.

Terminators

A Physical Parser MUST read a field that declares bddo:terminator by these rules:

  1. The terminator is the byte sequence given by bddo:terminator; an empty terminator is a description error.
  2. The search starts at the cursor and finds the first occurrence of the sequence that lies entirely within the search bound. For a bddo:string whose bddo:encoding has a multi-byte code unit (bddo:utf16le, bddo:utf16be), only occurrences that start at an offset from the search start that is a multiple of the code-unit size (2) count, so a terminator can never match across two code units. For every other encoding and for bytes the search is byte-aligned.
  3. The value is the bytes from the search start up to, and excluding, the terminator. The terminator is consumed: it is part of the field's byte extent but not of its value.
  4. With a declared region, the cursor then moves to the end of the region (the bytes after the terminator are padding); without one, the cursor moves to just after the terminator.
  5. If no occurrence lies within the search bound, raise a bounds error.

Struct-level size

A processor MUST apply a struct-level size as this section states. A struct-level bddo:size, bddo:sizeFromField or bddo:sizeFromExpression gives the size of the struct's bounded region, which starts at the struct's start offset (after any bddo:syncOnMarker seek). A literal size is applied before the first field is read. A field-supplied or computed size is evaluated once every field and local binding of this struct that it references is bound — that is, immediately after the last such member in declaration order is processed — and the region is applied from that moment on. Fields of ancestor structs are already bound and may be referenced freely.

  • The size MUST NOT reference a field of this struct that has not been bound when the struct's field list is exhausted (a field declared later than every field that could supply it, or one skipped by bddo:isPresentIf): that is a forward reference and raises a Type / HEL error. The struct MUST NOT be left unbounded instead.
  • If, when the region is applied, the cursor already lies beyond its end, raise a bounds error.
  • The expression is evaluated with the struct as instance, and sizeof() of a field already parsed is available to it.
  • sizeof(x) is the byte length of the node x names, wherever it is in the tree — a field, a struct, an array element or a node reached through parent, root or asset — once that node has been parsed: its end offset minus its start offset. A derived field (bddo:valueFromExpression) has no byte extent, and sizeof of it is a Type / HEL error.

Byte order and bit order

A Physical Parser MUST read a multi-byte integer or float in the byte order given by the first of the following that applies:

  1. The data type's own byte order: an explicit big- or little-endian type such as bddo:uint32be or bddo:float64le always reads in its own order.
  2. The field's own declaration: bddo:endianness on the field, or the first rule of the field's bddo:hasConditionalEndianness whose condition holds, evaluated just before the field is read.
  3. The containing struct's own declaration: its bddo:endianness, or its resolved bddo:hasConditionalEndianness (below). The two are mutually exclusive.
  4. The byte order inherited from the enclosing struct: the order that was in force (by this same list) for the field through which this struct is being parsed. This applies equally to a struct re-parsed from a decoded sub-stream.
  5. Big-endian.

Conditional byte order on a struct. A processor MUST resolve a struct's conditional byte order as follows. The bddo:EndiannessRules are evaluated in list order, against the struct as instance, after each field of the struct is bound, until one rule's bddo:condition is true. That rule's bddo:ruleEndianness then applies to every later field of the struct and, by inheritance, to their descendants; it is resolved at most once per struct instance. Until a rule matches, the fields are read in the provisional order — the order cases 4 and 5 give — which is why the discriminating field (TIFF's II/MM) is normally byte-order-agnostic. A condition that cannot yet be evaluated because it names a field not yet bound counts as not holding. If no rule has matched when the field list is exhausted, the provisional order was the struct's order throughout.

Bit order. A Physical Parser MUST take the bit order of a bddo:bitLength field from the first of these that applies: the field's own bddo:bitOrder; the containing struct's own bddo:bitOrder; bddo:MSBFirst. A field's declaration applies to that field alone, and a struct's to the bit fields it declares directly; neither is inherited by a nested struct, which starts again from this list, and a field's declaration never changes the order of the fields around it. Bits of one byte are taken in one order: a bit field whose effective order differs from that of the bit field read just before it MUST begin on the next whole byte boundary (the bit cursor realigns first, as before a byte-oriented read, and the partial byte's remaining bits are skipped). An offset-addressed read starts with a fresh bit cursor at its target.

Alignment and padding

bddo:alignment positions where a field or a struct starts; bddo:padTo extends where it ends. Both name a boundary in bytes, a positive integer, and both are measured from the same origin, the alignment origin the subject's bddo:alignmentOrigin selects (below): by default the start of the current stream — the input stream, or, inside a field decoded by hexplain:isEncodedWith and re-parsed as a struct, the decoded sub-stream, whose offsets start at 0 (Stream metadata). A bounded region does not move the stream origin, for padding as for alignment: a struct that starts at offset 6 and pads to 4 after reading one byte ends at offset 8, not 10.

The origin. bddo:alignmentOrigin on a field or a struct names the origin of its own bddo:alignment and bddo:padTo: bddo:streamOrigin, the start of the current stream, which is also what a subject that states none means, or bddo:structOrigin, the first byte of the containing struct instance, for a format whose records are padded relative to themselves wherever they lie. A Physical Parser MUST measure each boundary from the origin its subject selects. With bddo:structOrigin that origin is, for a field, the start of the instance of the struct whose member it is (the start ParseStruct recorded, ); for a struct's bddo:padTo, the start of the instance being read, so that the instance's extent becomes a multiple of the boundary; and for a struct's bddo:alignment, the start of the instance of the struct containing the field the struct types, a root struct, which no struct contains, being not moved. The origin is not inherited: a member that states none uses the stream's start whatever its struct states. Under bddo:structOrigin the struct of the example above ends at offset 10. A bddo:alignment or bddo:padTo on a derived field (bddo:valueFromExpression), which occupies no bytes, is refused by bddo:DerivedFieldShape, and a processor that meets one MUST raise a description error when the description is loaded.

A Physical Parser MUST advance the cursor for either property to the least multiple of the boundary that is not less than the cursor, after realigning the bit cursor to a whole byte (); a cursor already on the boundary does not move, and a boundary of 1 moves nothing. The bytes skipped are neither decoded nor bound in the context, and they are not emitted. A skip that would pass the end of the innermost bounded region, or of the current stream when none is in force, MUST raise a bounds error rather than stop at the region's end: the description states where the next element starts, and that position does not exist.

Where each applies: a field's alignment in ParseField (Alignment), a struct's before the struct is parsed, a field's padding after the field and a struct's after its last member (Struct alignment, Struct padding, Padding). Bytes skipped by alignment precede the element and are outside its extent; bytes skipped by padding follow its value and are inside it, so sizeof of a padded field or struct counts its padding.

The fill byte. bddo:padByte states the octet the padding of a bddo:padTo is expected to hold. It is informative about the data: a processor MAY compare the skipped bytes with it, and one that does MUST raise a validation error when a skipped byte differs, a check on bytes already passed that leaves the cursor sound (). A processor MUST accept padding of any content when no bddo:padByte is stated, and MUST NOT verify the bytes skipped by bddo:alignment, which has no fill byte. A Writer writes what a reader may verify: the padding of a bddo:padTo is written as the bddo:padByte declared beside it, as 0x00 when none is declared, and the bytes a bddo:alignment skips are written 0x00 (Serialisation, Padding, alignment and offsets). A bddo:padByte without a bddo:padTo on the same field or struct describes no padding and is refused by bddo:PaddingShape; a processor that meets one MUST raise a description error.

Float formats, fixed-point and binary-coded decimal

Width, signedness and byte order say how many bits a number has and in what order its bytes come; three properties say how those bits are read when they are not a two's-complement integer or an IEEE 754 float. Each is stated on a field, or on a bddo:DataType a description mints so that every field of that type shares it; the field's own statement is taken first, then its effective data type's, and bddo:NumericRepresentationShape holds each to the base type it is for.

Float formats. bddo:floatFormat names the bit layout of a floating-point field: bddo:ieee754, which is also what a field means when none is stated, bddo:ibmHexadecimal, bddo:vaxF, bddo:vaxD, bddo:vaxG or bddo:bfloat16. A Physical Parser MUST decode each as follows, the field's value being an IEEE 754 value in every case:

  • bddo:ieee754: binary16, binary32 or binary64 by the data type's width, in the byte order in force.
  • bddo:ibmHexadecimal, for a 32- or 64-bit data type: read in the byte order in force, the most significant bit is the sign s, the next seven bits the exponent e, and the remaining 24 or 56 bits the fraction f, an unsigned integer; the number is (−1)s × f × 16e − 64 − 6 for 32 bits and (−1)s × f × 16e − 64 − 14 for 64 bits. A fraction that is not normalised is read by this formula like any other, and a zero fraction is zero of the stated sign whatever the exponent.
  • bddo:vaxF, for a 32-bit data type (F_floating): the bytes are two 16-bit words, each stored least significant byte first, the first word the most significant; this word order is the format's own, and the byte order in force is not consulted. In the 32 bits so assembled the most significant bit is the sign s, the next eight the exponent e and the remaining 23 the fraction f. With e ≠ 0 the number is (−1)s × (0.5 + f / 224) × 2e − 128; with e = 0 and s = 0 it is zero, whatever the fraction; e = 0 with s = 1 is VAX's reserved operand, which is no number, and is a validation error. On a 64-bit data type bddo:vaxF is the deprecated spelling of bddo:vaxD, what it meant before the VAX formats had a term each, and is read exactly as bddo:vaxD is; bddo:FloatFormatWidthShape reports it at sh:Warning, so the description stays valid (Valid description).
  • bddo:vaxD, for a 64-bit data type (D_floating): four 16-bit words in the word order of bddo:vaxF; in the 64 bits so assembled the sign s, an eight-bit exponent e and a 55-bit fraction f. With e ≠ 0 the number is (−1)s × (0.5 + f / 256) × 2e − 128; zero and the reserved operand are as for bddo:vaxF.
  • bddo:vaxG, for a 64-bit data type (G_floating): four 16-bit words in the word order of bddo:vaxF; in the 64 bits so assembled the sign s, an eleven-bit exponent e and a 52-bit fraction f. With e ≠ 0 the number is (−1)s × (0.5 + f / 253) × 2e − 1024; zero and the reserved operand are as for bddo:vaxF.
  • bddo:bfloat16, for a 16-bit data type: read in the byte order in force, a sign bit, an eight-bit exponent and a seven-bit fraction, which are the sixteen most significant bits of the IEEE 754 binary32 value whose other sixteen bits are zero. The value is that binary32 value, NaN and the infinities included.

The number an bddo:ibmHexadecimal, bddo:vaxF, bddo:vaxD or bddo:vaxG field holds MUST be converted to the IEEE 754 format of the field's own width, binary32 or binary64, rounding to nearest with ties to even; a magnitude beyond that format's largest finite value becomes the infinity of its sign, and one below its smallest subnormal becomes zero of its sign. The converted value is the field's value wherever a value is read: in HEL, in a fixed-value comparison, in bddo:validIf and when the field is emitted (). A processor MUST raise a description error, when the description is loaded, for a float format on a width it is not defined for (bddo:FloatFormatWidthShape): bddo:ibmHexadecimal or bddo:vaxF on a 16-bit type, bddo:vaxD or bddo:vaxG on a 16- or 32-bit one, bddo:bfloat16 on a 32- or 64-bit one. A 64-bit bddo:vaxF is not among them: it is the deprecated spelling of bddo:vaxD. A float format on a field that is not floating-point is refused by bddo:NumericRepresentationShape, and is a description error likewise.

Binary-coded decimal. bddo:bcd true on an integer field says its bytes are packed decimal digits: two per byte, the high nibble the more significant digit of the pair, the bytes taken in the byte order in force (most significant pair first under big-endian, last under little-endian). A Physical Parser MUST read the field's value as the non-negative decimal number those digits spell, so the two big-endian bytes 12 34 are 1234 and the same bytes little-endian are 3412. A nibble above 9 is no digit: a processor MUST raise a validation error for it, the field's extent being known, so the cursor is sound. Packed decimal is a whole-byte, fixed-width representation: bddo:bcd true on a field with bddo:bitLength, on a variable-length integer on a number written as text or on a signed data type is a description error (bddo:BcdShape), as is bddo:bcd true together with bddo:fixedPointScale, which bddo:NumericRepresentationShape refuses. bddo:bcd false is the same as no statement.

Fixed-point scale. bddo:fixedPointScale k on an integer field says the integer read stands for itself times 2k: a Q16.16 number has scale −16. It changes nothing a Physical Parser does: the field's value in the logical tree, and so in HEL, in a fixed-value comparison and in bddo:validIf, is the integer as read. It is a Semantic Emitter that applies it, when the field's value is emitted (below), and a scale beyond the range a processor supports, which reaches −4096 to 4096 at least, is a description error there.

Decoding text

One rule decodes text wherever this document reads it: a bddo:string field (fixed-size, terminated or separated; with bddo:trimNull, only its value bytes, below), a number written as text, the content of a delimited, key/value or tree container, and a Bytes value that HEL reads as a String. The encoding is the bddo:encoding in force, bddo:utf8 when none is declared. Five encodings are decoded by every Physical Parser — bddo:utf8, bddo:ascii, bddo:latin1, bddo:utf16le and bddo:utf16be — and a byte sequence is well-formed in them as follows (the further encodings are below):

  • bddo:utf8: well-formed UTF-8 as [[RFC3629]] defines it — no truncated or overlong sequence, no encoded surrogate (U+D800–U+DFFF) and nothing beyond U+10FFFF.
  • bddo:utf16le, bddo:utf16be: an even number of bytes, every high surrogate immediately followed by a low surrogate, and no low surrogate that does not follow one.
  • bddo:ascii: every byte at most 7F.
  • bddo:latin1: every byte sequence.

Further encodings. BDDO registers twelve more encodings, and a description may mint its own. Each names its character set with bddo:ianaCharset, the set's name in the IANA Character Sets registry, compared without regard to case; the five encodings above state theirs too. The two UCS-2 encodings are the exception and state none: the registry's name for UCS-2, ISO-10646-UCS-2, does not determine a byte order, so the byte order of bddo:ucs2le and of bddo:ucs2be is given by the term and by nothing else. A processor that decodes a further encoding MUST decode it by its character set's mapping to Unicode, and MUST take a byte sequence as well-formed in it exactly as follows:

  • bddo:utf32le, bddo:utf32be: a multiple of four bytes, each four a Unicode scalar value in the encoding's own byte order (no surrogate, nothing beyond U+10FFFF). A byte order mark is ordinary content, and the struct's byte order is never consulted, as for UTF-16.
  • bddo:ucs2le, bddo:ucs2be: an even number of bytes, each two a character of the Basic Multilingual Plane. A surrogate code unit (D800–DFFF) is not well-formed, paired or not, which is what distinguishes UCS-2 from UTF-16.
  • bddo:windows1252, bddo:iso8859_2, bddo:iso8859_5, bddo:iso8859_7, bddo:iso8859_9, bddo:iso8859_15, bddo:ebcdic037: one character per byte, by the character set's registered mapping to Unicode. A byte to which the set assigns no character (81, 8D, 8F, 90 and 9D in windows-1252; AE, D2 and FF in ISO-8859-7) is not well-formed; it is never passed through as a control character.
  • bddo:shiftJis: one or two bytes per character by the Shift_JIS mapping; a lead byte (81–9F, E0–FC) with no trail byte after it, a trail byte outside 40–7E and 80–FC, and a pair to which the set assigns no character are not well-formed.
  • A bddo:CustomEncoding: by the character set its bddo:ianaCharset names, a sequence being well-formed when that set's decoder accepts all of it without substituting or dropping anything. The bddo:ianaCharset of a custom encoding MUST name a character set that determines the byte order of its code units (UTF-16BE, never UTF-16 or ISO-10646-UCS-2): a custom encoding has no term of its own to give one, and the name is all a processor has to decode the bytes with.

Everything this section says of text applies to them: a sequence that is not well-formed is a validation error and is never replaced. The code unit, which decides where a NUL or a multi-byte terminator may start (; ParseField, Value), is four bytes for the UTF-32 encodings, two for UCS-2 as for UTF-16, and one byte for every other encoding, the double-byte Shift_JIS included, none of whose trail bytes is 00.

A Physical Parser need not decode a further encoding (Refusal, case (e)). A processor MUST state the further encodings it decodes in its claims statement, as the member encodings: an array of the IRIs of the registered bddo:Encoding individuals it decodes beyond the five (https://hexplain.io/ns/bddo#windows1252); the five need not be listed, and a statement without the member states that the processor decodes no further encoding. The processor conformance suite runs a case that uses a further encoding only for a processor whose statement lists it. A processor that does not decode the character set of an encoding a description uses — a registered encoding beyond the five, or a bddo:CustomEncoding whose bddo:ianaCharset it has no decoder for — MUST raise an Unsupported feature error, and SHOULD raise it when the description is loaded, since the encoding is stated in the description and not in the data. It MUST NOT read the field in another encoding, as bytes, or as bddo:latin1 because every byte sequence is well-formed there: text decoded in the wrong character set is a plausible but wrong value. A processor that decodes the character set of a bddo:CustomEncoding MUST decode it exactly as it would a registered encoding of that set, so that ex:Latin2 with bddo:ianaCharset "ISO-8859-2" and bddo:iso8859_2 read the same bytes as the same text. The warning bddo:FieldShape reports for an encoding outside the registered set is a validation result about the description's portability, not an error of the parse. A bddo:CustomEncoding without exactly one bddo:ianaCharset names no character set, is refused by bddo:CustomEncodingShape, and is a description error.

A processor MUST NOT replace a sequence that is not well-formed with U+FFFD or any other character, nor drop it. Text read from the input that is not well-formed — the value of a string field, a number written as text, a container’s content — MUST be raised as a validation error. The field’s extent is known before its bytes are decoded, so the cursor is sound: a lenient mode records the error, leaves the field (or the container) unbound and continues with what follows it. A byte order mark is ordinary content, except at the start of a container or tree document where and say otherwise. For a fixed-size bddo:string field with bddo:trimNull true, a processor MUST decode only the bytes before the field's first NUL code unit, which is located in the raw bytes before any decoding (ParseField, Value), and MUST NOT decode or validate the bytes from that NUL to the end of the field: they are padding, not text, and a sequence there that is not well-formed is not an error. Those value bytes are text read from the input like any other, so a sequence in them that is not well-formed is a validation error. The digits, sign, point and exponent letter of a number written as text, and the whitespace around it, MUST be ASCII characters (whitespace being space, tab, line feed, vertical tab, form feed and carriage return): a non-ASCII digit or space makes the text not a number. HEL reads a Bytes value as a String by this same rule: one that is not well-formed equals no String and is an error where a String is required (HEL, Bytes vs. String).

Numbers written as text, separated tokens and varints

A Physical Parser MUST read these self-describing values as follows:

  • Text numbers. A field of bddo:asciiInteger or bddo:asciiDecimal (or any type with an integer or float base type and no bit width) is read from its extent () and decoded per its bddo:encoding. Surrounding whitespace and NUL bytes and a leading + are removed. An integer is then read in radix bddo:numericBase (8, 10 or 16; default 10); a decimal accepts a sign, a decimal point, and an exponent introduced by E, e, D or d, and the spelling nan in any case with an optional sign. Anything else, including an infinite value, is a validation error: the value is never kept as a string.
  • Separated tokens (bddo:separatedBy "whitespace"). The separator class is the bytes space, tab, CR and LF. An element consumes the run of separator bytes before it, then the token (the maximal run of non-separator bytes), then the run after it; the token is read as a text number. An empty token (the region holds only separators) is a bounds error. The scan is byte-wise, so the field's encoding MUST be UTF-8, US-ASCII or ISO-8859-1; any other is a validation error.
  • Varints. bddo:varuint is LEB128: seven value bits per byte, least-significant group first, the high bit set on every byte but the last. bddo:varint is a LEB128 value carrying a zigzag-encoded signed integer. bddo:sqliteVarint is one to nine big-endian bytes, the high bit of each of the first eight a continuation flag and the ninth contributing all eight bits. A varint that runs past its bound, or that exceeds the 64-bit range, is a bounds error.

Delimited, key/value and tree containers

A struct typed bddo:DelimitedRecords, bddo:KeyValueHeader, bddo:DelimitedTable or bddo:TreeDocument locates its fields by delimiter position, by key, or by path, not by byte offset. Such a container consumes all remaining bytes of the innermost bounded region — including a region established by the size of the field through which it is parsed — or, when it is the root or nothing bounds it, the rest of the current stream. Its field list is then processed as follows instead of by ParseField; bddo:isPresentIf, bddo:validIf, enumerations and mappings on its fields still apply to the values found.

Records

A Physical Parser MUST split a delimited container into records and values by these rules:

  1. The bytes are decoded in the bddo:encoding declared on the field through which the container is parsed, or as UTF-8 when none is declared. A sequence that is not well-formed () is a validation error (recorded as a finding and skipped in a lenient mode); it is never replaced silently. A leading UTF-8 byte order mark is ignored.
  2. The text is split into records at each occurrence of bddo:recordDelimiter (default 0A, LF) that is not inside a quoted value (below). When the delimiter is 0A, a CR immediately before it is removed, so CRLF text reads the same as LF text. A record delimiter at the very end yields no final empty record.
  3. The first bddo:skipRecords records (default 0) are discarded; then every record that, after leading whitespace, begins with bddo:commentPrefix is discarded.
  4. Values within a record. With bddo:fieldDelimiter, a record is split into values at each occurrence of the delimiter sequence outside a quoted value. With bddo:whitespaceSeparated true, values are separated by runs of space, tab, CR or LF: a run of any length separates exactly two values, and leading and trailing whitespace on the record is ignored; if bddo:recordDelimiter is also absent, the whole content is one flat sequence of values, whose shape comes from the field's layout or repeat count. With neither, a record is a single value.
  5. Quoting. With bddo:quoteChar q, a value that begins with q is quoted: it extends to the next q not immediately followed by another q, may contain the field delimiter, the record delimiter and line breaks, and has its quotes removed; a doubled qq inside it denotes one literal q. With bddo:escapeChar e, e followed by any character yields that character with no delimiter or quote meaning. A quoted value still open at the end of the container is a validation error.
  6. With bddo:trimWhitespace true, leading and trailing whitespace is removed from every key and value.

Key/value headers

A processor MUST locate the fields of a key/value header as this paragraph states. In a bddo:KeyValueHeader, each record is split at the first occurrence of bddo:keyValueSeparator into a key and a value; a record without the separator carries no pair and is ignored. Each field takes the value of the record whose key equals its bddo:key, or, for a field that declares no bddo:key, its simple key () (compared ignoring ASCII case when bddo:keyIsCaseInsensitive is true, else exactly); a key that no record carries leaves the field unbound (Null); when several records carry the key, the last wins. Record order is not significant, and records whose key no field names are ignored. The container yields one node.

Nested groups. A container with bddo:hasGrouping nests records into named groups by its bddo:groupingStyle: bddo:keyedGroup (a record whose key is bddo:groupOpenToken opens a group named by its value; one whose key is bddo:groupCloseToken closes the innermost open group), bddo:valuedGroup (the mirror: the value is the token and the key names the group), or bddo:sectionHeaded (a record groupOpenToken name groupCloseToken opens a group and closes the previous one; the last group runs to the end; sections do not nest). A field is then located by bddo:keyPath: the enclosing group names and finally the key, joined by bddo:pathSeparator (default /), matched by the same rules as bddo:key; a field of a grouped container located by bddo:key names a record outside every group. Group tokens are compared, and group names matched, by the same rule (ignoring ASCII case under bddo:keyIsCaseInsensitive), after removing surrounding whitespace. A record that carries no bddo:keyValueSeparator still counts as a group record when, after removing surrounding whitespace, it is the close token alone (keyed style: ODL's bare END_OBJECT) or a name, a run of whitespace and the open or close token (valued style: ERMapper's DatasetHeader Begin). A close token with no open group, or a group of the keyed or valued style still open at the end of the container, is a validation error.

Tables and record lists

A processor MUST bind the records of a table as this paragraph states. In a bddo:DelimitedTable or plain bddo:DelimitedRecords, each record yields one row node, in record order, and the container's value is the ordered array of rows. The values of a record are matched to the fields by position, in bddo:hasField order. A record whose number of values differs from the number of fields is a validation error; a lenient mode MAY record it as a finding and continue with the next record, binding the values it has and discarding the extra ones. (An empty value is a value: a record a,,c has three.)

Flat value sequences. A bddo:whitespaceSeparated container with no bddo:recordDelimiter is one sequence of values; every Physical Parser MUST support it. The values are bound to the container's field that repeats (by its repeat count, or by the element count of its data layout); a number of values different from that count is a validation error.

Typed values

A value found in any text container is a String unless its field's data type is a number written as text, in which case it is read by the text-number rule of . A value that does not parse as the declared number is a validation error; it MUST NOT be kept as a string, because an expression reading a declared number cannot tell such a string from a real one. An empty value of a numeric field is likewise a validation error; a value that is absent (no cell, no key) leaves the field unbound instead.

Tree documents

A bddo:TreeDocument hands its bytes to a parser for its bddo:treeSyntax: bddo:xml (XML 1.0 with namespaces) or bddo:json (JSON, [[RFC8259]]). A document that is not well-formed is a validation error. JSON is read as UTF-8, strictly as [[RFC8259]] defines it: a leading byte order mark is ignored, and malformed UTF-8, a trailing value, single quotes or NaN make the document not well-formed. An XML parser MUST NOT fetch external entities or DTDs, and entity expansion counts toward the resource limits; a processor MAY decline to process a document type declaration at all, and a reference to an entity that only a declaration would define is then a validation error (the reference implementation processes no DTD, so the billion-laughs and external-entity attacks both end there). A reference to an external entity MUST be reported as a validation error whether or not the processor reads the declaration, since the entity's text is never fetched.

  • Each field is located by its bddo:nodePath. For bddo:xml the path is abbreviated XPath restricted to child steps, one final attribute step (@name) and 1-based positional predicates ([n], the n-th child matching the step's name); its prefixes are those bound by bddo:hasNamespaceBinding (bddo:namespacePrefix to bddo:namespaceIRI; the empty prefix binds the default namespace), and a prefix not bound is a description error. Names are matched by namespace IRI and local name, never by the prefix the document happens to use; an unprefixed element step is in the namespace bound to the empty prefix (in no namespace if none is), an unprefixed attribute step is in no namespace, as in XML Namespaces, and the prefix xml is predeclared. A path beginning with / starts at the document root; one without starts at the context node, which for the container itself is the document. For bddo:json the path is a JSON Pointer [[RFC6901]]. A path that does not follow its syntax is a description error.
  • A path selecting no node leaves the field unbound. A path selecting several nodes (for JSON, a duplicated member name) is a validation error unless the field repeats (declares a repeat count), in which case its value is the selected nodes in document order, and a number of nodes other than the count is a validation error. Because a JSON Pointer selects one node, a repeating field whose pointer selects one JSON array repeats over the array's elements.
  • The value of a selected XML element is its string value (the concatenation of its descendant text), of an attribute its value; the value of a JSON string, number or boolean is its text, and JSON null leaves the field unbound. The value is then typed as in . Selecting a JSON object or array for a field that is not a struct is a Type / HEL error.
  • A field whose data type is a bddo:TreeDocument of the same syntax binds, for each node it selects, a struct whose fields are located with that node as the context: a JSON Pointer is evaluated against the selected value, and an XML path without a leading / from the selected element. Selecting an attribute or a JSON scalar for such a field is a Type / HEL error.

Data layouts

A field with hexplain:hasDataLayout is read as a byte block by the rules above; the DLV layout then says how cells are addressed within it. Before any cell is addressed, a processor MUST resolve the layout against the field's containing struct: each dlv:dimensionSizeFromField, dlv:dimensionStrideFromField, dlv:chunkSizeFromField and dlv:cellBitWidthFromField reads the named field (looked up as for bddo:sizeFromField), each dlv:dimensionSizeFromExpression, dlv:dimensionStrideFromExpression, dlv:chunkSizeFromExpression and dlv:cellBitWidthFromExpression is evaluated with the containing struct as instance (HEL, name binding), and the first holding arm of dlv:hasConditionalCellDataType and of dlv:hasConditionalDimensionOrder is selected (DLV conditional layout). A size, stride, chunk extent or packed width that does not resolve to an integer, or a conditional list with no holding arm, is a Type / HEL error. A stride that resolves to an integer that is not positive (dlv:dimensionStrideFromField reading 0 or a negative value, or dlv:dimensionStrideFromExpression yielding one) is a description error, which a processor MUST raise when the layout is resolved, before any cell is addressed: a literal stride is held positive by the DLV shapes, and one the stream supplies cannot address a cell either; an arm whose condition fails to evaluate is also an error, never an arm that is merely false. A packed cell (dlv:cellBitWidth not a multiple of 8) is an integer read in dlv:cellPackingOrder. A packed width on a cell type that is not an integer is a description error wherever the width comes from. A processor MUST raise this description error when the description is loaded where the width is a literal, and when the layout is resolved, before any cell is addressed, where the width comes from a field (dlv:cellBitWidthFromField) or is computed (dlv:cellBitWidthFromExpression) and the value it then has is not a multiple of 8: it is the description that pairs a cell type with a width it cannot have, whatever the stream supplied, so the error is never a validation error. The three computed forms complete what dlv:dimensionStrideFromExpression began: an extent, a chunk extent and a packed width may each be a literal, a field or an expression, and exactly one of the three, as the DLV shapes require. A processor MUST resolve a computed form when the layout is resolved, before any cell is addressed, and never per cell, so that an expression that reads the stream position or a field of the struct yields one value for the whole layout. A processor that claims chunk-order-other MUST order the chunk table of a dlv:morton or dlv:hilbert layout by the key DLV constructs for that order and no other: the bit-interleaved Morton key and the Hilbert index of Skilling's algorithm, over the chunk indices in declared dimension order, each dimension's chunk count padded to the next power of two and the keys of cells outside the real counts skipped (dlv:morton, dlv:hilbert; J. Skilling, Programming the Hilbert curve, AIP Conference Proceedings 707, 2004). Two processors that built the key differently would read different chunks from one table, so the construction is part of the order's meaning, not an implementation choice. Serialisation (write direction)

A Writer turns a logical tree T — struct, value and array nodes of the shape the parse algorithm produces for a description D and a root struct R — back into a byte stream. Writing is the optional feature writer (): it binds a Physical Parser that claims it, and no other processor. The rules below are the parse rules read in the other direction; where this section is silent, a Writer does what makes the parse rules read back what it wrote. A Writer MUST serialise a struct node by these rules, in field order, and MUST raise the stated error rather than write a stream that the description would not read back:

  1. Field order and presence. The members of bddo:hasField are written in list order, each present field once, at the position the parse rules read it (a bddo:syncOnMarker struct begins with its marker bytes). A field whose bddo:isPresentIf evaluates to false over the fields written so far is not written, and MUST be unbound (Null) in T; a field whose condition is true MUST be bound. A derived field (bddo:valueFromExpression) and a local binding write nothing. A tree that binds a field the description does not declare, leaves a required field unbound, or holds a node of another kind than the field's effective type calls for is inconsistent with D: a validation error. Kind here is the node's kind — a struct node, a value or an array node — so a struct node for a scalar field, a scalar for a struct and a single value for a repeated field are each refused; whether a value fits its data type (an integer out of range, text the encoding cannot represent) is decided by the rules below. A field with bddo:hasFixedValue is written as that constant, by the rules that compare it at parse (Fixed value): a tree that leaves the field unbound gets the constant, and a tree that binds a different value is a validation error, never a stream that the description would refuse to read.
  2. Dependent lengths, counts and checksums. A field that another member's extent, count or integrity depends on — the target of bddo:sizeFromField, bddo:repeatCountFromField, dlv:dimensionSizeFromField or dlv:cellBitWidthFromField, and a field with bddo:checksum — holds a derived value, recomputed from T: the serialised byte length of the dependent field (terminator included, codec applied, and the padding of rule 3 included where a bound length is the width a value is padded to), the number of elements of the dependent array, or the checksum over the covered bytes of the output. A Writer MUST write the recomputed value, and fills the field when T leaves it unbound. When T binds the field, what a differing value means depends on what the recomputation rests on. A length or a checksum that rests on bytes a codec produced — the length of an encoded field, a checksum whose covered range includes one — is recomputed and written even when T binds another value: an encoder's output is its own (another level, another implementation), so the value the tree carries from the stream it was parsed from says nothing about the bytes being written, and holding the tree to it would refuse every re-encoded tree. Every other bound dependent value — a length of bytes the tree itself determines, an element count, a checksum over such bytes — MUST equal its recomputation, and a Writer MUST raise a validation error when it differs, so that a tree is never silently corrected. A size or count given by bddo:sizeFromExpression or bddo:repeatCountFromExpression cannot be inverted: the expression is evaluated over the fields written so far, exactly as at parse, and a value that does not match what T serialises to is a validation error.
  3. Extent inference. A field's extent follows the size-resolution order of , read in the write direction. A Writer MUST write a field that has no declared region in the extent its type gives: a bddo:bitLength field as that many bits through the bit cursor in the effective bit order (the field's own bddo:bitOrder, else its struct's), a fixed-width type as bitWidth / 8 bytes in the effective byte order, and a varint as the shortest encoding of its value, whatever length the stream a tree was parsed from gave it. A separated field writes its token, and a Writer MUST precede an element by one separator byte (0x20) whenever the bytes written just before it are a token this Writer rendered — the previous element of the same array, or the token of the separated field before it — so that two consecutive separated scalar fields do not run together, and the first token of a region is preceded by nothing. A Writer MUST fill a declared region of literal bddo:size to its end with fill bytes after a shorter value, and MUST raise a validation error for a longer one. The value of an encoded field is its encoded bytes (rule 7): a Writer MUST raise a validation error for an encoding longer than its literal region, and for a shorter one unless the region, filled to its end, decodes by the field's steps to exactly the bytes that were encoded — a codec that stops at the end of its own data and ignores what follows reads the fill back; one that reads every byte it is given, as Store does, or that refuses bytes after its data, as a compressor does unless told to ignore them, does not. A region from a field or expression holds, for a scalar (bytes, a string, a number written as text), the value: when T leaves the length field unbound the region is the value's own length, which rule 2 writes into the field; when T binds it, or an expression gives it, that length is the region. A Writer MUST then pad a value shorter than the bound length where the parse rules remove the padding — a bddo:string with bddo:trimNull true is followed by NUL code units to the bound length, and a number written as text is padded as rule 5 states — and MUST raise a validation error for any other value whose length is not exactly the bound length (bytes, a string without bddo:trimNull, a string whose NUL padding would not be a whole number of code units) and for every value longer than it. For a nested struct the bound length is likewise the region: the struct is serialised into a region of the length the field or expression gives, its members must fit, and the region is filled to its end with fill bytes, as a literal size is. A Writer MUST write a terminated field as its value followed by the terminator, and MUST raise a validation error for a value in which the terminator sequence occurs (at a code-unit boundary, for a multi-byte encoding), since it would read back shorter. A bddo:sizeToEndOfStream field writes its value and ends the current region. A Writer MUST NOT pad a bddo:sizeToEndOfStream sequence read by bddo:repeatUntil whose condition ends it before the region does: it is written as its elements, the bytes after it being whatever follows in the tree. A struct's declared size is applied as a region: its fields MUST fit, and the region is filled to its end.
  4. Padding, alignment and offsets. A fill byte is 0x00, with one exception: the padding of a bddo:padTo is filled with the bddo:padByte declared beside it, and with 0x00 when none is declared (The fill byte). The unused low-order bits of a partial byte the bit cursor leaves at a realignment point are 0. bddo:alignment writes fill bytes to the next multiple of the alignment, measured from the alignment origin as at parse, and bddo:padTo writes its fill from the end of the field's value, or of the struct's last member, to the next multiple of its boundary, measured from the same origin. An offset-addressed field (bddo:atOffset and its forms, with its bddo:offsetBase) is written at its target, its bddo:padTo padding after its value there, and the cursor restored afterwards as at parse: the output is addressable, the bytes between the cursor and a target not yet written are fill bytes, and a target already written with different bytes, or a target before the start of the stream, is a validation error. Offset values are taken from T (the offset field's value or the expression's result); this version does not derive offset tables.
  5. Text and text numbers. A string is encoded in its bddo:encoding; a character the encoding cannot represent is a validation error. A bddo:string with bddo:trimNull true whose width is fixed — a literal bddo:size, or a length that a bound field or an expression gives (rule 3) — writes the value followed by NUL code units to that width; a value longer than the width is a validation error. A number written as text is rendered canonically: an Integer as its digits in radix bddo:numericBase (upper-case digits above 9), a - for a negative value and no +; a Float as the HEL canonical Float spelling, NaN as nan, and an infinite Float, which no text number spells, is a validation error; in a field of literal size, and in one whose width a bound field gives (the target of bddo:sizeFromField that T binds, whose value is then the width to write and is not recomputed from the rendering), the digits are padded on the left with 0 after the sign to the field's width, and a rendering that does not fit is a validation error. nan has no digits to pad: in a field wider than three bytes it is followed by spaces (0x20) to the field's width, which the parse rules remove. A terminated, separated or to-end text number is not padded.
  6. Type selection and byte order. A dispatch table, conditional data type, conditional byte order, parameter argument and local binding are evaluated over the fields written so far, with the bindings the parse gives them; the selected struct is the one the node is serialised as, and a node whose members are not exactly that struct's fields is a validation error. A node under a parameterised struct is serialised with the arguments the selecting rule names. The effective byte order and bit order are those of .
  7. Codec encode parameters. A field with hexplain:isEncodedWith or hexplain:hasEncodingStep is serialised to a fresh sub-stream (its struct, or its bytes), which is then encoded by the steps in list order — encode order — each step by its codec's contract with the step's parameters (a level of Deflate, a cname of Blosc) and parameter expressions and run-time selections evaluated over T as at parse; the encoded bytes are then the field's value for rule 2. Every encode starts a fresh session. A codec whose contract defines no encode direction, or which this processor does not encode, is refused with Unsupported feature; a pipeline whose kinds do not connect in encode order is a description error. Each encode output counts toward the decoded-byte limit (), and an output that exceeds it is a resource-limit error, raised before the bytes are written; it is the one error of a Writer that is not a refusal of the tree or of the description.
  8. Checksum back-patching. A bddo:checksum field is written as fill bytes in its place, and once every field of its struct is written the checksum is computed over the covered range of the output — the bounds resolved over T and the written offsets exactly as at parse, so coverage may include bytes written after the field — and written into the field's extent in the field's data type, width and byte order (rule 2 decides when a bound value is an error). Checksums are patched innermost struct first, so an outer checksum covers the patched bytes of an inner one.
  9. Numeric representations. A field with bddo:floatFormat, bddo:bcd or bddo:fixedPointScale is written by the inverse of , and where the representation has no bit pattern that reads back as the tree's value the Writer refuses the tree. A Writer MUST write a bddo:ibmHexadecimal field as the normalised number of the format nearest the value, ties to even — the fraction's leading hexadecimal digit not zero, the exponent between 0 and 127, in the byte order in force — and a zero as a zero fraction and a zero exponent under the sign of the zero. A Writer MUST write a bddo:vaxF, bddo:vaxD or bddo:vaxG field as the F_floating, D_floating or G_floating number equal to the value (a 64-bit bddo:vaxF as D_floating), in the format's own word order, and a positive zero as all-zero bytes. A Writer MUST write a bddo:bfloat16 field as the sixteen most significant bits of the binary32 value, NaN and the infinities included, in the byte order in force. A Writer MUST raise a validation error, and write nothing for the field, when the bits so chosen would not read back as the value by the parse rule: a NaN or an infinity in an IBM or a VAX field; a magnitude outside the format's range (an IBM exponent above 127 or below 0, a VAX exponent outside 1 to 255, or 1 to 2047 for G_floating); a negative zero in a VAX field, whose sign bit with a zero exponent is the reserved operand; a significand the format cannot carry exactly; and a binary32 value whose sixteen low bits are not zero in a bddo:bfloat16 field. A Writer MUST write a bddo:bcd field as the decimal digits of its value, two to a byte, the high nibble the more significant, padded with leading zero digits to the field's width and laid out in the byte order in force, and MUST raise a validation error for a negative value and for one of more digits than twice the field's width in bytes. A bddo:fixedPointScale changes nothing a Writer does: the tree holds the integer as read (Fixed-point scale), and a Writer MUST write that integer unchanged, never a value it has scaled. An IEEE 754 field (bddo:ieee754, or no stated format) is written as the binary16, binary32 or binary64 value of its width nearest the tree's value, ties to even — exactly the value, for a tree a parse produced; every NaN, infinity and signed zero has a bit pattern, and a finite value whose magnitude exceeds the width's largest finite value is a validation error, as an integer out of its type's range is.
  10. Scope. This version defines writing for the byte-level constructs. A Writer MUST refuse, with Unsupported feature, a description that reaches a text or tree container (a bddo:DelimitedRecords, a key/value header, a delimited table or a bddo:TreeDocument: ), a layout with a chunk table (dlv:chunkOffsetsFromField, dlv:chunkLengthsFromField), or a construct of a class or optional feature it does not claim.

Symmetry. For every tree T that a Physical Parser produced, without error and with no lenient-mode recovery, from a stream S with a description D and root R, a Writer MUST either produce a stream S' such that parsing S' with D and R yields a tree isomorphic to T, or raise the error these rules require; it MUST NOT produce a stream that parses to a different tree or does not parse. What symmetry forbids is that third outcome, a stream that reads back as something else. S' need not equal S byte for byte: fill bytes, the bytes a codec produced, a non-minimal varint, another spelling of a text number and the bits past a realignment point may differ, and parsing S' again yields the same tree.

Isomorphic trees. Two trees of one description and root are isomorphic when they have the same shape and the same values: the same keys bound node by node, the same kind of node under each key (a struct node, an array node, a value or Null), arrays of the same length compared element by element in order, and equal values — Integers and Floats equal as numbers of the same type (a NaN equal to a NaN, and -0.0 distinct from 0.0), Strings equal code point by code point, Bytes equal byte by byte, Booleans equal. One exception is made, and no other: a recomputed derived value — a field that rule 2 requires the Writer to recompute and write whatever T binds, which is the length of an encoded field and a checksum whose covered range includes one — need not equal the value T carried from S, and must equal its recomputation over S', which the parse of S' establishes by reading the length and verifying the checksum. Every other derived value (a length of bytes the tree determines, a count, a checksum over such bytes) is compared like any value, rule 2 having refused a tree in which it differs from its recomputation. A derived field (bddo:valueFromExpression) and a local binding are compared too: they are recomputed by the parse of S', and one that depends on a recomputed derived value, or on stream.length where S' has another length than S, differs with it and is within the same exception.

Refusals. A refusal is a conforming outcome wherever these rules require one, and they require one in exactly these families; a Writer raises no other error for a tree. Four are validation errors, a tree that no stream the rules allow reads back to:

  1. a tree inconsistent with the description (rule 1: an undeclared or missing member, a node of another kind, a present field unbound or an absent one bound, a fixed value contradicted; rule 6: a node whose members are not those of the selected struct);
  2. a bound derived value that differs from its recomputation, and a size or count expression that does not match what the tree serialises to (rule 2);
  3. a value that does not fit its extent or its representation: longer than a literal or bound region, or not exactly a bound length that cannot be padded; an encoding that does not fit a literal region; a struct whose members overflow its declared size; a value containing its terminator (rule 3); an offset target already written with other bytes or lying before the start of the stream (rule 4); a character the encoding cannot represent, a text number whose canonical rendering does not fit its width and an infinite Float in a text number (rule 5); an integer out of its type's range, and a number its bddo:floatFormat or bddo:bcd representation cannot hold (rule 9);
  4. a stream that would not read back although every member fits: an encoded field shorter than its literal region whose fill bytes its codec would not read back (rule 3).

One is Unsupported feature: a text or tree container, a chunk table, a codec with no encode direction or one this processor does not encode, and a construct of a class or optional feature the processor does not claim (rules 7 and 10). One is a description error, raised for the description whatever the tree: every error a load of the description raises, and a pipeline whose kinds do not connect in encode order (rule 7). And one is no refusal of the tree at all: a resource-limit error when an encode output exceeds the decoded-byte limit (rule 7), or the output a processor's own limit. Of these, a tree that a Physical Parser produced can meet only two (informative): Unsupported feature, and the validation errors of the third and fourth families that arise because the stream was not canonical — an encoded field in a region of literal size, whose re-encoding has another length than the bytes it was parsed from, so that it no longer fits, or no longer fills, the region; a text number whose canonical rendering does not fit its fixed width, the stream having spelt it another way; and a float that its bddo:ibmHexadecimal or bddo:vaxF field stored beyond the IEEE 754 range of its width, which the parse read as an infinity.

The codec vector suites carry a round-trip vector (an encode step whose output a decode step reads back) for every codec whose contract encodes; the processor conformance suite's Writer class gives a writer a description and a tree and fixes the bytes, or the refusal, these rules require, and its round-trip mode runs the symmetry requirement over every tree its Physical Parser cases state. A processor may claim the writer feature when it passes that class and the round-trip mode reports no failure. The Writer conformance target is stated by the specification index.

The HEL Parsing Context

The parsing context is the tree of nodes produced above. It is the sole input, besides stream metadata and (for a Bundle Processor) the asset, to HEL evaluation. Fields already parsed within the current and ancestor nodes are visible; forward references (to fields not yet parsed) MUST raise an error, except where this document defers an evaluation until its references are bound: a struct-level size (), a conditional byte order (), and the expressions of that are evaluated over the complete tree — hexplain:valueExpression, the hexplain:condition of a hexplain:MappingRule (a map guard) and of a hexplain:ClassMappingRule (a means-when guard) — for which a field parsed later is simply a field.

An expression is read from a literal typed xsd:string or bddo:HelExpression; the two are read alike, as HEL, expression literals requires, and authoring tools should write the latter. The HEL version the expressions of a description are written against is its declared HEL version, bddo:helVersion on its owl:Ontology (HEL, version marker).

The names instance, parent, root, self, stream, asset and param are bound exactly as the HEL name-binding table states; this document does not restate them. In particular, the key or condition of a bddo:DispatchTable and the condition of a bddo:DataTypeRule are evaluated against the containing struct, since the field whose type they choose does not exist yet; self is the field's value for bddo:validIf; every other expression on a field (presence, size, offset, repeat count, derived value) and every struct-level expression is evaluated with the containing struct as instance.

Parameters and local bindings. param.name reads the argument bound to a parameter of the struct instance that instance denotes (ParseStruct, Parameters). A local binding is read by bare name or instance.name in any expression evaluated with its struct instance as instance once its position in the member list has been reached; before that it is a forward reference, a Type / HEL error, exactly as a later field is. Inside an element-scoped argument over struct elements instance is each element (HEL, the quantifiers group), so there param.name reads the element’s arguments and a bare name the element’s local bindings, never those of the struct holding the expression. Neither is a child of the struct's node: parent., root., self., a subscripted element and a path from another struct do not reach them, and they are absent from the parsed tree, which is why they need no names distinct from those of other structs.

Argument types. Whether an argument is of its parameter's bddo:parameterType is known at different times, and its error category follows. An argument that is a literal, or a negated numeric literal, of the wrong kind for a typed parameter is known from the description alone: a processor MUST raise it as a description error, when the description is loaded. Any other argument is known only once it is evaluated: a processor MUST raise a value of the wrong type — Null for a bddo:NodeParameter or bddo:ArrayParameter, and a struct node or an array value for a parameter that is untyped or typed with a scalar type, included — as a Type / HEL error when the argument is evaluated (ParseField, Value), not as a description error. A struct node is of type bddo:NodeParameter and an array value, an array node or a computed array (HEL, array values), of type bddo:ArrayParameter; such an argument is passed by identity, never copied, so the parameter reads the caller's node itself (HEL, param).

bddo:repeatUntil. The condition is evaluated after each element. When the elements are structs, instance and self are the element just parsed, so a bare name reads a field of that element, and parent is the struct that contains the repeated field. When the elements are scalars, instance is the containing struct, parent its parent, and self the value just read. (parent.x therefore reads the containing struct's x for struct elements, and the grandparent's for scalar elements.)

The deprecated parent alias. In a dispatch key or a bddo:DataTypeRule condition, parent is an alias for instance. The alias is deprecated in HEL 1.0: a processor SHOULD warn when it loads a description that uses it, new descriptions MUST NOT use it, and an HDL compiler never emits it.

Stream metadata and eof()

The current stream is the input byte stream, or, inside a field decoded by hexplain:isEncodedWith and re-parsed as a struct, the decoded bytes (a fresh sub-stream whose offsets start at 0). The current bound is the end of the innermost bounded region in force (, ), or the end of the current stream if none is. A region's bound is suspended only for the duration of a bddo:streamScope read. At the moment an expression is evaluated:

NameValue
stream.lengthThe length in bytes of the whole current stream. It is not narrowed by bounded regions.
stream.positionThe cursor, as a byte offset from the start of the current stream (not from the start of the region). During a run of bit fields it is the offset of the first byte not yet touched, so a partly consumed byte counts as consumed.
stream.remainingThe current bound minus stream.position: region-relative.
eof()stream.remaining == 0: true at the end of the innermost bounded region, not only at the end of the stream. This is what makes bddo:repeatUntil "eof()" stop at the end of a length-delimited container.

The cursor seen by an expression is the one in force when it is evaluated: before alignment for presence and derived value; after alignment but before the field is read for size, offset, type selection and repeat count; after the element for repeatUntil; after the field for validIf and checksum coverage.

Instance IRI Minting

To make the instance graph queryable, every emitted subject MUST have a stable, deterministic IRI. The default policy mints every IRI as a fragment of the base: B'#path, where B' is the base IRI B with any fragment (and its #) removed. If B is absent, a processor MUST choose a base itself (for example a fresh urn:uuid: IRI) and report it with the graph.

Every node of the logical tree has a node path:

path     = "root" *( "/" segment )
segment  = key / index
key      = the field's simple key, escaped as below
index    = "0" / ( %x31-39 *DIGIT )      ; array position, 0-based, decimal, no leading zeros
  • The root node's path is root. When the root struct is itself parsed as a bddo:repeatUntil sequence, its i-th element's path is root/i.
  • A struct bound under field key k of a node with path p has path p/k; the i-th struct element of an array field k has path p/k/i. Segments are appended for every struct on the way down, whether or not it is mapped to a class.
  • A field's simple key is the local name of the field's IRI after its last ., so the struct-qualified IRI ex:Chunk.length that an HDL compiler mints and the flat IRI ex:length both give length. The exception is a field of a text container whose IRI is the container's IRI, a ., and the field's own bddo:key, bddo:keyPath or bddo:nodePath (what an HDL compiler mints for a quoted key with no alias): its simple key is that key or path, which may contain spaces, . and /.
  • A character of a key that is not permitted in an IRI fragment ([[RFC3987]] ifragment) is percent-encoded as its UTF-8 octets, upper-case hex; in particular U+0020 SPACE becomes %20. A / in a key is percent-encoded as %2F, so it is never read as a segment separator.
  • A % in a key MUST be percent-encoded as %25, always, even where the characters after it would read as a percent-encoded octet: the keys a b and a%20b mint the segments a%20b and a%2520b. Percent-encoding is then injective, so two distinct keys never mint one IRI.

So the root struct, when it is mapped by hexplain:mapsToClass (or a conditional class mapping), is B'#root; the fourth element of a Chunks array under the root is B'#root/Chunks/3, and a struct in its Data field is B'#root/Chunks/3/Data. Only a struct node that resolves to a class is minted. The literal properties of an unmapped struct are emitted on the nearest mapped ancestor's subject; an unmapped struct with no mapped ancestor emits nothing, and neither do its descendants. Two further nodes use the same path form: a unit-bearing value (hexplain:unit) is a quantity node B'#p/k, and a field with a data layout that has hexplain:mapsToObjectProperty is an array node B'#p/k, where p is the containing struct's path and k the field's key.

A processor MAY offer alternative minting policies (e.g. hash-based or field-derived keys) but MUST document them and MUST be deterministic: parsing the same bytes with the same description and base IRI MUST yield an isomorphic graph.

Primitive Value → RDF Literal Mapping

When a mapped field's value is emitted, its RDF literal datatype is the bddo:xsdType of the field's effective bddo:DataType. This fixes, for example, that a bddo:uint32be becomes an xsd:unsignedInt literal and a bddo:float64le becomes an xsd:double; the narrower bddo:uint24, bddo:int24 and bddo:float16 take xsd:unsignedInt, xsd:int and xsd:float, which hold each of their values exactly. Integers are decoded with the resolved endianness and signedness, a bddo:bcd field as the decimal number its digits spell; floats per IEEE 754, a field of another bddo:floatFormat as the IEEE 754 value it was converted to (Float formats), so a bddo:bfloat16 field on bddo:float16 is an xsd:float holding its binary32 value; bddo:string per its bddo:encoding; bddo:bytes as xsd:hexBinary.

Fixed-point values. A Semantic Emitter MUST emit a mapped field that declares bddo:fixedPointScale k, itself or through its data type, as the number the integer stands for, the integer read times 2k, in an xsd:decimal literal, which holds every such value exactly: the Q16.16 field holding 00 01 80 00 is emitted "1.5"^^xsd:decimal, and a scale of 2 on the integer 3 is emitted "12"^^xsd:decimal. The data type's bddo:xsdType is not used, since the scaled value is not in general an integer. The scale applies to this literal alone: a hexplain:valueExpression reads the integer as parsed and computes what it says, and an enumeration is matched against the integer as parsed. A Semantic Emitter MUST support every scale from −4096 to 4096, so that a description whose scales stay within that range is portable. A processor MUST raise a description error for a bddo:fixedPointScale outside the range it supports, when the description is loaded or, at the latest, when the field is emitted; it MUST NOT emit an approximation of the scaled value or the integer unscaled.

When a hexplain:valueDatatype D is given, a Semantic Emitter MUST emit a literal typed D whose lexical form is a lexical form of the result’s value in D, and MUST raise a Type / HEL error when the result has no value in D's value space: for xsd:decimal the result is an Integer or a finite Float; for the integer types derived from xsd:decimal (xsd:integer, xsd:long, xsd:unsignedByte and the others) it is an Integer within D’s range, and never a Float: a Float has no value in an integer datatype even when it has no fractional part, so 50.0 typed xsd:integer is an error, exactly as a Float is never an Integer in HEL (HEL, conformance), and 300 is not an xsd:unsignedByte; for xsd:double and xsd:float an Integer or a Float, rounded to the nearest binary32 value for xsd:float; for xsd:string a String; for xsd:boolean a Boolean; for xsd:hexBinary and xsd:base64Binary Bytes, which have a value in both. For any other D the result is a String, emitted unchanged as the lexical form. A processor never changes D to fit the result.

Semantic Triple Emission

The instance graph G is produced from the mapping properties of Hexplain Core, and holds nothing else except that a processor MAY annotate each minted resource with its physical extent: hexplain:byteOffset and hexplain:byteLength, typed xsd:nonNegativeInteger, the core vocabulary's range for both.

A Semantic Emitter MUST emit these triples:

  • For a Struct instance s whose description has hexplain:mapsToClass C, emit <IRI(s)> rdf:type C.
  • For a Field with hexplain:mapsToProperty P, emit <IRI(parent)> P "value"^^xsdType. If the field also carries hexplain:valueExpression E, emit instead the value obtained by evaluating E in the field's context (e.g. fixed-point or unit scaling), typed with hexplain:valueDatatype if given, else in the natural datatype of the HEL result.
  • For a Field with hexplain:mapsToObjectProperty P, emit <IRI(parent)> P o, where o is the IRI minted for the struct instance the field holds when its data type is a bddo:Struct, or the bddo:enumSymbol IRI of the matched bddo:EnumValue when the field carries an enumeration; a value that has neither emits nothing.
  • For a Field with hexplain:hasConditionalMapping, evaluate rules in order and emit the property of the first rule whose condition holds.
  • A repeated field emits one such triple per element, in element order; a Null element, like an unbound field, emits nothing.
  • For a Field with hexplain:hasDataLayout, the layout (DLV) governs how its multi-dimensional cells are addressed, and the field’s value is its array node, never a literal: a processor MUST emit nothing for hexplain:mapsToProperty on such a field, MUST emit <IRI(parent)> P <B'#p/k> for hexplain:mapsToObjectProperty P, B'#p/k being the array node of , and MUST NOT emit triples for its cells, which this version gives no vocabulary.
  • For a Field with hexplain:isEncodedWith A, a processor MUST decode the block with algorithm A (a concept from whichever codec or compression register the profile binds; see for the codecs every processor supports and the Unsupported feature error for the rest); when the field's effective data type is a bddo:Struct, it MUST then re-parse the decoded bytes as a fresh bounded sub-stream against that Struct.
  • If an enumeration matched and the matched bddo:EnumValue has a bddo:enumSymbol, a processor MUST also emit the symbolic value, <IRI(parent)> P <symbol>, alongside the raw literal (every matching symbol for a flags enumeration); a matched value without a symbol emits the literal alone. A field that carries an enumeration and both hexplain:mapsToProperty P and hexplain:mapsToObjectProperty Q is emitted under both, each by its own rule: a processor MUST emit the raw literal on P, the symbol IRI on P as this rule says, and the symbol IRI on Q as the object-property rule says, so a matched value with a symbol yields three triples (and one more pair per further matching symbol of a flags enumeration) and a matched value without one yields the literal on P alone.
  • A Semantic Emitter MUST evaluate hexplain:valueExpression, the hexplain:condition of a hexplain:MappingRule and the hexplain:condition of a hexplain:ClassMappingRule after the part's tree is complete, over the whole tree, with instance, parent and root bound as the HEL name-binding table states: a field declared later than the field or struct that carries the expression is a bound field there, not a forward reference, and an absent optional field reads as Null (). Their evaluation order is not observable, since an expression has no side effect.
  • A Semantic Emitter MUST write every typed literal it emits in the canonical lexical representation of the literal's datatype, as the canonical mapping of XSD 1.1 Part 2, section 2.3 (the lexical space and its canonical mapping) defines it for each built-in datatype [[XMLSCHEMA11-2]]: an integer datatype without a leading + or leading zeros (-0 is 0), xsd:boolean as true or false, xsd:hexBinary in upper-case hexadecimal digits, xsd:double and xsd:float as a mantissa with exactly one non-zero digit before the point and at least one digit after it, an E and an exponent without a + or leading zeros (1.05E1, 5.0E-1, 0.0E0, -0.0E0), the special values NaN, INF and -INF, and xsd:decimal with no exponent, no trailing zeros after the point and no point at all for an integral value (10.5, 100); a value given as a String for another datatype is emitted as that String. Two conforming emitters therefore produce isomorphic graphs for the same input, and the conformance suite compares emitted literals by their lexical form.
  • A processor MUST NOT emit anything for a bddo:Parameter or a bddo:LocalBinding: they are not nodes of the parsed tree, have no node path, and carry no mapping.

Multi-part Assets

A Bundle Processor processes an abnd:Asset: several files (parts) described together by an abnd:BundleProfile in the bundle aspect. Its input is the bundle profile, the descriptions its part specs are abnd:describedBy, the asset IRI, and the asset's files, each with its path relative to the asset root (/-separated; a flat sibling set is just the file names) and its IRI.

  1. Assembly. Each file is matched to an abnd:PartSpec of the profile. An abnd:extension value is the shorthand for the pattern *<ext> (so it matches a file at the asset root, not in a subdirectory), compared ignoring ASCII case, since a filename's case is not significant to the formats that name members by extension; an abnd:pathPattern is a glob matched exactly against the relative path (* within one segment, ** across segments, ? one character). Several values of either property are alternatives. A file that matches no part spec, or the part specs of more than one, is a validation error: the caller chooses which files form the asset, and a file that could be either of two parts would be read by a guess. The part count of each spec is the number of files matched to it; it MUST lie within abnd:minParts (default 1 when abnd:required is true, else 0) and abnd:maxParts (default 1 for a spec located by abnd:extension, which names one member; unbounded for a pattern). A count outside that range, including a required part with no file, is a validation error. A part's identity, and so the value of partExtension() for it, is fixed here, before any part is parsed: the abnd:extension alternative it matched, or, for a part located by a pattern, the part of its file name from the last .; in both cases lower-cased with its leading ., and empty when there is none.
  2. Order. Each part whose spec is abnd:describedBy a struct is parsed with that struct, and is named in HEL by the struct's local name; two part specs of one profile described by structs with the same local name are a description error. A part whose description (the struct and every struct reachable from it) reads asset.X.… MUST be parsed after part X; a processor MUST order the parts so that every such reference is to a part already parsed. partExtension(asset.X) reads a part's identity, not its content, and imposes no order. References that form a cycle, including a part reading its own content through asset, are a description error, raised before any part is parsed. Reading asset.X before X is parsed, naming a part the asset does not have, naming a part more than one file was matched to, or reading a key the part's root struct does not declare is a Type / HEL error, never Null. A part whose spec has no abnd:describedBy is carried but not parsed. Cross-part references are written with the asset root: a …FromField property resolves its field within the part being parsed, as it does in a single file.
  3. Parsing and minting. Each part is parsed as an independent stream by this document's rules, and its instance IRIs are minted against the part's own IRI as base, so the part's root is <part>#root. A part that is carried but not parsed (its spec has no abnd:describedBy) MUST still be minted the same way: its root is <part>#root, which the lifting below links and types, and which carries no triple of its own content.
  4. Lifting. The asset IRI is typed abnd:Asset, linked to the bundle profile by dcterms:conformsTo and to each part root by abnd:hasPart, and to the root of the part whose spec is abnd:primary by abnd:primaryPart when exactly one file was matched to that spec; each part root is typed abnd:Part and carries its spec's abnd:partRole. The bundle profile's triples are in the graph, since the lifting rule joins through them; the descriptions of the parts' bytes are not. The bundle aspect's lifting rule then copies each part's facet properties whose aspect the part's role abnd:carriesAspects onto the asset. No inverse (abnd:partOf) or other inferred edge is added.

A processor that is not a Bundle Processor MUST treat the asset root and partExtension() as HEL errors when a single part is parsed on its own, so that a description depending on a sibling part fails rather than reading Null. A Bundle Processor parsing a part on its own, outside an asset, does the same.

Conformance Evaluation

A Conformance Evaluator takes a parsed input (the parsing context of ), a conformance profile — the conf:Constraint, conf:ParseAttribution and req:Requirement resources of a description graph — and optionally the input's format version, and produces a run report: a conf:Run with one outcome per requirement, and the conf:Findings of the run. The vocabulary is defined in conf and req; this section defines the behaviour.

  1. Scope firing. A constraint whose conf:scope is a bddo:Struct MUST be evaluated once for every parsed instance of that struct, after the instance is complete, with instance and self bound to the instance, parent to the struct that holds it and root to the root of the input. A constraint whose scope is a bddo:Field MUST be evaluated once for every parsed value of that field — each element of a repeated field is one value, and an absent optional field fires nothing — with instance bound to the containing struct and self to the value. Instances are visited in document order.
  2. Assertion results. An assertion that evaluates to true passes. false yields one finding of kind conf:Violation, at the constraint's conf:severity (default sh:Violation), attributed to every requirement the constraint cites. Any other result, or an evaluation error, yields one finding of kind conf:RuleError at sh:Violation, attributed the same way. A ResourceLimit reached while evaluating an assertion is not a rule error and not a finding: it ends the run as item 5 states.
  3. Messages. A finding's conf:findingMessage is the constraint's conf:message with {field} replaced by the node path () of the focus node, and {value} replaced by the evaluated value when it is unambiguous — the field's value under a Field scope, and under a Struct scope the value of the instance's only bound scalar field when there is exactly one — and otherwise left as written. Values are rendered as conf:message defines. For a rule error the message describes the evaluation failure.
  4. Version. The input's format version is supplied by the caller; an evaluator MUST NOT guess it from the data. When it is supplied, a requirement with req:appliesToVersion values none of which equals it (exact string equality) is not applicable: its constraints are not evaluated on its behalf, and its outcome is conf:NotApplicable. When no version is supplied, every requirement is evaluated and the report MUST state that version scoping was not applied.
  5. Truncation. An evaluator MUST enforce resource limits on a run (at least the parse limits, and a limit on the number of findings). When one is reached it MUST either fail with a ResourceLimit error or stop and return a report marked truncated, stating the limit; it MUST NOT return an unmarked partial report. A parse that stops at an error likewise leaves the rest of the input unvisited.
  6. Parse attribution. An error raised while parsing the input () is reported as one finding of kind conf:Parse, with no constraint, at sh:Violation, stating its conf:errorCategory, one of the categories of other than ResourceLimit: conf:SyncError, conf:BoundsError, conf:ValidationError, conf:ChecksumError, conf:ExpressionError (a Type / HEL error), conf:DispatchError, conf:DescriptionError or conf:UnsupportedFeature. The category's name as a string (Sync, Bounds, Validation, Checksum, Expression, Dispatch, Description, Unsupported, its skos:notation) is a deprecated form of the same value. It is attributed to the requirement of the profile's conf:ParseAttribution for that category (each attribution cites exactly one requirement, and a profile attributes a category at most once), and to no requirement when none names the category. In a lenient mode that recovers from parse errors, each recorded error is such a finding. A ResourceLimit is never a finding: a limit reached while parsing ends the run as item 5 states, in a lenient mode too (), and a conf:ParseAttribution naming ResourceLimit is a description error, raised when the profile is loaded.
  7. Recovered trees. When a lenient parse recovered from errors and an assertion reads a declared field that is absent from the recovered tree, the evaluation of that instance yields no finding — neither a violation nor a rule error — and does not count as exercising the constraint: the defect is carried by the Parse finding.
  8. Outcomes. Every requirement of the profile receives exactly one outcome, the first of these that holds: conf:NotApplicable (item 4); conf:Errored, when a citing constraint raised a rule error; conf:Evaluated, when a citing constraint was evaluated without error on at least one instance, or a citing parse attribution was checked (the parse ran to its end, or raised the attributed category); conf:NotReached, when the run was truncated or the parse stopped before the whole input was visited; conf:NotExercised otherwise — including a requirement no constraint or parse attribution cites.
  9. Verdict. A run is conformant if and only if it was not truncated, the parse completed, no finding has a severity at or above the run's fail-on severity (sh:Violation unless the caller chooses sh:Warning or sh:Info; a Parse finding and a rule error are always at sh:Violation, so either makes the run non-conformant), and no requirement's outcome is conf:Errored or conf:NotReached. Findings below the fail-on severity are reported and do not affect the verdict.
  10. Report. A report written as RDF MUST be one conf:Run with exactly one conf:verdict (conf:Conformant or conf:NonConformant), exactly one conf:truncated flag, a conf:truncationReason when it is truncated, conf:versionScopingApplied (with the supplied version as conf:fileVersion when it is true), conf:failOn when the fail-on severity is not sh:Violation, one conf:outcome per requirement, and a conf:finding link to every finding; it names what was evaluated with conf:profile, conf:ruleSet and conf:input where it can. The report MUST validate on its own against the conf and req shapes: it MUST carry a copy of every req:Requirement, conf:Constraint and conf:ParseAttribution description it references, with each constraint's conf:scope typed bddo:Struct or bddo:Field, so that a finding's severity and attribution can be checked against its constraint and attribution without the profile. A requirement that is a blank node in the profile has no name a report can cite, so the report names it by a skolem IRI (RDF 1.1 Concepts, section 3.5); the reference implementation mints urn:hexplain:genid:requirement: followed by the SHA-256 of the requirement's normalised (req:fromStandard, req:requirementId) pair. Such a copy is a different node from the blank node: a report validated together with a rule set that states its requirements as blank nodes reports each of them twice to req:RequirementIdentityShape, and as a requirement without an outcome, which is expected. Validate the report on its own, or give the rule set's requirements IRIs.

Informative: the reference implementation reports the categories under its own error kinds (Sync, Bounds, Validation, Checksum and Expression as the kinds of the same name, Dispatch as DISPATCH, Description as a load-time description error, Unsupported as UNSUPPORTED; a ResourceLimit, recognised by the ResourceLimit marker, fails or truncates the run and is never a finding; a parse attribution naming it is refused when the rule set is loaded), writes the report as JSON or as conf: RDF, and its command-line validator's --fail-on=violation|warning|info option chooses the lowest severity that makes the command fail.

Security and Privacy Considerations

A processor reads two untrusted inputs, the bytes and the description, and publishes what it derives from them. This section gathers what that exposes and the rules that answer it; each rule is stated, with its detail, in the section it links to, and the requirements below are those this section adds.

Resource exhaustion

A few bytes can ask for unbounded work: a repeat count of 232, a struct that contains itself (directly, through a dispatch arm, or as a parameterised struct passing arguments to itself), a JSON or XML document nested thousands deep, a checksum or terminator scan over a gigabyte, an HEL expression generated to be deep, a quantifier nested in a quantifier, a regular expression that backtracks exponentially, a mapping that multiplies triples. Every one of these is bounded by a limit of , whose table gives the minimum a processor’s default configuration allows, and each is configurable. Exceeding a limit is a ResourceLimit error, fatal in every mode, including a lenient one, and never a partial tree, graph or report (, ). A processor MUST apply the limits to the work a description causes as well as to the bytes it reads: a limit MUST NOT be skipped because the description, rather than the input, asked for the work.

Inputs of unknown length

Every bound in this document is measured against |S|, the length of the input (): without it stream.remaining, eof(), streamEnd addressing and the search bounds of terminators and markers have no value, and a processor that parsed a stream as it arrived would have to guess them. This version therefore has no streaming model, and the known length is also what the input-byte limit of is applied to. A processor that accepts an input of unknown length therefore reads it to its end before it begins to parse, as requires, and counts the bytes against the input-byte limit as they arrive, so that an endless input is refused with a ResourceLimit error rather than buffered without bound.

Decompression bombs

A codec block of a few kilobytes can decode to gigabytes. A processor MUST count the output of every codec stage toward the decoded-byte limit as it is produced, and MUST stop and raise ResourceLimit as soon as the output would exceed what remains of the limit; it MUST NOT decode a block in full and compare its size afterwards. Where a format states its decoded size before the data — menc:LZ4Block’s decodedSize, an LZ4 frame’s content size, a Zstandard Frame_Content_Size — the check comes before any decoding (), so a bomb that announces itself costs nothing. A declared size that exceeds the limit is a ResourceLimit error even when the processor has a smaller cap of its own for one block.

External resources, entities and document types

A tree document can name external entities, DTDs and schemas, and a naive XML parser fetches them (XXE), leaking local files or reaching internal addresses, or expands nested internal entities exponentially (billion laughs). requires that no external entity or DTD is fetched, that entity expansion counts toward the limits, and that a reference to an external entity is a validation error. More generally, a processor MUST NOT fetch or open any resource that an input or a description names — an external entity, DTD, schema, stylesheet, XInclude, a file path or a URL in a value — while parsing or emitting: its only inputs are those of (and, for a Bundle Processor, the files the caller assembled into the asset).

Expressions

HEL has no loops, no recursion and no side effects, so an expression’s cost is bounded by its size, its nesting depth, its element budget — the predicate and element-expression evaluations of its element-scoped arguments and the elements, bytes and characters the quantifiers group's functions build or convert, each charged before the work it pays for (HEL, the element budget) — and the cost of its regular-expression matches. Each has a limit with a normative minimum in , and exceeding any of them is a ResourceLimit error (HEL, conformance), never a syntax or runtime error: an attacker who can make an expression expensive must not be able to turn a well-formed file into a finding of a different kind. A matches pattern comes from the description, and its subject from the data, so both are untrusted.

Privacy

The instance graph publishes what the description maps, and more than the mapped values: every minted IRI carries the base IRI and the node path, and a node path carries the keys of the containers it passes through (JSON member names, key/value keys), which the data chose. A base derived from the input’s name (urn:file:holiday-2026.jpg, file:///home/alice/scans/passport.pdf) repeats that name, and the directory it sits in, in every subject of the graph. The worked example’s urn:file: base is illustrative. A processor that chooses a base itself () MUST NOT derive it from the input’s file name or path; a fresh urn:uuid: IRI is sufficient. A Conformance Evaluator SHOULD NOT name its input by a file path in a report (conf:input) unless the caller supplied that IRI.

Mapped values can be personal data (an owner name, a location, a serial number); a processor cannot know which, and the publisher of a description is responsible for what it maps. The SPARQL function library (hxf) goes further: hxf:bytes and hxf:decodedBytes return the raw bytes of a node — including bytes no description maps, for a slice relative to a node — to anyone who can run a query where the functions are installed, and hxf:digest fingerprints them. The function library’s security and privacy rules bound what such an endpoint resolves and returns.

Recovery in a Lenient Mode

A lenient mode () records an error and continues. Continuing needs a cursor, and a processor that chose its own would record different errors, and return a different partial tree, from another given the same bytes. The rules below fix it. A check on a value that has been read in full — a fixed value, a checksum, a bddo:validIf or a text value that is not the declared number — leaves the cursor sound: the error is recorded, the field keeps its value and parsing continues with the next field. When reading a field fails, a processor in a lenient mode MUST record the error once and recover by the first of these rules that applies:

  1. Pointer. A field read at an offset (bddo:atOffset, bddo:atOffsetFromField, bddo:atOffsetFromExpression) that fails leaves the field unbound and does not move the cursor: the saved cursor is restored, as after any offset-addressed read, and parsing continues with the next field.
  2. Counted sequence of known-width elements. A repeated field whose count is known (its repeat count resolved) and each of whose elements has a width known before it is read (a data type with a bddo:bitWidth and no bddo:bitLength, or a literal bddo:size) is left unbound, and the cursor moves to the field's start plus count × width, or to the end of the innermost bounded region if that comes first; parsing continues with the next field.
  3. Otherwise, abandon up to the nearest known end. The field that failed is left unbound, and so is everything after it up to the nearest end the processor knows: the end of the failing field's own declared region (), of a bounded bddo:repeatUntil sequence, of a decoded block, or of a struct with a declared size (), whichever encloses the failure most closely. The cursor moves to that end and parsing continues with whatever follows it; the fields read before the failure keep their values, and each struct that was abandoned is bound, with the fields it has, in its parent. When no enclosing end is known, every struct up to the root is abandoned and the parse ends.

Each rule records exactly one error for the failure it recovers from, and recovery itself records none: a sequence element that consumes no bytes because the cursor was moved, say, is not a further error. A later field that then fails for a reason of its own is a new failure, recovered by the same rules. A processor MUST NOT recover from a ResourceLimit, Description or Unsupported feature error (), and MUST NOT use a recovery rule to skip a read it could have made.
