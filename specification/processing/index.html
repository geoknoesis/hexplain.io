The Hexplain Processing Model defines, normatively, how a conforming processor turns a binary stream plus a Hexplain description (BDDO + Core + domain vocabularies) into two outputs: a transient parsing context and a persistent RDF instance graph. It specifies the parse algorithm, the construction of the HEL context, the minting of instance IRIs, the mapping of primitive values to RDF literals, the emission of semantic triples, and error handling. This document makes Hexplain descriptions executable and reproducible across implementations.

This document is an unofficial draft produced for the purpose of defining the Hexplain standard. It has no official standing and is not endorsed by any standards body. This is the first version.

Introduction

The other Hexplain specifications define vocabulary; this one defines behaviour. Without a shared processing model, two implementations could parse the same file against the same description and emit different graphs, defeating the interoperability and SPARQL-query goals of the framework. Everything here is REQUIRED behaviour for a conforming processor unless marked otherwise.

Conformance

The key words "MUST", "MUST NOT", "REQUIRED", "SHALL", "SHALL NOT", "SHOULD", "SHOULD NOT", "RECOMMENDED", "MAY", and "OPTIONAL" in this document are to be interpreted as described in [[RFC2119]].

A conforming processor MUST implement the parse algorithm (§3), the context model (§4), IRI minting (§5), the value mapping (§6), and semantic emission (§7); and MUST support every construct of BDDO, Hexplain Core, DLV, and HEL.

Inputs and Outputs

Inputs
(1) a byte stream S with known length |S|; (2) a Hexplain description graph D; (3) a designated root Struct R in D; (4) an optional base IRI B for minting instance IRIs.
Outputs
(1) the parsing context C (transient, used by HEL); (2) the instance graph G (RDF, persistent). A processor MAY expose either or both.

Parse Algorithm

Parsing maintains a cursor (byte position, initially 0) and a bit cursor for bit-level fields. To parse the root, invoke ParseStruct(R, cursor=0, parent=nil).

ParseStruct(struct, cursor, parent)

  1. If struct has bddo:syncOnMarker, advance the cursor to the next occurrence of the marker bytes; if none exists, raise a sync error.
  2. Create a new context node n with a back-link to parent; record its start offset.
  3. Bounded region. If struct declares a size (bddo:size / bddo:sizeFromField / bddo:sizeFromExpression), it establishes a bounded region [start, start+size). A read by this struct or any descendant that would cross the region end raises a bounds error, and a descendant's bddo:sizeToEndOfStream resolves to the region end (not |S|). This is what lets length-delimited containers (ISOBMFF/MP4 boxes, EBML, chunk payloads) bound their children.
  4. Resolve the effective endianness and bit order (nearest declaration wins: DataType > Field > Struct > inherited from parent).
  5. For each field in the bddo:hasField list, in order, call ParseField(field, n). Members MUST be processed in list order.
  6. If struct declared a size, advance the cursor to start+size (skipping any trailing padding/unknown bytes); otherwise the end offset is the current cursor. Record the node's end offset (sizeof = end − start) and return n.

ParseField(field, node)

  1. Presence. If bddo:isPresentIf is present and its HEL expression evaluates to false, skip the field (bind it to Null in the context) and return.
  2. Alignment. If bddo:alignment = a, advance the cursor to the next multiple of a, measured from the start of the innermost enclosing bounded region (or the stream start if none).
  3. Addressing. If an offset property is present, compute the target offset from bddo:atOffset / atOffsetFromField / atOffsetFromExpression, relative to bddo:offsetBase (default streamStart; streamEnd counts backward from |S|). Save the current cursor, seek to the target, parse, then restore the saved cursor (an offset field does not advance sibling parsing) unless offsetBase is currentPosition. A target outside the innermost bounded region raises a bounds error, unless the field declares bddo:seekScope bddo:streamScope: then the target is resolved against the whole stream [0, |S|) and the region bound is suspended for the duration of this one read (and restored before the cursor is).
  4. Repetition. If a repetition property is present, determine the iteration policy: a fixed bddo:repeatCount, a count via repeatCountFromField/repeatCountFromExpression, or repeat-until (bddo:repeatUntil, evaluated after each element with self bound to it). Produce an ordered array node; each element is parsed by the single-value procedure below.
  5. Type selection. If bddo:hasDispatchTable is present, evaluate the table's key — the parsed value of bddo:dispatchOnField, or bddo:dispatchOnExpression evaluated exactly as a bddo:DataTypeRule condition is — and select the bddo:DispatchArm of that table whose bddo:armKey equals it (strings by code points, integers numerically); if none matches, use bddo:dispatchDefault, else bddo:dataType. A processor MUST collect arms from the whole description graph, including imported ontologies; two arms with one key are a description error. Otherwise, if bddo:hasConditionalDataType is present, evaluate each bddo:DataTypeRule in list order; the first whose bddo:condition is true supplies the effective type via bddo:ruleDataType. Otherwise use bddo:dataType. It is an error if none yields a type, or if both selection mechanisms are declared.
  6. Value. If the effective type is a bddo:Struct, recurse via ParseStruct. If it is a bddo:DataType:
    • Determine the field's byte size from (in priority order) the fixed width of the datatype (bddo:bitWidth/8), bddo:size, bddo:sizeFromField, bddo:sizeFromExpression, bddo:terminator (read until the terminator sequence), or bddo:sizeToEndOfStream (read to the end of the innermost enclosing bounded region, or |S|). Exactly one applies; a variable-length type (bytes/string) MUST resolve to one of these.
    • If bddo:bitLength is present, read that many bits per the bit-cursor rules (§3.3) instead of whole bytes.
    • Decode the raw bytes to a typed value per §6, honouring endianness and (for strings) bddo:encoding. For a fixed-size bddo:string with bddo:trimNull true, the value is the bytes up to (excluding) the first 0x00 within the field's width (NUL-padded strings, e.g. TAR/ZIP names).
  7. Fixed value. If bddo:hasFixedValue is present and the decoded value differs, raise a validation error.
  8. Enumeration. If bddo:enumeration is present, look up the raw value among the bddo:EnumValues; the matching symbol/label is attached to the value node (and emitted per §7). If the enumeration has bddo:enumIsFlags true, the raw value is a bitmask: every bddo:EnumValue whose raw value's bits are all set in the parsed value matches, and all matching symbols are attached/emitted.
  9. Checksum. If bddo:checksum is present, compute the algorithm over the covered byte range — from the first byte of coversFromField to the last byte of coversToField (inclusive), or the [start, end) range yielded by coversExpression — and compare with the stored value; a mismatch raises a checksum error.
  10. Bind the field's value into node under the field's simple key, and return.

Bit-level fields (the bit cursor)

Bit-level fields (bddo:bitLength) are read through a bit cursor that tracks the current byte offset and a bit offset within it (0–7):

  1. Consecutive bddo:bitLength fields pack contiguously: each consumes the next bitLength bits from the current bit offset, advancing the cursor (rolling into the next byte when it reaches 8).
  2. Bits are consumed within each byte per the effective bddo:bitOrder: bddo:MSBFirst takes bits from the most-significant end first; bddo:LSBFirst from the least-significant end.
  3. A field's integer value is assembled from its bits most-significant-bit first, so the decoded value is independent of storage order. A field spanning a byte boundary continues into the next byte in the same bit order.
  4. The bit cursor realigns to the next whole byte boundary before any byte-oriented read (a field without bitLength), before bddo:alignment, and at the end of a Struct; partial bits before the boundary are skipped.
  5. A bit read that would cross the end of the innermost bounded region (or |S|) raises a bounds error.

This makes sub-byte structures (IPv4 version/IHL, TCP data-offset + flags, PNG bit-packed samples) parse identically across implementations.

The HEL Parsing Context

The parsing context is the tree of nodes produced above. It is the sole input, besides stream metadata, to HEL evaluation. Fields already parsed within the current and ancestor nodes are visible; forward references (to fields not yet parsed) MUST raise an error. The roots instance, parent, root, self, and stream resolve as defined in HEL §2.

Instance IRI Minting

To make the instance graph queryable, every emitted subject MUST have a stable, deterministic IRI. The default policy:

  • The root instance IRI is the base IRI B (or a blank node if B is absent).
  • A nested Struct instance mapped by hexplain:mapsToClass receives the IRI B + '/' + path, where path is the slash-joined chain of field keys and array indices from the root to that node (e.g. B/Chunks/3/IHDR).
  • Array elements are indexed from 0.

A processor MAY offer alternative minting policies (e.g. hash-based or field-derived keys) but MUST document them and MUST be deterministic: parsing the same bytes with the same description and base IRI MUST yield an isomorphic graph.

Primitive Value → RDF Literal Mapping

When a mapped field's value is emitted, its RDF literal datatype is the bddo:xsdType of the field's effective bddo:DataType. This fixes, for example, that a bddo:uint32be becomes an xsd:unsignedInt literal and a bddo:float64le becomes an xsd:double. Integers are decoded with the resolved endianness and signedness; floats per IEEE 754; bddo:string per its bddo:encoding; bddo:bytes as xsd:hexBinary.

Semantic Triple Emission

The instance graph G is produced from the mapping properties of Hexplain Core:

  • For a Struct instance s whose description has hexplain:mapsToClass C, emit <IRI(s)> rdf:type C.
  • For a Field with hexplain:mapsToProperty P, emit <IRI(parent)> P "value"^^xsdType. If the field also carries hexplain:valueExpression E, emit instead the value obtained by evaluating E in the field's context (e.g. fixed-point or unit scaling), typed with hexplain:valueDatatype if given, else the natural datatype of the HEL result.
  • For a Field with hexplain:hasConditionalMapping, evaluate rules in order and emit the property of the first rule whose condition holds.
  • For a Field with hexplain:hasDataLayout, the layout (DLV) governs how the multi-dimensional cells are addressed; a processor MAY additionally emit per-cell triples but is not required to materialize them.
  • For a Field with hexplain:isEncodedWith A, a processor MUST decode the block with algorithm A (a concept from whichever codec or compression register the profile binds); when the field's effective data type is a bddo:Struct, it MUST then re-parse the decoded bytes as a fresh bounded sub-stream against that Struct.
  • If an enumeration matched, a processor SHOULD also emit the symbolic value (the bddo:enumSymbol IRI, if any) alongside the raw literal.

Error Handling

Processors MUST distinguish and report the following conditions rather than emit a silently-wrong graph:

ErrorCause
Sync errorbddo:syncOnMarker not found.
Bounds errorA read would pass the end of the stream or the innermost bounded region (or a negative offset).
Validation errorbddo:hasFixedValue mismatch.
Checksum errorbddo:Checksum mismatch.
Type / HEL errorA HEL type error, division/modulo by zero, undefined name, forward reference, or an array subscript out of range.
Dispatch errorNo bddo:DataTypeRule matched and no default bddo:dataType exists.

A processor MAY offer a lenient mode that records errors as annotations in G and continues; the default mode SHOULD halt on the first error.

Worked Example (abridged)

Parsing a PNG IHDR chunk against the descriptions in BDDO and Image Vocabulary, with base IRI <urn:file:example.png>, yields:

@prefix img: <https://hexplain.io/ns/image#> .
@prefix araster: <https://hexplain.io/ns/aspect/raster#> .
@prefix asamp: <https://hexplain.io/ns/aspect/sampling#> .
@prefix xsd: <http://www.w3.org/2001/XMLSchema#> .

<urn:file:example.png/Chunks/0/IHDR>
    a img:ImageHeader ;
    araster:width  "1920"^^xsd:unsignedInt ;
    araster:height "1080"^^xsd:unsignedInt ;
    asamp:bitDepth "8"^^xsd:unsignedByte ;
    img:colorType "2"^^xsd:unsignedByte .   # enum symbol: RGB
