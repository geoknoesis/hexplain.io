# ---------- Cross-part references ----------
# A part's description may name a field of ANOTHER part of the same asset. This is not an
# edge case: it is the defining shape of every raw-grid-plus-sidecar raster (ENVI, EHdr,
# GenBin, PAux, MFF, ISCE, ROI_PAC, RRASTER, SAGA, SNODAS, ...), where the grid's extents,
# sample type and byte order all live in the header file and the payload file carries
# nothing but bytes.
#
# Such a reference is written with HEL's `asset` root, e.g. "asset.Header.byteOrder == 0".
# A `...FromField` object property (bddo:sizeFromField, dlv:dimensionSizeFromField, ...)
# is NOT a cross-part reference: the Processing Model resolves it within the part being
# parsed, as in a single file. To size by another part's field, bring the value into the
# part's own scope with a derived field (bddo:valueFromExpression "asset.Header.nrows") and
# name that field -- the pattern the HDL conditional-layout example uses.
#
# Identity versus content. The two are available at different times, and conflating them makes
# a legal description look circular. A part's CONTENT -- what asset.X.field reads -- exists only
# once part X has been parsed. A part's IDENTITY, its name and so its extension, is fixed when
# the asset is ASSEMBLED, before any part is parsed. HEL's partExtension() asks about identity,
# so it is resolvable from the start and, unlike a content reference, a part may ask it about
# ITSELF without any ordering problem. That self-reference is the ordinary case: a PartSpec
# listing several abnd:extension values lists them as ALTERNATIVES, and which one matched can
# decide how that same part is read -- an ESRI .hdr-labelled grid is uint32 at NBITS 32 but
# float32 when the file is .flt, and only the filename distinguishes them.
#
# Resolution. `asset.X` is resolved against the enclosing abnd:Asset, by locating the part whose
# abnd:PartSpec is abnd:describedBy the struct whose local name is X. A description
# carrying a cross-part reference is therefore only meaningful when parsed as part of an
# asset; parsing such a part standalone MUST raise an error rather than yield Null, since a
# silently absent extent would produce a plausible but wrong grid.
#
# Ordering. A CONTENT reference's target part MUST be parsed before the referring one. A
# processor SHOULD derive that order from the references themselves; abnd:primary does not
# imply it, and in the sidecar case the primary part is the payload, which is the DEPENDENT
# one. Identity references impose no order, per the paragraph above, so they must not be
# counted when deriving it -- treating one as a dependency would report a false cycle for the
# ordinary case of a part conditioning on its own extension.
#
# Requiredness. A cross-part reference SHOULD name a part whose PartSpec is abnd:required
# true. Depending on an optional part means the referring description cannot be resolved
# when that part is absent, which is a defect in the profile rather than in the data.
