A Hexplain profile for HEIF, on a reusable ISO base media file format core

Scoped to what libheif actually implements, and answering the question that shapes the whole design: can the ISO/IEC 14496-12 box machinery be described once and reused by HEIC, AVIF, HEIF sequences, MP4, JPEG 2000-in-BMFF and JPEG XL, rather than re-described per format?

Yes — and the reuse belongs at the RDF level, not the text level

Yes, a reusable ISO base block is the right architecture, and HEIF is close to the ideal case for it. HEIF adds almost nothing structural to ISO/IEC 14496-12: the box header, the meta box, item location (iloc), item information (iinf/infe), item references (iref), item properties (iprp/ipco/ipma), item data (idat), entity groups (grpl) and data information (dinf/dref) are all defined by 14496-12 itself. What ISO/IEC 23008-12 contributes is a set of leaf property boxes (ispe, pixi, irot, imir, clap, auxC, colr…), four derived-item payload formats (grid, iovl, iden, tili), and brand and constraint sets. AVIF, in turn, adds one configuration box (av1C) and two brands.

But HDL cannot express that reuse today. There is no import, no module concept, and one format compiles to one self-contained .ttl — the HDL design parks a profile library in §15 as “authored .hx files, not language features”. More fundamentally, the RDF lowering of type dispatch, bddo:hasConditionalDataType, is an ordered rdf:List of rules, and an rdf:List is a closed structure: an importing graph cannot append an arm to a list defined in an imported graph without rewriting the whole list, at which point it is a copy, not a reuse.

Every extensible-tag format hits this, and the evidence is already sitting in the profile library. nitf-tre-blocka.ttl and nitf-tre-rpc00b.ttl define TRE payload structs and owl:imports the NITF profile — but nothing wires them in. nitf:TRE_CEDATA is still plain bddo:bytes ; bddo:sizeFromField nitf:TRE_CEL, because there is no way to extend the dispatch from an importing graph. HEIF is the same problem one order of magnitude larger: roughly sixty box types, an open registry, and four downstream formats that each want to add their own arms.

So the design has two halves: a module layering that says what belongs where, and four specification changes that make the layering expressible. Without the second half, “reuse” degrades to the compiler inlining a copy of the ISO structs into each derived format's namespace. That works, and it is the recommended fallback for a first milestone, but it leaves heic:FullBox and avif:FullBox as distinct resources that no query can join — which forfeits the reason to build this on RDF in the first place.

This document implements nothing. No .hx, .ttl, Kotlin or test is written or changed by it. The HDL fragments below are sketches of the intended authoring surface; field widths and orders are drawn from ISO/IEC 14496-12, ISO/IEC 23008-12 and the libheif sources, and must be verified against the standards text before any profile is authored. In profile-library terms everything here would ship NOT parse-verified until a behavioural test parses a real file.

2. Scope: what libheif implements, and therefore what the profile must cover

libheif is the right reference point because it defines a concrete, testable target: if the descriptor can express what libheif's box.h parses, the profile is useful. Its source tree also partitions almost exactly along the layers this design proposes, which is itself evidence that the layering is the natural one.

Two exclusions are deliberate, and both follow the boundary already settled in the descriptor-driven raster design: the descriptor owns structure, layout and the names of codecs; the engine owns generic mechanisms and codec lookup. The descriptor states the transform parameters and the grid geometry as facts; it does not perform them.

3. The module stack

Six modules, each an owl:Ontology with its own namespace and its own .hx source, related by owl:imports. A derived format's module contains only what that format actually adds.

iso-bmff ISO/IEC 14496-12 — Box, FullBox, ftyp, mdat, free, meta, hdlr, pitm, iloc, iinf, infe, iref, iprp, ipco, ipma, idat, dinf, dref, grpl. Owns the open box dispatch table. ~25 structs. No image semantics whatsoever.
iso-bmff-tracks ISO/IEC 14496-12 continued — moov, trak, mvhd, tkhd, mdia, minf, stbl and the sample tables. Separate module because still-image profiles never need it, and because it is where MP4 and CMAF get their weight. Imports iso-bmff.
heif ISO/IEC 23008-12 — image item properties, derived item payloads (grid, iovl, iden), Exif/XMP item framing, and the mif1/msf1 brand set. Extends the base dispatch table with ~15 arms. Imports iso-bmff.
miaf ISO/IEC 23000-22 — no new boxes at all. A pure constraint module: brand-conditioned requirement and conformance rules over the graph the heif module produces. Imports heif.
codec-hevc / codec-av1 / codec-vvc / codec-uncompressed One module per configuration record: hvcC (14496-15), av1C, vvcC, uncC+cmpd. Each adds one dispatch arm and binds a concept from the media-encoding register. Imports iso-bmff only — a codec config box is not image-specific, which is why hvcC is shared by HEIC and by HEVC tracks in MP4.
heic / avif / heif-sequence / jxl-bmff / jp2-bmff The leaf profiles. Each is a handful of triples: a brand set, the codec module(s) it imports, a primary-item constraint, and its file extension and media type. avif.hx is expected to be under 60 lines.

4. What HDL and the engine already express

More than expected. Four of the five things that make ISOBMFF awkward for a declarative description are already supported, and one of them was designed with ISOBMFF explicitly in mind. Establishing this matters, because it narrows the proposal in §5 to the four things that genuinely do not work.

4.1 The box header, including largesize, uuid and size 0

A box is a length-delimited container whose length is stated three different ways. HEL has a ternary conditional, and a struct's @size expression is re-evaluated after each field until it becomes computable — so the whole rule is one clause:

module iso.bmff
  @namespace "https://hexplain.io/ns/profile/iso-bmff#"
  @endian big

struct Box @size `instance.size == 1 ? instance.largesize
                  : (instance.size == 0 ? stream.remaining + 4 : instance.size)` {
  size      : u32
  type      : ascii[4]
  largesize : u64        if size == 1
  usertype  : bytes[16]  if type == "uuid"
  payload   : bytes[..]  switch type { ... }        // see 4.2 and gap G2
}

The bounded region this establishes is exactly what the Processing Model §3.1 describes, and that clause names ISOBMFF as its motivating case: “a descendant's bddo:sizeToEndOfStream resolves to the region end (not |S|). This is what lets length-delimited containers (ISOBMFF/MP4 boxes, EBML, chunk payloads) bound their children.” The engine implements it: Metaparser.parseStruct caps the buffer limit, and stream.remaining and eof() then describe the region rather than the file.

Rough edge The size == 0 arm (“box extends to the end of the enclosing container”) is written as stream.remaining + 4, where the + 4 accounts for the fact that only the four size bytes have been consumed when the expression first resolves. That is correct but fragile and reads badly. A one-keyword addition — @size to-region-end, lowering to a bddo:sizeToEndOfStream equivalent at struct scope — would remove the arithmetic. Small, optional, and not on the critical path.

4.2 Recursion and container nesting

A container box holds a sequence of boxes, of any type, until its own region ends. That is a self-referential struct, and it terminates because each nesting level is bounded:

struct ContainerBoxPayload {
  children : Box repeat until eof()      // eof() = end of the enclosing bounded region
}

Nothing new is needed: repeat until eof() is native HDL, self is bound to the current element for the until-predicate, and the engine's ParseLimits.maxDepth (default 64) plus maxVisitedNodes bound the recursion — the same defence libheif implements in security_limits.cc. A malformed file that declares a zero-length box inside a container is the classic infinite-loop bug here; the engine's node budget catches it, but a @valid size >= 8 clause on Box states the invariant where a reader can see it, and turns the failure into a validation error rather than a resource-limit error.

4.3 Version- and flag-dependent field widths

A FullBox carries a version and 24 flag bits, and in ISOBMFF nearly every version bump widens a field from 16 to 32 bits. Both mechanisms exist: conditional presence, and conditional data type.

struct FullBoxHeader {
  version : u8
  flags   : bits[24]
}

struct ItemInfoBox {                                  // 'iinf'
  hdr         : FullBoxHeader
  entryCount16 : u16   if hdr.version == 0
  entryCount32 : u32   if hdr.version != 0
  count        : derive hdr.version == 0 ? entryCount16 : entryCount32
  entries      : Box repeat count                     // each an 'infe'
}

The zero-byte derive field is the idiom that keeps the rest of the struct from repeating the ternary: it reads no bytes, computes once, and later clauses reference count directly.

4.4 iloc: integer widths chosen by nibbles at run time

The item location box is the hardest structure in ISOBMFF and the usual reason hand-written parsers exist. Three 4-bit fields choose the byte width — 0, 4 or 8 — of three later fields, independently, and width 0 means the field is absent rather than zero-length. Both halves are expressible:

struct ItemLocationBox {                              // 'iloc'
  hdr            : FullBoxHeader
  offsetSize     : bits[4]
  lengthSize     : bits[4]
  baseOffsetSize : bits[4]
  indexSize      : bits[4]                            // reserved when version == 0
  itemCount16    : u16  if hdr.version < 2
  itemCount32    : u32  if hdr.version == 2
  count          : derive hdr.version < 2 ? itemCount16 : itemCount32
  items          : IlocItem repeat count
}

struct IlocItem {
  itemId16           : u16  if parent.hdr.version < 2
  itemId32           : u32  if parent.hdr.version == 2
  reserved           : bits[12]  if parent.hdr.version >= 1
  constructionMethod : bits[4]   if parent.hdr.version >= 1
  dataReferenceIndex : u16
  baseOffset         : bytes[parent.baseOffsetSize]  if parent.baseOffsetSize != 0
  extentCount        : u16
  extents            : IlocExtent repeat extentCount
}

Judgement call bytes[n] yields xsd:hexBinary, not an integer, so a base offset read this way cannot drive an @at clause. The alternative is switch on the nibble to select u32 or u64, which yields a number but writes three arms per field. The sketch above is shorter; the profile will need the switch form. Either way this is expressible today — but see G3: what to do with the resulting offsets is where it stops working.

4.5 ipma: bit-packed association arrays

Property associations pack an “essential” flag and a property index into either 8 or 16 bits depending on one flag bit of the enclosing FullBox. Two variant structs plus a switch cover it, and the bit cursor semantics are already normative (Processing Model §3.3):

struct IpmaAssociation {
  variant : bytes[..] switch {
    when parent.parent.hdr.flags & 1 == 0 => IpmaAssoc8
    when parent.parent.hdr.flags & 1 == 1 => IpmaAssoc16
  }
}
struct IpmaAssoc8  { essential : bits[1]  propertyIndex : bits[7]  }
struct IpmaAssoc16 { essential : bits[1]  propertyIndex : bits[15] }

Verified against the engine's behaviour, not just the specification text: conditional data types, bit fields and bounded regions all have Metaparser tests today.

Conclusion for §4. The physical description of a HEIF file is expressible with today's BDDO, HEL and HDL, with one cosmetic wart (§4.1). What is not expressible is: sharing that description across formats, extending the box dispatch from an importing module, reaching item payloads through iloc, and turning the item/property/reference indirection into meaningful triples. Those are the four gaps.

5. Four gaps, and what to do about each

Implemented 2026-09: G1 (modules/import), G2 (dispatch tables), G3 (as G3c) — see docs/superpowers/plans/2026-09-06-heif-isobmff-profile.md. G4 is open. Two implementation findings not anticipated below: the compiler now emits bddo:dataType (the narrowest of uint8/16/32/64) alongside bddo:bitLength for every bits[N] field, and the HDL lexer drops a bare ? in an unbracketed expression, so a ?: ternary must be written inside [ … ] (e.g. @size [ … ], or a derived field count : derive [ v == 0 ? a : b ]) or as backtick raw HEL — derive <expr> itself being the zero-byte computed-field type, not a modifier on @size.

G1 — HDL has no modules blocking

Problem

One format declaration compiles to one .ttl. There is no way for heif.hx to say “Box is defined over there”, so today the only way to write the heif module is to paste the ISO structs into it — and again into avif.hx, and again into mp4.hx.

Proposal

module iso.bmff                                    // like `format`, but not a file format
  @namespace "https://hexplain.io/ns/profile/iso-bmff#"
  @ontology  "https://hexplain.io/ns/profile/iso-bmff"

format heif
  @namespace "https://hexplain.io/ns/profile/heif#"
import "../iso-bmff/iso-bmff.hx" as iso            // resolved by path or by ontology IRI

struct ImageSpatialExtents means araster:RasterGrid {
  hdr    : iso.FullBoxHeader                       // qualified reference to an imported struct
  width  : u32 means araster:width
  height : u32 means araster:height
}
  • module declares a namespace and an ontology IRI but no root struct and no file identity — it is not a format and must not be offered as one by a recognizer.
  • import … as <alias> brings the imported names into scope under a dotted qualifier. Unqualified names never leak, so two modules may both define Header.
  • The emitted Turtle carries owl:imports <imported ontology IRI>, so the RDF layer sees the same structure the source does.

G2 — ordered dispatch lists cannot be extended by an importing graph blocking for B

Problem

bddo:hasConditionalDataType takes an rdf:List of bddo:DataTypeRules, evaluated in order, first match wins. Ordered lists are the right model for predicate dispatch, where arms may overlap and precedence carries meaning. They are the wrong model for keyed dispatch, where arms are disjoint by construction, and they are structurally closed: appending to a list defined in another graph means rewriting its cells.

This is not hypothetical. It is why nitf:TRE_CEDATA is unparsed bytes while two TRE payload structs sit in adjacent files, imported and unreachable. HEIF needs roughly sixty arms on one field, contributed by five modules, from an open registry that gains new box types with every amendment.

Proposal: a keyed, open dispatch table in BDDO

# in iso-bmff.ttl -- the extension point, declared once
iso:BoxPayloadDispatch a bddo:DispatchTable ;
    bddo:dispatchOn iso:Box.type ;                    # the key field
    bddo:dispatchDefault iso:UnknownBoxPayload .      # unmatched key: opaque bytes, not an error

iso:Box.payload a bddo:Field ;
    bddo:dataType bddo:bytes ;
    bddo:hasDispatchTable iso:BoxPayloadDispatch .

# in heif.ttl -- contributed from an importing graph, no list rewrite
[] a bddo:DispatchArm ; bddo:armTable iso:BoxPayloadDispatch ;
   bddo:armKey "ispe" ; bddo:armDataType heif:ImageSpatialExtents .
[] a bddo:DispatchArm ; bddo:armTable iso:BoxPayloadDispatch ;
   bddo:armKey "ipco" ; bddo:armDataType iso:ContainerBoxPayload .

Authored as:

// iso-bmff.hx
dispatch BoxPayload on Box.type default UnknownBoxPayload

// heif.hx
extend dispatch iso.BoxPayload {
  "ispe" => ImageSpatialExtents
  "ipco" => iso.ContainerBoxPayload
  "irot" => ImageRotation
}

Why keyed rather than ordered

  • Openness. Arms are independent triples. Any importing graph may add one; nothing is rewritten; merge order is irrelevant.
  • Determinism. Keys are unique by SHACL constraint, so “first match” has no meaning and cannot be got wrong. A duplicate key across two modules is a validation error naming both — which is exactly the diagnostic you want when two profiles claim the same box type.
  • Speed. Ordered dispatch evaluates HEL predicates until one matches: with sixty arms, that is up to sixty evaluations per box in a file with thousands of boxes. A keyed table is one map lookup. This alone would be a reason to add it.
  • A default arm. Unknown box types are normal and legal in ISOBMFF, and libheif models them explicitly (Box_other). An ordered list has no notion of “none matched, take the fallback” short of a catch-all arm that every extender must be careful to stay behind — precisely the ordering hazard keyed dispatch removes.

bddo:hasConditionalDataType stays, unchanged, for genuine predicate dispatch (TIFF's inline-vs-pointer rule, NITF's presence conditions). The two coexist; a field carrying both is a validation error.

Impact

BDDO: six new terms and one SHACL shape. RdfToIrCompiler: collect arms by table across the loaded graph into a map — this is the natural home for the union, and it is where owl:imports has already been resolved. Metaparser: a map lookup beside the existing rule-list walk. The Processing Model gains one clause in §3.2 alongside the existing type-selection rule. Nothing about it is HEIF-specific: the first beneficiary is NITF's TRE registry, and PNG chunks, RIFF, EBML, TIFF tags and glTF extensions all want it.

G3 — item payloads are addressed from outside the box tree blocking

Problem

In HEIF the box tree is a directory, not a document. Actual image data lives in mdat (or idat) and is reachable only through iloc: per item, a base offset plus a list of extents, each an (offset, length) pair, interpreted by a construction_method — 0 means a file offset, 1 means an offset into idat, 2 means an offset into another item. Three things break:

  1. Region containment. An offset-addressed field is read relative to bddo:offsetBase, and a read that leaves the innermost bounded region raises a bounds error (Processing Model §9). The iloc field lives inside the meta region; mdat is outside it. The seek is exactly what the bounds rule is designed to prevent.
  2. No offset base of “that box”. bddo:offsetBase offers streamStart, streamEnd, parentStart and currentPosition. Construction method 1 needs “the first byte of the idat payload”, which is none of them.
  3. No iteration variable. There is no way to say “for each extent, read its offset and length”. HEL binds self only in a repeat until predicate; a repeated field cannot address itself per element.

Proposal

Point 3 is already solved by a mechanism built for exactly this shape, and the connection is worth naming: DLV's chunk table takes a vector of offsets and a vector of lengths read from fields and materialises the pieces — chunkOffsetsFromField, chunkLengthsFromField, chunkOffsetBase. TIFF's TileOffsets/TileByteCounts, NITF block offsets and iloc extents are one mechanism with different field bindings, and the LayoutExecutor being built for the descriptor-driven raster work is the component that executes it.

The mismatch is semantic, not mechanical: DLV chunks are pieces of one array, whereas iloc extents are the pieces of many independent items. Two ways to resolve it, and the choice should be made in review:

Construction methods 1 and 2 stay out of scope

Points 1 and 2 need two small BDDO additions in either case: bddo:offsetBaseField (base an offset at the start of a named field's parsed bytes — construction method 1, and equally TIFF's IFD-relative values), and an explicit opt-out from region containment for offset-addressed reads, e.g. bddo:seekScope bddo:StreamScope. The opt-out must be explicit and narrow: the containment rule is a safety property, and a descriptor that escapes it is asserting that it means to address the whole file. Construction method 2 (offsets into another item) is a genuine forward reference and should be declared out of scope for milestone 1 — libheif itself treats it as rare.

G4 — the semantics live in a join, not in a field design-level

Problem

This is the deepest of the four, and the one most likely to be underestimated. Hexplain Core maps bytes to triples structurally: a struct maps to a class, a field maps to a property of that struct's instance. HEIF's meaning is not structural. The width of an image is in an ispe box that sits in ipco, in property-index order, associated with an item only through an ipma entry that names an item id defined in an infe. The relation “this image is 4032 pixels wide” is a three-way join across three boxes that are not nested in each other.

Map ispe.width to araster:width naively and you get <file/meta/iprp/ipco/3> araster:width 4032 — true of a property box, meaningless as a statement about an image. The same applies to iref (thmb, dimg, auxl, cdsc relations between items), to pitm, and to entity groups.

Proposal: value joins in Core

# A resolution declared on the referring field: "the value of this field identifies
# the instance of <targetStruct> whose <targetKey> field has the same value".
hexplain:ipmaItemRef a hexplain:ValueJoin ;
    hexplain:joinFromField  iso:IpmaEntry.itemId ;
    hexplain:joinToStruct   iso:ItemInfoEntry ;
    hexplain:joinToKeyField iso:ItemInfoEntry.itemId ;
    hexplain:joinEmits      heif:describesItem .        # object property on the emitted graph

Authored as ref itemId -> iso.ItemInfoEntry.itemId as heif:describesItem. A processor resolves joins after the parse completes, over the instance graph it has just built, and emits object-property edges between minted IRIs. Three consequences worth stating plainly:

  • It is a second pass. The Processing Model is currently single-pass and forward-reference-free by design (§4: “forward references MUST raise an error”). Joins do not violate that rule — they run after parsing, not during it — but they add a phase to a normative algorithm, and the specification must say so explicitly rather than let implementations improvise.
  • It is declarative and format-neutral. ZIP central directory to local header, TIFF SubIFDs, glTF accessor to buffer view, NITF DES attachment: all the same shape. AXV already has CentralDirectory and ArchiveEntry classes with the same latent problem.
  • The alternative is to do nothing and emit a faithful box graph, leaving the join to a downstream SPARQL query or SHACL rule. That is a legitimate position — the descriptor stays a description of bytes — but it means a HEIF file cannot answer ?img araster:width ?w without a per-format query the framework does not carry, and the profile's semantic value collapses to “here are some boxes”. Reviewers should decide this one on purpose, not by default.

An intermediate position exists and may be the right milestone-1 answer: emit the box graph faithfully plus hand-written SPARQL CONSTRUCT rules shipped beside the profile, and promote them to a declared ValueJoin once two or three formats have proved the shape.

6.3 Item roles

The part-role register (rpr:) already carries Thumbnail, Metadata, Payload and Sidecar, minted for multi-file bundles but equally applicable to items inside one file. A HEIF item's role — primary image, thumbnail, alpha auxiliary, Exif metadata, derived grid — should bind to that register and extend it where needed, rather than mint a HEIF-local vocabulary. This keeps the query “show me the thumbnail” identical across a shapefile bundle and a HEIC file, which is the kind of payoff the aspect architecture exists for.

6.4 The codec boundary, restated

hvcC and av1C are described in full: they are configuration records with a fixed field layout, and their fields (profile, tier, level, chroma format, bit depth) are real metadata worth having in the graph. The coded picture data they configure is not described; it is a byte block annotated hexplain:isEncodedWith menc:HEVC. Whether the engine can then produce pixels depends on whether a codec plugin is registered — exactly the same contract as LZW in TIFF. Describing an HEVC bitstream declaratively would require HEL to become a bytecode VM, which the descriptor-driven raster design already ruled out on the record.

7. Conformance, brands and limits

7.1 Brands are conformance claims, and belong in req/conf

ftyp is not just a magic number: a compatible brand is a machine-readable claim that the file satisfies a named constraint set. That is precisely what the Requirements and Conformance vocabularies model, and it means MIAF needs no new structs at all — miaf.hx is a constraint module.

BrandClaimsCheckable from the graph?
mif1HEIF image file: a meta box with hdlr = pict, a pitm, and every item's properties associatedYes
heicPrimary item is HEVC-coded; an hvcC is associated and marked essentialYes (needs G4 for “associated”)
avifPrimary item is AV1-coded; av1C associated; MIAF constraints holdYes (needs G4)
msf1An image sequence: moov with at least one pict trackYes, once iso-bmff-tracks exists
MA1B (MIAF)Codec, colour and profile restrictions on the primary itemPartly — some MIAF rules are about the coded bitstream, and are unreachable by design (§6.4)

The useful property here is that brand claims are checkable against the file itself: a file declaring heic whose primary item has no associated hvcC is malformed, and the conformance graph can say so with a citation. That is a concrete demonstration of the framework doing something a hand-written parser does not.

7.2 Resource limits

libheif ships security_limits.cc because HEIF is a hostile-input format: nested boxes, an item graph that can contain cycles (dimg loops), enormous declared extents, and grids that multiply out to gigapixels. The engine's ParseLimits (maxDepth 64, maxVisitedNodes, maxInputBytes) covers the structural half. Two limits should be named explicitly in the profile's test plan because the descriptor makes them reachable: total declared extent bytes versus file size, and item-reference cycle detection once G4 resolves references. Both are engine concerns, not descriptor concerns, but the HEIF profile is what will first exercise them.

8.1 Verification, and what “verified” would mean here

The profile library's distinction between NOT parse-verified and parse-verified is the one that matters, and HEIF offers an unusually strong form of the second: libheif is a reference implementation with a public test corpus, so every claim the descriptor makes about a real file can be checked against what libheif reports for the same file — box offsets, item ids, extent boundaries, image dimensions, extracted payload bytes. That is a sharper gate than the GDAL pixel-parity comparisons, because it tests the descriptor rather than a hand-written decoder that happens to agree with it. The comparison should be scripted from M1 onward and should be the definition of done for each milestone, not a final step.

9.2 Open questions for review

  1. G3 — resolved as G3c during implementation (pointer read at the extent + bddo:seekScope); extent tables remain a possible later generalisation if a format needs offsets not co-located with lengths.
  2. G4 now or later — declared value joins in Core, or shipped SPARQL alongside the profile until a second format needs it? This decides whether the profile is semantic or merely structural at M4.
  3. Module naming — iso-bmff or iso14496-12? The latter is precise and ages well against amendments; the former is what people search for.
  4. Does module earn its keyword, or is a format with no root struct enough? A separate keyword is clearer and lets the compiler refuse to treat a module as a format; it is also one more thing in the grammar.
  5. Where do brands live — a register of brand codes (they are published four-character codes, which is exactly what a register is for), or profile-local enums? The register is more consistent with the media-encoding precedent.
  6. Does the heif module import codec-hevc, or does only heic? Keeping codecs out of heif is what lets AVIF import heif without dragging HEVC in — the answer that keeps the layering honest.
