Decision: fix the correctness gates before expanding the product.

The separation between domain, engine adapter and application is clear, and the existing fixtures prove a useful vertical slice. However, integer comparison, version compatibility, run verdicts and video validation can all produce wrong answers. The SaaS also has a critical dependency advisory and intentionally lacks a production tenancy boundary.

These are review findings, not implemented fixes. Application and specification sources were left unchanged. The report and reproducible probes are new local artifacts; nothing was published.

Scope and confidence

Reviewed the tracked repository inventory, specification HEL/DLV/video contracts and validator wiring; SaaS API controllers, services, in-memory adapters, domain models, profile differ, engine adapter, semantic viewer and main frontend flows. The adjacent hexplain-tools checkout is the SaaS’s real composite-build dependency, so its HEL evaluator and IR were inspected to verify mathematical behavior. This is not a full independent audit of that third repository.

Findings distinguish executed probes, direct code reasoning, vendor advisories and planned capability gaps. UX findings are based on source and interaction state flow; no user study, assistive-technology session, production penetration test or large-file performance benchmark was performed. The review cannot prove correctness for every format, codec, geometry predicate or platform.

P1 M01 · Mathematics · Executable probe

Integer comparisons lose information above 2⁵³

Both numeric equality and ordering call toDouble(). The probe evaluates 9007199254740992 == 9007199254740993 as true, and the reverse strict ordering as false.

Impact. Different 64-bit field values become indistinguishable; bounds, dispatch and conformance predicates can accept the wrong value.

Recommended change. Compare Integer–Integer operands exactly. Define mixed Integer–Float comparison without silently rounding the integer first; handle NaN and infinities explicitly.

Acceptance test. Boundary and property tests around 2⁵³, signed limits, adjacent values and mixed types; verify antisymmetry and strict ordering.

P1 M02 · Mathematics · Executable probe

Arithmetic silently wraps and indexes silently truncate

Long arithmetic is unchecked. 9223372036854775807 + 1 wraps to Long.MIN_VALUE; 1 << 64 evaluates to 1. substr('abc', 1.9, 1) returns b because indexOperand converts any Number to Long, then Int. Array access uses the same permissive numeric narrowing.

Impact. Counts, offsets and indexes can produce plausible but incorrect results. HEL does not define a modular integer model that would justify these results.

Recommended change. Specify integer bounds and overflow behavior, use checked arithmetic or arbitrary precision, reject fractional and out-of-range indexes, and define valid shift counts and operand widths.

Acceptance test. Overflow at each arithmetic operator; negative/64/huge shifts; fractional indexes; 2³¹ and 2³² indexes; reject rather than wrap.

P1 M03 · Mathematics · Probe + specification contradiction

HEL division and the BMP stride example use incompatible contracts

HEL delegates arithmetic to XPath, but the engine returns Integer 2 for 5 / 2. XPath numeric division returns 2.5. The DLV example ((width * bitsPerPixel + 31) / 32) * 4 assumes integer truncation: for width=1 and bitsPerPixel=24, real division yields 6.875 instead of the required 4-byte stride.

Impact. Independent implementations following the normative reference will disagree with the engine and the layout examples.

Recommended change. Define / and integer division separately, including result types and negative operands. Express BMP stride as 4 × floor((w × bpp + 31)/32) for nonnegative integers, or provide an explicit integer-divide operator. Do not change runtime division without migrating existing profiles.

Acceptance test. Golden vectors: 5/2, -5/2, modulo signs, BMP widths around 32-bit boundaries, and bit-packed row ceilings.

P2 M04 · Mathematics · Executable probe

Null inequality contradicts the normative comparison table

The spec says every comparison with Null other than Null == Null is false. OP_NEQ negates isEqual(), so an absent value != 1 is true. The probe uses a schema-less missing accessor to supply Null.

Impact. Optional-field conditions can take the opposite branch from a spec-conforming implementation.

Recommended change. Choose and document a complete Null truth table; implement != directly according to it. Separately distinguish absent declared fields from undefined names in every context.

P1 S03 · Correctness · Executable probe + counterexample

Conditional presence is incorrectly assumed to preserve compatibility

An added field is classified ADDITIVE whenever isPresentIf is non-null; an existing unconditional field becoming conditional is also ADDITIVE. A predicate can always be true or false. Making A conditional on false removes its byte consumption and shifts B, yet only a minor bump is requested.

Impact. The compatibility gate accepts changes that misparse existing bytes. The condition merely existing is not proof that old inputs are unaffected.

Recommended change. Classify presence changes as breaking unless compatibility on the old input domain is proved. Apply the same reasoning to added dispatch arms that can intercept previously valid data.

Acceptance test. Compare old/new parsers on [A,B] with A becoming absent and on an inserted conditionally-present field whose condition is true for old data.

P1 S04 · Correctness · Executable probe

Malformed semantic versions bypass the publish gate

versionIsConsistent returns true when either version fails Semver.parse. A breaking change targeting banana is accepted by that method. The first publish has no version validation. The parser also accepts leading zeros and plus signs, despite being named Semver.

Impact. Callers can bypass the guarantee that breaking changes require a major increment. An invalid version can also become the latest published baseline.

Recommended change. Validate the declared version syntax before compilation for every publish. Decide whether full SemVer or a strict major.minor.patch subset is supported; invalid versions must fail closed.

P1 S07 · Security · Documented prototype gap

P2 S08 · Reliability · Mathematical derivation + code review

32-bit random identifiers are too short for evidence records

Run, finding and profile IDs retain only eight UUID hex digits: a 2³²-sized space. At 100,000 IDs, the birthday approximation gives 1−exp(−n(n−1)/(2×2³²)) ≈ 68.8% collision probability per ID namespace. Repositories overwrite records with duplicate IDs.

Impact. Growing usage can overwrite runs/versions or merge finding buckets; findings reach this volume faster than runs.

Recommended change. Use full UUIDs or another sufficiently large identifier and enforce uniqueness at storage. Retry collisions; never overwrite immutable records.

Acceptance test. Inject a repeated ID and verify rejection/retry. Test unique constraints independently from random generation.

P2 V03 · Mathematics · Design gap

Video timing cannot preserve exact rational frame rates

frameRate is xsd:decimal, with no numerator/denominator or timebase. A finite decimal cannot exactly represent 30000/1001 because its reduced denominator contains primes other than 2 and 5. aspectRatio is a string with no relationship to pixel/sample aspect ratio.

Impact. Exact timing and long-duration frame-to-time conversions cannot be reconstructed from rounded display values alone. No runtime timing drift was measured.

Recommended change. Add exact rational timebase/rate terms with positive denominator, distinguish nominal/average and variable frame rates, and define duration/frame-count consistency only for appropriate constant-rate models. Keep decimals for display.

Acceptance test. Round-trip 30000/1001 and 24000/1001 without loss; explicit tests for variable frame rate and non-square pixels.

Practical improvement sequence

1 · Restore trust in results

  1. Patch and retest the framework dependencies (S01).
  2. Fix exact comparisons and settle the HEL numeric contract (M01–M04).
  3. Make failed comparisons indeterminate and repair cached attribution (S05–S06).
  4. Fail closed on malformed versions and unknown parsing changes (S02–S04).
  5. Include domain shapes and constrain video quantities (V01–V02).

2 · Make the workflow dependable

  1. Separate compiled/published/dirty states and cancel stale requests (U01–U02).
  2. Use actual lifted semantics in the viewer (S11).
  3. Add current-profile and byte-offset deep links from findings to the viewer, with the referenced version pinned.
  4. Support keyboard tree navigation, accessible errors and synchronized scrolling (U04).
  5. Introduce bounded, virtualized file viewing and measure it (U03).

3 · Establish a production boundary

Authentication and tenant enforcement, durable transactional storage, collision-resistant IDs, pinned engine artifacts, bounded compilation/parsing workers, request/body limits, cancellation, audit history, backups and health/metrics are the next platform milestone. Most are explicitly absent from the walking skeleton; they are roadmap work rather than evidence of hidden implementation. Avoid calling the current service production-ready until these boundaries are in place.
