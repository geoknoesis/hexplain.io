Release procedure

  1. Update canonical RDF and record changed validation behavior in the compatibility notes.
  2. Generate term documentation and synchronize the engine bundle and shared competency corpus.
  3. Run specification and engine tests. Create a new snapshot identifier with python tools/_snapshot_release.py YYYY-MM-DD.N; existing identifiers cannot be overwritten by this tool.
  4. Run the release compatibility gate. It checks archive and file hashes and replays the original cases against archived and current graphs.
  5. Review and publish the concrete artifacts through the repository's deployment process. Verify HTTP dereferencing and media types after deployment before describing the release as live.

The manifest records SHA-256 byte identities, not a signature or independent trust attestation. Repository review is still needed to prevent coordinated edits to an artifact and its manifest. Retaining version information and immutable versions follows W3C Data on the Web Best Practices.
